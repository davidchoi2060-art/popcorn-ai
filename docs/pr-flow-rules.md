## 1. main에 직접 push하지 않는다

- 모든 변경은 **브랜치 → PR → 병합**으로 들어간다. 클라우드 쪽과 PC 쪽 모두 같다.
- 브랜치 이름은 `종류/짧은-설명`. 종류는 `feat` · `fix` · `docs` · `ci` · `data` · `chore` 중 하나.
- **서버 장애로 바로 고쳐야 할 때**도 PR을 올린다. 리뷰를 기다리지 않고 중헌님이 병합할 수 있고, 리뷰는 병합 뒤에 받는다. 이 경우 PR 본문 첫 줄에 「긴급 · 사후 리뷰」라고 적는다.

## 2. PR은 작게

- **PR 하나 = 항목 하나.** 제목 앞에 항목 번호를 붙인다. 예: `[5] 판매가 마진 계산 통일`.
- **파일 20개 이하**를 기준으로 한다. 시드 데이터·이미지·자동 생성 파일은 세지 않는다. 넘으면 나누고, 나눌 수 없으면 본문에 이유를 적는다.
- **마이그레이션은 PR 하나에 하나가 원칙이다.** 여러 개가 함께 가야 하면 이유를 적는다.
- **되돌릴 수 없는 마이그레이션**(downgrade가 거부하는 것)은 PR 본문 맨 위에 그 사실을 적는다. 병합하면 공유 DB에 바로 적용되기 때문이다.
- 마이그레이션을 추가하면 **같은 PR에서 `docs/06_db-erd.md`도 고친다**(CLAUDE.md 「ERD 개정 → 새 마이그레이션」).
- 커밋 본문에 무엇을 왜 바꿨는지 적는다. 제목만 있는 커밋은 쓰지 않는다.

## 3. 줄바꿈·서식 변경을 기능 변경에 섞지 않는다

- 기능 PR에서 **파일 전체의 줄바꿈(CRLF↔LF)이나 들여쓰기·서식을 바꾸지 않는다.** 고친 줄만 바뀌어야 한다.
- 줄바꿈 정리는 **항목 2번의 단독 PR 하나**로만 한다(`.gitattributes` 추가 + 전체 정리). 그 PR에는 다른 변경을 넣지 않는다.
- 2번이 끝나기 전까지는 편집기가 **원래 파일의 줄바꿈을 유지**하게 둔다.
- 올리기 전에 확인한다. 두 숫자가 크게 다르면 줄바꿈이 섞인 것이다.

      git diff --stat origin/main...HEAD
      git diff --stat --ignore-cr-at-eol origin/main...HEAD

## 4. 병합 전에 초록이어야 하는 것

| 조건 | 언제 | 비고 |
|---|---|---|
| **「단위 테스트」 워크플로 통과** | 모든 PR | `.github/workflows/unit.yml`(PR #1). PR #1이 병합되기 전에는 본문에 로컬 실행 결과(`python tests/ci_run.py`)를 붙인다. |
| 알려진 실패 목록을 늘리지 않음 | 모든 PR | `tests/conftest.py`의 `KNOWN_FAILURES`. 줄이는 것은 자유, 늘리려면 원인과 담당을 적고 상대 쪽 리뷰를 받는다. |
| ERD 갱신 | 마이그레이션이 있는 PR | 위 2번. |
| 서버 회귀 결과 | 엔진·호환 규칙·게이트·원장·가격·커머스를 건드린 PR | 항목 4번(서버 회귀 복구)이 끝나기 전에는 「서버 회귀 미실행」이라고 본문에 적는다. 결과를 지어내지 않는다. |
| 리뷰 댓글 전부 답변 | 모든 PR | 아래 5번. |

테스트를 건너뛰기·삭제·주석 처리해서 초록을 만들지 않는다. 실패는 코드나 테스트를 고쳐서 해결한다(CLAUDE.md 「실패는 전부 코드 문제다」).

## 5. 리뷰와 댓글 처리

- **올린 쪽이 아닌 쪽이 리뷰한다.** 클라우드 PR은 PC 쪽이, PC PR은 클라우드 쪽이 읽는다.
- 두 쪽이 같은 GitHub 계정을 쓰므로 GitHub의 「Approve」 버튼은 쓸 수 없다. 대신 리뷰어가 **「리뷰 완료 · 병합 가능」 댓글**을 남긴다.
- 리뷰 댓글마다 올린 쪽이 **「고침 + 커밋」 또는 「안 고침 + 이유」**로 답한다. 답이 없는 댓글이 하나라도 있으면 병합하지 않는다.
- 한 번 주고받고도 의견이 갈리면 그 PR에서 더 다투지 않고, 중헌님 결정 묶음(분담표 「중헌님 결정 대기」)에 한 줄로 올린다.
- **병합은 올린 쪽이 한다.** 조건은 4번이 모두 초록이고 「병합 가능」 댓글이 있을 때다. 사업·운영 결정이 걸린 PR(가격 정책, 결제, 고객 공개 등)은 중헌님 확인 댓글이 추가로 필요하다.
- 리뷰를 반영해 고친 뒤에는 워크플로가 다시 초록이어야 한다.

## 6. PR 본문에 꼭 쓰는 네 가지

PC 쪽과 합의한 보고 형식이다([PR #2 댓글 6054664959](https://github.com/davidchoi2060-art/popcorn-ai/pull/2#issuecomment-6054664959)).

1. **바뀐 파일** — 목록 또는 `git diff --stat` 요약.
2. **기준 커밋** — 어느 main 커밋에서 갈라졌는지.
3. **실제로 한 검증** — 돌린 명령과 결과. 하지 않은 검증은 하지 않았다고 적는다.
4. **상대에게 다음 요청** — 없으면 「없음」.

여기에 분담표 규칙 3에 따라 **「끝까지 시나리오」 중 어느 단계가 이어졌는지**(항목 7 측정기가 생기면 그 결과)를 덧붙인다.

### 「완료」라는 말

진척은 다섯 단계로 나눠 말하고, 어디까지 왔는지만 적는다.

    담당 보고   만든 쪽이 끝났다고 보고함
    독립 확인   만들지 않은 쪽이 확인함(리뷰·검수)
    수용        중헌님이 결과를 받아들임
    배포        main에 병합되어 서버에 반영됨
    고객 경로   고객이 실제로 그 단계를 통과한 증거가 있음

「완료」는 **고객 경로까지 증거가 있을 때만** 쓴다. 항목 7 측정기가 생기면 그 단계가 초록일 때다. 코드가 있다는 것만으로 완료라고 하지 않는다.

## 7. 역할 경계

- **화면 UI 디자인 시안은 PC 쪽(Codex)이 이미지로 만든다.** 시안은 묻지 않고 바로 화면에 반영하고, 중헌님은 바꿀 곳만 말한다(2026-10-09 23:38 개정). 클라우드 쪽은 시안을 그리지 않고, 시안이 필요하면 PR 댓글로 요청한다(중헌님 지시 2026-10-08, 분담표 대화 규칙 6). 이미 승인된 시안은 다시 쓴다.
- 상대 담당 항목의 파일은 고치지 않는다. 겹칠 수밖에 없으면 고치기 **전에** 상대 PR이나 PR #2에 댓글로 알린다.
- 클라우드 쪽은 서버와 DB에 접속하지 않는다. 서버에서만 확인할 수 있는 것은 PC 쪽에 요청하고, 그 결과를 PR 본문에 출처와 함께 붙인다.

## 8. 중헌님께 허락·승인·설정 변경을 요청하지 않는다 (상시 규칙)

중헌님 원문(2026-10-09 23:37 · 23:38 KST): 「왜 자꾸 업무지시를 했는데, 또 허락, 또 승인」 · 「다 시키고 났는데, 또 다시 허락? 또 다시 승인? 그럼 내가 시킨 업무는 뭐지? 헛소리인가?」

- **지시가 곧 승인이다.** 중헌님이 시킨 일은 다시 허락이나 승인을 묻지 않고 한다.
- 중헌님께 설정 변경(GitHub · 클라우드 · PC 설정)을 해 달라고 요청하지 않는다. 우리 쪽이 할 수 없으면, 무엇이 막혔는지만 기록하고 할 수 있는 일을 계속한다.
- 중헌님은 결과를 보고 바꿀 곳만 말한다. 근거는 결정 로그 「2026-10-09 중헌님 결정」 ⑦ ⑧.
