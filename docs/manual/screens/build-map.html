운영자 매뉴얼 — 조립 호환 지도

화면을 처음 쓰는 직원이 이 문서만 보고 바로 일을 시작할 수 있도록 썼습니다. ⚠ 이 화면은 좌측 메뉴 이름과 화면 안 이름이 다릅니다 — 아래 「① 이 화면이 무엇을 하는 곳인가」 첫 번째 안내를 반드시 먼저 읽으십시오.

대상 관리자 화면(admin2)의 조립 호환 지도를 처음 보는 직원
화면 조립 호환 지도(좌측 메뉴 표시명) · 경로 /admin2/build-map · 화면 ID ADM-STD-020 (코드 api/admin_ui_build_map.py· api/admin_std.py 실측값입니다) · 화면을 열면 다른 이름(「조립 호환 조감도」)이 보입니다 — 잘못 들어온 것이 아닙니다.
왜 이 화면인가 "이 부품과 저 부품이 맞는지 판정하려면 무엇을 알아야 하고, 우리는 지금 어디까지 아는가"에 답하는 읽기 전용 진단 화면입니다. 관계(부품 쌍) 하나하나마다 「규칙이 있는가 · 양쪽 사양 값이 찼는가 · 그래서 지금 판정 가능한가」를 한 곳에서 보여주는 유일한 화면입니다 — 이 화면이 없으면 규칙 자체는 compat_rules 테이블을 직접 조회해야 하고, 항목별 충족률은 「조립 사양 표준」 화면에 있지만 그 항목이 어느 관계 판정에 쓰이는지는 거기서 보이지 않습니다.
코드·캡처 확인 기준일 2026-08-27 — 이 문서는 그 시점의 화면 코드와, 그 코드가 실제로 그리는 화면을 로컬 서버(127.0.0.1:8000, 실서비스와 같은 DB를 보는 개발 서버)에 직접 띄워 촬영한 결과, 그리고 같은 시각 GET /api/admin/std/compat-map 응답을 근거로 썼습니다. 지어낸 숫자는 없습니다.
이 화면의 숫자(관계 28건 등)는 DB 상태에 따라 바뀝니다 — 이 문서의 값은 2026-08-27 스냅샷입니다. 정확한 지금 값은 화면에서 직접 확인하십시오. (참고로 요구사항 정의서 docs/design/req/req-build-map.md가 적어 둔 2026-08-14 스냅샷과 오늘 값이 정확히 같습니다 — 관계 28 · 범위 안 22 · 검사 적용 9 · 판정 가능 11 · 사양 항목 64. 우연히 같을 뿐이며, 화면은 매번 이 API를 다시 조회합니다.)
1 눌러야 할 자리 · 봐야 할 정보(번호는 아래 목록과 1:1)
테두리 상자 = 하나로 묶어 보는 영역(번호가 있는 핀이 함께 표시됩니다)
화살표 = 누르면 무엇이 바뀌는지

1이 화면이 무엇을 하는 곳인가

⚠ 좌측 메뉴 이름과 화면 안 이름이 다릅니다. 좌측 메뉴(「상품사양관리」 그룹)에는 「조립 호환 지도」라고 나오는데, 화면 자신은 브라우저 탭 제목·화면 상단 위치 표시 (breadcrumb)·본문 어디에서도 「조립 호환 조감도」라고 표시합니다. 오늘 실측: <title>팝콘PC 관리자 · 조립 호환 조감도</title>, 상단 위치 표시 「상품사양관리 / 조립 호환 조감도」. 어느 쪽을 정식 이름으로 할지는 아직 결정되지 않았습니다 (2026-08-27 기준 미결). 이 문서는 좌측 메뉴 이름을 제목으로 삼되, 화면을 열면 다른 이름이 뜬다는 사실을 미리 알려 드립니다 — 메뉴에서 「조립 호환 지도」를 눌렀는데 화면에 「조립 호환 조감도」라고 뜨더라도 정상입니다.

「조립 사양 표준」 화면이 "어떤 사양 항목이 비어 있는가"를 부품 단위로 말한다면, 이 화면은 "그게 왜 문제인가"를 관계(부품 쌍) 단위로 말합니다. 아무것도 고치지 않는 읽기 전용 화면입니다 — 규칙을 만들거나 사양 값을 입력하는 동작이 전혀 없습니다.

부품 쌍마다 서버가 상태 하나를 판정해 내려줍니다(화면은 이 값을 그대로 쓰고 다시 계산하지 않습니다 — 세 가지 보기가 각자 계산하면 서로 어긋나기 때문입니다). 상태는 항상 색 + 기호 + 글자를 함께 씁니다(색약 배려):

기호이름뜻
◆규칙 미등록양쪽 사양 값은 이미 찼는데, 아직 아무 규칙도 이 관계를 막고 있지 않습니다 — 지금 당장 견적 엔진은 이 조합을 걸러내지 못합니다
○사양 값 부족규칙이 있든 없든, 판정에 필요한 사양 값 중 하나 이상이 0%입니다 — 코드 주석 그대로 "값이 하나라도 0%면 그 쌍은 판정이 반쪽"입니다
●검사 적용활성 규칙(compat_rules)이 이미 걸려 있습니다. ⚠ 사양 충족률이 100%라는 뜻은 아닙니다 — 아래 「조심할 것」 참고
·범위 밖지금 단계에서는 판정 대상이 아닙니다(모니터·팬·확장카드· ODD처럼 아직 부품 분류가 안 됐거나 주변기기라 사양 자체가 없음)

오늘 실측(GET /api/admin/std/compat-map): 관계 28건 중 범위 안 22건, 그중 검사 적용 9건 · 규칙 미등록 3건 · 사양 값 부족 10건 (범위 밖 6건은 별도) · 판정 가능(관련 값이 하나도 0%가 아닌 것) 11건 · 부품별 사양 항목 합계 64개. 관계가 걸리는 부품은 10종(CPU·메인보드·메모리·그래픽카드· 파워·케이스·SSD·HDD·CPU쿨러(공랭)·CPU쿨러(수랭))이고, 그 밖에 참조만 되는 5종(모니터· 팬·확장카드·광학드라이브·"구성 전체")도 지도에 노드로만 나타납니다 — 아직 부품 분류가 안 됐거나 (팬·확장카드·광학드라이브는 ETC로 미분류) 사양 체계가 없어서(모니터, "구성 전체") 범위 밖으로 빠져 있습니다.

관계마다 A1~F5 같은 코드(pair_key)가 붙습니다. 앞 글자는 여섯 묶음(group)을 가리킵니다 — A: 메인보드 중심(대부분의 관계가 메인보드로 수렴) · B: 물리 공간 (케이스 수용 여부) · C: 전력 · D: 냉각·간섭 · E: 출력(영상) · F: 선택 부품(팬·확장카드·ODD, 부품 분류 선행 필요). ⚠ 이 묶음 이름 자체는 API 응답(groups)에는 있지만 화면 어디에도 문구로 나오지 않습니다(코드 확인 — 화면 스크립트가 이 값을 읽는 곳이 0곳입니다) — 코드 앞 글자로만 짐작할 수 있습니다.

2언제 여기 오는가

  • 새 호환 규칙을 등록하기 전에, 그 관계에 실제로 사양 값이 준비됐는지(판정 가능한지) 먼저 확인할 때
  • 특정 부품(예: SSD)이 걸린 관계가 몇 개나 있고 그중 몇 개나 규칙으로 막혀 있는지 궁금할 때 — 부품을 클릭해 고정(pin)하고 살펴봅니다
  • 「조립 사양 표준」 화면에서 특정 사양 필드의 충족률이 낮다는 것을 본 뒤, 그 필드가 어느 관계 판정에 쓰이는지 거슬러 올라와 확인할 때
  • 규칙이 없는 관계부터 우선순위를 정해 다음에 등록할 규칙 순서를 정할 때 — 「진단형」 탭이 이 용도로 맞춰져 있습니다(규칙 미등록을 맨 앞 레인에 둡니다)
  • 부품 × 부품 격자로 「전혀 정의되지 않은 관계」와 「정의는 됐지만 상태가 무엇인지」를 한눈에 훑어보고 싶을 때 — 「매트릭스형」 탭

3화면 살펴보기

이 화면은 세 가지 표현(탭)을 갖고 있습니다 — 지도형·진단형·매트릭스형. 셋 다 같은 조회 한 번(GET /api/admin/std/compat-map)으로 그려지고, 탭을 바꿔도 다시 조회하지 않습니다(코드 확인 — 탭 전환은 hidden 속성만 바꿉니다). 아래에서 기본 탭(지도형)부터 하나씩 확대해 설명하고, 이어서 부품 고정(pin) 기능, 진단형· 매트릭스형 순으로 다룹니다.

그림 A전체 화면(지도형, 기본 탭)

  • 1왼쪽 메뉴(LNB) — 지금 있는 화면이 진하게 표시됩니다. 「상품사양관리」 그룹 안에 있습니다(메뉴 라벨은 「조립 호환 지도」)
  • 2위치 표시(빵부스러기) 그룹 이름 — 「상품사양관리」
  • 3위치 표시 화면 이름 — 「조립 호환 조감도」(⚠ 메뉴 라벨과 다릅니다 — 위 참고)
  • 4표현 전환 탭 3개(지도형·진단형·매트릭스형) — 자세한 위치는 그림 B
  • 5요약 표시 — 「관계 28 · 사양 64」(조회 성공 시) 또는 「세션 만료」·「조회 실패」(실패 시, 붉은 글자)
  • 6대상 고정(pin) 안내줄(테두리 상자) — 지금은 고정된 부품이 없어 "부품을 클릭하면 고정되어 탭을 바꿔도 유지됩니다" 안내만 보입니다
  • 7요약 카드 4개(테두리 상자) — 호환 관계 22(전체 28, 범위 밖 6) · 검사 적용 9(규칙 등록 완료) · 판정 가능 11(양측 사양 값 확보) · 사양 항목 64(부품별 합계)
  • 8지도 영역(테두리 상자) — 부품 노드와 관계선. 자세히는 그림 C
  • 9우측 레일(테두리 상자) — 부품별 사양 충족률 + 관계 목록. 자세히는 그림 D

그림 B상단 헤더 확대

  • 10위치 표시 그룹 — 「상품사양관리」
  • 11위치 표시 화면 이름 — 「조립 호환 조감도」
  • 12지도형 탭 — 기본 선택. 제약의 그물이 주인공(관계 하나 = 선 하나)
  • 13진단형 탭 — 격차가 주인공(규칙이 안 막는 관계를 일감으로 세움)
  • 14매트릭스형 탭 — 부품 × 부품 격자, 빈칸이 곧 "정의된 관계 없음"
  • 15요약 표시 — 조회 성공 시 "관계 N · 사양 N"
  • 16허브 — 새 탭에서 내부 접근 허브로 이동

그림 C지도 영역 확대(관계선 · 노드 · 범례)

  • 19좌하단 범례(테두리 상자) — 상태 4종을 선 색 · 기호 · 글자 · 건수로 함께 표시(◆ 규칙 미등록 3 · ○ 사양 값 부족 10 · ● 검사 적용 9 · · 범위 밖 6, "아까운 순")
  • 20부품 노드 예시 — CPU. 굵은 글자는 코드(CPU), 옅은 글자는 한글 이름. 관계선이 몰리는 노드일수록 화면 중앙에 배치됩니다(배치 자체는 데이터가 아니라 화면이 정한 고정값입니다)
  • 21부품 노드 예시 — SSD. 관계선 위에는 그 관계의 코드(예 "A5")가 작은 라벨로 붙습니다 — 선의 색과 굵기가 상태를 나타냅니다(검사 적용은 굵고 진하게, 범위 밖은 점선으로 옅게)

그림 D우측 레일 확대(부품별 충족률 · 관계 목록, 고정 없음)

  • 22캡션 「부품 10종 · 사양 충족률」
  • 23부품별 충족률 막대 목록(테두리 상자) — 사양 항목 수가 많은 순서로 10종이 나열됩니다(메인보드 15개 항목으로 최다). 오늘 값 예시: 메인보드 65% · 케이스 50% · 그래픽카드 38%(최저) · 파워 54% · CPU 86% · 메모리 57% · CPU쿨러(수랭) 50% · CPU쿨러(공랭) 58% · HDD 49% · SSD 88%(최고)
  • 24관계 목록 제목 — 고정된 부품이 없으면 「관계 28건 · 우선순위순」입니다. ⚠ 이 28은 범위 밖(out) 6건까지 포함한 전체 건수입니다 — 위 「호환 관계」 요약 카드의 22(범위 안만)와 다릅니다, 헷갈리지 않도록 주의하십시오
  • 25관계 목록 시작 지점 — 아래로 스크롤됩니다(목록 전체 높이가 이 레일 영역보다 커서 테두리 상자로 표시하지 않았습니다). 규칙 미등록(◆) → 사양 값 부족(○) → 검사 적용(●) → 범위 밖(·) 순으로 정렬됩니다("아까운 순" — 코드 주석 그대로). 각 행에 관계 코드 · 부품 쌍(코드 그대로, 예 "RAM ↔ MB") · 상태 배지 · 무엇을 비교하는지 · 연관 사양 충족률이 나옵니다

4무엇을 할 수 있는가

  • 표현(탭) 전환 — 지도형·진단형·매트릭스형 세 탭을 자유롭게 오갑니다. 셋 다 같은 데이터를 다른 방식으로 보여줄 뿐이라, 어느 탭에서 본 숫자든 서로 다르지 않습니다.
  • 부품에 마우스 올리기(미리보기) — 그 부품이 걸린 관계선·행이 진해지고 나머지는 흐려집니다. 마우스를 떼면 즉시 원래대로 돌아갑니다.
  • 부품 클릭(고정, pin) — 지도의 노드, 우측 레일의 부품 행, 진단형의 부품 카드, 매트릭스의 행 머리 중 어디를 클릭해도 같은 부품이 고정됩니다. 고정하면 상단에 📌 표시가 있는 안내줄이 뜨고, 탭을 바꿔도 고정이 풀리지 않습니다 — 세 표현을 같은 대상으로 비교할 수 있게 하기 위한 기능입니다. 다시 클릭하면 해제되고, 안내줄의 해제 ✕ 버튼이나 부품이 아닌 곳(바깥)을 클릭해도 해제됩니다. 자세히는 그림 E·그림 F.

5⚠ 조심할 것

「검사 적용(●)」이 사양 충족률 100%를 뜻하지 않습니다. 이 상태는 활성 규칙 (compat_rules)이 걸려 있다는 뜻일 뿐입니다. 예를 들어 D2(CPU쿨러(공랭)↔CPU, 발열(TDP) 판정)는 오늘 값으로 「검사 적용」이지만, 관련 사양 충족률은 20%·50%·74%에 그칩니다 — 코드에 남은 메모 그대로 "규칙 등록 완료 · 사양 값 부족으로 후보 탈락 다수"입니다. 규칙이 걸려 있어도 정작 그 규칙을 적용할 값이 없는 상품은 후보에서 조용히 빠질 수 있습니다.
"검사 적용(●)"은 compat_rules 기준이지 std 스키마 자체가 엔진에 반영된다는 뜻이 아닙니다. 이 화면이 참조하는 std.compat_pairs· std.spec_defs는 새로 세우는 표준이고, 실제 견적 엔진은 public.compat_rules·public.product_specs만 읽습니다(화면 하단에 항상 떠 있는 안내 문구 그대로).
이 화면은 아무것도 쓰지 않습니다. 규칙을 새로 걸거나 사양 값을 입력하는 동작이 전혀 없습니다. 규칙 편집은 「조립 호환 규칙」(정의서만 있고 아직 화면은 없습니다), 값 입력은 「조립 사양 표준」·「상품 사양 검수」 화면의 몫입니다.
「대상 고정」은 마우스를 올리기(hover)만으로는 되지 않습니다. 올려두기는 미리보기일 뿐이라 마우스를 떼면 즉시 사라집니다. 탭을 바꿔도 남는 「고정」은 반드시 클릭해야 됩니다(그림 E). 클릭 없이 마우스만 올린 채 탭을 누르면, 탭으로 이동하는 순간 마우스가 부품을 벗어나 강조가 풀립니다.
레일 제목의 「관계 28건」과 요약 카드의 「호환 관계 22」는 다른 수입니다. 고정 없이 볼 때 레일 제목의 28은 범위 밖(out) 6건까지 포함한 전체 관계 수이고, 상단 요약 카드의 22는 범위 안만 센 수입니다. 같은 화면 안에서 분모가 다른 두 숫자이니 헷갈리지 않도록 주의하십시오.
관계 목록의 부품 이름은 화면 전체에서 한글로 안 바뀝니다. 지도의 노드 라벨(작은 글씨)만 한글 이름을 보여주고, 우측 레일·진단형 카드·매트릭스 격자에 나오는 "RAM ↔ MB" 같은 부품 쌍 표기는 코드(part_type) 그대로입니다.
값을 받지 못하면 사유를 구분해 안내합니다. 세션 만료(401)면 "세션 만료" + /admin2/login으로 이동하는 링크가, 그 밖의 실패면 "데이터 조회 실패 — {서버 오류 메시지}" + [다시 시도] 버튼이 뜹니다(코드 확인). 자동으로 다시 조회하지 않으므로 반드시 버튼을 눌러야 합니다.
이 화면의 숫자는 매번 새로 조회됩니다. 관계 28건·범위 안 22건 같은 수치는 DB 상태에 따라 바뀝니다. 지금 정확한 값은 화면을 열어 직접 확인하십시오.

6자주 겪는 상황

  • 「메뉴에서 눌렀는데 화면 제목이 다르다」 → 정상입니다. 좌측 메뉴는 「조립 호환 지도」, 화면 안은 「조립 호환 조감도」입니다. 위 「① 이 화면이 무엇을 하는 곳인가」 참고.
  • 「지도에 선이 너무 많아서 뭐가 뭔지 모르겠다」 → 궁금한 부품 하나를 클릭해 고정하십시오(그림 E). 그 부품이 걸린 관계선만 진해지고 나머지는 흐려집니다.
  • 「탭을 바꿨더니 방금 보던 부품 강조가 사라졌다」 → 마우스를 올리기만(hover) 했을 가능성이 큽니다. 탭을 넘나들며 유지하려면 반드시 클릭해서 고정해야 합니다.
  • 「매트릭스 칸이 비어 있다」 → 그 두 부품 사이에는 정의된 관계 자체가 없다는 뜻입니다(아직 검사를 안 한 것과는 다릅니다 — 미검사 상태는 기호가 있는 칸으로 나타납니다).
  • 「SSD가 왜 여기서 안 보이나 했더니 관계가 하나뿐이다」 → SSD가 걸리는 관계는 A8(SSD↔메인보드, "인터페이스별 장착 위치") 하나뿐입니다. 오늘 실측으로 이 관계는 활성 규칙이 없는 상태(rule_active=false)이고 사양 값도 일부 0%라 상태는 「사양 값 부족」입니다 — SSD는 지금 이 화면 기준으로 어떤 활성 규칙의 보호도 받지 못합니다.
  • 「규칙이 이미 걸려 있다는데(●) 왜 후보가 잘 안 늘어나나」 → 규칙이 걸려 있어도 관련 사양 값이 비어 있으면(0%) 그 규칙을 적용할 상품 자체가 적습니다. 위 「조심할 것」의 D2 사례를 참고하십시오.
  • 「화면에 '세션 만료'라고 뜬다」 → 로그인이 끊긴 상태입니다. 안내에 뜨는 링크로 다시 로그인하십시오.
  • 「이 문서에 적힌 숫자와 화면 숫자가 다르다」 → 정상입니다. 이 문서는 2026-08-27 스냅샷이고, 화면은 열 때마다 다시 조회합니다.

화면이 바뀌면 아래 명령으로 캡처를 다시 찍고, 이 문서의 --x·--y· --w·--h 값도 새 build-map-coords.json에 맞춰 다시 옮겨야 합니다(좌표는 손으로 만든 값이 아니라 그 시점 캡처의 실측값이므로, 화면이 바뀌면 함께 낡습니다 — 단, 그림 D의 25번처럼 목록이 화면보다 길어 실측 높이가 뜻이 없는 항목은 이 문서를 만들 때 사람이 화면 안쪽 지점을 가늠해 골랐습니다). 화살표(그림 E의 SVG 선)는 좌표 JSON에 담기지 않습니다 — viewBox 1680×1050 기준 원시 픽셀 좌표를 이 문서 안에 직접 적어 두었으므로, 화면 레이아웃이 바뀌면 사람이 캡처를 보고 다시 맞춰야 합니다.

.venv/Scripts/python scripts/manual_shots_build_map.py

이 스크립트는 Playwright를 씁니다 — .venv에는 이미 설치돼 있지만 requirements.txt에는 없습니다. 새 환경(다른 PC·재설치한 venv)에서는 pip install playwright 후 playwright install chromium이 먼저 필요합니다.

확인하지 못한 것

  • 이 문서를 만드는 작업에는 브라우저(화면을 눈으로 보는 도구)가 없어, 완성된 이 HTML 문서 자체가 브라우저에서 실제로 어떻게 보이는지(핀·상자 좌표가 캡처 위에 정확히 맞는지, 그림 E의 화살표가 실제로 노드→안내줄을 정확히 잇는지)는 직접 확인하지 못했습니다 — 별도 확인이 필요합니다.
  • 오류 상태 화면(401 「세션 만료」 카드, 그 밖의 「데이터 조회 실패」 카드)은 캡처하지 못했습니다. 재현하려면 이 화면의 인증 세션을 깨야 하는데, 캡처 시점에 다른 네 명이 같은 개발 서버·로그인 세션을 동시에 쓰고 있어 그들의 작업에 영향을 줄 위험이 있다고 판단해 시도하지 않았습니다.
  • 관계가 0건인 경우(이론상 상태 — 정의서도 "지금까지 실사용에서 관측되지 않았다"고 적어 두었습니다)는 오늘도 28건이 항상 존재해 캡처할 수 없었습니다.
  • 조회 전용(뷰어) 등급 계정에서 이 화면이 어떻게 보이는지는 확인하지 못했습니다 — 캡처는 owner 등급 점검 계정으로만 찍었습니다(이 화면은 애초에 쓰기 동작이 없어 등급별 차이가 크지 않을 것으로 보이지만, 실제로 비교 확인하지는 않았습니다).
  • API 응답의 groups(관계 여섯 묶음의 이름·설명)는 화면 스크립트가 어디서도 읽지 않는 것으로 코드에서 확인했습니다 — 다만 이것이 "아직 안 쓴 것"인지 "쓸 계획이 없는 것"인지는 이 작업 범위 밖이라 판단하지 못했습니다.
