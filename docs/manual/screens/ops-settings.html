화면 오픈 단계 설정 · 경로 /admin2/ops-settings · 화면 ID ADM-OPS-010 (코드 api/admin_ops.py·api/admin_ui_ops_stage.py 실측값입니다. 옛 이름은 「운영 전환 설정」이었고, 2026-08-13 결정(A-34)으로 화면 라벨만 「오픈 단계 설정」으로 바뀌었습니다 — 화면 ID·데이터 API 경로는 그대로입니다.)
왜 이 화면부터인가 활동 기록 실측(2026-08-25)에서 이 화면의 처리(target_kind=ops)가 전체 관리자 동작 중 5위였습니다(누적 1,007건 — 22개 종류 중 1위 상품 사양 검수 3,694건에는 크게 못 미치지만, 정산·회원·환불 같은 화면 여럿을 합친 것보다 많습니다). 다만 건수보다 더 중요한 이유가 있습니다 — 이 화면은 작지만 서비스 전체 동작을 바꿉니다. 스위치 하나(결제)가 고객이 어디서 돈을 내는지 자체를 가릅니다.
코드·캡처 확인 기준일 2026-08-25 — 이 문서는 그 시점의 화면 코드와, 그 코드가 실제로 그리는 화면을 로컬 서버(127.0.0.1:8000, 실서비스와 같은 DB를 보는 개발 서버)에 직접 띄워 촬영한 결과를 근거로 썼습니다.
이 화면은 실서비스 동작을 바꾸는 스위치 화면입니다. 로컬에서 값을 저장하면 배포된 고객 서버에도 즉시 반영됩니다(로컬과 배포가 같은 Cloud SQL을 봅니다) — 이 문서를 만드는 동안 스위치는 한 번도 누르지 않았습니다(근거는 맨 끝 「문서 정보」 참고). 캡처 시점의 건수·이력은 매일 바뀝니다 — 정확한 지금 값은 화면에서 직접 확인하십시오.

1이 화면이 무엇을 하는 곳인가

회원·결제·정산·배송·환불 다섯 가지 기능을 「우리가 직접 하는지」 「팝콘PC 쇼핑몰에 맡기는지」 정하는 스위치 화면입니다. 오늘(2026-08-25) 실측한 값은 다음과 같습니다.

기능지금 값
회원·가입자체(own)
결제쇼핑몰 인계(mall)
환불쇼핑몰 인계(mall)
정산쇼핑몰 인계(mall)
배송쇼핑몰 인계(mall)

다섯 중 넷이 「쇼핑몰」입니다 — 지금은 팝콘PC 쇼핑몰로 인계해 판매하는 단계(MVP1)이기 때문입니다. 이 화면 하나가 없으면 지금 값이 무엇인지 볼 방법이 API를 직접 부르는 것뿐이고, 값을 바꿀 방법이 아예 없습니다 — 다른 어떤 관리자 화면도 이 값에 쓰기 요청을 보내지 않습니다.

2026-08-13 결정(A-34)으로 이 화면은 「스위치판」에서 한 걸음 더 나아가 「지금 어느 단계(MVP1/MVP2/MVP3)에 무엇이 열려 있는가」를 보여주는 현황판을 겸하게 됐습니다. 그래서 성격이 다른 두 가지 축을 함께 보여줍니다.

  • 전환 축(5종) — 사람이 켜고 끄는 정책 스위치. 회원·결제·정산·배송·환불.
  • 구축 축(41항목) — 관리자 기능이 실제로 지어졌는지 보여주는 진행 현황판. 이 화면에서 켜고 끌 수 없는 조회 전용입니다(정본은 api/admin_nav.py, 이 화면은 그 값을 그대로 옮겨 보여줄 뿐입니다).

스위치 하나(결제)가 고객이 어디서 돈을 내는지를 통째로 가릅니다. 결제가 「쇼핑몰 인계」이면 고객 결제는 POST /api/handoff로 열리고 POST /api/orders (자체 결제)는 409로 막힙니다. 결제를 「자체」로 바꾸면 정반대가 됩니다 — 인계가 409로 막힙니다. 코드 근거는 api/orders.py·api/handoff.py이고, 그 결과는 아래 「무엇을 할 수 있는가」·「조심할 것」에서 다시 다룹니다.

2언제 여기 오는가

  • 사업 단계가 바뀌어(MVP1 → MVP2) 결제·배송·환불·회원가입 중 일부를 자체로 전환할 때
  • 「지금 이 기능이 실제로 자체인지 쇼핑몰인지」가 헷갈려 값을 확인하러 올 때
  • 스위치를 바꾸는 것이 실제로 서버 동작을 바꾸는지(「동작 중」), 아직 코드가 없는지 (「미구현」)를 먼저 확인할 때 — 켜도 아무 일도 안 일어나는 스위치가 있습니다
  • 사고 원인을 조사할 때 — 최근 변경 이력에서 누가·언제·무엇을 바꿨는지 찾고, 잘못 바뀐 것을 되돌릴 때
  • 다음 단계(MVP2) 진입 준비가 얼마나 됐는지 — 전환 축 5종 중 몇 개가 실제로 「동작 중」인지 점검할 때
  • 관리자 화면 구축 진행률(41개 중 몇 개 지어졌는지)을 한눈에 보고 싶을 때

3화면 살펴보기

이 화면은 탭 넷(MVP1·MVP2·MVP3·단계 미정)으로 조회 범위가 나뉩니다. 처음 열면 「현재 단계」인 MVP1 탭이 기본으로 열리는데, MVP1에는 전환 축(스위치)이 하나도 없는 것이 정상입니다 — 다섯 스위치는 전부 MVP2·MVP3 소속입니다. 먼저 기본 진입 화면을 보고, 이어서 MVP2 탭으로 넘어가 실제 스위치가 나타나는 모습을 확인합니다.

4무엇을 할 수 있는가

  • 탭(MVP1/MVP2/MVP3/단계 미정)을 눌러 조회 범위를 바꿉니다 — 조회만 바뀌고 값은 바뀌지 않습니다.
  • 전환 축의 이름·요약 부분(그림 E)을 누르면 상세 패널(그림 F)이 열립니다 — 값 선택 카드, 판정 설명(근거 포함), 「이 값이 바뀌면」 목록을 봅니다.
  • 행 안의 own/mall 토글 버튼이나 상세 패널의 값 카드를 눌러 값을 바꿉니다 — 이 순간 DB에 저장되는 것이 아니라 그 행에 「변경됨」 표시만 붙습니다. 실제 반영은 아래 저장 절차를 거쳐야 합니다.
    • 정산(settle)은 결제(pay)를 그대로 따르도록 잠겨 있어 직접 고를 수 없습니다.
    • 환불(refund)을 「자체」로 선택해도 결제가 「쇼핑몰」이면 저장 시 서버가 자동으로 「쇼핑몰」로 되돌립니다(PG 취소 권한이 없어서) — 화면이 이 보정을 저장 전 확인 단계에서 미리 보여줍니다.
  • 저장 — 확인 단계로를 누르면 확인 모달이 열립니다. 「요청한 것 vs 실제 적용될 것」 대조표에서 서버가 자동으로 보정한 값은 「서버 보정」 태그로 따로 표시됩니다. 결제를 「자체」로 바꾸는 경우에는 위험 경고와 함께 정확한 확인 문구(인계를 막습니다)를 그대로 입력해야만 확인 모달의 저장 버튼이 눌립니다 — 그 순간부터 팝콘PC 인계가 409로 막히기 때문입니다.
  • 단계 프리셋 3종(현행/자체 결제 전환/전면 자체 운영) 버튼으로 값 조합을 한 번에 채웁니다 — 채우기만 하고 저장은 여전히 별도입니다.
  • 최근 변경 이력(최대 20건)에서 누가·언제·무엇을 바꿨는지 보고, 되돌리기로 그 건 하나만 이전 값으로 복원합니다 — 이미 되돌려진 건은 다시 되돌릴 수 없습니다(그림 I).
  • 하단의 되돌리기(저장 전용) — 아직 저장하지 않은 임시 변경을 서버에 있는 값으로 원위치합니다. 위 이력의 되돌리기와는 다른 버튼입니다 — 저장 이력에 남지 않습니다.
  • 구축 축 표(단계 미정 탭, 그림 H)에서 그룹별 「구축/전체」 건수와 항목 칸을 조회합니다. 초록 칸(구축됨)을 누르면 그 관리자 화면으로 바로 이동합니다.

5⚠ 조심할 것

처음 열면 스위치가 하나도 안 보이는 것은 고장이 아니라 정상입니다. 기본 탭(MVP1)에는 전환 축이 원래 없습니다 — 「지금은 인계로 판매하는 단계라 켤 것이 없다」는 뜻입니다. 다섯 스위치를 보거나 바꾸려면 위 탭에서 MVP2(결제·환불·배송·회원 4종) 또는 MVP3(정산 1종)을 눌러야 합니다.
이 화면의 저장은 즉시, 그리고 실제 배포된 고객 서버에도 반영됩니다. 로컬 개발 환경과 배포 서버가 같은 Cloud SQL을 공유하기 때문입니다. 2026-08-12에 이 경로로 실제 사고가 났습니다 (스위치는 바뀌었는데 배포된 코드가 그 값을 처리하지 못하는 상태가 됨) — 화면 자신도 저장 확인 모달에 이 경고를 그대로 띄웁니다(「이 저장은 배포된 고객 서버에도 즉시 반영됩니다」).
결제를 「자체」로 바꾸는 순간 팝콘PC 인계가 즉시 막힙니다(409). 지금(2026-08-25) 확정된 유일한 구매 경로가 인계이므로, 이 전환은 사실상 「주문을 받을 곳이 없어지는」 조작입니다. 그래서 화면이 정확한 확인 문구 입력을 강제합니다 — 실수로 스치듯 저장할 수 없게 만든 장치입니다.
다섯 스위치 중 실제로 서버 처리가 갈리는 것은 「결제」·「환불」 둘뿐입니다(오늘 실측: 동작 중 2 · 잠듦 1(정산) · 미구현 2(배송·회원·가입)). 「배송」·「회원·가입」을 바꿔도 값과 이력은 남지만, 그 값을 읽어서 처리를 분기하는 코드가 아직 없어 실제로는 아무 일도 일어나지 않습니다. 이 판정(동작 중/잠듦/미구현)은 서버가 매 요청 다시 검사하는 것이 아니라 2026-08-13 코드 감사를 그대로 옮긴 스냅샷입니다(헤더의 「판정 기준일 2026-08-13」이 그 뜻입니다, 그림 K의 49번) — 그 뒤 코드가 바뀌어도 판정 문구는 자동으로 따라오지 않습니다.
⚠ 이력이 남는 자리가 두 곳으로 갈라져 있고, 그중 하나는 죽어 있습니다. DB 설계도 (docs/06_db-erd.md)에는 이 화면 전용 이력 표(ops_settings_history)가 따로 정의돼 있습니다. 오늘 직접 확인한 결과 이 표는 딱 2행뿐이고, 그 2행마저 2026-07-23 초기 시드 데이터입니다 — 그 이후로 이 표에 쓰는 코드가 api/ 전체에 한 줄도 없습니다. 실제로 그 표의 마지막 행은 「pay: mall→own」이라 적혀 있는데, 지금 실제 값은 pay=mall입니다 — 표 자체가 지금 사실과 어긋나 있습니다. 화면이 실제로 보여주는 이력(그림 A의 12번, 그림 I)은 이 표가 아니라 관리자 활동 기록 (admin_operator_activity_logs, target_kind='ops')에서 옵니다 — 여기는 오늘 기준 1,007건(변경 505건 + 되돌리기 502건, 계속 늘어나는 중)이 실제로 쌓여 있고 화면의 「최근 변경 이력」·「되돌리기」 버튼이 실제로 이 표를 읽고 씁니다. 정리하면 — 이력은 남습니다. 다만 화면이 보여주는 이력과 DB 설계도가 말하는 전용 이력 표는 서로 다른 곳입니다.
조회(viewer) 등급 계정은 값을 볼 수는 있어도 스위치·프리셋·저장·되돌리기 버튼이 전부 눌리지 않는 상태(회색, 마우스를 올리면 「권한이 부족합니다」)로 보입니다.

6자주 겪는 상황

  • 「화면을 열었는데 스위치가 하나도 없다」 → MVP1 탭이 기본으로 열려 있어서입니다 (정상 — 위 「조심할 것」 참고). MVP2 탭을 누르십시오.
  • 「환불을 자체로 바꾸고 저장했는데 도로 쇼핑몰로 남아 있다」 → 결제(pay)가 여전히 쇼핑몰이면 서버가 자동으로 환불도 쇼핑몰로 보정합니다(쇼핑몰 결제 건은 PG 취소 권한이 없어서). 결제부터 자체로 바꿔야 합니다.
  • 「정산 토글 버튼이 안 눌린다」 → 정산은 항상 결제와 같은 값으로 잠겨 있습니다 (그림 G). 결제를 바꾸면 정산도 자동으로 따라 바뀝니다.
  • 「저장 버튼을 눌렀는데 아무 반응이 없다」 → 하단의 저장 — 확인 단계로는 확인 모달을 여는 버튼입니다. 실제 반영은 그 모달 안에서 한 번 더 저장을 눌러야 일어납니다(2단계 확인).
  • 「결제를 자체로 바꾸려는데 저장 버튼이 안 눌린다」 → 확인 모달의 입력칸에 정확한 확인 문구를 토씨 하나 틀리지 않고 입력해야 버튼이 활성화됩니다.
  • 「이력에 되돌리기 버튼이 없는 행이 있다」 → 그 행 자체가 이미 「되돌리기」 동작 이거나(되돌린 것을 또 되돌릴 수는 없습니다), 이미 다른 되돌리기로 취소된 변경(「되돌려짐」 태그)입니다.
  • 「구축 축 표를 보고 싶은데 안 보인다」 → MVP1/MVP2/MVP3 탭에는 안내 문구나 「정황상 대응」 카드만 있습니다. 실제 표(그룹별 8행, 41항목)는 「단계 미정」 탭에만 있습니다(그림 H).
  • 「분명히 이력이 쌓이는데 DB의 ops_settings_history 표를 보면 텅 비어 보인다」 → 정상입니다. 그 표는 죽어 있고(2026-07-23 시드 2행뿐), 실제 이력은 활동 기록 표에 쌓입니다 — 위 「조심할 것」 참고.
