운영자 매뉴얼 — 상품 분류 관리

화면을 처음 쓰는 직원이 이 문서만 보고 바로 일을 시작할 수 있도록 썼습니다.

대상 관리자 화면(admin2)의 상품 분류(판매 탐색 트리)를 처음 관리하는 직원
화면 상품 분류 관리 · 경로 /admin2/categories · 화면 ID ADM-CAT-010 (코드 api/admin_ui_product_category.py·templates/admin/product_category.html.j2 실측값입니다. 작업 지시에는 API 모듈이 api/admin_ui_categories.py로 적혀 있었으나 실제 파일명은 api/admin_ui_product_category.py입니다 — 화면 자체는 같은 화면이 맞습니다, 확인 기준은 경로(/admin2/categories)입니다). 데이터 API는 api/admin_categories.py(GET/POST/PATCH/DELETE /api/admin/categories, PUT /api/admin/categories/{id}/margin)입니다.
왜 이 화면부터인가 좌측 메뉴 「상품관리」 그룹의 맨 위 항목이고, 활동 기록 실측 (2026-08-25)에서 category 종류 처리가 관리자 전체 동작 중 4위(누적 1,489건)였습니다. 다만 뒤 「최근 500건 안 80건」에서 보듯, 이 category 표시에는 이 화면이 아니라 「상품 분류 매핑」 화면의 동작도 섞여 있습니다 — 자세한 것은 아래 「⚠ 조심할 것」참고.
코드·캡처 확인 기준일 2026-08-25 — 이 문서는 그 시점의 화면 코드와, 그 코드가 실제로 그리는 화면을 로컬 서버(127.0.0.1:8000, 실서비스와 같은 DB를 보는 개발 서버)에 직접 띄워 촬영한 결과, 그리고 document.elementFromPoint()로 실제 클릭 가능 여부를 확인한 진단 결과를 근거로 썼습니다.
이 화면은 실데이터를 다룹니다. 캡처 시점의 건수(분류 34건 · 위반 523건 등)는 상품 적재·검수가 진행되며 바뀝니다 — 정확한 지금 값은 화면 상단 지표 카드를 직접 확인하십시오.
⚠ 이 화면과 이름이 닮은 「상품 분류 매핑」(/admin2/category-mapping, api/admin_category_mapping.py)은 다른 화면입니다. 이 화면(상품 분류 관리)은 분류 트리 자체(대분류·소분류·이름·마진)를 만들고 다듬는 곳이고, 「상품 분류 매핑」은 실제 상품을 그 트리 어딘가로 옮기는 곳입니다. 일괄 이동 상한(MAX_MOVE=2000)은 그 다른 화면의 것이고, 이 화면에는 상품을 옮기는 기능 자체가 없습니다 — 혼동하지 않도록 아래 「⚠ 조심할 것」 1번에 근거와 함께 다시 적었습니다.

테두리 상자 = 하나로 묶어 보는 영역

1이 화면이 무엇을 하는 곳인가

상품을 담을 판매 탐색 트리(categories 표)를 만들고 다듬는 화면입니다. 대분류 밑에 소분류를 두는 2단 트리이고, 분류마다 이름 · 정렬순서 · 노출 여부 · 허용 부품 종류 · 마진율을 관리합니다. 실제 상품을 이 트리의 어느 칸에 옮겨 담는 일은 이 화면이 하지 않습니다 (그것은 「상품 분류 매핑」 화면 소관입니다) — 이 화면은 상품을 담을 그릇 자체를 만드는 자리입니다.

화면 상단 배너가 이 화면의 경계를 스스로 밝힙니다(실측 그대로 인용):

「엔진은 이 트리를 읽지 않습니다 — 분류를 옮겨도 견적 결과는 바뀌지 않습니다」
「카테고리는 판매 탐색 축입니다 — 엔진(견적)은 이 표를 읽지 않습니다. 카테고리를 옮겨도 견적 결과는 달라지지 않습니다.」

견적 엔진이 실제로 읽는 축은 part_type·category_group이고, 이 둘은 categories 표와 완전히 다른 컬럼입니다(api/taxonomy.py 실측 — 「판매용 분류는 별도 축인 categories가 맡는다 — 그쪽은 운영자가 자유롭게 만든다」). 이 화면에서 분류를 아무리 옮기거나 이름을 바꿔도 상품이 견적 추천 후보에서 빠지거나 들어오는 일은 일어나지 않습니다.

2026-08-25 실측 기준: 분류 34건(대분류 6 · 소분류 28) · 개별 마진이 걸린 분류 0건(전부 전역 기본 12%를 상속) · 허용 종류 위반 523건(7개 노드에 분산 — 경고일 뿐 저장을 막지는 않습니다) · 분류 미배정 상품 51건(재고 있음 33건 포함) · 분류를 고를 때 쓰는 표시 종류 18종(쿨러 공랭·수랭을 하나로 접은 값).

2언제 여기 오는가

  • 새 판매 카테고리(대분류 또는 소분류)를 만들어야 할 때
  • 카테고리 이름을 바꾸거나 다른 상위 분류 밑으로 옮겨야 할 때
  • 특정 분류에만 다른 마진율을 걸어야 할 때(걸지 않으면 상위 또는 전역 기본값을 그대로 상속)
  • 상단 지표의 「허용 종류 위반」이 늘어난 것을 보고 원인을 살피러 올 때(단, 실제로 상품을 옮겨 바로잡는 것은 이 화면이 아니라 「상품 분류 매핑」 또는 상품 상세 화면입니다)
  • 「분류 미배정 상품」이 있는지 확인하러 올 때(옮기는 것은 역시 다른 화면)
  • 좌측 메뉴 「상품관리」 그룹의 「상품 분류 관리」에서 옵니다 — 직접 주소 (/admin2/categories)로도 들어올 수 있습니다

그림 F분류를 클릭하면 열리는 위치

  • 30방금 클릭한 행(강조 표시)
  • 31우측에 뜨는 상세 서랍(테두리 상자) — 확대는 그림 G·그림 H
  • 32「+ 하위 분류 추가 — 메인보드」로 바뀐 버튼 — 분류를 선택하면 왼쪽 아래 추가 버튼의 라벨이 이렇게 바뀝니다. 그런데 지금 이 순간 이 버튼은 실제로 눌리지 않습니다 — 서랍과 함께 뜨는 반투명 배경막이 이 버튼 위까지 덮고 있어서입니다 (화살표가 그 범위를 가리킵니다). document.elementFromPoint()로 이 버튼의 정중앙 좌표를 실측한 결과, 그 자리에서 실제로 맨 위에 있는 요소는 버튼이 아니라 배경막 (#pcBackdrop)이었습니다 — 클릭은 하지 않고 좌표만 읽어 확인했습니다. 자세한 내용과 실제로 겪는 결과는 아래 「조심할 것」 2번을 반드시 읽으십시오.

그림 G상세 서랍 확대 — 허용 종류 위반이 있는 분류

  • 33분류 이름 · 「대분류/소분류」 배지 · 닫기(✕)

  • 36상위 분류 — 이동 드롭다운. 선택지는 최상위(대분류) 노드만 입니다(실데이터가 2단이라 그렇게 좁혀 둔 것 — 서버 자체는 더 깊은 이동도 받습니다). 자기 자신이나 자기 하위로 옮기려 하면 그 항목에 「순환」 표시가 붙고 고를 수 없습니다.
  • 37정렬순서 입력창(숫자)
  • 38허용 부품 종류 칩(테두리 상자) — 표시 종류 18종 중 원하는 만큼 선택합니다(칩 색이 진해지면 선택된 것). 비우면 「제한 없음」입니다. 저장은 화면이 자동으로 실제 part_type 코드로 바꿔 보냅니다(쿨러를 고르면 공랭·수랭 둘 다).

  • 40노출 스위치 — 「노출 켜짐(is_visible=true)」. 아래 안내 문구가 스스로 「지금은 이 값을 읽는 소비처가 없어 꺼도 목록에서 사라지지 않습니다」라고 밝힙니다.
  • 41위반 경고(테두리 상자, 이 분류에 위반이 있을 때만 나타남) — 「이 분류에 허용 종류를 어기는 상품 54건이 이미 있습니다 — 경고일 뿐 저장은 막지 않습니다. 옮기는 것은 "상품 분류 매핑" 화면에서 합니다.」
  • 42삭제 — 확인 창이 없습니다 (아래 「조심할 것」 3번 참고). 이 예시(상품 2,107건)는 눌러도 서버까지 가지 않고 화면이 먼저 「상품 2,107건이 이 카테고리에 있습니다 — 먼저 옮기세요」라고 막습니다 — 다만 버튼 자체는 회색으로 비활성화돼 있지 않습니다(코드 확인, 실제로 누르지는 않았습니다).
  • 43되돌리기 — 서버 저장을 되돌리는 것이 아니라, 아직 저장하지 않은 이 화면의 임시 수정을 저장 전 상태로 되돌리는 버튼입니다. 바뀐 것이 없으면 비활성입니다.
  • 44저장 — 바뀐 것이 없으면 비활성입니다.
  • 45하단 안내 문구 — 「변경 사항이 없습니다」처럼 지금 상태를 알려줍니다. 권한이 없으면 「권한이 부족합니다(필요: operator, 현재: …) — 조회만 가능합니다」로 바뀝니다.

그림 H상세 서랍 확대 — 저장 전 미확정 상태

  • + 대분류 추가 — 트리에서 아무것도 안 고른 상태에서 누르면 최상위에 「새 대분류」를 즉시 만듭니다(확인 창 없음). 같은 자리에 같은 이름이 이미 있으면 새로 만들지 않고 그 분류를 열어 보여줍니다.
  • + 하위 분류 추가 — <이름> — 분류를 고른 상태에서 버튼 라벨이 이렇게 바뀌고, 그 분류 바로 아래에 「새 소분류」를 만드는 용도로 설계돼 있습니다. 다만 지금은 마우스로 실제로 눌리지 않습니다 — 반드시 아래 「조심할 것」 2번을 읽으십시오.

5⚠ 조심할 것

이 화면은 견적·추천 후보에 영향을 주지 않습니다 — 「분류를 잘못 옮기면 상품이 후보에서 빠진다」는 이 화면 이야기가 아닙니다. 작업 지시에는 그런 위험이 있다고 적혀 있었지만, 코드를 실측한 결과 사실이 아니었습니다: 이 화면이 다루는 categories.category_id는 api/recommend.py 어디에서도 참조되지 않고(0건), 화면 배너도 「분류를 옮겨도 견적 결과는 바뀌지 않습니다」라고 스스로 밝힙니다. 견적 후보를 정말로 좌우하는 축은 part_type·category_group이고, 그건 상품 상세·카탈로그 적재가 다루는 완전히 다른 컬럼입니다. 마찬가지로 「일괄 이동 상한 MAX_MOVE=2000」도 실재하는 값이지만 이 화면이 아니라 「상품 분류 매핑」 화면(api/admin_category_mapping.py:43) 것입니다 — 이 화면에는 상품을 옮기는 기능 자체가 없습니다. 두 화면을 섞어 안내하면 운영자가 엉뚱한 화면에서 원인을 찾게 됩니다.
「+ 하위 분류 추가 — <이름>」 버튼은 지금 마우스로 눌리지 않습니다(실측 확인). 분류를 선택하면 이 버튼의 라벨이 바뀌지만, 그 순간 함께 뜨는 반투명 배경막(서랍을 닫는 용도)이 이 버튼 위까지 덮습니다. document.elementFromPoint()로 버튼 정중앙 좌표를 실측하니 실제로 맨 위에 있는 요소는 배경막(#pcBackdrop)이었고, 버튼 자신은 isButtonReachable: false였습니다(클릭은 하지 않고 좌표만 읽어 확인 — 그림 F 참고). 배경막을 없애려면 서랍을 닫아야 하는데, 서랍을 닫으면 선택 자체가 풀려 버튼 라벨이 곧바로 「+ 대분류 추가」로 되돌아갑니다 — 그래서 지금 구조로는 「특정 분류 아래에 하위 분류를 만든다」는 이 버튼의 목적을 마우스 클릭만으로는 이룰 수 없습니다. 급하면 일단 + 대분류 추가로 최상위에 만든 뒤, 서랍의 「상위 분류 — 이동」으로 원하는 대분류 밑으로 옮기는 두 단계로 우회할 수 있습니다. 이 결함은 화면 코드 (templates/admin/product_category.html.j2)를 고쳐야 풀리는데, 이 작업의 담당 파일 밖이라 여기서는 고치지 않았습니다 — 제작 보고서에 남깁니다.
삭제·+ 대분류 추가·「+ 하위 분류 추가」는 전부 확인 창이 없습니다. 조건(하위 분류 없음 · 직속 상품 없음)만 맞으면 클릭 한 번으로 즉시 서버에 반영됩니다. 삭제된 분류는 되돌릴 API가 없어 되살릴 방법이 이력 열람 말고는 없습니다(이름 · 정렬순서 · 마진 설정을 사람이 다시 입력해야 합니다).
되돌리기는 전부 「미구현」입니다. 헤더의 되돌리기 버튼, 우측 레일 이력 목록의 되돌리기 버튼 모두 항상 비활성입니다. 트리 편집(추가·이름·이동·삭제·마진)은 활동 로그에 기록만 되고 역방향으로 되돌리는 API 자체가 없습니다(실측 — api/admin_categories.py에 undo 라우트 0개).
우측 레일의 「최근 변경」 목록에는 이 화면과 무관한 항목도 섞여 나옵니다. 이 목록은 활동 로그에서 kind==='category'인 것만 걸러 보여주는데, 그 종류 표시는 이 화면의 트리 편집뿐 아니라 「상품 분류 매핑」 화면의 「이동」·「이동 되돌림」에도 똑같이 붙습니다(실측 2026-08-25: 최근 500건 안 category 80건 중 46건이 「카테고리 매핑 이동」류였습니다). 그런데 이 화면은 그 항목에도 예외 없이 「미구현」 배지를 붙입니다 — 실제로는 「상품 분류 매핑」 화면에서 되돌릴 수 있는 항목인데도 여기서는 구분 없이 「안 된다」로 보입니다.
마진을 저장해도 판매가는 그 자리에서 바뀌지 않습니다. 「다음 판매가 재산정」에서만 반영됩니다 — 서랍·응답 문구가 매번 이 사실을 알려주지만, 급하게 가격을 내려야 하는 상황에서 이 화면만 만지고 끝냈다고 착각하기 쉽습니다.
노출(is_visible) 스위치는 지금 아무 효과가 없습니다. 화면이 스스로 「사각지대」 카드로 이 사실을 밝힙니다 — 꺼도 상품 등록 화면의 분류 선택지 등 어디에서도 사라지지 않습니다. 값은 저장되고 이력에 남을 뿐입니다.
「분류 미배정 상품」 수는 정의가 하나가 아닙니다. 이 화면(과 이 API)이 세는 「미배정」은 category_id IS NULL 기준(2026-08-25 51건)뿐입니다. 「미분류」라는 이름의 노드에 담긴 상품이나 부품 종류 자체를 못 정한(part_type='ETC') 상품은 다른 개념이고, 이 화면은 그 수를 세지 않습니다 — 세 수를 서로 더하거나 비교하지 않도록 주의하십시오.
허용 종류가 기타(ETC)뿐인 소분류(2026-08-25 기준 13개)는 서로 구분되지 않습니다. 예를 들어 케이블 · 쿨링용품 · 프린터가 각각 다른 소분류에 있어도, 전부 「기타(ETC)」 하나만 허용하므로 허용 종류 위반 판정으로는 서로 구분되지 않습니다. 이 화면은 이 사실을 밝히기만 하고 2차 판별은 하지 않습니다.
로컬 서버에서 고친 것이 운영에 바로 반영됩니다. 개발 DB와 운영 DB가 같은 Cloud SQL 인스턴스를 봅니다 — 로컬 화면에서 분류를 추가·삭제하거나 마진을 걸면 배포 서버 (admin.popcornai.co.kr)의 값도 즉시 바뀝니다. 이 문서를 만드는 과정에서는 조회 (GET)만 했고 쓰기 동작은 한 번도 누르지 않았습니다.

6자주 겪는 상황

  • 「분류를 옮겼는데 견적·추천에 아무 변화가 없다」 → 정상입니다. 이 화면은 견적 엔진이 읽는 축(part_type·category_group)과 무관합니다. 추천 후보를 바꾸려면 상품 상세에서 부품 종류·분류를 직접 고쳐야 합니다.
  • 「어떤 분류 아래에 소분류를 새로 만들고 싶은데 버튼이 안 눌린다」 → 지금 구조의 알려진 한계입니다(위 「조심할 것」 2번). + 대분류 추가로 만든 뒤 「상위 분류 — 이동」으로 옮기는 두 단계로 우회하십시오.
  • 「허용 종류 위반이 뜨는데 어떻게 없애나」 → 이 화면에서는 없앨 수 없습니다. 위반은 이미 분류에 들어와 있는 상품의 종류가 허용 목록과 다르다는 뜻이라, 실제로 상품을 옮기는 것은 「상품 분류 매핑」 화면이나 상품 상세의 몫입니다. 이 화면에서 허용 종류 자체를 넓히거나 좁힐 수는 있습니다.
  • 「마진을 걸었는데 판매가가 그대로다」 → 정상입니다. 「판매가 재산정」에서 미리보기 후 확인해야 실제 판매가에 반영됩니다.
  • 「분류를 지웠는데 되돌리고 싶다」 → 되돌리기 API가 없습니다. 같은 이름 · 같은 자리에 새로 만들고, 마진 · 허용 종류를 사람이 다시 입력해야 합니다.
  • 「이력에 '카테고리 매핑 이동'이라고 뜨는데 여기서 되돌릴 수 없다」 → 이 화면 소관이 아닙니다. 「상품 분류 매핑」 화면(/admin2/category-mapping)에 가면 그 화면 자체의 되돌리기 기능으로 처리할 수 있습니다.
  • 「쓰기 버튼을 눌러도 반응이 없다」 → 조회(viewer) 권한만 있으면 버튼이 눌리지 않고, 호버하면 「권한이 부족합니다(필요: operator, 현재: viewer)」 같은 안내가 뜹니다. 운영자 (operator) 이상 등급이 필요합니다.

확인하지 못한 것 — 이 문서를 만드는 작업에는 브라우저(화면을 눈으로 보는 도구)가 없어, 완성된 HTML 문서 자체가 브라우저에서 실제로 어떻게 보이는지(핀 좌표가 캡처 위에 정확히 맞는지, 인쇄 시 페이지가 어떻게 나뉘는지)는 직접 확인하지 못했습니다. 좌표는 Playwright로 화면 요소의 실제 위치를 재서 계산한 값이고, 스크린샷을 읽어 문구·구조가 서술과 맞는지는 대조했지만, 이 매뉴얼 문서 자체를 브라우저로 열어 번호가 실제 캡처 위 버튼·영역과 정확히 겹치는지는 별도 확인이 필요합니다. 또한 「조회」 등급 계정에서 쓰기 버튼이 실제로 어떻게 비활성으로 보이는지는 코드로는 확인했지만 화면으로 직접 보지는 못했습니다(이 캡처는 owner 등급 점검 계정으로만 찍었습니다).
