### 8-7. 손대지 않은 것

- **products 표** -- 이번 작업은 product_supplier_prices INSERT와 suppliers 1행 UPDATE뿐이다.
  products.supplier 원문 텍스트도 고치지 않았다(몰에서 온 사실 그대로 유지).
- **품절 10,433건** -- 사장님 결정으로 이번에 잇지 않았다.
- **재고있음 1,331건** -- 공급처명이 아니라 매칭 대상 자체가 아니었다.
- **기존 공급처 4곳**(id 1 MSI(웨이코스)·95 점검-공급처-A·104 용산 중앙·216
  화면점검-공급처-임시) -- 이번 매칭 풀 밖이라 연결하지 않았다.
- **locked_fields** -- 이번 작업은 products 표를 전혀 쓰지 않으므로 잠금 필드 자체가 해당
  없다(product_supplier_prices에는 locked_fields 개념이 없다).

### 8-8. 방법론

1. 로컬 서버(포트 8000, 사장님 서버)는 건드리지 않고 SQL을 직접 실행했다 -- 대량 INSERT라
   API 왕복보다 SQL 직접이 적합했다(지시서 지정).
2. 실행 전 되돌리는 명령을 먼저 작성했다(8-6, 이번 장 작성 이전에 스크래치패드에 기록).
3. 드라이런: 매칭 규칙(8-3)을 그대로 구현해 대상 6,555건을 산출하고, 사장님이 준 8종

4. 적용 직전 드라이런을 다시 한 번 재실행(같은 로직, 시점만 다름)해 6,555건으로 동일함을
   재확인한 뒤 삽입했다 -- 드라이런과 적용 사이 데이터가 바뀌었을 가능성을 배제하기 위해서다.
5. `statement_timeout` 15초(`api/db.py`) 제약을 감안해 500건씩 14개 배치로 나눠 삽입했고,
   배치마다 커밋하고 실제 삽입 건수를 세었다(ON CONFLICT DO NOTHING의 RETURNING으로 정확히
   셌다 -- 예측치가 아니라 실측치다).
6. suppliers id=495는 상태가 현재 '활성'인 경우에만 '중지'로 바꾸도록 조건을 걸어 실행했다.

   신규 공급처별 연결 여부, 음수 매입가 재확인을 실행했다(8-4·8-5).

같은 종류다.

**막은 지점(단일 원천, 두 벌 두지 않음)**: `api/mall_supplier_parse.py`의
`resolve_supplier()` -- CLI(`tools/mall_supplier_fetch.py --from-dir`)와 HTTP
(`api/admin_mall_supplier.py POST /api/admin/mall-supplier/ingest`) 둘 다 이 함수
하나를 거친다. 매칭을 시도하기 **전에** 걸러 별도 판정(`match_kind =
"excluded_stock_status"`)을 반환하고, 두 호출부 모두 이걸 "미매칭"(unmatched)이 아니라
"제외"로 따로 센다.

**어휘는 하드코딩 한 단어로 끝내지 않았다** -- `STOCK_STATUS_TOKENS`는 이 페이지가
이미 쓰는 재고상태 어휘(`STATE_MAP`의 판매중/품절/단종)에 그 대칭꼴(재고있음/재고없음)을
더한 것으로 한정했다. 판정은 **정확히 일치**만 본다(문자열 맨 앞이 토큰과 같고 그
다음이 공백 또는 문자열 끝인 경우만) -- "재고나라" 같은 진짜 상호가 있을 수 있다는
지시서 경고 때문에 부분/포함 일치는 쓰지 않았다. `tools/mall_supplier_fetch.py
--selftest`에 이 경계를 지키는 사례를 넣었다: "재고나라"·"재고있음상사"(토큰 뒤에
공백/끝이 아닌 문자)는 제외되지 않고 "재고있음"·"재고있음 {계정}"·판매중/품절/단종
단독 표기만 제외된다.

### 9-5. 드라이런 대 실측 (캐시 100건, `--from-dir .cache/mall_supplier`)

| 항목 | 수정 전(원본) | 필터만 적용 (등록 전) | 필터 + 신규 5곳 등록 후 |
|---|---:|---:|---:|
| 공급처 매칭 실패(unmatched) | 26건 · 6종 | **14건 · 5종** | **0건 · 0종** |
| 공급처가 아닌 값이라 제외 | (구분 없음, unmatched에 섞여 있었음) | **12건** | 12건(불변 -- 매칭과 무관) |
| 공급처 매칭 성공(고유 업체) | 56곳 | 56곳 | **61곳**(신규 5곳 반영) |

세 값 전부 실측(중복 없는 실제 카운트)이고, "필터만 적용" 열은 신규 5곳을 등록하기
**전**에(등록 순서를 바꿔) 따로 한 번 더 돌려 필터 자체의 효과만 분리해 확인한
것이다(26 - 12 = 14, 지시서가 요구한 대조).

`api/admin_mall_supplier.py`(HTTP 경로)도 별도로 확인했다 -- 포트 8000(사장님 서버)은
건드리지 않고, 빈 포트(8104)에 임시 서버를 띄워 `POST /api/admin/mall-supplier/ingest`를
`dryrun:true`로 상품 97820(공급처 3행 -- "재고있음" 1 + 신규 등록 2곳)에 대해 호출했다.
응답 `excluded_non_supplier=1`(정확히 "재고있음" 1건) · `unmatched_suppliers=[]`(나머지
둘은 이번에 등록한 (주)와이즈컴퍼니·(주)제이케이씨앤피와 매칭됨) -- 확인 후 임시 서버는
종료했다(사장님 서버 8000·8110은 시작·종료 모두 손대지 않았다).

### 9-6. 되돌리는 명령

오늘 DB에 쓴 것은 신규 supplier 5행뿐이다(product_supplier_prices는 이번에 --apply를
쓰지 않아 전혀 쓰지 않았다 -- 드라이런만 실행). 삭제 금지 규약대로 상태 전이로
되돌린다:

    UPDATE suppliers SET status = '중지' WHERE supplier_id IN (517, 518, 519, 520, 521);

되돌림 확인:

    SELECT supplier_id, name, status FROM suppliers WHERE supplier_id IN (517, 518, 519, 520, 521);
    -- 5행 전부 status='중지'여야 완료

코드 변경(`api/mall_supplier_parse.py`·`tools/mall_supplier_fetch.py`·
`api/admin_mall_supplier.py`)은 아직 커밋 전이라 `git diff`/`git restore --staged`
범위다 -- 커밋하지 않았으므로 별도 되돌리기 명령이 필요 없다(작업 지시 범위 밖).

### 9-7. 손대지 않은 것

- **기존 122곳** -- 등록 전후 스냅샷(전 컬럼)이 완전히 같다. UPDATE 0건(9-3의 id=400
  포함, 전수 재확인).
- **products·product_supplier_prices** -- 이번 작업은 `suppliers` 등록과 파서 수정까지다.
  `--apply`를 한 번도 실행하지 않았다(지시서 금지 사항).
- **id=2·id=495(클릭나라)** -- 이번 작업과 무관, 손대지 않음.
- **`재고있음` 1,331건(products.supplier)** -- §8-2·8-7에서 이미 손대지 않기로 한
  범위이고, 이번 작업도 그 결정을 바꾸지 않는다(공급처 화면 수집 경로의 같은 오염을
  추가로 걸렀을 뿐, `products` 표는 이번에도 쓰지 않았다).
- **locked_fields** -- 이번 작업은 `products`를 전혀 쓰지 않으므로 해당 없음(2026-08-25와
  같은 사유, §8-7).
- 커밋 -- 지시에 따라 실행하지 않았다.

### 9-8. 방법론

1. 드라이런: 신규 5곳 이름을 `lower(btrim(name))` 기준으로 기존 122곳과 대조(완전일치·
   상호간 충돌 모두 0건), 길이 제한(100자) 확인.
2. 등록 전 스냅샷(122행 전 컬럼)을 먼저 떠 두고(되돌리기·회귀 대조용), 되돌리는 명령을
   먼저 적었다(9-6).
3. 로컬 서버(포트 8000, 사장님 서버 -- 종료하지 않았다)에 owner로 로그인해
   `POST /api/admin/suppliers`를 5회 호출(성공 5, 실패 0).
4. 등록 후 스냅샷(127행)을 다시 떠 122행 전 컬럼이 등록 전과 완전히 같은지 diff로
   재확인했고, `admin_operator_activity_logs`에 `supplier_create` 5건이 남은 것도
   확인했다.
5. "재고있음" 필터는 `api/mall_supplier_parse.py`(단일 원천 -- CLI·HTTP 둘 다 이 모듈을
   import)에 구현하고, 실물 캐시(97820.html)에서 뽑은 행으로 `--selftest`에 회귀
   케이스를 추가했다(계정 식별자만 자리표시자로 치환 -- 회사명 "재고있음"·상품번호는
   실제 값 그대로, 2026-08-26(1차) 픽스처 관례와 동일).
6. `--from-dir .cache/mall_supplier`(캐시 100건, 몰에 새 요청 0건)로 필터 단독 효과
   (26->14)와 필터+등록 합산 효과(26->0)를 각각 실측했다(9-5).
7. HTTP 경로(`api/admin_mall_supplier.py`)는 포트 8000이 이 신설 파일을 아직 로드하지
   않은 상태(--reload 없이 기동돼 있음, 신설 시점이 기동 이후)라 별도로 확인할 방법이
   필요했다 -- 빈 포트(8104)에 임시 서버를 띄워 확인 후 즉시 종료했다(8000·8110은
   시작도 종료도 하지 않았다).
8. 회귀 960건 실행(`tests/regression.py --quiet`) -- 전 항목 통과. 회귀 실행 전후로
   suppliers 스냅샷을 다시 대조해 회귀가 suppliers 표를 건드리지 않음을 확인했다.
