# 판매조건 고객 전달 계약과 자료 요청

## 현재 구현과 연결 범위

판매조건 등록/설명 충돌검사/추천 재검토는 기존 구현을 사용한다. 관리자 상세 GET /api/admin/pc-configurations/{id}은 내부 검토자료를 포함하므로 고객단에서 직접 사용하면 안 된다. 현재 pc_configuration_copy 상세는 customer_publishable=False이고 configuration_consultation은 관리자 상담 API다. 일반 recommend는 products 기반 추천이며 저장된 PC 구성 판매조건을 연결한 고객 공개 API로 취급하지 않는다.

고객단 담당이 사용할 안전한 변환 함수 api.pc_sales_conditions.customer_conditions(config,parts,offers)를 추가했다. 신규 공개 라우트나 고객 UI는 만들지 않았고 기존 권한·셸·DB·API 응답을 변경하지 않았다. 고객단 라우트 연결은 통합 담당과 고객단 담당의 계약 확정 후 이루어져야 한다. 아래 계약이 실제 고객 응답에 이미 붙었다고 보고하지 않는다.

## 전달 필드

반환 키는 os/keyboard/mouse/monitor/warranty 5개다. 각 항목은 state, detail, months, needs_reconfirmation, customer_statement만 포함한다. 포함 여부는 unknown/included/excluded, 보증은 unknown/verified. unknown 상세는 빈 문자열, months는 verified 보증에서만 전달한다. 미확인 입력초안과 이전 조건도 고객에게 전송하지 않는다.

근거에 연결된 구성·부품·판매제안이 바뀌면 unknown 및 needs_reconfirmation=true. 이때 이전 포함/미포함/보증기간을 고객 문구로 재사용하지 않는다. source/evidence/확인일/operator_id/confirmed_at/scope_basis/previous는 관리자용이며 공개 반환에 넣지 않는다. 검증된 detail은 고객 조건 상세로 표시하되 HTML로 해석하지 말고 텍스트로 출력한다. 보증기간만 보이고 상세 범위를 누락하지 않는다.

이 계약은 상품 공개·재고·최종가격·추천 가능 여부의 승인값을 포함하지 않는다. 추천승인은 기존 review_allows/검토 basis를 사용한다. 판매조건 저장으로 검토 basis가 달라지므로 이전 승인은 그대로 재사용하지 않는다. 고객단에 전체 content, 관리자 상세 또는 AI 입력 전체를 넘기는 방식으로 이 계약을 우회하지 않는다.

## 출처가 필요한 항목

대표 N04/N07/AC11F5AEA43924DBA의 실제 판매조건은 아직 미등록이다. 제품/견적 버전별 OS 라이선스·설치 포함 여부, 키보드/마우스/모니터 제공 모델과 범위, 보증 판매자/제조사·기간·부품/작업 범위를 증명하는 판매 구성표·견적서·확정 정책이 필요하다. 확인 내용, 출처 문서명 또는 링크, 확인일을 함께 제공해야 한다. 포함과 보증은 조건 상세, 보증은 개월 수가 추가 필요하다. 부품 BOM/기존 상품설명/AI 제안만으로 확정 등록하지 않는다.

## 검사와 통합 요청

관련 fixture 55개 통과: 유효조건·파생/구성/가격변경 재확인·설명충돌/기간확대 차단·개정 충돌·확인자 서버지정·권한·교차사이트·보관제품·추천승인 basis 무효화. 추가 고객계약 fixture는 내부자료/이전 주장/unknown 초안 비노출, 확인된 보증범위·기간 보존 및 추천/공개 승인과 분리를 확인한다. 네트워크 AI나 운영 저장은 없다.

통합 담당 요청: 고객단 담당에게 이 계약을 전달하고 실제 고객 endpoint 소유자를 지정한다. 고객 공개 허용 정책과 최신 근거 조회는 해당 라우트에서 별도로 검사해야 한다. 전용 변경파일은 api/pc_sales_conditions.py, tests/test_pc_sales_conditions.py, 이 문서뿐이다. 공통 DB/셸/인증/타담당 UI 변경 없음. 운영 배포는 다른 병렬 커밋과 통합 담당이 조율한다.
