# 카테고리 등록·관리 + 상품 매핑 — 구현방안

> 작성 2026-08-04 · 근거: `docs/research/legacy-admin-2026-08-04.md`(기존 임대 관리자 실사)
> 상태: **승인 대기.** 이 문서는 방안이고, 확정 결정은 `decision-log.md`가 원천이다.

---

## 0. 이 방안이 지키려는 것 한 줄

**기존 시스템이 망가진 이유는 카테고리 하나가 다섯 가지 일을 했기 때문이다.
그래서 우리는 축을 가르고, 엔진이 읽는 축은 운영자가 못 건드리게 한다.**

---

## 1. 지금 우리 상태 (2026-08-04 실측)

| 축 | 정체 | 값 | 누가 읽나 |
|---|---|---|---|
| `products.part_type` | 부품 종류 | **17종** | **엔진**(recommend·candidates·swap·게이트) + 25개 모듈 |
| `slot` | 견적서의 자리 | **8종** | 엔진. `part_type`에서 파생(`COOLER_CPU_*` → `COOLER`) |
| `products.category_group` | 거친 묶음 | **3종**(core_part 12,982 · etc 5,474 · peripheral 4,382) | 거의 안 씀 |
| 판매 카테고리 | — | **없음** | — |

**즉 우리에겐 판매용 카테고리가 아예 없다.** 사용자가 요청한 것은 이 빈 축을 새로 만드는 일이다.

### 1.1 그런데 바닥이 고르지 않다 — 먼저 고쳐야 할 것

**`SLOT_KO`가 네 파일에 각각 정의돼 있고, 이미 어긋났다:**

| | admin_setup | admin_swap_logs | candidates | swap |
|---|---|---|---|---|
| `SSD` | SSD | SSD | SSD | **저장장치** ←다름 |

부품 교체 안내에서만 "저장장치"라고 나간다. 나머지 화면은 "SSD"다.
`CORE_TYPES`(admin_pool) / `CORE_PARTS`(admin_products)도 같은 10종을 두 벌 갖고 있다(현재는 일치).
라벨 맵은 `PART_TYPE_LABELS`(17) · `PART_KO`(16) · `SLOT_KO`(8) 세 어휘가 여섯 곳에 흩어져 있다.

> **이것이 기존 시스템의 `베스트7주력부품`과 같은 병이다** — 분류 정의를 여러 벌 두면 어긋난다.
> 카테고리 테이블을 이 위에 얹으면 **여섯 번째 복제본**이 된다. 그래서 바닥부터 고른다.

### 1.2 ETC 5,148건 — 이미 자라고 있는 쓰레기통

재고>0인 ETC 2,415건 안에 이런 것들이 섞여 있다:
```
케이블 473 · USB 144 · 쿨링부자재 141 · 네트워크 67 · 음향 52 · USB허브 45 · 장패드 28 …
그리고 미식별 1,413건 = 마우스패드 · 캡처보드 · 확장카드(시리얼/컨트롤러) · 시스템팬 ·
                        키스킨 · 하드랙 · 그래픽카드 지지대 · ARGB허브 …
                        그리고 "한경희 미니 건조기"(PC와 무관)
```
기존 시스템의 `기타주변기기`가 우리 안에서도 자라고 있다. **카테고리는 이걸 갈라내는 도구여야 한다.**

## 2. 설계 원칙 — 축을 가른다

기존 시스템의 대분류 20개가 섞고 있던 다섯 축을, 우리는 **다섯 개의 서로 다른 것**으로 둔다.

| 축 | 우리 구현 | 편집 권한 | 엔진이 읽나 |
|---|---|---|---|
| ① 부품 종류 | `part_type` (닫힌 집합 17종) | **코드만** — 늘리려면 슬라이스 | **읽는다** |
| ② 판매 탐색 | **`categories` (새 트리)** | **운영자 자유** | **안 읽는다** |
| ③ 완제품 유형 | 이후 `build_type` | 운영자 | 별건 |
| ④ 마케팅 노출 | `tag_*` (선례: `tag_silent`/`tag_white`) | 운영자 | 태그별 |
| ⑤ 생명주기·상태 | `sale_status` · `stock_qty` 등 기존 컬럼 | 시스템 | 읽는다 |

### 가장 중요한 계약

> **`categories`는 엔진이 읽지 않는다.**
> 운영자가 카테고리를 고쳐도 **견적 결과가 변하면 안 된다**(A-02 재현성).
> 이것을 회귀 불변식으로 못 박는다. 지키지 않으면 "카테고리를 옮겼더니 견적이 달라졌다"가 생긴다.

### 기존 시스템에서 배운 금지 사항

1. **고정 깊이 금지** — 저쪽 4단 고정이 미매핑 1,458건을 만들었다. 우리는 `parent_id` 자기참조로 **가변 깊이**.
2. **트리는 한 벌만** — `베스트7주력부품` 같은 복제 트리를 만들 수 없게 한다.
3. **카테고리에 업무 상태를 넣지 않는다** — `내부관리용`·`삭제대기`·`상품평 21~50개` 같은 것.
4. **필드 풀 격리 유지** — `spec_field_defs.part_types`가 이미 배열로 격리돼 있다(저쪽 메인보드 324필드 참사가 우리에겐 없다). 유지한다.

## 3. 슬라이스 계획

### 슬라이스 A (선행) — 어휘를 하나로 모은다

**왜 먼저:** 카테고리를 얹기 전에 바닥을 고르지 않으면 복제본이 하나 더 는다. 그리고 이미 어긋나 있다.

- 새 모듈 `api/taxonomy.py` = **부품 어휘의 단일 원천**
  - `PART_TYPES`(17) · `PART_LABELS` · `SLOTS`(8) · `SLOT_LABELS` · `CORE_TYPES`(10) · `slot_of(part_type)`
- 흩어진 정의 제거: `SLOT_KO`×4 · `CORE_TYPES`/`CORE_PARTS`×2 · `PART_TYPE_LABELS`/`PART_KO`
- **`swap.py`의 `SSD`→"저장장치" 드리프트 수정**(→ "SSD"로 통일)
- 회귀 추가:
  - `part_type` 상수 집합 **= DB 실측 distinct**
  - 라벨 맵은 `taxonomy.py` 밖에서 정의되지 않는다(소스 스캔)
  - `slot_of()` 결과 = 기존 `QUOTE_SLOTS` 매핑과 동일

**검증:** 회귀 전량 통과 + 일부러 라벨을 어긋나게 해 실패하는 것을 확인.

---

### 슬라이스 B — `categories` 테이블 + 카테고리 관리 화면

**테이블**
```sql
categories(
  category_id      serial PK,
  parent_id        int NULL REFERENCES categories,   -- 가변 깊이
  name             varchar NOT NULL,
  sort_order       int NOT NULL DEFAULT 0,
  is_visible       bool NOT NULL DEFAULT true,
  allowed_part_types jsonb NULL,   -- NULL=제한없음. 매핑 오류를 잡는 안전장치
  created_at, updated_at
)
UNIQUE (parent_id, name)           -- 같은 부모 밑 같은 이름 금지
```

- `depth`는 **저장하지 않고 파생**한다(고정 깊이를 만들지 않기 위해).
- `allowed_part_types`: 예) "그래픽카드" 카테고리에 `["GPU"]`. 위반 매핑을 화면이 경고한다.
  기존 시스템에 없던 안전장치 — 저쪽은 이게 없어서 아무거나 들어갔다.

**불변식(회귀)**
- 순환 참조 없음(자기 조상이 될 수 없다)
- `parent_id`가 가리키는 행이 반드시 존재
- 상품이 매핑된 카테고리는 삭제 불가(먼저 옮겨야 함)

**화면 `ADM-CAT-010 카테고리 관리`**
- 트리 표시 · 추가 · 이름 변경 · **드래그 없이** 부모 지정으로 이동 · 노출 토글 · 삭제
- 각 노드에 **매핑 상품 수**를 같이 보여준다(빈 카테고리가 눈에 띄게)

---

### 슬라이스 C — 상품 → 카테고리 매핑

**컬럼:** `products.category_id int NULL REFERENCES categories`

**단일 카테고리로 간다**(다중 아님). 이유: 저쪽이 같은 CPU를 두 트리에 넣어 담당자 기분에 좌우됐다.
"여러 곳에 노출"이 필요하면 그건 카테고리가 아니라 **태그(④축)**의 일이다.

**화면 `ADM-CAT-020 상품 카테고리 매핑`**
- 좌: 카테고리 트리 / 우: 상품 목록(part_type·재고·판매상태 필터)
- **미매핑 상품을 기본 화면으로** 띄운다 — 저쪽 `카테고리매핑오류`의 좋은 점을 앞당긴 것
- 일괄 선택 → 카테고리 이동 (드라이런 없이 즉시, 단 **되돌리기 로그 남김**)
- `allowed_part_types` 위반 시 **경고 + 사유 표시**(막지는 않되 근거를 말한다)

**되돌리기:** 매핑 변경은 `_log`로 남긴다(원장 규약 승계). 대량 이동은 한 건의 배치로 묶어 되돌릴 수 있게.

---

### 슬라이스 D — 정합을 화면과 회귀가 지킨다

- 관리자 대시보드에 **"미매핑 판매중 상품 N건"** 표시 (저쪽은 1,458건을 방치했다)
- 회귀 불변식 추가:
  - **`categories`를 `recommend`·`candidates`·`swap`이 읽지 않는다**(소스 스캔) ← 가장 중요
  - 카테고리 트리에 순환 없음
  - `allowed_part_types` 위반 매핑 수를 세어 보고
  - 카테고리 변경 전후로 **같은 입력 → 같은 견적**(A-02 재현성 실측)

---

### 별건 — 카드수수료 2.585% (사용자 확정 2026-08-04)

`pricing_settings.card_fee_rate` 0.022 → **0.02585**. 기존 시스템 운영값에 맞춘다.
- 영향: 판매가 산정 공식 `매입가 × (1 + 카드수수료 + 마진)`의 결과가 전 상품에서 움직인다.
- **세워 둔 "판매가 재산정"과 함께 처리해야 한다** — 수수료만 바꾸고 재산정을 안 하면
  설정과 실제 판매가가 어긋난 채로 남는다.
- 기존 값 0.022는 이력으로 남긴다(`pricing_settings`는 이미 append 방식).

## 4. 슬라이스 순서와 이유

```
A (어휘 단일화)  →  B (카테고리 트리)  →  C (상품 매핑)  →  D (정합 회귀)
                                                              별건: 수수료 2.585% + 판매가 재산정
```

A를 건너뛰면 카테고리가 일곱 번째 복제본 위에 앉는다.
D를 건너뛰면 저쪽처럼 1,458건이 조용히 쌓인다.

   (c) 기존 시스템 트리를 가져와 정리
   → **(b)를 제안한다.** 22,838건을 즉시 매핑할 수 있고, ETC만 손으로 갈라내면 된다.

   관리자 전용으로 먼저 두고 고객 노출은 나중에 정해도 된다.
