## 0. 무엇이 문제였는가 — 실측

```
usage_floors 용도 9종   ai · design · game · game_casual · gaming_high
                       office · trading · video · video_3d

software 카테고리 9종   3D·설계 7 · 영상편집 6 · 개발 6 · 사무보조 5 · 사진·디자인 5

**개발(6) · 음악(4) · 방송·스트리밍(2) = 12종, 전체 42종의 28% 가 갈 곳이 없었다.**

```

UF.match("프로그래밍하려고요")   -> None        하한 0건
UF.match("방송 송출")          -> None        하한 0건
UF.match("작곡")              -> None        하한 0건
UF.match("영웅문")            -> None        하한 0건   ← software 의 행 이름인데
UF.match("사무실에서 주식")      -> office      RAM 8GB   ← trading(16GB) 이 아니다

## 1. 신설 3종 — 값과 근거

`software.rec_ram_gb` · `rec_storage_gb` · `rec_gpu` 와
`software_community_spec.ram_gb` 를 실조회해서 정했다. **한 값도 지어내지 않았다.**

### 1-1. `dev` 「개발」 — RAM 16GB · SSD 500GB · GPU 없음

| 프로그램 | 공식 `rec_ram_gb` | 커뮤니티 `ram_gb` | `rec_gpu` | `bottleneck` |
|---|---:|---:|---|---|
| 비주얼 스튜디오 코드 | — | **16** | NULL | ram |
| 비주얼 스튜디오 | **16** | 32 | NULL | ram |
| 안드로이드 스튜디오 | — | 32 | NULL | ram |
| 인텔리제이 IDEA | — | 32 | NULL | ram |
| 도커 데스크톱 | — | 32 | NULL | ram |
| WSL2 | — | — | NULL | ram |

- **RAM 16** = 카테고리에서 가장 낮은 커뮤니티 값(VS Code 16) + 비주얼 스튜디오
  공식 권장 16. 「모두가 공통으로 필요한 선」이 하한이다.
- **32GB 는 하한이 아니라 겨냥**으로 보낸다(§4 기준 · `usage_tier_rules` dev 행).
- **SSD 500** = 비주얼 스튜디오 공식 설치 `rec_storage_gb=50` + 소스·컨테이너 이미지.
  0016 이 쓰던 개발 하한 500GB 를 그대로 유지한다.
- **GPU 하한 없음** — 6종 전부 `rec_gpu` 가 NULL(불요). 사장님 확정 「환경축」이 이것이다.

### 1-2. `stream` 「방송 송출」 — RAM 16GB · SSD 500GB · GPU 없음

| 프로그램 | 공식 `rec_ram_gb` | 커뮤니티 `ram_gb` | `rec_storage_gb` | `rec_gpu` |
|---|---:|---:|---:|---|
| 스트림랩스 데스크톱 | **16** | 16 | **512** | NULL |
| OBS 스튜디오 | — | 16 | — | NULL |

- **RAM 16** — 둘 다 16 으로 일치. ⚠ 0016 의 옛 값은 32GB 였는데 **근거가 없었다.**
  실측에 맞춰 내린다.
- **SSD 500** = 스트림랩스 공식 512(재고에 512GB 30종 — 하한 500 이면 통과).
- **GPU 하한 없음** — 둘 다 NULL. OBS 커뮤니티가 「NVENC 권장」을 말하지만 그건
  **인코더 선택**이지 성능 하한이 아니고, 우리 표에 그걸 표현할 필드가 없다
  (0057 의 「걸 수 있는 것만 건다」 규약).

### 1-3. `music` 「음악 작업」 — RAM 16GB · SSD 500GB · GPU 없음

| 프로그램 | 공식 `rec_ram_gb` | 커뮤니티 `ram_gb` | `rec_storage_gb` | `bottleneck` |
|---|---:|---:|---:|---|
| 에이블톤 라이브 | **16** | 16 | **500** | cpu |
| FL 스튜디오 | 8 | 16 | — | cpu |
| 큐베이스 | — | 32 | — | cpu |
| 로직 프로 | — | — | — | — (플랫폼 불일치) |

- **RAM 16** = 에이블톤 공식 권장 16 + 커뮤니티 「16GB 가 편안한 제작 최소선」.
- **32GB(큐베이스 · 에이블톤 "무거운 라이브러리")는 겨냥**으로 보낸다.
- **SSD 500** = 에이블톤 공식 `rec_storage_gb=500`(샘플 라이브러리).
- **GPU 하한 없음** — `rec_gpu` 가 에이블톤만 "영상 작업 시에만 외장 GPU". 조건부
  문구라 하한이 아니다.

## 2. `office` 하한 수정 — RAM 8GB → **16GB**

> ## ⚠ 이 절은 **0102 로 개정되었다** — 아래 §2-개정을 먼저 읽어라.
> 0101 이 한 「8 → 16 일괄 상향」은 **틀렸다.** 근거로 든 16GB 네 건 중 셋이
> 조사자의 «해석»이었고(각 `note` 가 스스로 "해석 · confidence 추정"이라 적는다),
> 넷 모두 근거가 «동시에 쓴다»였지 프로그램이 무거워서가 아니었다.
> 0102 가 `office` 를 **`office_simple`(8GB) · `office_complex`(16GB)** 둘로 갈라
> 둘 다 맞게 한다. 아래 본문은 **그 판단의 이력**으로 남긴다(지우지 않는다 —
> 왜 16 으로 올렸다가 갈랐는지가 다음 사람에게 필요하다).

### 근거 (`software` 사무·문서 3 + 사무보조 5)

| 프로그램 | 공식 `rec_ram_gb` | 커뮤니티 `ram_gb` | 비고 |
|---|---:|---:|---|
| 줌 | **16** | — | "공식 권장이 이미 충분히 보수적" |
| MS 오피스 | — | **16** | "4GB 공식 최소로는 쾌적하지 않다" |
| 마이크로소프트 팀즈 | 8 | **16** | 상시 구동 + 오피스 동시 사용 전제 |
| 웹브라우저 다중 탭 | — | **16** | |
| 한글 (한컴오피스) | — | 8 | "한글 단독으로는 논의 대상이 아니다" |
| 카카오톡 PC · PDF 뷰어 | — | — | 정량치 미확보 |

**4종이 16GB 를 가리키고, 8GB 를 가리키는 것은 「한글」 하나뿐**이며 그것도 단독
사용을 전제하지 않는다는 단서가 붙어 있다.

### 판단이 갈린 자리 — 사장님 실판매는 8GB 다

사장님 실판매 사무 견적은 8GB 를 쓴다. 그건 **다나와 최저가 순위 경쟁용**이다.
우리는 「모든 견적에는 이유가 있습니다」가 정체성이라 **근거 없는 사양 깎기를 하지
않는다.** 16GB 로 올린다. (되돌리려면 0101 downgrade 가 정확히 8 로 복원한다.)

### 영향

SSD 하한 250GB 는 **바꾸지 않았다** — 사무·문서 카테고리에 이를 올릴 근거가 없다.

## 2-개정 (0102). `office` 를 **«단순 사무용» · «복합 사무용»** 둘로 가른다

> 마이그레이션 `0102_office_split_simple_complex.py` · 사장님 확정 2026-09-18
> 0101 은 이미 적용됐으므로 **수정하지 않고** 새 파일로 개정했다.

### 왜 §2 가 틀렸는가 — note 를 다시 읽었다

§2 는 "4종이 16GB 를 가리킨다"고 썼다. 그런데 그 네 건의 `note` 원문은 이렇다
(`software_community_spec` 실조회):

| 프로그램 | 값 | `note` 가 **스스로** 말하는 것 | 성격 |
|---|---:|---|---|
| 줌 (id 39) | `rec_ram_gb` **16** | confidence `확인` | **제조사 공식값** |
| MS 오피스 (id 36) | 커뮤 16 | "…16GB가 현실적 기준이라는 **해석**. 정량 표본은 빈약하므로 confidence 추정" | 해석 |
| 팀즈 (id 40) | 커뮤 16 | "Teams 단독 정량 표본은 **미확보** … 현실적이라는 **해석**. confidence 추정" | 해석 |
| 웹브라우저 (id 42) | 커뮤 16 | "다른 프로그램 상담 중 반복적으로 등장(Lightroom/Photoshop 스레드)" | 간접 인용 |
| 한글 (id 35) | 커뮤 8 | "한글 단독으로는 논의 대상이 아니며 … **동시 구동**이 전제" | 해석 |
| PDF (37) · 카톡 (41) | — | "정량 커뮤니티 권장치 **미확보**(null)" | 없음 |

**공식 최소는 전부 4GB 이하다** — 한글 2 · MS 오피스 4 · 줌 4 · 팀즈 4.
그리고 16GB 를 부르는 근거는 네 건 **모두 「동시에 쓴다」**이지 프로그램이 무거워서가
아니다. note 원문이 그렇게 적는다("브라우저·메신저 동시 구동" · "상시 구동 + 오피스·
브라우저 동시 사용" · "브라우저 다중 탭·엑셀과 동시 구동").

즉 `office` 한 키에 **한글만 쓰는 사람**과 **엑셀+줌+브라우저 30탭을 동시에 켜는
사람**이 섞여 있었다. 8이냐 16이냐 싸운 이유가 그것이다 — **나누면 둘 다 맞는다.**

사장님 지시가 정확히 그 말이었다:
> "대다수 오피스 문서작성 등은 8GB 램이면 충분한데" /
> "단순 작업.. 그리고 좀 더 무거운 작업.. 이런식으로 구분해서" /
> "**단순 사무용, 복합 사무용** 이러면 어떨까?"

### 확정된 표

| usage_key | 라벨 | RAM | SSD | 근거 |
|---|---|---:|---:|---|
| `office_simple` | **단순 사무용** | 8GB | 250GB | 한글 커뮤 8GB · 공식 최소 2~4GB · 순차 작업(문서·PDF·웹) |
| `office_complex` | **복합 사무용** | 16GB | 500GB | **줌 공식 권장 16GB**(이 표에서 유일한 제조사 공식값) · 동시 구동 |

`office_complex` RAM 의 근거는 **줌 공식값 하나로 세운다.** MS오피스·팀즈·브라우저의
16 은 스스로 "해석·추정"이라 적으므로 `detail_fmt` 에 **보조 근거로만** 적었다 —
값을 지어내지 않되, 해석인 것은 해석이라고 표시하고 쓴다.

### 방안 ⓐ/ⓑ/ⓒ — **ⓑ(개명 + 신설)** 를 골랐다

- **ⓐ** `office` 를 남기고 둘을 추가 → 세 키가 되면 「사무용」이 어디로 갈지가 **다시**
  모호해진다. 사장님 구분의 요점은 «둘 중 하나로 갈라라»다. 버린다.
- **ⓒ** `office` 를 지우고 둘 다 신설 → `usage_alloc` 3행이 `usage_key='office'` 를
  들고 있고 **회귀 [52]① 이 `usage_alloc.usage_key ⊆ usage_floors.usage_key` 를
  불변식으로 검사한다.** 지우는 순간 깨진다. `floor_id` 20·21 이력도 끊긴다. 버린다.
- **ⓑ** `office` → `office_simple` **개명**(floor_id 20·21 유지) + `office_complex`
  신설. `usage_alloc` 3행도 개명하고 복합용 3행을 **복제**. 고른 쪽.

RAM 이 8 로 «돌아가는» 것은 0101 이전으로의 복귀가 아니라 **한글 커뮤니티 8GB 라는
실측값의 재확인**이다 — 출처가 다르다.

### 「사무용」처럼 모호한 말은 → **단순 쪽** (사장님 확정)

> "내 아는 사람도 노트북인데, i3 CPU에 8GB 메모리를 쓰는데, 대부분 문서작업과
> 학교 수업자료 준비기 때문에 큰 어려움은 없어보여.. 그런 사람들에게 비용은
> 좀 부담일 수 있어"

**단순 사무용은 «최저가 등급»이 아니라 «맞는 사양»이다.** 실측 차이가 작지 않다 —
단순 41만 vs 복합 45만(가성비형), 추천형은 예산을 그대로 쓴다. 모호할 때 비싼 쪽을
내밀면 얻는 것 없이 돈만 더 받는다. 우리 정체성은 「왜 이 부품인지 설명하는 신뢰
판매자」이고 **필요 없는 걸 권하지 않는 것도 그 약속**이다.

#### 구현 — 목적 둘을 분리했다

`match()` 는 `sort_order` 순 **첫 usage_key 하나만** 쓴다.

```
office_complex   sort 60, 61   (앞)   낱말이 전부 «특정 신호»
office_simple    sort 62, 63   (뒤)   모호한 말은 여기에만
```

- **모호 → 단순**: 「사무」·「사무용」 같은 모호한 말은 `office_simple` **에만** 둔다.
  복합의 낱말에 안 걸리므로 자연히 단순으로 떨어진다.
- **구체적 신호가 이긴다**: 복합을 *앞에* 둬서 "문서작성이랑 화상회의"가
  **복합으로 간다.** 「화상회의」는 동시 구동을 명시한 신호이고 「문서」는 아무 말도
  아니다. 순서를 뒤집으면 이 문장이 단순(8GB)으로 접히는데, 그건 **고객이 말한
  신호를 버리는 것**이라 안 된다.

⚠ `sort_order` 60~63 은 `office` 가 쓰던 60,61 자리를 그대로 쓴다 —
trading(21,22)·dev(23)·stream(25)·music(27) 이 먼저 잡히는 **0101 §3 의 관계를
한 줄도 깨지 않는다**(60~63 은 여전히 27 뒤, video_3d 103 앞).

### 낱말 (match_terms)

```
office_simple   문서작성 한글 워드 문서 인터넷 웹서핑 인강 강의
                가벼운 사무 단순 사무 사무용 사무 수업
office_complex  엑셀 대용량 화상회의 줌 팀즈 다중작업 동시작업
                재택근무 복합 사무 업무용
```

- **「웹」을 뺐다** — 부분일치로 너무 많이 삼켰다(「웹 개발」이 office 로 갔던 0101 §3
  의 원인 중 하나). 「인터넷」·「웹서핑」으로 좁혀 대신한다.
- **「수업」을 더했다** — 사장님이 직접 든 사례 "학교 수업자료 준비"가 실측에서
  **아무 하한도 못 받았다**(`match` → `None`). 그 사람이 바로 단순 사무용의 정의인데
  표에 낱말이 없었다. 다른 usage_key 낱말에 '수업'이 부분문자열로 없음을 확인했다.
- **「업무용」은 복합**(사장님 지시 목록 그대로). 다만 **「업무」가 아니라 「업무용」**
  으로 좁혔다 — 「회사 업무」·「업무 보조」는 단순으로 떨어진다. **판단이 갈린 자리**:
  「업무용」은 「사무용」만큼 모호해서 위 «모호→단순» 원칙과 충돌한다. 지시서 목록을
  따랐다.

### 근거 문구 — «부족해서 싼 게 아니라 맞아서 이 값»

`office_simple` RAM 의 `detail_fmt` 가 이유와 상향 조건을 같이 말한다:

> `8GB — 문서·웹·인강은 한 번에 하나씩 쓰는 순차 작업이라 8GB 로 충분합니다`
> `(한글 공식 최소 2GB · MS오피스 공식 최소 4GB, 커뮤니티 해석 8GB 를 하한으로).`
> `엑셀 대용량 파일과 화상회의를 «동시에» 쓰신다면 복합 사무용을 보세요`

### `usage_alloc` — 값을 **새로 짓지 않았다**

여기서 비율을 지어내면 이 마이그레이션이 고치려는 바로 그 잘못을 반복한다.

3D 렌더링    부제: 블렌더 · 마야 · 3ds 맥스
```

### 왜 나누는가 — `software` 실조회가 병목이 «정반대»라고 말한다

| 프로그램 | `bottleneck` | min/rec RAM | min/rec VRAM | `bottleneck_note` 요지 |
|---|---|---:|---:|---|
| 오토캐드 | **cpu** | 8 / 32 | 2 / 8 | "코어 수가 아니라 **클럭**을 지목" |
| 솔리드웍스 | **cpu** | 16 / 32 | — / — | "형상 재생성이 **순차 연산**" |
| 인벤터 | **cpu** | 16 / 32 | 2 / 8 | "부품 500개↑ 32GB, 초대형 64GB" |
| 스케치업 | vram | — / 8 | — / 8 | "PBR 재질은 VRAM 32GB↑" |
| 블렌더 | **gpu** | 8 / 32 | 2 / 8 | "Cycles 렌더링이 **GPU 연산**" |
| 마야 | balanced | 8 / 16 | — / — | "뷰포트는 GPU, 렌더링(Arnold)은 CPU" |
| 3ds 맥스 | cpu | 4 / 8 | — / — | "공식이 현저히 낮아 그대로 쓰면 안 된다" |

**앞 넷은 CPU/VRAM 병목, 뒤 셋은 GPU/혼합이다.** 그런데 `video_3d` 는 이 일곱을
한 키로 묶고 **GPU 850W · RAM 64GB · SSD 2TB** 를 걸었다. 850W 는 `software`
어디에도 근거가 없고(0090 이 시장 표본 없이 넣었다), 캐드 고객에게 이 하한을 걸면
**그가 쓰지 않는 GPU 때문에 CPU 예산이 깎인다** — 오토캐드 note 원문이 정확히 그
반대를 말한다("GPU는 화면 표시용이라 권장(8GB)을 넘겨 투자할 실익이 작다").

### 방안 ⓐ/ⓑ/ⓒ — **ⓑ(`video_3d` 를 `render_3d` 로 개명 + `cad` 신설)**

0102(office 분할)와 같은 방식·같은 이유다(회귀 [52]① 불변식 · floor_id 이력).
★ **어느 쪽을 개명하는가 — 렌더링 쪽.** 근거 둘:

1. **값이 렌더링 쪽이다.** GPU 850W · RAM 64GB 는 «GPU 를 몰아 쓰는 무거운 쪽»을
   겨눈 값이다. 그 성격을 물려받을 자리는 블렌더(bottleneck=gpu · 커뮤니티 RAM 64 ·
   VRAM 12)가 있는 렌더링이지 CPU 병목 넷이 있는 캐드가 아니다.
2. **라벨의 이력이 렌더링 쪽이다.** `grid_cells.usage` 12행 · `consult_sessions`
   60건 · `grid_quotes.payload` 72건이 문자열 「3D 그래픽」을 들고 있다. 조사
   산출물도 「3D 그래픽」을 **렌더링 쪽 이름의 기각 후보(A2)**로 다뤘다 — 그 말이
   가리키던 사람은 렌더링 고객이다. 그래서 `render_3d` 의 낱말에 **「3D 그래픽」을
   그대로 남겨** 옛 세션·격자 입력을 상속한다.

### ★ CPU 클럭 하한을 쓸 수 있었는가 — **못 쓴다. 쓰지 않았다**

캐드의 핵심 근거는 「코어 수가 아니라 클럭」인데(오토캐드·인벤터·솔리드웍스 3종
note 공통), **재고에 CPU 클럭 값이 없다.** 실조회(2026-09-19):

```
spec_field_defs.clock_mhz   part_types = ['RAM']        ← CPU 가 아니다
product_specs               CPU 683행 중 clock_mhz 0행 (전부 NULL)
                            clock_mhz 가 채워진 것은 RAM 1,697행뿐(1600~21000)
```

`usage_floors.passes()` 는 «값을 모르면 불통과»가 원칙이라, 클럭 하한을 넣으면
**CPU 683종이 전부 탈락해 견적이 0건**이 된다. 근거는 있는데 데이터가 없다 —
**없는 규칙을 지어내지 않는다.**
⇒ 후속 과제: `spec_field_defs.clock_mhz.part_types` 에 `'CPU'` 추가 + 수집.
  그 전까지 캐드의 「고클럭」은 견적에 반영되지 않는다.

**차선으로 한 것**: 클럭을 못 올리는 대신 **GPU 를 묶어 예산이 CPU·RAM 으로
흐르게** 했다 — `usage_tier_rules` 에 `cad GPU vram_gb lte 8`(아래).

### 확정된 표 — 값은 전부 `software`/`software_community_spec` 실조회다

| usage_key | 라벨 | GPU | RAM | SSD | sort_order |
|---|---|---|---|---|---:|
| `cad` | 캐드·설계 | **VRAM ≥8GB** | ≥16GB | ≥500GB | 100·101·102 |
| `render_3d` | 3D 렌더링 | **VRAM ≥12GB** | ≥32GB | ≥500GB | 103·104·105 |

각 값이 어디서 왔는가:

- `cad` **RAM 16** — 솔리드웍스 `min_ram_gb=16` · 인벤터 `min_ram_gb=16`(공식 최소
  둘) + 솔리드웍스 커뮤니티 "조립품 500MB 미만 16GB" + 인벤터 공식 "부품 500개
  미만 16GB". **넷이 같은 선을 말한다.** (오토캐드 min 8 은 더 낮지만 16 을 말하는
  근거가 셋이다. 커뮤니티 aggregate 는 넷 다 32 이고 그건 겨냥으로 보냈다)
- `cad` **VRAM 8** — 오토캐드 커뮤니티 `vram_gb=8` · 인벤터 커뮤니티 `vram_gb=8` ·
  스케치업/오토캐드/인벤터 공식 `rec_vram_gb=8`. 카테고리 최저이자 유일한
  커뮤니티 VRAM 값이 8 이다. **옛 850W(전원) 는 버렸다 — `software` 에 근거 없음.**
- `cad` **SSD 500** — 인벤터 `min_storage_gb=40`(4종 중 최대) + 도면·조립품 보관.
  옛 2000GB 는 근거 없음(캐드 파일은 영상 소스와 성격이 다르다).
- `render_3d` **RAM 32** — 마야 커뮤니티 `ram_gb=32`(렌더 3종 중 **최저** 커뮤니티값;
  블렌더 64 · 3ds맥스 null) + 블렌더 공식 `rec_ram_gb=32`. 64 는 겨냥으로.
- `render_3d` **VRAM 12** — 블렌더 커뮤니티 `vram_gb=12`(렌더 3종 중 **유일한**
  커뮤니티 VRAM 값이라 최저이자 최고). 공식 8 보다 높은 쪽을 쓰는 이유는 note
  원문이 "부족하면 시스템 메모리로 넘어가 성능이 크게 떨어진다"고 적기 때문 —
  렌더링의 VRAM 부족은 느려짐이 아니라 작업 실패에 가깝다(AI 의 하드 제약과 같은 성격).
- `render_3d` **SSD 500** — 마야 7 · 3ds맥스 9 로 프로그램 자체는 작다. 500 은
  렌더 출력·텍스처 보관 기준이자 재고가 넓은 선. 옛 2000GB 근거는 찾지 못했다.

### 낱말 — `ambiguity_rules` 를 그대로 구현했다

조사 산출물이 `shared_words = ["모델링", "3d", "디자인"]` 을 **단독으로 분기하면
안 되는 말**로 지목했다. 0102 와 **같은 장치**로 푼다:

- `cad` 의 낱말은 전부 «특정 신호»다(프로그램명·도면·설계·건축). 모호어가 없다.
- 모호어(「3D」·「3D 작업」·「모델링」)는 **`render_3d` 만** 갖는다.
- **`cad` 가 sort_order 에서 앞선다**(100~102 < 103~105).

따라서 「3D 캐드」·「3D 모델링 인벤터」처럼 **둘 다 걸리는 문장은 `cad` 가 이긴다** —
프로그램명이라는 구체적 신호가 「3D」라는 빈 말을 이겨야 한다. 모호어만 있으면
`render_3d` 로 떨어진다(조사 결론: 「3D 작업」이 입말 7회로 3D 계열 최다
자기호명어이고, 캐드 고객은 자기를 「캐드」라고 부른다).

⚠ **`match()` 는 대소문자를 구분한다**(`t in value`). 옛 시드가 `'CAD'`·`'Maya'`·
`'Blender'` 만 넣어 둔 탓에 **실제 고객 말이 하나도 안 걸렸다** — 수정 전 실측:

```
UF.match("캐드 돌리려고요")  -> None      UF.match("오토캐드 쓰는데") -> None
UF.match("블렌더 배우려고요") -> None      UF.match("렌더링")         -> None
... 20개 중 19개가 None (유일한 히트는 라벨 원문 "3D 그래픽")
```

이것이 이번 분할이 고치는 **두 번째 결함**이다. 그래서 양쪽 표기를 다 넣었다.

### `design` 보강 — 「그래픽 작업(포샵, 일러)」이 3D 로 새지 않게

조사자가 지적한 실측 위험이다("그래픽작업"은 국내 입말에서 2D 를 뜻한다). 실조회하니
`design` 낱말이 **`["디자인"]` 하나뿐**이라 이 문장은 아무 데도 안 걸렸다(match →
None). 2D 프로그램명을 넣어 `design` 이 받는다:
`["디자인","포토샵","포샵","일러스트","일러","인디자인","라이트룸","피그마"]`
⚠ 「그래픽」이라는 말 자체는 **넣지 않았다** — 넣으면 `render_3d` 가 물려받은 옛 라벨
「3D 그래픽」이 `design`(sort 15)에 먼저 걸려 격자가 끊긴다.
⚠ 알려진 변화: 옛 `video_3d` 시드 낱말 「건축 디자인」은 이제 `design` 이 먼저 잡는다
(「디자인」 부분일치). 「건축」·「건축 설계」는 `cad` 로 정상 이동한다.
`ambiguity_rules` 의 "「디자인」 단독 → 2D" 와 방향이 같아 그대로 둔다.

```

## 3. 주식 HTS 를 `office` 에서 `trading` 으로

`software` 의 「주식 HTS (영웅문 등)」는 **사무보조** 카테고리에 있고 커뮤니티
`ram_gb = 32` 다. 그런데 실측상 「사무실에서 주식」이 `office`(RAM 8GB)로 접혔다 —
'사무'(sort 19)가 '주식'(21)보다 앞이기 때문이다.

### 고친 방법 — **`office` 를 뒤로 민다**(19,20 → 60,61)

`trading` 을 앞으로 당기는 선택지도 있었지만 19 앞의 빈 번호가 8·17·18 셋뿐이라
신설 3종까지 넣을 자리가 없다. `office` 를 미는 쪽이 더 옳기도 하다:

- `office` 의 낱말(`사무`·`인강`·`문서`·`웹`·`화상회의`)이 **표에서 가장 넓다.**
  넓은 낱말이 맨 뒤에 서는 것이 `match()` 의 「좁은 것 먼저」 원칙과 맞다.
- 60 은 기존 최대(trading 22)보다 크고 `video_3d`(103)보다 작아 **기존 키들 사이의
  상대 순서를 한 줄도 바꾸지 않는다.**

### 낱말 보강

`trading` 에 **`영웅문` · `키움`** 을 더했다(기존 낱말은 한 개도 빼지 않았다).
⚠ 「차트」 단독은 넣지 않았다 — 「차트 디자인」 같은 무관한 문장을 끌어온다.

### 값

`trading` 하한 RAM 16 은 **그대로 둔다.** 같은 커뮤니티 표본이 두 가지를 말한다:

> "창을 수십 개 띄우는 전업 트레이더 기준 32GB 이상" ↔ "HTS + MTS + 엑셀 병행은 16GB면 쾌적"

전업이 아닌 사람에게 32GB 를 강제할 근거가 없다. **하한 16 · 겨냥 32** 로 가른다
(§4 기준 그대로).

## 4. ★ 표의 역할 구분 기준 — 이제 표가 셋이다

> 다음 사람이 둘(셋)을 섞지 않도록 **판정 질문을 순서대로** 적는다.

| 표 | 축 | 성격 | 못 맞추면 |
|---|---|---|---|
| `usage_floors` | 용도 | **고정 하한** | **조합을 포기한다** |
| `usage_tier_rules` | 용도 × 예산 | 겨냥 | 규칙을 풀고 짓는다 |
| `part_cond_rules` ★신설 | **이미 고른 다른 부품** | 조건부 겨냥 | 규칙을 풀고 짓는다 |

### 판정 질문 (위에서부터 묻는다)

1. **다른 슬롯의 선택에 달렸는가?** → `part_cond_rules`
   예산이 아니라 «무엇을 골랐는가»가 조건이다. (VRAM 8GB → RAM 32GB)
2. **예산이 오르면 값도 오르는가?** → `usage_tier_rules`
   같은 용도인데 값이 여럿이다. (AI 150만 32GB · 400만 64GB)
3. **예산과 무관하게 이 밑으로는 그 용도를 «못 하는가»?** → `usage_floors`
   돈이 없어도 내릴 수 없는 선. (개발 RAM 16GB — 8GB 로는 IDE 가 스왑한다)

### 값을 고르는 기준도 다르다

```
하한(usage_floors)      그 카테고리 프로그램들의 커뮤니티 권장치 중 «가장 낮은» 값
                        = 모든 사용자가 공통으로 필요한 선
겨냥(usage_tier_rules)  같은 카테고리의 «무거운 쪽»(전업·대형 프로젝트) 수치
```

**개발이 이 기준을 가장 잘 보여 준다.**
32 를 하한으로 박으면 60만원 개발 PC 가 아예 안 나오고, 16 만 두면 예산이 있어도
32 로 안 올라간다 — **둘 다 필요해서 표가 둘이다.**

### 이번에 추가한 겨냥 규칙

| usage_key | budget_min | 슬롯·필드 | 값 | 근거 |
|---|---:|---|---:|---|
| `dev` | 150만 | RAM | ≥32 | 재활성화(0090 이 내린 것) — 안드로이드 스튜디오·인텔리제이·도커 커뮤니티 32GB |
| `dev` | 800만 | RAM | ≤64 | 재활성화 — 「정직하게」(128GB 로 예산 채우지 않는다) |
| `music` | 150만 | RAM | ≥32 | 큐베이스 커뮤니티 32 · 에이블톤 "무거운 라이브러리는 32GB 권장" |
| `trading` | 150만 | RAM | ≥32 | 주식 HTS 커뮤니티 32 "전업 트레이더 기준" |

⚠ `dev` 2행은 0090 이 **삭제가 아니라 `active=false`** 로 내려 둔 것이다(회귀 [51]
「활성 `usage_tier_rules.usage_key` ⊆ `usage_floors.usage_key`」 불변식 때문).
`dev` 가 돌아왔으니 되살렸다.

## 5. ★ 조건부 RAM 규칙 — 넣을 수 있었는가

### 결론: **`usage_tier_rules` 로는 못 넣는다. 새 표 `part_cond_rules` 를 만들었다.**

### 왜 못 넣는가 (구조 실측)

```python
# api/usage_tier_rules.py:96
def passes(part: dict, rules: list) -> bool:
    for field, op, val, _label in rules:
        v = part.get(field)          # ← 부품 «하나»의 «자기 슬롯» 필드만 본다
```

- 축이 `(usage_key, budget_min)` 이다 — 규칙에 **"어떤 GPU 를 골랐는지"가 들어올
  자리가 없다.**
- `passes()` 는 **부품 하나**를 **자기 슬롯의 규칙**과 비교한다. RAM 을 판정할 때
  GPU 행은 손에 없다.
- `usage_floors` 도 완전히 같은 한계다.
- `games` 에도 자리가 없다 — 이건 **게임별 값이 아니다.** 같은 게임이라도 12GB
  카드를 쓰면 16GB 로 충분하고 8GB 카드를 쓰면 32GB 가 필요하다.

예산 티어로 «흉내»내는 우회(예: 150만~300만 구간에 RAM 32 강제)는 기각했다 —
그 구간에서 12GB 카드를 고른 사람에게 **거짓 근거**를 말하게 된다.

### 신설 표

```sql
CREATE TABLE part_cond_rules (
    cond_id     SERIAL PRIMARY KEY,
    usage_key   VARCHAR(32),        -- NULL = 모든 용도
    when_slot   VARCHAR(16)  NOT NULL,   -- 'GPU'
    when_field  VARCHAR(64)  NOT NULL,   -- 'vram_gb'
    when_op     VARCHAR(8)   NOT NULL,   -- 'lte'
    when_value  VARCHAR(255) NOT NULL,   -- '8'
    then_slot   VARCHAR(16)  NOT NULL,   -- 'RAM'
    then_field  VARCHAR(64)  NOT NULL,   -- 'capacity_gb'
    then_op     VARCHAR(8)   NOT NULL,   -- 'gte'
    then_value  VARCHAR(255) NOT NULL,   -- '32'
    label       VARCHAR(80)  NOT NULL,
    note        TEXT,  active BOOLEAN, sort_order INTEGER, created_at TIMESTAMPTZ
);
```

⚠ `value` 를 처음부터 **VARCHAR** 로 뒀다. `usage_tier_rules` 가 INTEGER 로
만들었다가 `op='in'`(칩셋 집합) 때문에 뒤늦게 넓히고 로더에 캐스팅을 덧대야 했다
(`api/usage_tier_rules.py` 45행 주석). 같은 실수를 반복하지 않는다 — 숫자 캐스팅은
로더가 한 곳에서 한다.

### 시드 1행 (근거)

> TechSpot 2026-01 전수 확인(검은신화 오공 · 킹덤컴 딜리버런스2 · 사이버펑크2077 ·
> 배틀필드6): **최신 게임 대부분 시스템 램 16GB 로 충분.** 32GB 가 필요해지는
> 결정적 조건은 **VRAM 8GB 그래픽카드를 쓸 때**다 — 8GB 초과분이 시스템 램으로
> 넘어가 페이지파일 스왑이 일어나 프레임타임이 무너진다. 32GB 로 1% low 60% 개선.

`usage_key = NULL`(모든 용도)로 넣었다. VRAM 을 넘기는 스왑은 게임만의 문제가
아니다 — 같은 일이 영상·3D·AI 에서도 일어난다.

### 하한인가 겨냥인가 — **겨냥이다**

8GB 카드 + 16GB 램도 «돌아간다». 프레임타임이 나쁠 뿐이다. 예산이 모자라 32GB 를
못 넣으면 **규칙을 풀고 짓되 근거에 그 사실을 남긴다.**

### 로더 — `api/part_cond_rules.py`

```python
extra = PCR.apply({"GPU": gpu_row}, usage_key)
# -> {"RAM": [("capacity_gb", "gte", 32, "VRAM 8GB 이하 그래픽카드 — 메모리 32GB")]}
```

돌아오는 모양이 `usage_floors.slot_floors()` 와 **같아서** 부르는 쪽은 기존
`passes()` 를 그대로 쓴다 — 판정 술어를 새로 만들지 않는다.

NULL 원칙: VRAM 을 모르는 GPU 는 조건이 **성립하지 않아** 추가 규칙이 안 걸린다.
하한의 「값을 모르면 불통과」와 방향은 반대지만 뜻은 같다 — **모르는 것을 근거로
삼지 않는다.**

### ⚠ 아직 안 한 것 — 엔진 연결

**표와 값과 로더까지만 만들었다.** `api/recommend.py` 연결은 이번 범위 밖이다
(다른 제작자가 같은 시각에 그 파일에서 내장그래픽 엔진을 고치고 있어 충돌한다).

연결 지점 (다음 담당자용):

```
api/recommend.py:1705 부근   usage_tier_rules 적용 자리 바로 «뒤»
  1. GPU 를 확정한 뒤
  2. extra = PCR.apply({"GPU": chosen_gpu}, usage_key)
  3. RAM 후보를 고르기 전에 extra["RAM"] 을 기존 floors 와 AND 로 합친다
  4. 조합이 안 나오면 extra 만 풀고(usage_floors 는 유지) 근거에 남긴다
     — usage_tier_rules 의 재시도 경로(1879행)와 같은 처리
  5. 응답 evidence 에 {"part_cond_rules": {"applied": bool, "items": PCR.items(extra)}}
```

   무의미하다. 폴백(NULL 행)으로 충분한지 실견적으로 확인해야 한다.
3. **`office` SSD 250GB 유지** — 올릴 근거가 `software` 에 없다.
4. **방송 GPU 하한 없음** — OBS 커뮤니티의 「NVENC 권장」은 인코더 선택이지 성능
   하한이 아니고, 표에 표현할 필드가 없다. 새 설계 없이는 못 채운다.
5. **입문 게이밍 65~90만 칸 · 환경축 3단계 · 조립공임 30,000원** — 격자/가격
   담당 범위다. 이 문서는 «용도 규칙» 만 다룬다.
6. **「사무 8GB vs 16GB」** — ~~사장님 실판매와 다른 판단이다(§2).~~
   **0102 에서 해소.** 용도를 둘로 갈라 둘 다 맞게 했다(§2-개정). 사장님 확정.
7. **(0102 신설) `grid_cells` 격자는 아직 안 갈렸다** — `usage_floors` 하한은
   `office_simple`·`office_complex` 로 갈렸지만 `grid_cells.usage` 는 여전히
   「사무·인강」 12행 하나다. 두 용도가 같은 가격대 카드를 본다.
   `tools/grid_generate.py` 재실행 + 격자 축 분할이 후속 작업이다.
8. **(0102 신설) `usage_alloc` 배분율이 두 갈래 공용이다** — 0086 표본이 «나누기
   전의 사무 전체»라 갈래별 값이 아니다. 갈래별 재측정이 필요하다(값을 지어내지
   않으려고 같은 값을 그대로 뒀다).
9. **(0102 신설) 「업무용」이 복합인 것** — 지시서 목록을 따랐으나 「사무용」만큼
   모호해서 «모호→단순» 원칙과 충돌한다. 사장님 확인 대상.
