## ① 화면 성격

**구조 관리 화면이다.** 대기열이 아니라 판매 분류 트리를 세우고 다듬는 자리다.
트리를 보는 **조회**와 노드를 등록·수정·삭제하는 **쓰기**가 한 화면에 있다.

재구축으로 바뀌는 것은 **탐색 방식**이다. 트리 전개형에서 **단계별 연속 탐색형**으로 간다 —
상위 단계에서 노드를 선택하면 다음 단계의 하위 목록이 열리고, 대분류 → 중분류 → 소분류 →
세분류 4단을 한 화면에서 연속으로 다룬다.

- **엔진(추천·견적)은 이 트리를 읽지 않는다.** `categories`는 부품 종류(`part_type`,
  엔진이 읽는 닫힌 집합)와 다른 축이다 — 분류를 옮겨도 견적 결과는 바뀌지 않는다
  (A-02 재현성 · 회귀 `[33]`). 이 경계는 재구축 후에도 그대로다.
- 조회는 로그인 등급 viewer 이상.
- 등록·수정(이동·이름·정렬 순서·노출·허용 부품 종류)·삭제·마진 설정은 **owner·operator**
  등급만(실측: `api/admin_categories.py:52` `_operator()` — 2026-08-13 확대분. 구
  정의서 `req-product-category.md`가 「owner만」이라 적은 것은 낡은 값이다).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **상품에 판매 분류를 매길 대상 자체가 없다.** 「상품 분류 매핑」 화면
  (`/admin2/category-mapping`)은 이 트리가 있어야 상품을 옮길 자리가 생긴다.
- **마진을 분류 단위로 상속시킬 방법이 없다.** `category_margin_policies`는
  `categories.category_id`를 PK·FK로 삼는다(A-29). 트리가 없으면 상속 체계가 서지 않는다.
- **허용 부품 종류(`allowed_part_types`) 설정처가 없다.** 이 값이 있어야 「상품 분류 매핑」이
  위반 매핑을 경고한다.
- **4단 표준분류를 세울 작업 도구가 없다.** 2026-09-03 확정 표준분류(대·중·소·세 4단 ·
  70행, `docs/design/category-4tier-handoff-2026-09-04.md` §7)를 실제 트리로 옮기려면
  3단·4단 노드를 만들고 옮길 화면이 필요하다. **현행 화면군에는 그 경로가 온전하지 않다** —
  구 화면의 「상위 분류 이동」 선택지가 최상위 노드만 나열해 3단 이상 노드를 다른 가지로
  옮길 길이 없다(같은 문서 §3-① ㉢). 재구축이 이 구멍을 닫는다.
- **재구축 전후로 견적·추천은 그대로 동작한다** — 의도된 경계다.

## ④ 데이터 — API · 테이블 · 필드 (실측 근거)

### 실측 방법 · 조건

`PYTHONIOENCODING=utf-8 PYTHONPATH=. .venv/Scripts/python`으로 `api.db.engine`에 접속해
**재귀 CTE로 직접 SELECT**했다(읽기 전용, DB 미변경). 2026-09-10 실측.

    WITH RECURSIVE t AS (
      SELECT category_id, parent_id, name, 1 AS depth
        FROM categories WHERE parent_id IS NULL
      UNION ALL
      SELECT c.category_id, c.parent_id, c.name, t.depth+1
        FROM categories c JOIN t ON c.parent_id = t.category_id
    )
    SELECT depth, count(*) FROM t GROUP BY depth ORDER BY depth;

**측정 조건을 함께 적는다** — `categories`에 `depth` 컬럼이 없으므로 단계 값은 저장값이
아니라 **최상위(`parent_id IS NULL`)에서 내려오며 파생한 값**이다. 따라서 위 분포는
「최상위에서 도달 가능한 노드」만 센다. 도달 불가 노드(고아 행)는 **0건**으로 확인했으므로
아래 분포의 합과 전체 행수가 일치한다.

### 현재 계층 실측치 (2026-09-10)

| 단계 | 노드 수 | 조건 |
|---|---|---|
| 1단(대분류) | **6** | `parent_id IS NULL` |
| 2단(중분류) | **28** | 1단의 직속 하위 |
| 3단(소분류) | **1** | 2단의 직속 하위. 단 하나 — `부품 > 파워 > 새 소분류`(`category_id=512`) |
| 4단(세분류) | **0** | **실측 0건 — 4단 구조가 아직 실재하지 않는다** |
| 합계 | **35** | `SELECT count(*) FROM categories` = 35 · 고아 행 0 |

**⚠ 이 값은 인계 문맥에 적힌 `depth1=7 · depth2=30 · depth3=1 · 38행`과 다르다.**
2026-09-10 재측정 결과는 **6 · 28 · 1 · 35행**이다. 화면 설계·제작은 이 문서의 숫자가
아니라 **`GET /api/admin/categories` 응답**을 근거로 삼는다.

부속 실측치(같은 시각):

| 항목 | 값 |
|---|---|
| 최상위 6개 · 직속 하위 수 | 부품 9 · 주변기기 8 · 확장·연결 4 · 쿨링·튜닝용품 1 · 완제품 2 · 기타 4 |
| 말단(하위 없음) 노드 | 2단 27개 · 3단 1개 (1단 말단 0개) |
| 상품이 걸린 단계 | **2단에만 23,100건**. 1단·3단은 각 0건 |
| 상품 총계 · 미매핑 | 23,151건 · 미매핑 51건 |
| `is_visible` | 35개 전부 `true`(비노출 0건) |
| `allowed_part_types` 설정 | 28개 노드(나머지 7개는 NULL = 제한 없음) |
| `category_margin_policies` | **0행** — 어떤 노드도 직접 마진을 걸고 있지 않고 전부 전역 기본값을 상속한다 |

**함의(설계 입력):** 3단은 시험 흔적으로 보이는 1건뿐이고, **4단은 데이터에 존재하지 않는다.**
따라서 4단 컬럼형 화면은 재구축 직후 **4번째 단계가 항상 비어 있는 상태로 열린다.**
그 상태의 처리는 ⑦에 적는다.

### 쓰는 테이블

| 테이블 | 역할 | 컬럼(실측) |
|---|---|---|
| `categories` | 분류 트리 본체 | `category_id` int PK · `parent_id` int NULL(자기참조 인접목록) · `name` varchar · `sort_order` int · `is_visible` bool · `allowed_part_types` jsonb(NULL=제한 없음) · `created_at` · `updated_at`. **`depth` 컬럼 없음 — 매 조회마다 재귀 CTE로 파생한다.** 스키마에 깊이 상한이 없으므로 **4단은 스키마 변경 없이 가능하다** |
| `category_margin_policies` | 노드별 직접 마진율 | `category_id` PK·FK **`ON DELETE CASCADE`**(`db/migrations/versions/0030_category_margin_by_node.py:36`) · `margin_rate` NUMERIC(7,6) CHECK(0 이상 1 미만) · `updated_at` |
| `products.category_id` | 상품 ↔ 분류(N:1) | NULL 허용. **이 화면은 이 컬럼을 쓰지 않는다** — 상품 배정은 「상품 분류 매핑」 소관 |
| `pricing_settings.margin_rate` | 전역 기본 마진율 | 상속 종점 |

### 쓰는 API — **구 화면(ADM-CAT-010)과 같은 API를 공유한다**

`api/admin_categories.py` 하나를 두 화면이 함께 쓴다. **재구축에서 새 API를 만들지 않는다.**

| 엔드포인트 | 위치 | 역할 | 권한 |
|---|---|---|---|
| `GET /api/admin/categories` | :140 | 트리 전체(노드별 `parent_id`·`name`·`sort_order`·`is_visible`·`allowed_part_types`·`allowed_labels`) + 직속(`product_count`)·자손합계(`subtree_count`)·재고 있음(`in_stock_count`) 상품 수 + 마진 3종(`margin_rate` 자기값·`margin_effective` 적용값·`margin_source` 출처 문장) + 위반 건수 + 미매핑 집계 + 선택지 `part_types`(표시 종류 18종) + `default_margin` | viewer 이상 |
| `POST /api/admin/categories` | :192 | 노드 등록(`name`·`parent_id`·`sort_order`·`allowed_part_types`) | owner·operator |
| `PATCH /api/admin/categories/{cid}` | :227 | 이름·상위(이동)·정렬 순서·노출·허용 부품 종류 부분 수정. **준 필드만 반영**하고 바뀐 것이 없으면 400 | owner·operator |
| `DELETE /api/admin/categories/{cid}` | :300 | 삭제 — 하위·상품이 있으면 막는다(⑦ 참조) | owner·operator |
| `PUT /api/admin/categories/{cid}/margin` | :343 | 노드 마진율 설정 또는 해제(`null` = 상속으로 되돌림) | owner·operator |

**단계 값은 응답에 없다.** `GET`은 `parent_id`만 준다 — 화면이 4개 컬럼을 만들려면
`parent_id`로 단계를 파생해야 한다. 파생 규칙을 화면이 다시 정의하지 않도록, **응답에 단계를
포함할지**는 결정 필요 지점으로 남긴다(아래 「결정 필요 지점」 3).

**되돌리기 API는 없다.** 실측: `api/admin_categories.py`에 `undo` 엔드포인트가 없다
(「상품 분류 매핑」의 이동 되돌리기와 다르다).

## ⑤ 기능 (동사)

원안의 동작을 옮기되, 원안은 브라우저 저장(localStorage) 데모다 — 재구축본은 **서버에
저장한다.** 아래에서 ⚠ 표시는 **원안대로 옮기면 위험한 지점**이다.

### 조회

- 대분류 목록을 조회한다.
- 상위 단계의 노드를 선택해 그 하위 목록을 다음 단계에서 조회한다(4단까지 연속).
- 단계별 노드 수를 조회한다.
- 노드별 연결 상품 수를 조회한다. ⚠ 원안은 **직속 상품 수**만 센다(`productCount(c.id)`).
  상위 단계 노드는 직속 0건이 보통이라 그대로 옮기면 상품 13,000여 건을 담은 「부품」이
  **0으로 보인다**. `GET` 응답의 `subtree_count`(자손 합계)를 쓸지 `product_count`(직속)를
  쓸지, 또는 둘 다 표시할지 정해야 한다(원안에는 이 구분이 없다).
- 선택 경로(대 › 중 › 소 › 세)를 조회한다.

### 등록 · 수정

- 각 단계에서 하위 분류를 **등록한다.** ⚠ 원안은 「새 대분류」 같은 임시 이름으로 즉시 행을
  만들고 미저장 상태로 둔다. 서버 바인딩에서는 `POST`가 이름을 요구하므로(빈 이름 400),
  **① 이름을 먼저 입력받고 등록하거나 ② 기본 이름으로 즉시 등록하고 개명을 이어서 받는** 두
  방식 중 하나를 정해야 한다.
- 노드 이름을 **수정한다**(인라인 입력). ⚠ 저장 시점 문제 — ⑥ 참조.
- 노드의 노출 여부를 **수정한다.**
- 노드를 **삭제한다.** ⚠ 하위·상품 처리 — ⑦ 및 ⑥ 참조.
- 변경 내용을 **저장한다**(단계별 저장 · 전체 저장). ⚠ 원자성 문제 — ⑥ 참조.

### 원안에 없으나 데이터·API가 요구하는 것 (누락 여부를 정해야 한다)

원안의 카테고리 화면은 **이름 · 노출 · 삭제 · 등록** 넷만 다룬다. 그러나 현행 API·스키마는
아래를 갖고 있고, 구 v2 화면이 이미 이를 다루고 있다. **재구축본이 이 기능을 이어받지 않으면
설정 경로가 사라진다.**

| 기능 | 근거 | 원안 |
|---|---|---|
| 정렬 순서 수정 | `categories.sort_order` · `PATCH` | 없음 |
| 허용 부품 종류 설정·해제 | `allowed_part_types` · `PATCH`(`clear_part_types`) | 없음 |
| 상위 분류 변경(다른 가지로 이동) | `PATCH`(`parent_id`·`move_to_root`) | 없음 — 원안은 같은 부모 안에서만 다룬다 |
| 노드 마진율 설정·해제 | `PUT /{cid}/margin`(A-29) | 없음 |
| 미매핑 상품 수 · 허용 종류 위반 수 조회 | `GET` 응답 `unmapped`·`violations` | 없음 |

⚠ **특히 「상위 분류 변경」이 빠지면 4단 구축이 막힌다.** 3단 이상 노드를 다른 가지로 옮길
길이 없으면 잘못 만든 노드를 화면에서 되돌릴 수 없다(`category-4tier-handoff-2026-09-04.md`
§3-① ㉢ — 「깊이를 늘리기 전에 먼저 고쳐야 한다」).

## ⑥ 인터랙션 — 입력 · 선택 · 저장 · 이동의 흐름과 결과

### 연속 탐색

- 어떤 단계에서 노드를 선택하면 **그 하위 단계들의 선택이 모두 해제되고** 다음 단계에
  해당 노드의 하위 목록이 열린다(원안 `select` 동작: `for (k=i+1; k<4; k++) s[k]=null`).
- 상위 단계가 선택되지 않은 하위 단계는 **잠금 상태**이며 등록도 막힌다(원안 `locked`).
- 선택 경로를 화면이 표시한다. 아무것도 선택하지 않은 상태의 안내는 「대분류 선택 필요」.

### 저장 — ⚠ 원자성을 정해야 한다

원안은 이름 변경분을 미저장 초안(`drafts`)에 모아 두고 **① 단계별 저장** 과
**② 전체 저장** 두 경로로 반영한다(`saveNames(ids)`). 서버 바인딩에서 이것이 문제가 된다:

- **`PATCH`는 노드 하나 단위다.** N건을 저장하려면 요청이 N번 나간다. **중간에 하나가
  실패하면 앞의 것은 이미 저장되고 뒤의 것은 저장되지 않는다** — 부분 반영이다.
  단계별 저장과 전체 저장은 **대상 범위만 다를 뿐 같은 위험을 갖는다.** 전체 저장은 대상이
  넓어 부분 반영의 폭이 더 크다.
- 원안은 실패를 「이름이 비어 있음」 한 가지로만 다루고 해당 노드만 초안에 남긴다. 서버는
  **409(같은 위치 같은 이름) · 400(이름 길이 80자 초과 · 바뀐 내용 없음) · 403(권한) ·
  404(없는 노드)** 를 낼 수 있다.
- 따라서 정해야 한다: **㉮ 부분 반영을 허용하고 「N건 중 M건 저장 · 실패 K건」을 그대로
  보고한다** / **㉯ 일괄 저장 API를 신설해 한 트랜잭션으로 처리한다**(신설이므로 P-08 경로) /
  **㉰ 일괄 저장을 두지 않고 항목별 즉시 저장만 둔다.**
- **어느 쪽이든 저장 성공 표시만 남기고 실패를 삼켜서는 안 된다**
  (`.claude/CANON.md` §4 — 조용한 포기 금지).

### 인라인 개명 — ⚠ 저장 시점을 정해야 한다

원안은 **이름은 저장 조작을 해야 반영**하고 **노출 전환은 즉시 반영**한다(원안 579행).
같은 행에서 두 항목의 저장 시점이 다르다.

- 위험: 이름을 고치고 저장하지 않은 채 **다른 노드를 선택하면** 미저장 값이 화면에 남는다
  (원안은 초안을 `drafts`에 유지한다). 운영자는 저장된 것으로 오인할 수 있다.
- 위험: 미저장 상태에서 **화면을 떠나면 변경이 사라진다.** 원안에는 이탈 확인이 없다.
- 위험: 원래 이름 그대로 저장을 시도하면 서버가 **400 「바뀐 내용이 없습니다」** 를 낸다.
  화면은 변경 없는 항목을 요청 대상에서 제외해야 한다.
- 정해야 한다: **㉮ 원안대로(이름은 명시 저장 · 노출은 즉시)** / **㉯ 전부 즉시 저장** /
  **㉰ 전부 명시 저장.** 어느 쪽이든 **미저장 건이 있는 상태의 이탈·탐색 이동 처리**를
  함께 정한다.

### 삭제 — ⚠ 하위 노드와 그 분류에 걸린 상품의 처리

원안은 삭제 전에 화면 스스로 판정한다: 하위가 있으면 하위를 먼저 삭제하라 하고, 연결 상품이
있으면 상품의 분류를 먼저 바꾸라 하고, 아니면 되돌릴 수 없다는 확인 후 삭제한다.

**실제 서버 동작(코드 확인 — `api/admin_categories.py:300`~:320):**

1. 노드가 없으면 **404** 「카테고리를 찾을 수 없습니다」.
2. `SELECT count(*) FROM categories WHERE parent_id=:i` — **직속 하위가 1건이라도 있으면
   409** 「하위 카테고리 N개를 먼저 옮기거나 지우세요」. **연쇄 삭제하지 않는다.**
   판정은 **직속 하위**만 본다(자손 전체가 아니다).
3. `SELECT count(*) FROM products WHERE category_id=:i` — **그 노드에 직접 걸린 상품이 있으면
   409** 「상품 N건이 이 카테고리에 있습니다 — 먼저 옮기세요」. 코드 주석이 이유를 밝힌다:
   지우면 그 상품들이 조용히 미매핑이 되기 때문이다.
4. 둘 다 통과해야 `DELETE` 하고 활동 로그(`kind='category'`)를 남긴다.

**즉 서버는 「직속 하위도 없고 직속 상품도 없는 말단 노드」만 지운다. 하위 노드도, 그 분류에
걸린 상품도 자동으로 처리되지 않는다 — 운영자가 먼저 옮겨야 한다.** 원안의 화면 측 사전
판정은 서버 규칙과 방향이 같다. 다만 다음을 요구로 명시한다:

- **화면의 사전 판정을 저장 조건으로 삼지 않는다.** 판정 근거는 서버 응답이며 화면 판정은
  안내일 뿐이다(다른 운영자가 그 사이 상품을 옮겼을 수 있다).
- **상품 수 판정 기준이 다르다.** 서버는 **직속 상품**만 센다. 화면이 자손 합계
  (`subtree_count`)를 표시하기로 하면 **표시 수와 삭제 차단 사유의 수가 서로 다른 값이
  된다** — 어느 수를 삭제 안내에 쓸지 명시해야 한다.
- ⚠ **삭제되는 노드에 직접 걸린 마진 정책은 함께 사라진다.** `category_margin_policies`의
  FK가 `ON DELETE CASCADE`다(0030 마이그레이션). 삭제는 말단 노드에만 가능하므로 하위로
  번지지는 않으나, **그 노드가 상속을 끊고 있었다면 삭제로 마진 상속 결과가 바뀐다.**
  삭제 확인 문구에 이 사실을 포함할지 정해야 한다.
- ⚠ **삭제에 되돌리기가 없다.** 원안 문구 「되돌릴 수 없습니다」는 실제와 맞다
  (`api/admin_categories.py`에 `undo` 없음).

### 이동 · 마진 상속 — ⚠ 분류를 옮기면 마진 상속이 함께 바뀐다

- 마진은 **자기 노드 → 조상 → 전역** 순으로 상속된다(A-29 · `api/pricing.resolve_margins`
  단일 원천 — 이 계산을 다른 곳에서 다시 하지 않는다). **노드를 다른 가지로 옮기면 조상이
  바뀌므로 그 노드와 자손 전체의 적용 마진이 바뀔 수 있다.** 「상위 분류 변경」을 재구축본에
  넣는다면 **저장 결과가 이 사실과 영향 상품 수를 함께 알려야 한다.**
- **다만 판매가는 그 자리에서 바뀌지 않는다.** 저장된 판매가는 「판매가 재산정」에서
  미리보기 후 확정해야 반영된다(`GET` 응답 `margin_note`가 이 문장을 이미 준다).
  **화면이 이미 반영된 것처럼 말하면 안 된다.**
- 자기 자신 또는 자기 하위로의 이동은 저장 전에 400으로 막힌다(순환 방지).
- **현재 `category_margin_policies`가 0행이므로 지금 옮기면 실제로 바뀌는 값은 없다.**
  마진이 걸린 뒤에는 달라진다 — 요구에서 빼지 않는다.

### 재구축 후 트리를 4단으로 세울 때

- 3단·4단 노드를 새로 등록하면 그 하위 단계가 이어서 열린다.
- ⚠ 상품은 **현재 전량이 2단 노드에 걸려 있다**(23,100건). 4단으로 재분류하려면 상품을
  하위 노드로 옮겨야 하는데, **그 이동은 이 화면이 하지 않는다** — 「상품 분류 매핑」
  화면(`/admin2/category-mapping`) 소관이고 **1회 이동 상한 2,000건**이 있다
  (`api/admin_category_mapping.py:43` `MAX_MOVE`). 이 화면에서 해당 화면으로 넘어가는 이동
  지점을 둘지 정한다.

### 원안 「데모 초기화」 — ⚠ 실데이터 화면에 그대로 둘 수 없다

원안 상단의 `resetDemo`는 **분류와 상품을 기본 데모 데이터로 되돌린다.** 원안이 브라우저
저장 기반이라 성립하는 동작이며, **실데이터 화면에 그대로 옮기면 분류 35건과 상품 23,151건의
매핑을 되돌리는 조작이 단추 하나가 된다.** 대응하는 API도 없다.

**선택지만 올린다 — 이 문서에서 정하지 않는다.**

| 안 | 내용 |
|---|---|
| ㉮ | 재구축본에서 **삭제한다**(기능을 옮기지 않는다) |
| ㉯ | **미저장 변경 취소**로 의미를 바꾼다 — 서버 데이터는 건드리지 않고 화면의 미저장 초안만 비운다. 명칭은 「변경 취소」 |
| ㉰ | 그대로 두되 **별도 확인 절차와 권한 제한**을 둔다(대응 API 신설 필요 — P-08 정규 경로) |

## ⑦ 상태 · 예외

### 빈 4번째 컬럼 — 재구축 직후의 기본 상태

**실측상 4단 노드는 0건이고 3단도 1건뿐이다(④).** 따라서 화면이 열릴 때의 정상 상태는
다음과 같다. **이것을 오류나 적재 실패로 표시하지 않는다.**

| 상태 | 조건 | 요구 |
|---|---|---|
| **잠금(선택 대기)** | 상위 단계에서 아무 노드도 선택하지 않음 | 「상위 분류 선택 필요」를 표시하고 등록을 막는다. **이것이 3·4단의 초기 상태다** |
| **비어 있음(하위 없음)** | 상위 노드를 선택했으나 하위가 0건 | 「하위 분류 없음 · 등록 가능」을 표시하고 **등록은 허용한다.** 오류가 아니다 |
| **말단 표시** | 선택한 노드에 하위가 없음 | 하위 탐색 조작을 비활성으로 둔다. **「하위 없음」과 「추가 불가」를 구분해 표시한다** — 스키마에 깊이 상한이 없으므로 둘은 다른 뜻이다 |
| **4단 상한** | 4번째 단계 노드를 선택함 | ⚠ **원안은 4단 노드를 무조건 말단으로 고정한다**(`isLeaf: i === 3`). 그러나 **DB·API에는 깊이 상한이 없어 5단 이상이 저장될 수 있다.** 화면이 4단에서 멈추면 5단 이하 노드는 **어느 단계에도 보이지 않고 화면에서 되돌릴 수 없다.** 처리를 정해야 한다(결정 필요 지점 2) |

**4번째 단계가 비어 있다는 사실 자체를 화면이 결함으로 표시하지 않는다.** 현재 트리는 2단
중심이며 4단은 2026-09-03 표준분류로 **앞으로 세울 대상**이다. 화면은 그 작업의 도구다.
같은 이유로 **3단도 현재 1건뿐이므로, 대분류를 골라도 3·4단이 계속 비어 있는 상태가 정상이다.**

### 권한

- 미로그인은 401 「로그인이 필요합니다」(공통 미들웨어).
- viewer는 조회만 가능하다. 쓰기 시도는 **403 「운영자 이상만 카테고리를 바꿀 수 있습니다」**
  (`api/admin_categories.py:60`). 화면은 viewer에게 쓰기 조작을 비활성으로 두되,
  **판정 근거는 서버 응답이다.**

| 상황 | 코드 · 문구 |

| 없는 상위 분류 지정 | 404 「상위 카테고리를 찾을 수 없습니다」 / 이동 시 「옮길 상위 카테고리를 찾을 수 없습니다」 |
| 자기 자신·자기 하위로 이동 | 400 「자기 자신이나 하위 카테고리 밑으로는 옮길 수 없습니다」 |

| 마진율 범위 밖 | 400 「마진율은 0 이상 1 미만이어야 합니다(0.13 = 13%)」 |
| 상속 상태 노드의 마진 해제 | 400 「이 분류에 직접 걸린 마진이 없습니다」 |
| 없는 부품 종류 지정 | 400 「없는 부품 종류입니다: …」 |

### 그 밖의 상태

- **빈 트리**: 최상위가 0건이 되면 상품 등록·분류 매핑에서 고를 분류가 사라진다.
  현재는 35행이 있어 실사용 중 마주치지 않는다.
- **`is_visible`은 저장은 되지만 읽는 소비처가 없다.** 실측: `GET /api/admin/categories`도
  `GET /api/admin/category-mapping`도 이 값과 무관하게 전 노드를 돌려준다. 실데이터도
  **35건 전부 노출**이다. 원안은 노출 전환을 즉시 반영하고 상태를 표시한다 — **지금은 꺼도
  관리자 화면에서 사라지지 않는다는 사실을 화면이 감추지 않아야 한다.**
- **동시 편집**: 두 화면(ADM-CAT-010 · ADM-CAT-011)이 같은 API를 공유하므로 다른 운영자가
  같은 트리를 동시에 고칠 수 있다. 낙관적 잠금이 없다 — 나중 저장이 이긴다.
  **미저장 초안을 오래 유지하는 방식일수록 이 위험이 커진다**(⑥ 인라인 개명 참조).

## 비범위 — 이 화면이 하지 않는 일

- **엔진(추천·견적)에 영향을 주지 않는다.** 분류를 옮기거나 지워도 견적 결과는 그대로다
  (A-02 · 회귀 `[33]`).
- **상품을 분류에 배정하지 않는다.** 「상품 분류 매핑」(`/admin2/category-mapping`) 소관.
- **판매가를 바꾸지 않는다.** 마진율을 정해도 재산정은 「판매가 재산정」에서 일어난다.
- **`part_type` 축을 건드리지 않는다.** 두 축의 통합 여부(㉮ 파생 / ㉯ 통합 / ㉰ 병존)는
  `category-4tier-handoff-2026-09-04.md` 미정-3으로 열려 있다.
- **4단 표준분류를 자동으로 세우지 않는다.** 70행 시드 투입은 마이그레이션·재매핑 작업이며
  이 화면의 요구가 아니다(같은 문서 §5-②).
- **고객에게 분류 탐색을 제공하지 않는다.** 관리자 전용이다.

## 사장님 결정 필요 지점 (임의로 정하지 않았다)

1. **저장 원자성** — ⑥의 ㉮ 부분 반영 보고 / ㉯ 일괄 저장 API 신설 / ㉰ 즉시 저장 전용.
2. **깊이 상한** — 화면을 4단에서 멈출 것인가. 멈추면 5단 이상 노드가 화면에 보이지 않고
   되돌릴 수 없다. 2026-09-04 미정-2(4단 대 7단)와 직결된다.
3. **단계 값의 원천** — `GET` 응답에 파생 단계(`depth`)를 포함할 것인가, 화면이
   `parent_id`로 계산할 것인가. 화면이 계산하면 「깊이는 파생한다」 규약의 구현이 두 벌이 된다.
4. **명칭 통일** — 화면 어휘는 「분류」, 서버 응답 문구는 「카테고리」로 갈라져 있다.
   어느 쪽으로 맞출지(화면만 교정 / 응답 문구까지 개정).
5. **「데모 초기화」 처분** — ⑥의 ㉮ 삭제 / ㉯ 미저장 변경 취소로 전환 / ㉰ 확인 절차·권한
   제한 후 존치.
6. **원안에 없는 기능의 존치** — 정렬 순서 · 허용 부품 종류 · 상위 분류 변경 · 마진 설정
   (⑤ 표). 특히 **상위 분류 변경을 빼면 4단 구축 중 오등록을 되돌릴 수 없다.**
7. **상품 수 표시 기준** — 직속(`product_count`) / 자손 합계(`subtree_count`) / 둘 다.
   삭제 차단 사유는 직속 기준이므로 표시 기준이 다르면 안내가 어긋난다.
8. **삭제 되돌리기** — 현재 API에 없다. 「되돌림은 역방향 전이」 원칙에 맞추려면 신설이
   필요하다.
9. **구 v2 처분** — **재구축 완료 시점에 정한다**(2026-09-10 확정). 여기서 정하지 않는다.
