# 요구사항 정의서 — 작업 기록에서 되돌리기 (admin2 기능 확장)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). **화면 설계는 사장님이
> 이 문서를 입력으로 하신다**(`req-work-request.md` 선례와 같은 절차).
>
> **새 화면이 아니다.** 기존 조회 화면(ADM-SYS-030 「작업 기록」· `/admin2/activity-logs`)에
> **되돌리기 실행**이라는 쓰기 동작 하나를 추가하는 작업이다. ②에서 그 근거를 밝힌다.
>
> 작성일 2026-08-28. ④의 건수·비율은 그 시각의 실측 스냅샷이다(대부분 이 작업 착수
> 전 다른 팀원의 조사를 인용했고, 코드 인용 부분은 이 세션이 파일을 직접 열어
> 재확인했다 — 어느 쪽인지 각 항목에 표시한다). **화면은 이 문서의 숫자를 박지 않는다.**
> DB 재조회는 하지 않았다 — 작업 시점에 확인자 세션이 별도 포트로 서버를 띄워 두고
> 있어 DB를 다시 두드리지 않았다(코드 열람만).

---

## ① 화면 성격

**작업 화면(제한적 쓰기) — 지금은 조회 전용, 이번에 되돌리기 실행 하나가 더해진다.**

```
지금            /admin2/activity-logs — 순수 조회. 원장을 이 화면에서 지우거나
                고치지 않는다(templates/admin/activity_logs.html.j2:7 자기 설명).
                「되돌려짐」 배지는 이미 있다 — 과거에 실행된 되돌리기를 표시만 한다.

이번에 더하는 것  같은 목록의 같은 행에서 「아직 되돌려지지 않은」 원본 행을 골라
                되돌리기를 **실행**하는 동작. 표시(과거형)에서 실행(현재형)으로 성격이 늘어난다.
```

### 신설 배경

**「상품 분류 매핑」은 되돌림이 이동의 92%다**(④ 표 참조). 그런데 되돌리기 목록이
**화면 안 JS 배열에만** 있어 새로고침하면 사라진다. 서버 API(`POST
/api/admin/category-mapping/undo`)는 시점 제한이 없는데, 그 API를 부를 수 있는
화면 창구가 **그 이동을 실행한 세션이 살아 있는 동안뿐**이었다.

사장님께 세 안을 올렸고 **「작업 기록(`/admin2/activity-logs`)에서 되돌리게」를
고르셨다**(2026-08-28). 이유: 거기엔 이미 모든 도메인의 모든 이동이 남고
「되돌려짐」 배지까지 파생돼 있다 — 되돌리기 전용 새 원장을 또 만들 필요가 없다.

### ⚠ 승인 디자인에도 「실행」 선례가 없다

기존 화면의 승인 디자인(`docs/design/dc-activity-logs.html`)에는 되돌림 관련
문구가 31곳 있지만, **전부 「되돌려짐/판정 불가/되돌려지지 않음」 배지 표시**다
(`dc-activity-logs.html:295-408`, `undoneMeta()`/`undoneTitle`/`undoneDesc`).
**되돌리기를 «실행»하는 단추·확인 흐름은 원안에 없다.** 지금 만드는 것은 이
화면 자체에도 처음 붙는 상호작용이라, 참고할 기존 배치가 없다 — 사장님이
새로 그리셔야 하는 부분이라는 뜻이다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

**서버는 되돌릴 수 있는데, 그 사실에 닿을 길이 그 순간이 지나면 사라진다.**

되돌리기 API 17개(④)는 전부 **시점 제한이 없다.** `log_id` 하나만 있으면 언제든
부를 수 있다. 그런데 지금 그 `log_id`를 화면에 쥐고 있는 곳은 **작업을 실행한
그 페이지의 JS 변수뿐**이다 — 새로고침·다른 화면 이동·다음날 접속이면 없어진다.

그리고 **되돌림이 드문 일이 아니다** — 도메인 대부분에서 «원래 하려던 일»보다
«방금 한 일을 무르는 일»이 훨씬 잦다:

```
                    원본 건수 → 되돌림 건수   되돌림 비율
오픈 단계 설정        535 →   532                99.4%
상품 사양             496 →   491                99.0%
상품 수정             533 →   519                97.4%
상품 분류 변경        478 →   458                95.8%
상품 분류 매핑        405 →   374                92.3%
재고 입고              22 →    13                59.1%
검수(4종 합계)      4,204 →    29                 0.7%
```
(2026-08-28 스냅샷 — 다른 팀원의 DB 조사를 인용, 이 세션은 재조회하지 않았다.
이 문서 자신이 낡는다는 뜻이다 — 화면은 이 표의 숫자를 쓰지 않는다.)

**검수만 예외적으로 낮다** — 검수는 «처음 판정하는» 화면이라 되돌릴 일이
드물고, 나머지는 대부분 «일괄로 옮기고 잘못 옮긴 것을 바로잡는» 성격이라
되돌림이 주된 사용법에 가깝다. 이 화면이 없으면, 그 되돌림들이 **API로는
여전히 가능한데 실행할 창구가 없어** 사람이 log_id를 따로 적어 두거나(비현실적),
DB를 직접 두드리거나(운영자 몫이 아니다), 포기하는 수밖에 없다.

### 되돌리기 API — 17개다 (이름으로 세면 놓친다)

`api/*.py` 전체에서 경로에 `undo`가 있는 `@router.post`를 직접 grep해 재현했다
(이 세션이 직접 실행 · 재현 가능):
```
grep -rn '@router\.(post|put|patch)\(.*undo' api/
```

되돌리기를 호출할 «자격 정보»는 이미 충분하다. **화면이 실제로 모르는 것은
대상 식별이 아니라 두 가지다 — (a) 이 `log_id`의 현재 되돌리기 가능 상태,
(b) 17개 중 어느 경로를 어떤 인자 방식(path vs body)으로 불러야 하는지.** 이
매핑표 자체가 지금 코드 어디에도 없다(`grep -r "UNDO_ENDPOINT" api/` 0건,
이 세션 직접 확인).

**⚠ 3개 도메인(카테고리 매핑·판매가 재산정·상품 상태 일괄 변경)은 action이
한글로 코드에 직접 박혀 있다.** `ACTION_LABELS` 딕셔너리(`api/admin_activity_logs.py:55-113`)에
이 셋의 원본 action이 아예 없다 — 이미 한글이라 번역이 필요 없기 때문이다. **행위
이름 문자열 매칭으로 「되돌리기 가능한 도메인」을 짐작하면 이 셋을 놓친다.**

### 이미 있는 판정 선례 — `_undo_state()` (재고 입고)

`GET /api/admin/stock-inbound/history`(`api/admin_stock.py:565`)만 이미 각
행에 **`undoable`(bool) · `undo_state`(문자열) · `undo_note`(사람이 읽는 사유)**를
서버가 계산해 내려준다. 판정 함수는 `_undo_state()`(`api/admin_stock.py:476-504`,
전문 확인함). 상태는 여섯 갈래다 — 원 함수 주석이 밝힌 넷(`undo_inbound()`와
순서·술어가 같아야 하는 것)에 **실패를 삼키지 않기 위한 방어 하나**(`log_incomplete`
— 수량 필드가 없으면 500 대신 이 상태로 응답)가 더해져 있다:

```
not_inbound       action != 'stock_inbound' — 원본이 입고가 아니다(예: 이미 되돌림 행)
undone            이미 되돌린 입고다
product_missing   조회 이후 상품이 삭제됐다
log_incomplete    기록에 수량이 없다 — 실행하면 KeyError로 500이 났을 자리
stock_short       입고분보다 현재 재고가 적다(그새 판매·조정이 있었다)
ok                되돌리기 가능
```

**함수 자신의 docstring이 위험을 명시한다**(`api/admin_stock.py:477-480`):
> 되돌릴 수 있는가 — **서버가 판정한다. 화면은 표시만 한다.** 순서·술어가
> `undo_inbound()`와 같다. **갈라지면 목록이 「가능」이라 말한 건에서 409가 난다.**

**이 선례를 나머지 16개로 옮기는 것이 이 기획의 핵심이다.** 다만 아래
「이중 실행 방지 — 도메인마다 다르다」가 보이듯, 재고 입고 하나의 술어를
그대로 복사해서는 안 된다 — 17개가 각자 다른 조건을 본다.

### 이중 실행 방지 — 도메인마다 다른 술어를 쓴다

위 표에서 직접 확인한 10개(✓직접확인 표시)만 봐도 **일곱 가지 서로 다른 모양**이 나온다:

```
① ref_log_id EXISTS 만                     카테고리 매핑 · 상품 상태 일괄 변경 ·
                                            판매가 재산정
② ref_log_id EXISTS(원 되돌림 action 한정)   상품 수정
③ 실시간 상태 비교 하나                       주문 처리
④ 실시간 비교 + 비가역 분기 + 교차 충돌 스캔   환불 처리(가장 복잡 — 3중)
⑤ ref_log_id EXISTS + 다중 필드 스냅샷 대조   정산 마감(4필드) · 매입 모델 연결
                                            해제(2필드)
⑥ 실시간 상태 비교(필드 하나) — "경합 방어의   검수 처리(4종 통합 — 원 코드
   전부"라고 원 코드가 스스로 밝힌다            주석이 자백)
⑦ 전용 상태 함수(6분기, undoable 필드까지)    재고 입고 — 유일하게 이미
                                            판정 결과를 화면에 내려준다
```

**⚠ 서버가 이 17개를 위해 「지금 되돌릴 수 있는가」를 새로 계산하려면, 이
술어 각각을 알아야 한다 — 하나로 뭉뚱그리면 안 된다.** `_undo_state()`
docstring의 경고("갈라지면 「가능」이라 말한 건에서 409")가 재고 입고
하나에서도 나온 경고인데, 17개 각자 다른 조건이면 그 위험이 17배가 된다.

### ⚠ 「N건 복구」가 실제 반영 건수가 아닐 수 있다 (이 세션이 코드를 읽다 발견)

대량 되돌리기(카테고리 매핑·상품 상태 일괄 변경·판매가 재산정)는 원 로그의
`before[]` 배열을 순회하며 `UPDATE ... WHERE product_code=:pc`를 실행한다
(`admin_category_mapping.py:277-280` 등). **이 `UPDATE`는 대상 행이 이미 없어도
에러 없이 0건 갱신으로 조용히 넘어간다** — 즉 원 이동 이후 그 상품이 삭제됐으면
그 건은 되돌아가지 않는데도, 응답의 `restored`/`moved` 값은 여전히
`len(before)`(«시도한» 건수)를 그대로 쓴다. **화면이 이 수를 「실제로 되돌아간
건수」로 표시하면 지어낸 값을 내미는 것과 같다**(`CLAUDE.md` §화면 정직성과
같은 종류의 문제 — 다만 이번엔 화면이 아니라 서버 응답 자체의 셈법이 원인이다).
이 문서는 코드를 고치지 않는다 — **사실만 남긴다.**

### 지금 조회 API(`GET /api/admin/activity-logs`)가 주는 것 / 안 주는 것

응답 필드(`api/admin_activity_logs.py:264-278`, 전문 확인함) — 행마다:
```
log_id · at · operator · kind · kind_label · action_label ·
is_undo · target · summary · undone
```
**`undoable` 필드가 없다.** 그리고 **원문 `action`(영문 코드)·`detail`(jsonb
원문)도 응답에 없다** — `action_label`·`summary`만 서버가 이미 해석해
내려준다(같은 파일 260-263행 `unmapped_actions` 참조 — 사전에 없는 action은
`action_label`이 원문 그대로 새는 것으로 그 한계를 스스로 알린다).

**`kind`만으로는 되돌리기 가능 여부를 못 가른다** — 예:
```
kind="product" 안에
   되돌리기 있음   product_edit · spec_edit · part_type_change · product_merge
   되돌리기 없음   product_register · product_delete
```
`product_delete`는 `DELETE FROM products`로 행을 **실제로 지운다**
(`admin_products.py:1611-1615`, `_log()`에 `refs`만 남기고 원본 행 스냅샷은
남기지 않는다) — 값 복원이 아니라 행 재생성이 필요해 지금 구조로는 되돌릴
근거 자체가 없다. `product_register`도 대응하는 `_undo` 액션이 없다
(`ACTION_LABELS`에 단짝이 없음, 코드 인용 위 표).

### ⚠ 조회 API 자체의 한계 — 되돌리기 신설과 별개로 이미 있던 제약

`templates/admin/activity_logs.html.j2:20-37`(화면 자신의 데이터 계약 설명,
전문 확인함)이 이미 밝히고 있다:
```
서버 파라미터        date_from · date_to 둘뿐. 운영자·도메인(kind)·행위(action)·
                    되돌림 여부·자유검색 파라미터는 없다
정렬                 log_id DESC 고정
상한                 LIMIT 500(모듈 상수) — 넘으면 "최근 500건만 표시"로 정직 표기
그 밖의 필터          "지금 불러온 배치(최대 500건) 안에서" 클라이언트가 거른다
```
**이것이 되돌리기 기능과 부딪힌다.** 17개 도메인이 **하나의 로그 테이블**을
공유하므로(`admin_operator_activity_logs`), 어떤 날짜 구간에 다른 도메인
로그가 많이 섞여 있으면 정작 찾는 도메인(예: 오래전 검수 처리 하나)의 원본
행이 500건 상한 밖으로 밀려 **화면에 아예 뜨지 않을 수 있다** — API 자체는
시점 제한이 없는데, 화면의 조회 창구가 그보다 좁다. **이 문서가 다루는
「되돌리기 실행」과는 별개의, 이미 있던 제약이다.** 사장님이 고르신 안
(「작업 기록에서 되돌리게」)이 «오래된» 이동까지 실제로 닿으려면 이 한계도
함께 볼지 판단이 필요하다 — 아래 결정 표 7번.

### 권한 — 실측

`api/auth.py:405-424`(`required_role()`, 전문 확인함)의 기본 규칙:
```
GET 류                        viewer(조회) 이상
그 밖의 쓰기                    operator(운영자) 이상
OWNER_WRITE_PREFIXES 경로 + 쓰기   owner만
```
`OWNER_WRITE_PREFIXES`는 12개 접두어를 갖고 있다(`api/auth.py:362-389`, 전문
확인함) — `/operators`·`/ops-settings`·`/catalog-import`·`/spec-fields`·
`/usage-floors`·`/pricing-settings`·`/category-margins`·`/ai-task-settings`·
`/ai-integration`·`/ops-assistant`·`/mall-supplier`·`/request-decisions`.
**이 12개 중 위 17개 되돌리기 경로와 겹치는 것은 `/ops-settings` 하나뿐이다.**
`/reprice`는 이 목록에 없다 — 그 도메인의 owner 전용은 **미들웨어가 아니라
그 모듈 자신의 `_owner()` 함수**가 진다(`admin_reprice.py:67-71, 254`, 확인함).
**그 밖의 15개는 기본값(operator)** — `product_edit`(상품 수정) undo를
직접 읽어 확인했고(`admin_products.py:785-826`), 함수 안 어디에도 role
검사 코드가 없다(미들웨어에만 의존).

**그러므로:**
```
조회 등급(viewer)      화면은 볼 수 있다(GET 기본값)
운영자 등급(operator)   15개는 실행할 수 있다
관리자 등급(owner)      17개 전부 실행할 수 있다 — 오픈 단계 설정·판매가 재산정
                       «만» 이 등급이 필요하다
```
⚠ **조회 등급이 단추를 보고 눌렀다가 403을 받는 상태가 될 수 있다** — 지금 화면은
이 문제 자체가 없었다: `templates/admin/activity_logs.html.j2:164-168`
(전문 확인함)이 스스로 밝히듯 **"이 화면은 역할별로 잠그는 버튼이 하나도
없다"** — 쓰기 동작이 없었기 때문이다. 되돌리기를 더하는 순간 이 문장이
더는 사실이 아니게 된다.

## ⑤ 기능

### 서버(신설 대상)
- 각 행에 대해 **되돌릴 수 있는가를 판정**해 목록 응답에 싣는다(재고 입고의
  `undoable`/`undo_state`/`undo_note` 선례를 나머지 16개로 확장)
- 어느 행에 대해 **어느 되돌리기 경로를 어떤 인자 방식으로 불러야 하는지** 결정한다
  (지금 화면·API 어디에도 이 매핑이 없다 — ④)
- 되돌리기를 **실행**하고, 그 실행 자체를 새 활동 기록으로 남긴다(기존 관례 그대로
  — `ref_log_id`를 단다)
- 등급별로 **실행을 허용/거부**한다(오픈 단계 설정·판매가 재산정은 owner만)

### 조회 등급(viewer)
- 목록을 본다. 되돌리기를 **실행할 수 없다**(현재 규칙 그대로 — auth.py 기본값)

### 운영자 등급(operator)
- 되돌릴 수 있는 행에서 되돌리기를 **실행**한다(오픈 단계 설정·판매가 재산정 제외)
- 대량 이동(예: 카테고리 매핑 다건)을 되돌릴 때 **영향 규모를 실행 전에 안다**
  — 확인 절차와 하나로 합쳐 「N건이 되돌아갑니다」를 보여준다(결정 2·4번,
  `decision-log.md` A-123 ②④)

### 관리자 등급(owner)
- 17개 전부 실행한다
- 운영자가 이미 「작은 것」으로 실행한 되돌리기도 다시 되돌리라고 지시할 수
  있다(구조적으로 막혀 있음 — ④ 「되돌림의 되돌림」 참조. 재실행이 아니라
  **별도 판단**이 필요하다는 뜻)

### 공통
- 도메인·되돌리기 가능 여부로 **거르기**(지금 화면의 클라이언트 필터 관례를 따름)
- 이미 되돌려진 행과 아직인 행을 **구분해 본다**(기존 「되돌려짐」 배지 유지)

## ⑥ 인터랙션

### 목록에서
1. 사람이 목록의 한 행을 본다. **그 행이 되돌릴 수 있는 상태인지는 서버가 이미
   판정해 실어 보낸 값을 그대로 따른다** — 화면이 다시 판정하지 않는다(재고
   입고 선례와 같은 원칙, `_undo_state()` docstring의 경고 그대로).
2. 되돌릴 수 없는 행(이미 되돌림·되돌리기 자체가 없는 행위·등급 부족)은
   그 사실과 사유를 함께 안다 — 안내 없이 그냥 안 되는 상태로 두지 않는다
   (재고 입고의 `undo_note` 관례).

### 실행할 때
1. 사람이 되돌리기를 실행한다.
2. 화면은 그 행의 `log_id`로 **해당 도메인의 되돌리기 경로**를 호출한다 —
   17개 중 어느 것인지, path 인자인지 body 인자인지는 **화면이 도메인을 몰라도
   서버 쪽 매핑이 정한다**(④의 「매핑표가 지금 없다」 문제를 이번에 푼다는 뜻).
3. **관리자 전용 두 도메인**(오픈 단계 설정·판매가 재산정)은 운영자 등급에게
   그 행의 「관리자만」 표시로 실행 불가 사유가 미리 보인다 — 단추 자체는
   1번 원칙대로 비노출이다(결정 3번, `decision-log.md` A-123 ③).

### 성공했을 때
- 그 행에 「되돌려짐」 표시가 붙는다(기존 배지 파생 그대로 — 새 로직 불필요,
  `ref_log_id` 역참조 EXISTS 판정을 그대로 탄다).
- 되돌리기 실행 자체도 **새 기록으로 목록에 나타난다**(기존 원장 관례 그대로).
- 대량 되돌리기의 실제 반영 건수가 «시도 건수»와 다를 수 있다는 사실(④의
  발견)을 화면이 어떻게 다룰지는 미정이다 — **서버가 주는 값을 그대로 표시할지,
  다르다는 사실 자체를 알릴지는 서버 쪽 계산이 먼저 정리돼야 한다.**

### 실패했을 때
- 서버가 준 사유(404/409의 메시지)를 **그대로** 보여준다 — 화면이 사유를
  다시 짓지 않는다(`CLAUDE.md` §실패를 삼키지 않는다와 같은 원칙).
- 경합(조회 시점엔 가능했는데 실행 시점엔 다른 사람이 먼저 처리한 경우)은
  409로 온다 — 이 경우도 사유를 그대로 보여준다.

| 상황 | 화면이 해야 할 일 |
|---|---|
| 조회 등급이 되돌리기 단추를 누름 | **해당 없음** — 단추 자체가 DOM에 없어 누를 수 없다(결정 1번, A-123 ①). API를 직접 두드리면 여전히 403(서버 쪽 방어는 그대로 유지) |

| 이미 되돌려진 행을 다시 시도 | 409 — 서버 사유를 그대로 표시(위 도메인마다 사유 문구가 다르다) |

| 최근 500건/선택 기간 밖의 원본 | 화면에 애초에 안 보인다 — 지금은 상한을 넓히지 않는다(결정 7번, A-123 ⑦). 대신 「되돌릴 수 있는 것만 보기」 필터로 같은 500건 안에 더 먼 과거까지 닿게 한다 |
| 서버가 아직 판정할 수 없는 상태(경합 등) | 「가능」도 「불가」도 지어내지 않고 미판정으로 둔다(`CLAUDE.md` §화면 정직성의 「원천이 아직 답할 수 없는 것은 판정하지 않는다」와 같은 원칙) |
| 되돌리기 자체가 없는 행위(상품 등록·삭제 등) | **단추 자리를 비워 둔다 — 「되돌릴 수 없음」이라고 적지 않는다**(결정 6번, A-123 ⑥. ⚠ 이 행은 2026-08-28 확정 전까지 반대 내용 — 「명시한다」 — 을 적고 있었다, 결정과 어긋나 정정했다) |
| 대량 되돌리기 실행 | 실행 전 「N건이 되돌아갑니다」를 확인 절차와 함께 보여준다(결정 2·4번, A-123 ②④). 실행은 원 이동과 마찬가지로 한 트랜잭션이다 — 부분 성공은 없다(도중 오류면 전체 롤백, `admin_category_mapping.py`·`admin_reprice.py`·`admin_products.py`(bulk-status) 공통 확인) |
| 되돌리기를 또 되돌리기(되돌림의 되돌림) | 구조적으로 막혀 있다 — 되돌림 로그 자신은 원 action명과 다르므로 되돌리기 경로가 「되돌릴 원본 행위가 아니다」로 404를 낸다(17개 전부 원 action명 매칭 방식이라 공통 — ④ 표의 「이중 실행 방지」 열) |

DOM 에도 내보내지 않는다.** | 지금 이 화면엔 등급별로 잠그는 단추가 하나도 없었다(④) — 처음 생기는 경우다. 2026-08-27 요청·승인 화면(ADM-SYS-060, 커밋 `f64bc2a`)에서 같은 모양의 문제를 실제로 겪었다 — Jinja가 조건 없이 렌더하고 JS가 `hidden` 속성만 토글해, 개발자 도구로 `hidden`만 지우면 결재 UI가 열렸다. `{% if is_owner %}`로 서버 렌더 단계에서 가르는 것으로 고친 전례를 그대로 따른다 — 등급별로 단추를 감추는 것이 이 저장소에서 두 번째 사례다 |
| 2 | **둔다 — 실행 전 「N건이 되돌아갑니다」를 보여준다.** | 카테고리 매핑은 한 번에 최대 `MAX_MOVE`건까지 묶인다(`admin_category_mapping.py:43`). **그리고 「N건 복구」가 실제 반영 건수와 다를 수 있다**(이 기획서 190행 발견 — 대상 행이 이미 삭제됐으면 `UPDATE`가 조용히 0건으로 넘어가는데 응답의 `restored`/`moved`는 «시도한» 건수를 그대로 쓴다). 실행 «전» 예상 건수를 보여주면 실행 후 서버가 돌려주는 값과 대조할 수 있다 — 어긋나면 그 자리에서 드러난다 |
| 3 | **단추는 1번 원칙대로 비노출. 다만 그 행에 「관리자만」 표시를 남긴다.** | 6번(되돌리기 없는 행)과 구분이 선다 — 「관리자만」은 다른 사람은 할 수 있어 표시가 «필요»하고, 「되돌리기 없음」은 아무도 못 해 표시가 «불필요»하다. 운영자가 그 행에 단추가 없는 것을 보고 「내 등급 때문인가, 원래 안 되는 것인가」를 물을 수 없어야 한다 |
| 4 | **둔다. 2번과 합친다 — 확인 창 하나에 건수를 담는다.** | 원장을 바꾸는 일이다. 확인 창과 건수 고지를 따로 두면 두 번 멈춘다 — 하나로 합치면 「무엇이 몇 건 되돌아가는지」를 보고 한 번에 정한다 |
| 5 | **도메인 모듈마다 판정 함수를 두고, 활동 기록 API가 그것들을 모은다.** | `_undo_state()`(재고 입고) docstring의 경고 그대로 — 순서·술어가 `undo_inbound()`와 갈라지면 목록이 「가능」이라 말한 건에서 409가 난다. 활동 기록이 17개 조건을 직접 알면 각 도메인이 바뀔 때마다 활동 기록도 따라 고쳐야 하고, **그것이 갈라지는 경로다.** 이 저장소가 정확히 그 병을 두 번 겪었다 — `REASON_TARGET_PATH`(추천 가능 재고 현황)·`admin_ui_home.py`의 `_TARGET_PATH`가 NAV 변화를 스스로 못 알아채 각각 여러 날 낡은 채 있었다(두 파일 자신의 주석에 경위가 남아 있다). 도메인 옆에 판정 함수를 두면 그 파일을 고치는 사람이 판정 함수도 같이 본다 |
| 6 | **단추 자리를 비워 둔다. 「되돌릴 수 없음」이라고 적지 않는다.** | 되돌릴 수 있는 행에만 단추가 있으면 「단추가 없다 = 못 되돌린다」가 자명하다. 매 행에 적으면 목록이 시끄러워진다 — 이 화면은 한 번에 최대 500행을 다룬다. 3번과의 구분은 위 3번 근거 참고 |
| 7 | **지금은 확장하지 않는다. 대신 「되돌릴 수 있는 것만 보기」 필터를 먼저 둔다.** | 상한을 올리면 화면이 무거워진다. 되돌리려고 오는 사람은 「되돌릴 수 있는 것」만 보면 되고, 그 필터를 걸면 같은 500건 안에 훨씬 먼 과거까지 들어온다(되돌림 대상이 전체의 일부이기 때문이다). 그래도 닿지 않으면 그때 상한을 올린다 — 순서가 그렇다 |
