# 요구사항 정의서 — 엑셀 다운로드 관리 (admin2 신규 구축 · 완전 신설)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> **구화면 대응 없음 — 완전 신규.** `api/admin_nav.py`의 LNB 비고 원문이 이미
> 성격을 못 박아 뒀다: *"신설 — 비동기 큐"*. 옮겨올 옛 화면·API·테이블이
> 존재하지 않는다(아래 ④가 그 부재를 실측으로 확인한다).
>
> 작성일 2026-08-13. ④는 **"없다"는 사실 자체가 실측 결과**다(`grep`·
> `requirements.txt`·`api.db.engine`의 `information_schema` 조회로 전수 확인,
> 2026-08-13). 이 화면이 다뤄야 할 데이터 항목은 이 문서가 **요구로 제안**하는
> 것이며, 정확한 테이블·컬럼 설계는 이 문서의 권한 밖(구현 작업)이다.

---

## ① 화면 성격

**관리 화면(신설) — 비동기로 처리되는 대용량 다운로드 요청의 진행 상태를 보고
완료된 파일을 받는 곳.** 지금 이 시스템에는 "요청 → 큐 적재 → 백그라운드 처리
→ 완료 → 다운로드"라는 흐름 자체가 하나도 없다(아래 ④). 이 화면은 그 흐름이
생길 때 **처음으로 서는 비동기 작업 인프라**가 된다 — 즉 이 문서가 다루는
범위는 "다운로드 큐를 관리하는 화면"이지, "어느 목록 화면에 다운로드 버튼을
붙일지"는 포함하지 않는다(아래 비범위).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

지금 관리자가 목록 데이터를 파일로 받으려면 **수단이 없다** — 실측(②):
`mockups/admin/*.html`(백업용 동결분 포함 실화면 전체)에서 "내보내기"·
"다운로드"·"Export" 문구를 검색하면 vendor 라이브러리 파일과 템플릿 잔재
(`_demo-products.html`, 화면으로 치지 않는 파일)만 걸리고, 실제 화면 0건이
이 기능을 갖고 있다. 이 화면이 없으면:

- 대용량 목록(상품 22,840건 등, 아래 ④)을 표 밖에서 다시 보거나 다른
  시스템에 옮길 방법이 없다.
- 설령 어느 목록 화면에 "내보내기" 버튼을 붙이더라도, **그 요청을 동기로
  처리하면** 이미 이 프로젝트가 한 번 겪고 고친 문제(전 행 반환 금지 — 아래
  ④)를 다운로드 버전으로 다시 만든다.
- 요청이 여러 건 쌓였을 때 무엇이 진행 중이고 무엇이 끝났는지 볼 곳이
  없다.

## ④ 데이터 — 지금은 "없다"가 실측 결과다

### 실측 방법

`grep -r`로 `api/` 전체에서 비동기 처리 흔적(Celery·RQ·arq·huey·
`BackgroundTasks`) 검색 + `requirements.txt` 의존성 전수 확인 +
`information_schema.tables`에서 이름에 export·download·job·queue·task가
들어간 테이블 검색 + `openpyxl` 실제 사용 방향(읽기/쓰기) 확인 +
`deploy/popcorn-api.service`·`deploy/nginx-popcorn.conf` 배포 설정 확인.
2026-08-13.

### 없는 것 (전수 확인)

- **비동기 작업 라이브러리 0종**: `requirements.txt`에 Celery·RQ·arq·huey
  없음. 코드 전체에 FastAPI `BackgroundTasks` 사용 0건.
- **다운로드/큐/작업 테이블 0종**: `information_schema.tables`에서 이름에
  export·download·queue·task가 들어간 테이블은 없다. `job`이 들어간 테이블은
  `csv_import_jobs` 1개뿐인데, 이것은 **업로드(적재) 기록**이지 다운로드가
  아니다(아래 "가장 가까운 기존 사례" 참조).
- **파일 쓰기 방향 openpyxl 사용 0건**: `openpyxl`은 `requirements.txt`에
  있지만, 실제 코드에서 부르는 곳은 `api/price_parser.py`
  `openpyxl.load_workbook(...)`(업로드된 단가표 **읽기**) 한 곳뿐이다.
  `Workbook()`으로 새 파일을 **쓰는** 코드는 `api/` 전체에 0건.
- **다운로드 파일 응답 0건**: `StreamingResponse`·`FileResponse`·
  `Content-Disposition` 패턴이 `api/`에 없다(`dash.py`의
  `StreamingResponse`는 SSE 실시간 스트림이며 파일 다운로드가 아니다).

| 컬럼 | 타입 |
|---|---|
| job_id | bigint PK |
| file_name | varchar |
| row_total / row_ok / row_error / row_review | integer |
| status | varchar |
| created_by | bigint |
| created_at | timestamp |
| data_origin | varchar |
| source | varchar |

실측 11행, `row_total` 최대 **24,303**(단일 배치). 이 표는 **"작업" 개념의
선례**이긴 하지만 ① 방향이 반대(들여오기, 내보내기 아님) ② **동기 처리다** —
지금 이 표는 업로드 요청이 이미 끝난 뒤 결과를 기록하는 용도이지, 별도
워커가 큐를 소비하며 채우는 방식이 아니다(위 "없는 것"에서 확인한 대로
비동기 실행 수단 자체가 없다). 그대로 베끼면 "이름만 큐, 실제로는 동기"가
된다.

### 왜 동기 처리로는 안 되는가 — 인프라 실측 근거

- **이 프로젝트가 "전 행 반환 금지"를 이미 한 번 원칙으로 못박았다**
  (`CLAUDE.md`): "목록·검수 큐는 서버 페이지네이션이다(전 행 반환 금지).
  재고 입고 15,259건 + 카탈로그 22,838건을 매 요청 전량 보내고 있었다
  (슬라이스 54)." **다운로드는 정의상 "필터에 맞는 전 행"을 한 파일로
  묶어야 하므로, 화면 페이지네이션과 같은 방식(요청마다 100건만)으로는
  풀리지 않는다** — 그래서 "요청 접수는 즉시, 생성은 별도 처리"로 분리하는
  것 말고는 이 프로젝트가 이미 겪은 문제를 다시 만들지 않을 방법이 없다.
- **API 프로세스가 1개뿐이다**: `deploy/popcorn-api.service`의
  `ExecStart`는 `uvicorn api.main:app`을 **`--workers` 지정 없이** 띄운다
  (기본값 = 워커 1개, 단일 프로세스). `api/main.py`는 관리자·고객 라우터를
  **전부 같은 `FastAPI()` 인스턴스**에 올린다(주문·견적·인계 등 고객
  API도 포함). **동기로 대용량 파일을 만드는 요청 하나가 이 하나뿐인
  프로세스를 붙잡으면, 그 시간 동안 다른 관리자 요청은 물론 고객 견적·결제
  요청까지 함께 멈춘다.**
- **nginx가 120초에서 끊는다**: `deploy/nginx-popcorn.conf`
  `proxy_read_timeout 120s`. 120초를 넘기는 동기 다운로드 요청은 클라이언트
  쪽에서 타임아웃 에러를 받는데, **서버(단일 프로세스)는 이미 시작한 작업을
  멈추지 않고 계속 붙잡고 있어** 다른 요청까지 계속 막힌다 — 사용자는 실패로
  보고 재시도하는데, 서버는 이전 요청을 여전히 처리 중인 상태가 될 수 있다.
- **배포 서버의 쓰기 권한이 좁게 잠겨 있다**: `deploy/popcorn-api.service`는
  systemd 강화 옵션(`ProtectSystem=strict`, `ProtectHome=true`)으로 앱
  프로세스가 파일을 쓸 수 있는 곳을 **`ReadWritePaths=/srv/popcorn-ai/.cache`
  단 한 곳**으로 제한한다(지금 이 폴더는 다나와 원문 캐시가 쓰고 있다 —
  `CLAUDE.md` "원문은 `.cache/`(gitignore)"). **생성될 다운로드 파일도 이
  제약 안에서 저장 위치를 정해야 한다.**
- **실제 규모가 작지 않다**: 상품 22,840건 · 재고 이동 원장 7,771건 ·
  상담 세션 4,419건 · 작업 기록 5,118건(계속 증가) · 기존 최대 단일 배치
  24,303행(`csv_import_jobs` 실측) — "적당히 작아서 동기로도 괜찮다"고
  가정할 근거가 없다.

### 이 화면이 다뤄야 하는 데이터 요구 (제안 — 스키마 확정은 범위 밖)

**필요한 사실**(구현 시 어떤 형태로 저장하든 이 화면이 보여줘야 하는 것):

- 요청 1건이 **무엇을**(어느 목록·어떤 필터 조건) 대상으로 하는지.
- **누가·언제** 요청했는지.
- 지금 **상태**(대기/처리 중/완료/실패/만료 등 — 정확한 상태값 집합은 구현
  시 정의).
- 처리된 **행 수**(완료 후 — 요청 시점엔 알 수 없을 수 있다).
- 완료 시각과 **받는 방법**(다운로드 경로) — 그리고 그 경로가 **누구나
  접근 가능한 정적 URL이면 세션 없이도 남의 데이터를 내려받을 수 있다는
  것**을 이 화면(과 뒤따르는 API)이 반드시 고려해야 한다. 이 시스템은
  이미 "계정 목록 조회조차 owner 전용"처럼 민감도에 따라 열람 등급을
  가르는 관행이 있다(`req-operators-roles.md` ②) — 다운로드 파일은 화면에
  뿌려주는 것보다 **더 많은 데이터를 한 번에, 오프라인으로** 반출하므로
  최소한 같은 수준의 접근 통제가 필요하다.
- 실패 시 **사유**(빈 결과를 성공처럼 보여주면 안 된다 — CANON.md 절대
  규칙 "실패를 삼키지 않는다").
- 파일 **보관 기한**(무한정 쌓아두지 않을 것이라면 언제 지워지는지).

### 쓰는 API · 테이블

**없음.** 이 화면이 구현되려면 최소한 다음이 신설돼야 한다(요구 수준의
나열이며, 정확한 경로·이름·스키마는 이 문서의 권한 밖):

- 큐 상태를 저장할 테이블(위 "필요한 사실" 참조).
- 조회 API(이 화면이 목록을 보여줄 것) + 개별 요청 상태 조회.
- 요청 생성 API(각 소스 목록 화면이 부를 것 — 이 화면 자체가 만드는 것은
  아니다, 비범위 참조).
- 완료된 파일을 내려받는 API(접근 통제 포함).
- 실제로 큐를 소비해 파일을 만드는 백그라운드 실행 수단(현재 0종 — 위
  "없는 것" 참조. 무엇을 도입할지는 이 문서의 권한 밖).

## ⑤ 기능 (동사) — 이 화면에 요구되는 최소 동작

- 지금까지 접수된 다운로드 요청을 상태별로 본다(대기/처리 중/완료/실패 등).
- 각 요청이 무엇을(대상·조건), 누가, 언제 요청했는지 본다.
- 완료된 요청의 파일을 받는다.
- 실패한 요청의 사유를 본다.
- (필요 시) 오래된 완료 파일이 언제 만료되는지 본다.

## ⑥ 인터랙션

- **이 화면 자체는 요청을 발생시키지 않는다**(비범위 참조) — 각 목록
  화면에 붙을 "내보내기" 버튼이 요청의 발신원이며, 이 화면은 이미 발생한
  요청들의 상태를 보여주는 창구다. 다만 지금은 발신원이 하나도 없으므로,
  이 화면이 먼저 서는 동안(발신 버튼이 붙기 전) "지금 요청이 하나도 없다"는
  것이 정상 상태여야 한다.
- 처리 중인 요청은 완료될 때까지 상태가 바뀌는 것을 다시 조회해 확인할
  수 있어야 한다(즉시 완료를 가정하지 않는다 — 비동기라는 성격 자체가
  "지금 당장은 모른다"를 전제한다).
- 실패한 요청은 재시도할 수 있는지, 아니면 새로 요청해야 하는지는 이
  문서가 정하지 않는다(사장님 결정 필요 지점 참조).

## ⑦ 상태 · 예외

- **요청 0건**(지금의 실제 상태 — 발신 버튼이 아직 없다): 오류가 아니라
  정상 초기 상태로 다뤄야 한다.
- **처리 중 실패**: 사유를 화면이 감추지 않는다(CANON.md "실패를 삼키지
  않는다").
- **완료 후 파일이 만료·삭제된 경우**: "완료했지만 지금은 받을 수 없다"는
  상태를 별도로 구분해야 한다(완료 자체를 안 한 것처럼 보이면 안 된다).
- **대용량 요청이 처리 중 서버 재시작과 겹치는 경우**: 단일 프로세스
  구조(위 ④)에서는 배포·재시작이 진행 중이던 작업을 끊을 수 있다 — 이
  경우 "실패"로 정직하게 남아야 하며, 재시작 전 상태로 조용히 "완료"
  처리되면 안 된다.
- **권한 없는 사용자가 완료 파일에 접근 시도**: 위 ④에서 밝힌 접근 통제
  요구가 지켜지지 않으면 이 항목 자체가 성립하지 않는다 — 이 화면의
  요구사항에 접근 통제가 반드시 포함돼야 하는 이유다.

## 비범위 — 이 화면이 하지 않는 일

- **어느 목록 화면에 "내보내기" 버튼을 붙일지 정하는 일** — 상품 관리
  (22,840건)·작업 기록(5,118건)·재고 이동 원장(7,771건) 등이 후보로 보이지만,
  우선순위·범위는 이 문서가 정하지 않는다(각 화면의 요구사항 소관이거나
  별도 결정 사안).
- **비동기 실행 수단(큐 라이브러리·워커 프로세스 등) 도입 자체** — 이는
  인프라/백엔드 결정이며 이 문서는 "왜 필요한지"의 근거만 남긴다(위 ④).
- **파일 형식(xlsx/csv) 확정** — LNB 명칭은 "엑셀"이지만, 어느 목록이든
  같은 큐를 공유한다면 형식 선택 자체가 요청 시점의 파라미터일 수 있다.
  이 문서는 형식을 못박지 않는다.
- **`csv_import_jobs`(업로드 이력) 화면과의 통합 여부** — 이름이 비슷하고
  "작업 목록"이라는 성격이 겹치지만, 방향(들여오기 vs 내보내기)과 처리
  방식(동기 vs 비동기)이 다르다. 통합할지 별개로 둘지는 이 문서가 정하지
  않는다.

## 사장님 결정이 필요한 지점

1. **어느 화면부터 "내보내기" 발신 버튼을 붙일지, 그리고 그 우선순위.**
   이 화면은 발신원이 하나도 없어도 서 있을 수 있지만, 실사용 가치는
   발신원이 생겨야 발생한다.
2. **비동기 실행 수단을 무엇으로 도입할지**(예: FastAPI `BackgroundTasks`로
   단순화할지, 별도 워커 프로세스·큐를 둘지) — 단일 프로세스·systemd
   강화 제약(위 ④) 안에서 선택지가 갈린다. 이는 개발팀의 기술 선택이지만,
   "동기로 충분하다"는 선택지는 위 실측 근거로 배제하는 것이 맞다고 본다.
3. **완료 파일의 보관 기한과 접근 통제 수준.** 상품 마스터처럼 상대적으로
   덜 민감한 목록과, 회원·매입가처럼 민감한 목록이 같은 큐를 공유한다면
   접근 등급을 파일 단위로 달리 가져가야 하는지 결정이 필요하다.
4. **실패한 요청의 재시도 방식**(자동/수동, 몇 회까지) — 이 문서는 "사유를
   감추지 않는다"까지만 요구하고 재시도 정책은 열어 둔다.
