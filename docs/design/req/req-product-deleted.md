# 요구사항 정의서 — 삭제 상품 조회 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> **이 화면은 완전히 신설이다** — 대응하는 구화면이 없다. `api/admin_nav.py`의 비고가
> "신설"이라 못박고, `docs/design/admin-ia-draft-2026-08-09.md`(✅ 확정, decision-log
> UX-34, 구 UX-14) 6번 행은 "도매꾹 `myitemdelete`"를 이름 유래로 적는다 — **실제 연동이 아니라
> 설계 참고 출처일 뿐이다**(실측: `api/` 어디에도 도매꾹 API 클라이언트 코드가 없다).
>
> **화면뿐 아니라 "이 상태만 골라 보여주는 조회 API" 자체가 아직 없다** — 아래 ④에서
> 상세히 밝힌다. 이 문서는 그 사실을 감추지 않고 요구사항에 그대로 반영한다.
>
> 작성일 2026-08-13. ④의 수치는 **그 시각의 실측 스냅샷**이다 — 화면은 이 문서에 적힌
> 숫자가 아니라 서버 응답만 써야 한다. 재측정은 `.venv/Scripts/python`으로
> `api.db.engine`을 통해 `products`·`admin_operator_activity_logs`를 다시
> SELECT(읽기 전용)하면 된다.

## ① 화면 성격

**조회 화면이자, 좁은 범위의 되돌림·정리 작업 화면이다.** 순수 보고서는 아니다 —
"복원"·"완전 삭제" 같은 실제 쓰기 동작을 갖는다. 다만 **상품 정보 자체를 고치는 편집
폼은 아니다**: 이름·가격·사양 같은 필드를 고치려면 "상품 관리"(ADM-PRD-010)로 넘어가야
한다 — "상품 관리가 상품 작업의 유일한 편집 진입점"이라는 기존 원칙을 이 화면도 따른다
(이 화면은 상태 전이만 다룬다).

- 조회는 로그인만 되면 등급 무관(viewer 이상 — 아래 ④·⑦에서 밝히듯 이 화면이 쓸 조회
  경로 자체가 신설이므로, 권한 수준은 "상품 관리" 목록(`GET /api/admin/products`,
  viewer 이상)과 같은 선례를 따르는 것이 자연스럽다).
- 복원·완전 삭제 같은 쓰기 동작은 **기존 상품 관리 API(아래 ④)를 그대로 쓰면 operator
  이상**이다 — "상품 분류 관리"(owner 전용)와 달리 상품 자체의 상태 변경·삭제는 지금
  operator 등급도 할 수 있다(실측: `api/admin_products.py`의 수정·병합·삭제 엔드포인트
  어디에도 owner 전용 검사가 없다). 이 비대칭이 "완전 삭제"처럼 되돌릴 수 없는 동작에도
  그대로 적용해도 되는지는 사장님 결정이 필요하다(아래).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **삭제 대기 상태(`products.status='삭제대기'`)로 내려간 상품을 따로 찾아볼 방법이
  없다.** 지금 "상품 관리" 목록(ADM-PRD-010)은 상태를 4개 버킷(추천가능/검수대기/
  재고없음/가격검토)으로만 나누는데, **`삭제대기`는 이 중 어디에도 전용 자리가 없고
  "검수 대기" 버킷에 실제 검수 대상 상품들과 섞여 들어간다**(실측:
  `api/admin_products.py` `derive_status()` — `review_required_yn`이 참이면 무조건
  `review`로 분류되고, 편입(병합) 처리 시 이 플래그를 같이 켠다. 106행 주석이 이
  섞임을 스스로 "단종·삭제대기 안전망"이라 표현한다). 즉 지금은 삭제대기 상품이
  사양 검수가 필요한 상품과 구분 없이 검수 목록에 섞여 있다.
- **중복 상품 정리(편입, "상품 관리"의 `POST /products/{code}/merge`)가 만든 결과를
  한눈에 되짚을 곳이 없다.** 편입은 원본을 남기고 중복을 삭제대기로 내리는 방식으로
  설계됐는데(원장 보존·되돌리기 가능), 그 결과물을 모아 보는 화면이 없으면 "편입해
  둔 것들이 지금 몇 건이고 뭐가 남았는지"를 아무도 확인할 수 없다.
- **완전 삭제(하드 삭제)로 갈 대상을 고르는 자리가 없다.** 상품 완전 삭제
  (`DELETE /api/admin/products/{code}`)는 이미 존재하지만, 지금은 이걸 부를 "삭제
  후보 목록"이 없어 상품 코드를 아는 사람만 개별로 부를 수 있다.

## ④ 데이터

### 실측 방법

`api.db.engine`으로 `products`·`admin_operator_activity_logs`를 직접
SELECT(읽기 전용). 아래는 2026-08-13 스냅샷.

### ⚠ 이 화면 전용 "목록 조회" API가 지금 없다 — 가장 먼저 밝혀야 할 사실

`products.status`는 4개 값(판매중·품절·단종·삭제대기, `EDITABLE`/`STATUS_OK` 상수로
DB CHECK 없이 애플리케이션 레벨에서 관리)을 갖는 NOT NULL 컬럼이다. 그런데 지금
`GET /api/admin/products`의 `status` 파라미터는 **이 원본 값이 아니라 파생 버킷**
(`ok`/`review`/`oos`/`price`)만 받는다 — 원본 `status='삭제대기'`를 직접 필터링하는
경로가 어디에도 없다(실측: 코드 전체에서 `status='삭제대기'`를 WHERE 절에 쓰는
API가 없다). **즉 이 화면이 요구하는 가장 기본적인 조회 자체가 신설 대상이다** —
데이터가 없는 게 아니라, 그 값만 골라 돌려주는 API가 없다.

### 쓰는 테이블(신설 조회가 읽어야 할 컬럼)

| 테이블 | 관련 컬럼 |
|---|---|
| `products` | `product_code`·`sku`·`product_name`·`part_type`·`status`(='삭제대기' 필터)·`stock_qty`·`sale_price`·`updated_at` |
| `admin_operator_activity_logs` | `action`(`product_merge`·`상품 상태 일괄 변경`·`product_edit`)·`detail`(JSONB) — **"왜 삭제대기가 됐는지"를 알려면 이 로그를 함께 봐야 한다(아래 참고)** |

### 실측 현재 상태 (2026-08-13)

- `products.status` 분포: **판매중 7,602 · 품절 15,238 · 단종 0 · 삭제대기 0**
  (전체 22,840건). **지금 실데이터 기준 이 화면은 빈 상태로 열린다.**
- 그런데 관련 기능은 존재하고 과거에 호출된 적이 있다 — 활동 로그 실측:
  `product_merge` 2건 · `product_merge_undo` 1건 · `product_delete` 6건. 대상
  상품코드(20489106~20489108)를 대조하면 전부 초 단위 간격으로 "생성→편입→(일부는
  즉시 되돌림)→완전 삭제"가 이어진 패턴이고, 코드 형식(`P-91xx`,
  `register_product()`의 `2048{num}` 채번 규칙과 일치)도 자동 생성 상품과 일치한다
  — **실제 운영에서 상품을 정리한 흔적이 아니라 회귀 테스트가 남긴 흔적으로 보인다**
  (개발 서버 특성상 부작용 있는 검사가 허용됨, `CLAUDE.md` 참고). 즉 **지금까지 이
  기능이 실제 업무에서 쓰인 사례는 실측되지 않는다** — 화면이 없다고 업무가 막힌 게
  아니라, 업무 자체가 아직 이 경로를 타지 않았다는 뜻이다.

### 삭제대기로 가는 경로가 셋이고, 되돌리는 API도 각각 다르다(실측, 매우 중요)

| 경로 | 만드는 API | 되돌리는 API | 비고 |
|---|---|---|---|
| ① 중복 편입 | `POST /api/admin/products/{code}/merge` | `POST /api/admin/products/merge/undo/{log_id}` | 재고·공급처를 원본으로 옮기고 중복을 삭제대기로. 로그 action `product_merge`인 것만 되돌릴 수 있다 |
| ② 단건 상태 수정 | `PATCH /api/admin/products/{code}` `{changes:{status:'삭제대기'}}` | `POST /api/admin/products/undo/{log_id}` | 로그 action이 정확히 `product_edit`인 것만 되돌릴 수 있다 |
| ③ 일괄 상태 변경 | `POST /api/admin/products/bulk-status` `{status:'삭제대기', product_codes:[...]}` | `POST /api/admin/products/bulk-status/undo` | 로그 action이 정확히 `상품 상태 일괄 변경`인 것만 되돌릴 수 있다 |

**세 경로 모두 결과(상태='삭제대기')는 같지만, 어느 API로 되돌려야 하는지는 그 상품이
"어느 경로로 삭제대기가 됐는지"에 달려 있다.** 지금은 이 판정(이 상품이 셋 중 무엇으로
내려갔나)을 한 번에 알려주는 API가 없다 — 상품별로 관련 활동 로그를 시간 역순으로
찾아 판정해야 한다. **이 화면이 새로 만들어야 하는 조회 로직의 핵심이 여기 있다.**

### 완전 삭제(하드 삭제) — 별도 경로, 되돌릴 수 없음

`DELETE /api/admin/products/{code}?force=` — 삭제대기 상태와 무관하게 어떤 상품에도
쓸 수 있는 별개 기능이다.

- **`order_items`(주문 이력)가 하나라도 있으면 `force`와 무관하게 항상 409로 거부된다**
  (`BLOCK_DELETE`, 실측: 과거 주문서가 깨지는 것을 막는 유일한 무조건 차단선).
- 그 외 8개 테이블(재고 원장·근거 클릭·부품 교체 이력·찜·가격 이력·재고 예약 등,
  `CHECK_REFS`)에 참조가 있으면 409로 **경고**하되, `force=true`면 통과해 **그 참조
  행을 전부 함께 지운다**(실측: `stock_reservations`·`promo_click_logs`·
  `member_favorites`·`product_price_history`·`stock_movements`·
  `supplier_product_map`·`product_sourcing_quotes`·
  `product_sourcing_match_candidates`·`product_supplier_prices`·`product_reviews`·
  `product_specs`·`swap_event_logs`를 순서대로 DELETE한 뒤 `products` 행 자체를
  지운다). **`stock_movements`(재고 원장)까지 함께 사라진다** — 이 프로젝트가 다른
  곳에서는 "재고는 원장 밖에서 바뀌지 않는다"·"되돌림은 삭제가 아니라 역방향 전이"를
  절대 규칙으로 두는 것과 결이 다른, **유일하게 원장을 실제로 지우는 경로**다(아래
  "사장님 결정 필요" 참조).
- 이 동작에는 **되돌리기가 없다**(하드 삭제이므로 구조적으로 불가능).

## ⑤ 기능 (동사)

- 삭제대기 상태인 상품 목록을 본다(신설 조회 — 위 ④).
- 각 상품이 **어느 경로로 삭제대기가 됐는지**(편입/단건 수정/일괄 변경) 본다 — 편입인
  경우 어느 원본 상품으로 옮겨졌는지도 함께 본다.
- 편입으로 내려간 상품을 원래대로 되돌린다(재고·공급처·상태를 편입 이전으로 복원).
- 직접 상태 변경(단건·일괄)으로 내려간 상품을 판매중/품절로 되돌린다.
- (신중하게) 삭제대기 상품을 완전히 삭제한다 — 주문 이력이 없는 경우에 한해.
- 이 상품의 전체 상세(사양·가격·공급처 등)를 보려면 "상품 관리" 상세로 넘어간다.

## ⑥ 인터랙션 — 입력 · 선택 · 저장 · 이동의 흐름과 결과

- 목록의 각 행은 "왜 삭제대기인가"에 따라 되돌리기 동작이 달라진다 — 화면이 그 경로를
  먼저 판정해 알맞은 되돌리기 버튼(그리고 그 결과로 무엇이 함께 복원되는지: 편입이면
  재고·공급처까지, 단순 상태변경이면 상태값만)을 보여줘야 한다. 판정할 수 없는 경우
  (예: 오래돼 활동 로그가 없거나, 세 로그 중 어느 것과도 안 맞는 경우)는 "왜 그런지
  모른다"는 사실 자체를 감추지 않고 밝혀야 한다(값을 지어내지 않는다).
- 되돌리기를 실행하면: 그 상품은 더 이상 이 목록에 없어야 한다(상태가 삭제대기를
  벗어났으므로). 이미 되돌려진 기록을 다시 되돌리려는 시도는 409로 막힌다(각 되돌리기
  API가 이미 이 가드를 갖고 있다).
- 편입으로 내려간 상품은 "이 상품으로 옮겨졌습니다"라는 원본 상품 링크가 함께 보여야
  한다(상품 관리 상세로 이동).
- **완전 삭제는 실행 전에 무엇이 함께 사라지는지(재고 원장·가격 이력·찜 등 몇 건씩)를
  먼저 보여줘야 한다** — 지금 API(`DELETE .../{code}`)는 참조가 있으면 우선 409로
  그 목록(`refs`: 테이블별 건수)을 돌려주므로, 이 응답을 먼저 사람에게 보여준 뒤
  `force=true`로 다시 확인받는 2단계 흐름이 자연스럽다. 주문 이력이 하나라도 있으면
  그 자리에서 아예 막혀야 한다(재시도 여지 없음 — 위 ④ "무조건 차단선").
- 이 화면은 상품명·가격 등을 직접 고치지 않는다 — 그런 수정이 필요하면 "상품 관리"
  상세(`/admin2/products?code=`)로 이동해야 한다.

## ⑦ 상태 · 예외

- **빈 목록**: 지금 실데이터 기준 정상적으로 빈 상태다(위 ④, 실측 0건). 빈 상태 문구는
  "삭제 대기 중인 상품이 없습니다"처럼 **이 기능이 고장난 것이 아니라 지금 그런 상품이
  없다는 사실**을 정확히 전달해야 한다.
- **경로 판정 불가**: 삭제대기 상품인데 세 가지 알려진 경로(편입/단건수정/일괄변경) 중
  어느 활동 로그와도 대응이 안 되는 경우(예: 로그가 소급 정리됐거나, 이 셋 외의 방법
  — 예를 들어 카탈로그 재적재의 `status` 갱신 — 으로 우연히 그 값이 들어간 경우)를
  화면이 처리할 수 있어야 한다. 이 경우 되돌리기 버튼을 감추거나, "이 상품은 자동으로
  되돌릴 방법을 찾지 못했습니다 — 상품 관리에서 직접 상태를 바꿔야 합니다"로 안내해야 한다
  (침묵 금지).
- **권한 없음**: 미로그인 401 "로그인이 필요합니다". 되돌리기·완전 삭제 시도는 최소
  operator 등급 필요 — viewer가 시도하면 403 "권한이 부족합니다(필요: operator,
  현재: viewer)".
- **이미 되돌려진 기록**: 같은 편입/수정/일괄변경을 다시 되돌리려 하면 409(각 API가
  이미 처리).
- **완전 삭제 — 주문 이력 있음**: 항상 409("… 이 있어 지울 수 없습니다 — 편입하거나
  '삭제대기'로 내려야 합니다") — 이 경우 상품은 이미 삭제대기 상태이므로 이 안내
  문구 자체가 이 화면 맥락에서는 다소 어색하다는 점을 감안해야 한다(원 문구는 "상품
  관리"에서 막 삭제를 시도하는 맥락으로 쓰여 있다 — 이 화면에서 재사용할 때 문구
  조정이 필요할 수 있다).
- **완전 삭제 — 다른 참조만 있음**: 409로 참조 목록을 먼저 보여주고, `force=true`
  재요청 시에만 실행된다(경계값: 참조가 정확히 0건이면 바로 삭제된다 — 이 경우에도
  "정말 삭제할지" 확인은 화면 쪽 책임이다).
- **동시 정리**: 두 사람이 같은 상품을 동시에 되돌리거나 삭제하려 하면 먼저 도착한
  요청이 이기고 뒤 요청은 404(이미 없음) 또는 409(이미 처리됨)를 받는다 — 침묵하면
  안 된다.

## 비범위 — 이 화면이 하지 않는 일

- **상품 정보(이름·가격·사양·공급처)를 직접 고치지 않는다** — "상품 관리" 소관.
- **중복 편입 자체를 새로 시작하지 않는다**(어떤 상품을 어디로 합칠지 고르는 것은
  "상품 관리" 상세의 닮은 상품 찾기·편입 기능 소관) — 이 화면은 **이미 내려간 것**을
  다루는 사후 화면이다.
- **`단종` 상태는 이번 범위에 포함하지 않는다**(실측 0건이며, 개념상 "삭제 대상으로
  내려간 것"과 다르다 — 아래 결정 필요 참조).

## 사장님 결정 필요 지점 (임의로 정하지 않았다)

1. **완전 삭제(하드 삭제)를 이 화면에 넣을지, 넣는다면 권한을 강화할지.** 지금 API
   (`DELETE /api/admin/products/{code}?force=true`)는 operator 등급이면 실행할 수
   있고, 실행하면 `stock_movements`(재고 원장)를 포함한 참조 테이블들이 **실제로
   지워진다** — 이 프로젝트가 다른 모든 곳에서 지키는 "원장은 지우지 않고 역방향
   전이로 되돌린다" 원칙과 유일하게 어긋나는 경로다. "상품 분류 관리"처럼 owner
   전용으로 강화할지, 2단계 확인(문장 재입력 등, 텔레그램 승인과 같은 방식)을 추가로
   요구할지, 아니면 지금 수준(operator + `force` 파라미터 확인)을 그대로 둘지.
2. **경로 판정 로직을 신규로 만들 것을 이 문서가 요구하는데(④·⑥), 그 판정에 실패하는
   경우(로그 소실·제3의 경로)를 얼마나 폭넓게 허용할지.** 되돌리기를 아예 막을지,
   "상태만 판매중으로 되돌리기"라는 더 단순한 대안 동작을 항상 곁들일지.
3. **화면 ID(②)를 `ADM-PRD-060`으로 확정할지**, 다른 번호 체계(예: 신설 축이니
   `ADM-DEL-010` 같은 새 접두어)를 쓸지.
4. **`단종`(discontinued) 상태를 이 화면에 함께 포함할지.** 이름상 "삭제 상품"과는
   결이 다르지만(단종은 편입·정리와 무관하게 그냥 더 안 파는 상품), 운영자 입장에서는
   "지금 안 팔리는 상품 모아보기"로 한 화면에서 같이 보고 싶을 수 있다. 지금은 둘 다
   0건이라 실사용 압력으로 판단하기 어렵다.
