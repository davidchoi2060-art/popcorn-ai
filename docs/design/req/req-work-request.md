# 요구사항 정의서 — 요청 · 승인 (admin2 신규)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). **화면 설계는 사장님이
> 이 문서를 입력으로 하신다**(2026-08-26 사장님: *"UI기획서를 정리해주면 내가
> 화면설계서를 만들어줄께"*).
>
> 작성일 2026-08-26. ④의 수치는 그 시각의 실측 스냅샷이다 — 화면은 이 문서의
> 숫자를 박지 않는다.

---

## ① 화면 성격

**요청 접수 · 결재 화면.** 세 사람이 한 자리를 본다.

```
직원(운영자)   화면을 쓰다 불편한 것을 캡처와 글로 올린다
하네스(AI)     읽고 판단한다 — 작은 것은 바로 고치고 결과를 남기고,
                              큰 것은 사장님 결재로 올린다
사장님(owner)  승인 · 반려 · 보류를 정한다
```

지금은 이 흐름이 **파일**(`OWNER-DECISIONS.md`·`docs/open-items.md`)에 있어 직원이
쓸 수 없다. 사장님과 하네스만 본다.

## ② 제목 · 화면 ID · 경로

| 항목 | 값 | 근거 |
|---|---|---|
| 화면 라벨 | **요청 · 승인** (제안) | 「요구사항」은 우리 안에서 «요구사항 정의서»를 뜻해 겹친다. 직원이 쓰는 말로 「요청」이 맞다고 본다 — **확정은 사장님** |
| 화면 ID | **ADM-SYS-060** (제안) | 「시스템」 그룹의 다음 번호. `docs/decisions/admin-identity.md` 실측: SYS-010 오픈단계 · 020 운영자 · 021 로그인 · 022 내정보 · 030 작업기록 · 040 일괄등록이력 · 050 엑셀다운로드 |
| 경로 | **/admin2/requests** (제안) | |
| LNB 위치 | 「시스템」 그룹 (제안) | 다만 직원이 매일 쓰는 자리라 **최상위가 나을 수도** 있다 — 사장님 판단 |

**⚠ 새 그룹을 만들지, 시스템 하위에 둘지가 첫 결정이다.** 직원이 하루에 여러 번
쓸 화면이면 시스템 그룹 안쪽은 찾기 어렵다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

**직원이 본 것이 우리에게 닿을 길이 없다.** 지금 경로는 셋뿐이고 전부 사장님을 거친다:
사장님이 직접 말씀하시거나, 사장님이 캡처를 보내시거나, 우리가 스스로 발견하거나.

운영 직원이 늘면(2026-08-26 한 명 합류) 그 사람이 본 것이 가장 정확한 재료인데
받을 자리가 없다. 오늘만 해도 「글자가 작다」는 직원 얘기가 사장님을 거쳐 왔다.

또한 **하네스가 무엇을 고쳤는지 직원이 모른다.** 올린 것이 어떻게 됐는지 그 자리에서
보이지 않으면 다시 올리거나, 안 올리게 된다.

## ④ 데이터

### 새로 만들어야 하는 것

기존 표로는 안 된다 — **실측 근거:**

| 후보 | 왜 안 되나 |
|---|---|
| `admin_operator_activity_logs` | **「지금 상태」 컬럼이 없다.** append-only 원장이라 상태를 알려면 로그를 되짚어야 한다 |
| `dash_memos` | 스레드·상태 컬럼 없음. 1회 소비형 큐다(`used_at`/`used_count`) |
| `product_reviews` | 상품 사양 전용. 성격이 다르다 |

**그래서 새 표 둘이 필요하다:**

```
요청           request_id · 제목 · 본문 · 올린 사람 · 올린 시각
               상태 · 대상 화면(선택) · 급함 정도(선택)
               판정(하네스가 「작은 것/큰 것」 중 무엇으로 봤나)
               처리 결과 · 처리 시각 · 처리한 주체

댓글           comment_id · request_id · 쓴 주체(직원/하네스/사장님)
               내용 · 시각
```

### 캡처를 어디에 저장하나 — 이미 있는 방식을 쓴다

⚠ **배포 서버는 파일을 거의 못 쓴다.** 실측 확인:
```
deploy/popcorn-api.service
  ProtectSystem=strict
  ReadWritePaths=/srv/popcorn-ai/.cache      ← 여기 한 곳뿐
```

**「내 정보」 프로필 사진이 이미 이 제약을 피해 간다** — `api/admin_profile_photo.py`:

```
저장     Postgres BYTEA (admin_operator_photos.bytes) — 디스크를 안 쓴다
크기     1MB. Content-Length 선검사 + 스트림 중 초과 즉시 끊음
형식     파일 «앞머리»(매직넘버)로 판정 — JPEG/PNG/WebP만
         SVG 는 명시적으로 거부(스크립트가 숨을 수 있다)
```

**같은 방식을 캡처에 그대로 쓴다.** 새로 궁리하지 않는다.

**⚠ 다만 1MB는 화면 캡처에 빠듯할 수 있다.** 1920×1080 PNG가 흔히 1~3MB다.
- 브라우저에서 줄여 올릴지(화질 손실)
- 한도를 올릴지(예 3MB — DB가 커진다)
- **사장님 판단이 필요하다**

**→ 확정(2026-08-27): 3MB.** 실제로 직원이 화면 캡처를 올리다 1MB 한도에 막힌
사례가 나와 위 우려가 맞았다. `api/admin_requests.py`의 `CAPTURE_MAX_BYTES` 기본값을
3MB로 올렸다(줄여서 올리는 방식은 채택하지 않았다 — DB가 커지는 쪽을 감수한다).

### 상태값

**⚠ 기존 「반려」는 제대로 안 돼 있다.** 실측:
```
product_reviews 의 반려 = review_status '보류' + detail 에 「[반려 사유: …]」 텍스트
→ 반려와 보류를 «셀 수 없다». 실제로 쓴 적 0건
```

새 화면에서는 **반려를 별도 상태로** 둔다:

```
접수      직원이 올림. 아직 아무도 안 봄
검토      하네스가 읽고 판단 중
처리      하네스가 «작은 것»으로 보고 바로 고침 → 결과가 붙는다
결재대기  하네스가 «큰 것»으로 보고 사장님께 올림
승인      사장님이 하라고 함 → 하네스가 고친다
반려      사장님이 안 한다고 함 (사유 필수)
보류      나중에 다시 본다 (사유 선택)
완료      고치고 배포까지 끝남
```

### 권한 — 실측

`api/auth.py`의 기본 규칙:
```
GET 류        viewer(조회) 이상
그 밖의 쓰기   operator(운영자) 이상
OWNER_WRITE_PREFIXES 에 등록된 경로 + 쓰기   owner 만
```

그러므로:
- **등록·댓글은 운영자 등급이면 된다** — 새 직원이 운영자 등급이다(2026-08-26 확정)
- **승인·반려·보류는 owner 전용** — 이 경로를 `OWNER_WRITE_PREFIXES`에 넣어야 한다
- ⚠ **안 넣으면 운영자도 자기 요청을 승인할 수 있다**

### 지금 인원 (2026-08-26 실측)

```
운영자 계정 18명 (활성 14 · 정지 4)
등급 분포   owner 15 · operator 1 · viewer 2
```
⚠ **owner 가 15명이다.** 승인 권한이 owner 전용이면 15명이 승인할 수 있다.
**사장님만 승인하시려면 등급 정리가 먼저**다 — 이 화면의 범위 밖이지만 함께 봐야 한다.

## ⑤ 기능

### 직원(운영자)이 할 수 있는 것
- 요청 **등록** — 제목·본문·캡처(여러 장)·대상 화면(선택)
- 자기가 올린 것 **목록으로 보기** · 상태 확인
- **댓글 달기** — 하네스가 물으면 답한다
- 자기 요청 **취소** (아직 처리 전인 것만)

### 하네스(AI)가 할 수 있는 것
- 요청 읽고 **판단 기록** — 「작은 것」/「큰 것」
- **댓글로 답하기** — 「이렇게 고치겠습니다」 또는 「이건 사장님 결정이 필요합니다」
- 작은 것은 **바로 고치고 결과 남기기**
- 큰 것은 **결재 올리기**

### 사장님(owner)이 할 수 있는 것
- **승인 · 반려 · 보류** (반려는 사유 필수)
- 하네스가 「작은 것」으로 보고 이미 고친 것도 **되돌리라고 지시**
- 전체 목록 보기 · 상태별 거르기

### 공통
- 상태·올린 사람·대상 화면으로 **거르기**
- 처리된 것과 안 된 것 **나눠 보기**

## ⑥ 인터랙션

### 올릴 때
1. 「요청 등록」 → 제목·본문 입력
2. 캡처 붙이기 — **화면 캡처를 붙여넣기(Ctrl+V)로 올릴 수 있으면 가장 좋다**
   (직원이 캡처 → 파일 저장 → 찾아서 올리기를 안 해도 된다)
3. 대상 화면 고르기(선택) — 목록은 `admin_nav.py`에서 온다
4. 등록 → 상태 **「접수」**

### 하네스가 볼 때
- 새 요청이 있으면 **알림**이 필요하다
  ⚠ **어떻게 알릴지가 미정이다** — 지금 하네스는 사장님 메시지로만 깨어난다.
  작업 현황판의 「말 걸기」 경로를 쓸 수 있는지 확인이 필요하다

### 결재할 때
- 결재 대기만 모아 보기
- 승인 → 하네스가 고침 → 상태 **「완료」**로 자동 전이
- 반려 → **사유를 반드시** 적는다

### 처리 결과가 그 자리에 남는다
- 무엇을 고쳤는지 · 언제 배포됐는지 · 커밋이 무엇인지
- **직원이 자기가 올린 것이 어떻게 됐는지 안 물어봐도 안다**

## ⑦ 상태 · 예외

| 상황 | 화면이 해야 할 일 |
|---|---|
| 요청이 하나도 없음 | 「아직 등록된 요청이 없습니다」 · 등록 단추를 눈에 띄게 |
| 캡처가 한도(3MB, 2026-08-27 확정)를 넘음 | **올리기 전에** 알린다. 다 올린 뒤 거부하면 시간을 버린다 |
| 캡처 형식이 아님(SVG·PDF 등) | 무엇이 되는지 알린다 |
| 조회 등급이 등록을 시도 | 403 · 「등록은 운영자 등급부터 가능합니다」 |
| 운영자가 승인을 시도 | 403 · 「승인은 관리자만 가능합니다」 |
| 반려하며 사유를 안 씀 | 막는다 — 사유 없는 반려는 다음에 되짚을 수 없다 |
| 하네스가 고치다 실패 | 상태를 「완료」로 만들지 않는다. **실패 사유를 그 자리에** |
| 이미 처리된 것을 또 처리 | 막는다 |
| 오래 방치된 요청 | **며칠 지난 것을 눈에 띄게** — 조용히 묻히면 안 올리게 된다 |

## 사장님이 정하셔야 하는 것

화면을 그리시기 전에 이 다섯이 정해져야 합니다.

| | 무엇 | 왜 |
|---|---|---|
| 1 | **메뉴 위치** — 시스템 하위 / 최상위 | 직원이 매일 쓰면 안쪽은 찾기 어렵다 → **확정(2026-08-27): 시스템 하위** |
| 2 | **화면 이름** — 「요청 · 승인」이 맞는지 | 「요구사항」은 우리 안에서 다른 뜻으로 쓰인다 |
| 3 | **캡처 크기 한도** — 1MB / 3MB / 줄여서 올리기 | 1MB는 화면 캡처에 빠듯하다 → **확정(2026-08-27): 3MB** |
| 4 | **승인 권한** — 지금 owner 가 15명이다 | 사장님만 승인하시려면 등급 정리가 먼저다 → **그대로 둔다(2026-08-27 사장님 판단) — 등급 정리는 이 화면 범위 밖** |
| 5 | **하네스에게 어떻게 알릴지** | 지금은 사장님 메시지로만 깨어난다 → **확정(2026-08-27): 등록 시 DB 알림 큐**(`harness_notify_queue`, 0071) — `POST /api/admin/dash/say` 의 로컬 파일 큐는 배포 서버가 못 쓴다(systemd `ProtectSystem=strict`)는 사실이 뒤늦게 드러나 DB 로 우회했다. 댓글 · 취소는 알리지 않는다(너무 잦은 알림은 무시된다) |

## 이 문서가 정하지 않은 것

- 배치·색·컴포넌트 — **사장님 화면 설계서의 몫**
- 「작은 것 / 큰 것」의 경계 — 하네스가 판단하되, 그 기준은 별도로 적는다
- 알림 수단 — 위 5번
- 기존 `OWNER-DECISIONS.md`·`docs/open-items.md`를 이 화면으로 옮길지 —
  옮기면 파일이 사라지고, 안 옮기면 두 곳이 된다. **별도 판단**
