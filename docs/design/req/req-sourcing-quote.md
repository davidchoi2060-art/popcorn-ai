# 요구사항 정의서 — 매입 견적(용산) (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> **대상은 admin2 신규 구축이다 — 구 `mockups/admin/sourcing.html`을 옮기는 것이
> 아니라 새로 만드는 것이다.** 구화면은 백업용 동결(수정·링크 금지, P-09).
>
> 작성일 2026-08-13. ④의 수치는 **그 시각의 실측 스냅샷**이다(`api.db.engine`으로
> `products`·`product_sourcing_quotes`·`sourcing_batches`·`suppliers`를 직접
> SELECT, 읽기 전용). 화면은 이 문서의 숫자를 그대로 박지 않는다 — 서버 응답만 쓴다.

---

## ① 화면 성격

**작업 화면(work queue)** — 재고가 소진됐거나 안전재고 미달인 상품에 대해 운영자가
공급처 여러 곳에 견적을 요청하고, 회신을 대행 입력하고, 최저가로 매입을 확정하는
화면이다. 조회가 아니라 **행위(요청·회신·확정)를 원장에 남기는** 화면이다.

## ② 제목 · 화면 ID · 경로

| 항목 | 값 | 근거 |
|---|---|---|
| 화면 라벨 | 매입 견적(용산) | `api/admin_nav.py`, "매입 · 소싱" 그룹 2번째 |
| 화면 ID | **ADM-SRC-010** | 기존 식별자. `api/admin_sourcing.py` 모듈 docstring·`mockups/admin/sourcing.html`의 `data-screen-id`가 이미 이 ID를 쓴다 |
| 경로(신) | **/admin2/sourcing**(제안) | `admin_nav.py`의 이 항목은 현재 `href=None`(신설예정). 형제 재구축 화면들의 "구 mockup 파일명 stem = 신 경로" 관행을 따른 제안 — **확정은 이 문서의 권한 밖** |
| 구화면 | `mockups/admin/sourcing.html` | 백업용 동결. 참고만, 수정·안내·링크 금지 |
| LNB 위치 | "매입 · 소싱" 그룹(공급처 → **매입 견적(용산)** → 단가표 반영) | |

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

재고가 없는 상품에 대해 여러 공급처의 매입가를 비교해 최저가로 매입을 확정하는
화면이다. **확정은 가격 결정일 뿐 재고를 늘리지 않는다** — 실제로 물량이 들어오는
사건(입고)은 별도 화면(ADM-SRC-020, 이 문서의 비범위) 소관이다. 이 화면이 없으면
`product_supplier_prices`(공급처별 매입가)를 대량으로 갱신할 정상 경로가 없다 —
남는 것은 상품 상세의 단건 보정(전화로 받은 값 하나씩 입력)뿐이다.

**대기 목록은 저장하지 않고 파생한다.** `products.stock_qty=0 OR (안전재고가 있고
그보다 적음)`을 매 조회마다 계산한다 — 별도 큐 테이블을 두면 재고가 바뀔 때마다
동기화해야 하고 그 동기화 자체가 버그의 원천이 되기 때문이다(`api/admin_sourcing.py`
docstring, ERD §3.10). 저장하는 것은 **운영자가 실제로 한 행위**(견적 요청·회신
기록·확정)뿐이다.

## ④ 데이터

### 실측 방법

`api.db.engine`으로 직접 SELECT(읽기 전용). 아래는 2026-08-13 스냅샷.

### 대기 목록의 파생 조건과 실측 규모

```
FROM products p
WHERE p.status NOT IN ('단종','삭제대기')
  AND (p.stock_qty = 0 OR (p.safety_stock IS NOT NULL AND p.stock_qty < p.safety_stock))
```

- **실측 15,338건**(전체 상품 22,840건 중) — 이 화면을 그대로 열면 이 규모가 "대기"로
  잡힌다. 현재 `products.status`에는 '단종'·'삭제대기' 값 자체가 존재하지 않으므로
  (실측: 판매중 7,602 · 품절 15,238 두 값뿐), 저 제외 조건은 **지금은 아무것도
  걸러내지 못한다**.
- 이 중 **진행 중인 견적(요청·회신 상태)이 있는 상품은 5건뿐**이다 — 15,338 대 5,
  거의 전부가 아직 손대지 않은 상태다.
- **이 파생 조건은 "재고 입고"(ADM-SRC-020, LNB에서 제외된 화면) 화면의 대기 조건과
  완전히 동일하다** — 대시보드 `pending_counts()`의 `inbound` 키도 같은 SQL을 쓴다.
  소싱(공급처에 새로 발주할지 판단)과 입고(이미 온 물량을 원장에 반영)는 개념이
  다른데, 지금은 같은 모집단에서 파생된다(자세한 내용은 "사장님 결정이 필요한
  지점" 참조).

### 쓰는 테이블

|---|---|---|

| `sourcing_batches` | 견적 요청 묶음(한 상품에 여러 공급처 동시 요청) | 총 6건 — 진행 5 · 완료 1 |

### API(기존 계약)

| 엔드포인트 | 역할 |
|---|---|
| `GET /api/admin/sourcing` | 대기 목록(**서버 페이지네이션**) + 검색(q: 상품명·SKU·상품코드) + 부품종류 필터 + 상품별 진행중 견적/최근 확정 이력 |
| `POST /api/admin/sourcing/request` | 공급처 복수 선택 → 배치+공급처별 quote 행 생성 |
| `POST /api/admin/sourcing/quotes/{id}/reply` | 회신가·메모 대행 입력 |
| `POST /api/admin/sourcing/quotes/{id}/confirm` | 최저가 확정 → `product_supplier_prices` 갱신 + 재판정(`_reprice`) |

**서버 페이지네이션은 필수다** — 슬라이스 86 실사고: 예전에는 조건에 맞는 전 행을
그대로 돌려줬고 실측 15,261건·3.6MB였다(지금의 15,338건과 같은 규모). 화면이 열리는
데 몇 초가 걸렸고 브라우저가 그 표를 통째로 그려야 했다.

### 확정(confirm) 시 실제로 일어나는 일 — `admin_price_import._reprice()` 공유

1. `product_supplier_prices` UPSERT(해당 상품·공급처의 `cost_price`·`supply_state='가능'`).
2. **매입가(`purchase_price`) 재판정** — 그 상품의 모든 공급처 중 '가능' 상태 최저가로
   갱신(없으면 전체 최저가). **이 재계산은 잠금(`locked_fields`)과 무관하게 항상
   일어난다** — 실측: `locked_fields`에 `'purchase_price'`가 등록된 상품은 **0건**이다.
   즉 지금 코드에는 매입가를 잠가서 이 재계산을 막는 경로 자체가 없다(카탈로그 CSV
   재적재는 `purchase_price`의 잠금을 존중하는데, 이 확정 경로는 그렇지 않다 — 같은
   컬럼을 쓰는 두 쓰기 경로의 보호 수준이 다르다).
3. **판매가(`sale_price`) 재판정** — `locked_fields`에 `'sale_price'`가 있으면 건드리지
   않는다(응답에 `sale_locked`로 표시). 없으면 정책 공식(매입가×(1+카드수수료+마진))으로
   갱신.
4. 같은 배치의 나머지 요청·회신 건은 자동 '취소', 배치 상태는 '완료'로 전환.
5. `product_price_history`에 `reason='sourcing'`, 출처 공급처(`supplier_id`)와 함께 기록.

## ⑤ 기능 — 동사

- 대기 목록을 본다(상품명·SKU·재고·안전재고·현재 매입가·대기 사유("재고 0 — 자동
  등록" 또는 "재고 N → 안전재고 M 미달")와 함께).
- 상품명·SKU·상품코드로 검색하고 부품 종류로 좁힌다.
- 특정 상품에 대해 공급처를 하나 이상 골라 한 번에 견적을 요청한다.
- 공급처의 회신(가격·메모)을 대행 입력한다 — **자동 수신이 아니라는 사실을 화면이
  숨기지 않는다**(전화·메일로 온 값을 사람이 옮겨 적는다).
- 같은 상품에 대해 여러 공급처의 회신을 나란히 비교하고(최저가 표시) 하나를 확정한다.
- 오늘 확정한 건수를 확인한다.
- 이미 확정됐지만 아직 입고되지 않은 상품(확정가·확정 공급처)을 대기 목록에서
  계속 참고한다(확정 ≠ 입고이므로 사라지지 않는 이유를 설명해야 한다).

## ⑥ 인터랙션

- 필터(검색어·부품 종류)를 바꾸면 서버에 다시 요청한다 — 전량을 한 번에 받지 않는다.
- 견적 요청: 공급처를 하나도 안 고르면 400. 이미 진행 중인 요청(상태 '요청'·'회신')이
  있으면 409로 거부한다(중복 발주 방지).
- 회신 기록: 가격이 1원 이상이어야 한다(0 이하 400). 상태가 '요청'·'회신'이 아닌
  견적(이미 확정·취소)에 회신을 시도하면 409.
- 확정: 회신이 기록된(가격 있는) 견적만 가능하다(그 외 409). 확정 즉시 위 ④의
  5단계가 한 트랜잭션으로 일어나고, **응답의 `purchase_changed`·`sale_changed`·
  `sale_locked`를 화면이 그대로 드러내야 한다** — 판매가만 승인한 줄 알았는데
  매입가도 바뀌었을 수 있고(공급처가 둘 이상인 상품), 판매가가 잠겨 있어 반영이
  스킵됐을 수도 있다. 이걸 조용히 넘기면 "왜 값이 그대로지/왜 바뀌었지"에 답할 수 없다.
- 확정 후에도 재고는 늘지 않는다 — 결과 화면은 "가격만 정해졌고 입고는 별도"라는
  사실을 명시해야 한다(대기 목록에서 그 상품이 사라지지 않는 이유이기도 하다).

## ⑦ 상태 · 예외

- **빈 상태**: 검색·필터 결과 0건과 "대기가 원래 없음"을 구분해야 한다. 실측상
  지금은 15,338건이라 당장은 해당하지 않지만, 조건을 만족하는 상품이 없어지면
  이 화면은 정상적으로 빌 수 있다.
- 공급처 미선택 요청: 400 "견적을 요청할 공급처를 선택하세요".
- 이미 진행 중인 요청 존재: 409 "이미 진행 중인 견적 요청이 있습니다".
- 존재하지 않는 상품/공급처: 404.
- 회신 가격 0 이하: 400 "회신 매입가는 1원 이상이어야 합니다".
- 상태 불일치(회신 없는 견적에 확정 시도 등): 409 "회신이 기록된 견적만 확정할 수
  있습니다".
- **공급처가 0건이면 이 화면에서 견적 요청 자체가 성립하지 않는다** — 공급처
  화면(req-suppliers.md)으로의 안내가 필요한 지점이다.

## 비범위 — 이 화면이 하지 않는 일

- **실제 발주 메일·API 전송** — "요청 발송"은 실제 전송이 아니라 **요청 기록**이다
  (발송 연동은 이관됨, `api/admin_sourcing.py` docstring 명시).
- **회신 자동 수신** — 전화·메일 등 외부 채널로 오는 값을 사람이 대행 입력한다.
- **재고 입고 처리**(ADM-SRC-020) — 확정된 매입이 실제로 몇 개 들어왔는지 원장에
  남기는 일은 다른 화면 소관이며, 2026-08-11 LNB 개편에서 **의도적으로 제외**됐다
  ("재고 원장은 쇼핑몰이 갖는다").
- **공급처 신규 등록** — 공급처 화면(req-suppliers.md) 소관.

## 사장님 결정이 필요한 지점

1. **대기 파생 조건(재고 0 또는 안전재고 미달)이 "재고 입고" 화면과 완전히 같다.**
   재고 입고가 LNB에서 빠지면서("재고 원장은 쇼핑몰이 갖는다"는 결정과 맞물려),
   실측 15,338건이라는 규모가 지금도 "용산에서 직접 소싱해야 할 후보" 모집단으로
   유효한지, 아니면 좁혀야 하는지(예: 판매중 상품만, 핵심 부품만, 또는 추천 후보
   풀에 영향을 주는 상품만) 확인이 필요하다. 확인 없이 지으면 15,338건짜리 목록이
   그대로 화면에 뜬다.
2. **매입가(`purchase_price`) 잠금이 실제로는 구현돼 있지 않다.** 2026-08-11 결정
   원문("공급가와 판매가를 직접 수정할 수도 있는 케이스")은 매입가도 잠글 수 있어야
   함을 시사하는데, 확정(confirm) 경로는 잠금을 전혀 확인하지 않는다 — 직접
   소싱해서 정한 매입가가 있어도 다음 확정에서 덮어써질 수 있다는 뜻이다. 잠금을
   추가할지, 이 경로는 "항상 공급처 최저가를 따른다"는 지금 동작을 그대로 둘지
   결정이 필요하다(req-sale-price.md의 결정 필요 5와 같은 사안).
