# 요구사항 정의서 — 추천 기준 설정 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 결정권자(또는 지정 경로)가 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/policy-weights.html`(ADM-ENG-020)은
> 백업용 동결 — 참고만 하고 옮기지 않는다(P-09).
>
> 작성일 2026-08-13. ④의 수치는 그 시각의 실측 스냅샷이다. 재측정은
> `GET /api/admin/engine-rules`의 `tiers`·`budget`·`weights` 부분과
> `SELECT count(*) FROM policy_weights`를 다시 돌리면 된다.

---

## ① 화면 성격

**조회 화면이다 — 지금은 쓰기 기능이 없다.** "지금 견적이 실제로 어떤 기준으로
3단계(가성비/추천/고성능)를 나누고, 예산을 부품에 어떻게 배분하는지"를 사람이 읽을 수
있게 노출하는 자리다. **화면 이름과 옛 설계 문서가 그리는 모습("가중치 5축 슬라이더")
과 실제 구현이 크게 다르다** — 이 간극을 이 문서가 가장 먼저 밝혀야 한다(아래 ④
참조).

- 열람은 로그인만 되면 등급 무관(viewer 이상).
- 값을 고치는 동작은 **현재 어떤 등급에도 열려 있지 않다** — 규칙은 코드 상수이지
  DB 값이 아니다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **"가성비형·추천형·고성능형이 각각 무엇을 기준으로 정렬되는지"를 확인할 자리가
  없다.** 세 티어는 스코어 가중치가 아니라 **정렬 규칙 + 예산 상한**으로 결정된다
  (아래 실측). 이 화면이 없으면 운영자가 "추천형은 왜 이 부품을 골랐나"를 코드를
  읽지 않고는 설명할 수 없다.
- **예산이 부품별로 어떻게 쪼개지는지 보이지 않는다.** 예산 상한이 있는 견적은
  부품별 배분율(`BUDGET_ALLOC`)로 후보를 먼저 좁힌다 — 이 배분율이 눈에 안 보이면
  "왜 예산 200만원인데 이 GPU까지밖에 안 나오나"를 설명할 수 없다.
- **태그(저소음·화이트) 조건이 어느 부품에만 적용되는지 보이지 않는다** — 스코프 밖
  부품은 무조건 통과하는데, 이 사실을 모르면 "저소음을 골랐는데 왜 CPU는 그대로냐"는
  질문에 답할 수 없다.

## ④ 데이터 — **실제 구현은 "가중치"가 아니다(가장 중요한 실측 사실)**

### 실측 방법

`GET /api/admin/engine-rules` 실행 + `api/recommend.py`·`api/candidates.py` 코드
직접 대조. 2026-08-13.

### 옛 설계와 실제 구현의 간극

`docs/decisions/admin-identity.md`(2026-07-13)는 이 화면을 "가중치 5축 슬라이더
(합계 100 강제), 프리셋(가성비/균형/고성능), 변경 미리보기, 정책 버전 발행"으로
그렸다. **실제로 구현된 추천 로직은 가중치 스코어링이 아니다:**

- **`policy_weights` 테이블은 실존하지만 0행이다**(2026-08-13 실측, 컬럼은
  `key`·`weight`·`updated_at` 3개뿐). `api/admin_engine_rules.py`가 이 테이블을
  조회는 하지만, **이 값을 실제로 읽어 견적에 반영하는 코드가 어디에도 없다**
  (2026-08-13 전수 검색: `policy_weights`를 참조하는 곳은 이 조회 코드 한 줄뿐).
- 대신 실제 추천은 **티어별 정렬 규칙 + 총액 가지치기(DFS) + 부품별 예산 배분율 +
  태그 스코프**로 결정된다:

| 티어 | 정렬 기준 | 예산 상한 |
|---|---|---|
| 가성비형(value) | 슬롯별 가격 오름차순 | 예산 상한 적용(최소 구성이 예산 밖이면 전 티어 불성립) |
| 추천형(recommend) | 상한 내 가격 내림차순 + 총액 가지치기(DFS) | 예산 상한 적용(상한 내 최고가 합산이 예산을 넘지 않도록 총액으로 재차 자름) |
| 고성능형(highend) | 전체 풀 가격 내림차순 | **예산 상한 미적용** — 초과 시 'over'로 정직 표기(숨기지 않음), 대신 `HIGHEND_CAP_X=1.5`(추천형 총액의 1.5배)로 폭주를 막음 |

- **동률 처리(재현성, A-02)**: 조건이 같으면 `product_code` 오름차순 — 같은 입력·같은
  재고면 항상 같은 결과.
- **성능 대리 지표**: 벤치마크 원천이 없어 **가격**을 성능의 대리값으로 쓴다(정직
  명기 — 「부품 등급 관리」축이 채워지고 엔진에 연결되면 교체될 예정이지만, 2026-08-13
  현재 등급 축은 엔진에 연결되지 않았다).
- **부품별 예산 상한 배분율(휴리스틱, `candidates.BUDGET_ALLOC`)**: CPU 25% · GPU 40%
  · MB 15% · RAM 10% · SSD 12% · HDD 8% · POWER 10% · CASE 8% · 공랭/수랭 쿨러 각 8%.
  "이상"이나 숫자 없는 예산 표현("AI 추천 예산" 등)에는 적용되지 않는다.
- **태그 스코프**: `저소음` → `tag_silent`, 적용 범위 GPU·POWER·CASE·공랭/수랭 쿨러(스코프
  밖 부품은 무조건 통과). `화이트` → `tag_white`, 적용 범위 CASE만.

**이 화면의 이름("추천 기준 설정")이 암시하는 "설정"은 지금 존재하지 않는다** — 위 표의
모든 값(배분율·티어 규칙·스코프)은 **코드 상수**이고, 이 화면이 지금 요구할 수 있는
것은 "그 상수를 읽어서 보여주는 것"뿐이다. "설정"(바꾸는 것)을 요구하려면 별도의
백엔드 작업(값을 코드에서 DB로, `policy_weights`처럼 옮기고 실제로 읽게 만드는 작업)이
선행돼야 한다.

## ⑤ 기능 (동사) — 지금 API가 실제로 지원하는 것 기준

- 3개 티어 각각의 정렬 기준·예산 상한 적용 여부를 본다.
- 동률일 때의 처리 규칙(`product_code` 오름차순)과 그 이유(재현성)를 본다.
- "성능 지표가 없어 가격을 대리로 쓴다"는 사실을 정직 표기로 본다.
- 부품별 예산 배분율 10종을 본다.
- 태그(저소음·화이트) 조건의 적용 범위(스코프)를 본다.
- 지금 추천 후보 풀 크기(`pool_size`, 재고>0 기준)를 함께 본다.
- `policy_weights` 표가 비어 있다는 사실과 "지금 추천은 가중치 스코어가 아니라
  티어별 정렬+제약으로 결정된다"는 정직 설명을 본다.

## ⑥ 인터랙션

- 화면을 열면 티어·배분율·태그 스코프가 한 번에 온다 — 조작 없이 진입 즉시 전체를
  본다.
- **지금은 슬라이더·프리셋·저장에 해당하는 상호작용이 전혀 없다.** 옛 설계 문서의
  "합계 100 강제 슬라이더"·"가성비/균형/고성능 프리셋"은 지금 데이터 모델(`policy_weights`
  단순 key-value, 프리셋 개념 없음)로는 표현할 수 없다 — 이 문서가 임의로 그 인터랙션을
  써넣지 않는다.
- 배분율·태그 스코프에서 특정 부품(예: GPU)을 클릭하면 「추천 가능 재고 현황」이나
  「부품 등급 관리」처럼 그 부품이 실제로 얼마나 있는지 보여주는 화면으로 넘어갈 수
  있으면 좋다 — "이 배분율이 실제로 무엇을 배제하는지"를 확인하는 연결이다(단, 이동
  대상 화면의 정확한 필터 파라미터는 이 문서의 범위가 아니다).

## ⑦ 상태 · 예외

- **`policy_weights` 0행**: 오류가 아니라 **지금의 정상 상태**다. 화면은 이것을 "설정을
  못 불러왔다"처럼 보여주면 안 되고, "지금 추천은 이 표 대신 아래 규칙으로 동작합니다"는
  사실을 명확히 알려야 한다.
- **서버 실패**: `GET /api/admin/engine-rules` 실패 시 침묵하지 않는다.
- **권한**: 미로그인 401. 열람 자체는 등급 무관.
- **`budget.cap`이 없는 견적(예산 미지정·"AI 추천 예산")**: 배분율 자체가 적용되지
  않는 케이스라는 사실을 화면이 함께 밝혀야 한다 — 그렇지 않으면 "왜 이 배분율이 이
  견적에는 안 먹혔지"라는 오해가 생긴다.

## 비범위 — 이 화면이 하지 않는 일

- **마진율·카드 수수료율 설정(`pricing_settings`)** — `GET /api/admin/engine-rules`가
  같은 응답에 `pricing` 필드로 담아 보내고 있지만, 이건 **"판매가" LNB 그룹의 마진
  정책 화면 소관**이다(쓰기 API `POST /api/admin/pricing-settings`도 실제로 그
  화면을 위해 존재한다 — owner 전용). 이 화면(추천 기준 설정)의 요구사항에 마진율
  입력을 넣으면 두 화면이 같은 값을 다르게 편집하게 된다.
- **호환 규칙(`compat`) 값** — 같은 API 응답 안에 있지만 「조립 호환 규칙」(ADM-ENG-010)
  화면 소관.
- **`policy_weights`를 실제로 채우고 엔진에 연결하는 백엔드 작업** — 이 화면은 "지금
  있는 그대로"를 보여줄 뿐, 가중치 스코어링 엔진을 새로 만드는 일은 범위 밖(별도
  슬라이스).
- **부품 등급(`part_grades`)의 정렬 반영 여부** — 「부품 등급 관리」 화면 소관이며,
  그 축도 아직 엔진에 연결되지 않았다(req-part-grade.md 참조).

## 사장님 결정이 필요한 지점

1. **"추천 기준 설정"이라는 이름과 화면 성격을 지금 실체(조회 전용, 코드 상수 노출)에
   맞춰 정의할지, 옛 설계(가중치 슬라이더+프리셋+정책 발행)를 목표로 다시 백엔드부터
   구축할지.** 이름이 "설정"인데 실제로 설정할 수 있는 게 없다는 간극이 가장 크다.
2. **`policy_weights` 죽은 표를 이 시점에 정리(삭제)할지, 미래 스코어 엔진을 위해 그대로
   둘지.** 지금은 조회 코드만 있고 아무도 쓰지 않는다.
3. **배분율(`BUDGET_ALLOC`)·태그 스코프처럼 지금 코드 상수인 값을 이 화면에서 바꿀 수
   있게 열지.** 열면 "설정 변경이 기존 진행 중인 견적/스냅샷에 영향을 주지 않는다"는
   원칙(용도 하한과 동일)을 새 API에도 적용해야 한다.
4. **마진·호환 규칙과 응답을 공유하는 지금의 API 구조(`engine-rules` 한 응답에 4개
   화면분 데이터가 섞여 있음)를 화면별로 쪼갤지.** 지금 구조로도 화면별로 필요한 부분만
   골라 쓰면 되지만, 응답 하나가 여러 화면의 소관을 섞어 나르는 구조 자체를 유지할지는
   판단이 필요하다.
