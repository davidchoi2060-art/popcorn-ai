# 요구사항 정의서 — 상품등록/수정 (신설)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> 작성일 2026-09-10. 입력 = 승인 디자인 원안
> `docs/design/incoming/dc-product-unified-admin.html`(isProduct 블록 247~526행 ·
> 상태 정의 676~708행 · 핸들러 985~1100행) + 계약 요약
> `docs/design/spec-product-unified.md` §4 사장님 확정 4건.
>
> ④의 스키마 대조는 `PYTHONIOENCODING=utf-8 .venv/Scripts/python` + SQLAlchemy
> (`from api.db import engine`) **읽기 전용 조회**로 실측했다(2026-09-10 스냅샷).
> 화면은 이 문서의 숫자가 아니라 **서버 응답만** 쓴다(CANON §2-1).

---

## ① 화면 성격

**상품 원본 등록·수정 작업 화면.** 조회 화면이 아니라 값을 만들어 저장하는 자리다.

**범위 규정(2026-09-10 사장님 확정 ②):** 이 화면이 다루는 것은 **몰(팝콘PC 윈윈)로
내보낼 상품 원본**이다. 팝콘AI는 판매하지 않는다(2026-08-11 확정 유지 — 결제·배송·
환불·회원은 몰 소관). 배송비·반품/교환비·혜택·노출 채널 항목은 **본 시스템이 그 업무를
수행한다는 뜻이 아니라, 몰에 실어 보낼 값을 담는 자리**다. 화면 문구가 이 구분을
흐리지 않는다(⑥ 문구 교정안 참조).

등록(신규)과 수정(기존)을 한 화면에서 처리하며, 대상 상품 지정 여부로 두 모드를
가른다(원안 `editingId` 상당).

## ② 제목 · 화면 ID · 경로

| 항목 | 값 | 근거 |
|---|---|---|
| 화면 라벨 | 상품 등록·수정 | 관리도구 용어 표준(명사형). 원안 제목 「상품등록」/「상품 수정」의 통합 라벨 |
| 화면 ID | **ADM-PRD-011 (가칭 · 확정 전)** | 저장소 전수 검색 결과 `ADM-PRD-011`은 미사용. 확정 전이므로 이 문서 밖(코드·회귀·메뉴)에 아직 박지 않는다 |
| 경로 | **/admin2/product-new** | `spec-product-unified.md` §4-① 확정 |
| 상위 화면 | 상품 관리 `/admin2/products`(ADM-PRD-010) | 진입·복귀 대상 |
| 인증 | 페이지·데이터 모두 `/admin2/*`·`/api/admin/*` 게이트 | `api/auth.py:422` — GET=viewer, 그 밖=operator. `/api/admin/products*`는 `OWNER_WRITE_PREFIXES`(362행)에 **없다** → owner 전용이 아니다 |

> ⚠ **선행 결정과의 충돌을 명시한다.** `decision-log.md` **A-22**(2026-07-27)와
> `CLAUDE.md`:202는 「상품 작업의 유일한 진입점 = 상품 관리(ADM-PRD-010)」로 정하고
> 좌측 메뉴에서 등록·수정 화면을 없앴다. 이번 신설은 그 결정을 **경로 분할 쪽으로
> 뒤집는다**(§4-① 확정). 화면 ID·좌측 메뉴 등재 여부를 확정할 때 A-22를 함께
> 갱신해야 한다 — 두 기록이 갈리면 다음 작업자가 반대로 읽는다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **상품 원본을 만들 자리가 없다.** 현행 admin2에 등록 전용 화면이 없다.
  `templates/admin/products.html.j2:1453`의 모달이 `POST /api/admin/products`를
  부르는 것이 전부이며, 그 모달이 보내는 값은 **상품명·분류·제조사·매입가·
  다나와 코드·공급처** 수준이다(`api/admin_products.py:305` `RegisterBody`).
  즉 몰로 내보낼 상품 원본에 필요한 값의 대부분을 지금은 입력할 곳이 없다.
- **등록 이후 값을 이어서 채울 자리가 없다.** 등록 API는 판매가를 NULL로 두고
  `review_required_yn=true`·`ai_candidate_yn=false`로 넣는다(같은 파일 380행 부근).
  검수·판매가 산정을 통과해야 추천에 쓰이는데, 그 값을 넣는 화면이 admin2에 없다.
- **중복 등록을 사전에 거르는 자리가 없다.** 판정 API(`GET /product-similar`,
  1503행 · 임계 `dedupe.SIMILAR_THRESHOLD`)는 이미 있으나, 등록 화면이 없어
  409 응답을 사람에게 보여 줄 자리가 없다.
- **몰 반출 전 값의 완결성을 확인할 자리가 없다.** 필수 항목 충족 여부를 저장 전에
  확인하는 절차가 현행에 없다.

### 원안 12섹션 필드 × 현행 스키마 대조 (전수)

원안 필드 원천 = `EMPTY_FORM()`(709행) + 각 섹션 마크업.
판정 = ○ 있음 / △ 유사(의미 확인 필요) / ✕ 없음 → **표 신설 필요**.
**✕ 항목의 스키마는 이 문서에서 설계하지 않는다** — ERD 개정은 별도 작업
(`spec-product-unified.md` §5-③).

## ⑤ 기능 (동사)

### 등록 모드

- 선택지를 **서버에서 받아 채운다**(`GET /api/admin/product-meta`) — 분류 · 제조사 ·
  판매상태. 화면 마크업에 선택지·예시 값을 박지 않는다.
- 분류를 선택한다(2단 선택 트리 지원. 기본값 없음 — **「분류를 선택하세요」**로 시작).
- 기본정보를 입력한다.
- 카테고리를 상위부터 순서대로 선택한다.
- 판매가격·재고를 입력한다.
- 중복 상품을 **저장 전에 확인한다**(`GET /product-similar`, 임계
  `dedupe.SIMILAR_THRESHOLD`). 같은 상품이면 기존 상품 수정으로 이동한다.
- 필수 항목 충족 여부를 확인한다(서버가 판정한 결과를 표시).
- 등록한다(`POST /api/admin/products`).
- 입력을 초기화한다.
- 임시저장한다 · 임시저장을 불러온다 *(저장 위치 미정 — 결정 8)*.
- 기존 상품을 복사해 초기값을 채운다 *(저장 위치·복사 범위 미정 — 결정 8)*.

### 수정 모드

- 대상 상품을 불러온다(`GET /api/admin/products/{code}`).
- 수정 가능한 필드를 수정한다(`PATCH /api/admin/products/{code}` — `EDITABLE` 목록).
- 수정 값을 잠근다 / 잠금을 해제한다(`lock`, 기본 잠금).
- 사양 값을 입력해 검수 대기를 해소한다(`PATCH /{code}/specs`).
- 공급처별 매입가를 등록·수정한다(`POST /{code}/suppliers`).
- 수정을 취소하고 상품 관리로 복귀한다.

### 공통

- 섹션을 펼친다 · 접는다 · 전체 펼친다 · 전체 접는다.
- 미충족 필수 항목으로 이동한다.
- 카테고리 관리 화면으로 이동한다.
- 상품 관리 목록으로 복귀한다.

### 이 화면이 하지 않는 일 (비범위)

- **판매·결제·배송·환불·회원 처리를 하지 않는다.** 몰 소관(2026-08-11 확정 유지).
- **사양 항목 정의를 다루지 않는다.** 「조립 사양 표준」·「상품 사양 정의」 소관.
- **검수 승인·반려를 처리하지 않는다.** 검수 큐(`/admin2/reviews`) 소관.
- **분류 체계를 편집하지 않는다.** 카테고리 관리(`/admin2/categories-v2`) 소관.
- **판매가를 산정하지 않는다.** 마진은 `api/pricing.resolve_margins`가 단일 원천.

## ⑥ 인터랙션 — 입력 · 선택 · 저장 · 이동의 흐름과 결과

### 진입

- 상품 관리 목록의 [등록] → 등록 모드로 진입한다. **모든 입력 항목은 빈 값으로
  시작한다.** 예시 값을 초기값으로 두지 않는다(과거 사고 — 다른 상품명·가격이
  기본값으로 저장될 뻔했다).
- 상품 관리 목록의 [수정] → 대상 상품 코드로 진입한다. 서버 응답으로 초기값을
  채우고, 잠긴 필드는 잠금 상태를 함께 표시한다.

### 선택

- 분류 선택 시 제조사 선택지를 다시 받는다(`product-meta`는 `part_type`으로 좁혀
  응답한다 — :514). 분류가 정해지기 전에도 호출할 수 있다.
- 카테고리는 상위 단계부터 선택한다. 상위가 비면 하위 선택은 비활성이다.
- 하위 분류가 없는 단계는 비워 둔다.

### 저장 — 등록

1. 필수 항목 미충족 시 저장을 진행하지 않고 미충족 항목을 안내한다.
2. `POST /api/admin/products` 호출.
3. **409 `similar_products`** 수신 시 유사 상품 목록을 제시하고 선택을 받는다.
   - 「기존 상품 수정」 선택 → 해당 상품의 수정 모드로 이동한다.
   - 「다른 상품으로 등록」 선택 → `confirm_similar=true`로 재요청한다.
4. 성공 시 서버가 준 SKU·상품코드와 **후속 상태 안내**를 그대로 표시한다
   (서버 응답 문구: 검수 대기 상태이며 추천 풀에 들어가지 않는다는 사실).
5. 등록 직후 상태는 서버가 정한다 — `sale_price` NULL · `review_required_yn=true` ·
   `ai_candidate_yn=false` · `stock_qty=0`. **화면이 이 값을 지어내지 않는다.**
6. 등록 후 이동 대상(목록 복귀 / 수정 모드 계속)은 확정이 필요하다(결정 9).

### 저장 — 수정

1. 변경된 필드만 `PATCH`로 보낸다. `EDITABLE` 밖의 필드를 보내면 400이다.
2. 성공 시 변경 전·후 값과 잠금 결과를 표시한다.
3. 가격·재고 변경은 원장에 함께 남는다(`product_price_history` ·
   `stock_movements` — 서버가 처리). 화면은 그 사실을 안내한다.

### 실패 처리

- 실패 시 **서버가 준 사유를 그대로** 보인다. `if(!res.ok) return;` 같은 침묵 금지
  (CANON §4).
- 네트워크 오류 · 401(세션 만료) · 그 밖의 서버 오류를 **구분해** 안내한다
  (ADM-PRD-010이 이 구분이 없어 결함으로 기록돼 있다 — 같은 결함을 반복하지 않는다).

## ⑦ 상태 · 예외

### 빈 상태

- **등록 모드 초기**: 전 항목 빈 값. 분류·카테고리 선택은 「분류를 선택하세요」 ·
  「카테고리를 선택하세요」로 시작한다. **예시 값을 초기값으로 두지 않는다.**
- **선택지 미수신**: 분류·제조사 선택지를 못 받으면 해당 선택을 비활성으로 두고
  사유를 표시한다. 화면이 임의 선택지를 만들지 않는다.
- **수정 모드에서 사양이 비어 있음**: 「미입력」으로 표시한다. 0으로 표시하지 않는다.
- **공급처별 매입가 없음**: 「등록된 공급처 없음」.

### 권한 없음

- 조회(GET) = viewer 이상, 등록·수정(POST/PATCH) = operator 이상
  (`api/auth.py:422`). `/api/admin/products*`는 `OWNER_WRITE_PREFIXES`에 없어
  owner 전용이 아니다.
- viewer 등급으로 저장 시도 시 403 「권한이 부족합니다(필요: operator, 현재:
  viewer)」(공통 미들웨어 표준 문구).
- viewer 등급에서는 저장 동작을 **비활성으로 두고 사유를 밝힌다.** 눌러도 반응 없는
  상태로 두지 않는다.
- 미인증 접근 시 `/admin2/*` 게이트가 로그인 안내 HTML로 응답한다.

## 사장님 결정이 필요한 지점

1. **분류(`part_type`) 항목이 원안 폼에 없다.** 현행 `products.part_type`은 NOT NULL
   이고 등록 API 필수 인자다. 원안의 카테고리(`categories`)와는 **다른 축**이다
   (부품 종류 · 진열 분류). 이 화면에 분류 선택을 추가할지, 카테고리에서 파생할지
   확정이 필요하다. — **임의로 정하지 않았다.**
2. **SKU 발번 정책.** 현행은 서버 자동 발번(`P-{MAX+1}`). 원안은 운영자 직접 입력 +
   [자동생성] 버튼. 어느 쪽을 정본으로 할지 확정이 필요하다.
3. **판매상태 값 집합.** 현행 `판매중·품절·단종·삭제대기` · 원안 `판매중·판매대기·
   품절·판매중지`. 현행 값이 정본이라고 보나 확인이 필요하다.
4. **「정상가」의 정체.** `products.market_price`(시장가)를 쓸지, 별도 항목으로 둘지.
   가격 검토 화면이 `market_price`를 기준으로 쓰고 있어 겹치면 서로 흔든다.
5. **필수 항목 집합.** 원안 필수 6종(상품명·SKU·카테고리·판매가·재고수량·노출 채널)은
   현행 정책과 충돌한다 — 등록 시 `sale_price`는 NULL 유지가 정책이고 `stock_qty`는
   0 고정이다. 필수 집합 재확정이 필요하다.
6. **카테고리 4단.** 실데이터는 2단까지만 존재한다(1단 6 · 2단 29). 4단 시드 반영
   시점과 이 화면의 관계 확인이 필요하다.
7. **이미지·태그 상한의 정본.** 원안 값(이미지 1+9 · 네이버 10 · 쿠팡 20)은 마크업
   상수이고 서버 규칙이 없다. 화면이 숫자를 지어내지 않으려면 서버가 줘야 한다.
8. **임시저장(draft)·상품복사의 저장 위치 — 선택지만 올린다. 정하지 않았다.**

   | 안 | 저장 위치 | 함의 |
   |---|---|---|
   | ㉮ 서버 표 신설 | 신설 draft 표(스키마는 ERD 개정에서 설계) | 기기·브라우저를 넘어 이어 작성 가능 · 여러 운영자 간 가시성 · 표 신설과 정리 정책 필요 |
   | ㉯ 브라우저 보관 | 브라우저 로컬 저장소 | 표 신설 불요 · 다른 기기에서 이어 작성 불가 · 브라우저 정리 시 소실 · 원안 데모 방식 |
   | ㉰ 저장하지 않음 | — | 미저장 이탈 시 경고만 · 구현 최소 · 장시간 작성 중 소실 위험 |

   상품복사의 **복사 대상·제외 항목 목록**도 함께 확정이 필요하다(원안은
   「이미지와 SKU는 복사하지 않는다」로 적었으나 근거가 데모 구현이다).

9. **등록 성공 후 이동 대상.** 목록 복귀 · 해당 상품 수정 모드 계속 · 연속 등록.
   원안은 목록 복귀(1089행)이나 확정이 필요하다.
10. **화면 ID `ADM-PRD-011` 확정 및 A-22 결정 갱신**(② 경고 참조).
11. **좌측 메뉴(IA) 등재 여부.** A-22가 「좌측 메뉴에 편집 화면을 따로 두지 않는다」로
    정했다. 등재한다면 `api/admin_nav.py`(단일 원천)를 갱신해야 한다.
