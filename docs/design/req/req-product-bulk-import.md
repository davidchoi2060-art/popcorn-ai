# 요구사항 정의서 — 상품 일괄 등록 (admin2 신규 구축 · 3화면 통합)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/csv-upload.html`·`csv-jobs.html`·
> `imports.html`(아래 ②의 ID 참조)은 **백업용 동결** — 참고만 하고 옮기지 않는다(P-09).
>
> **이 화면은 옛 3화면(업로드 · 이력 · 오류건/원본자료)을 하나로 합친다** —
> `docs/design/admin-ia-draft-2026-08-09.md`(✅ 확정, decision-log UX-34, 구 UX-14) 5번 행:
> "일괄 등록 + 이력 + 적재 오류건 3화면을 하나로. 올리고 → 결과 보고 → 틀린 것 확인이
> 연속 동작이다." `api/admin_nav.py`의 LNB 비고도 "이력·오류건 통합 예정"이라 못박는다.
>
> 작성일 2026-08-13. ④의 수치는 **그 시각의 실측 스냅샷**이다 — 화면은 이 문서에 적힌
> 숫자가 아니라 서버 응답만 써야 한다. 재측정은 `.venv/Scripts/python`으로
> `api.db.engine`을 통해 `csv_import_jobs`·`csv_import_errors`·`product_imports`·
> `products`를 다시 SELECT(읽기 전용)하면 된다.

---

## ① 화면 성격

**가장 위험한 쓰기 동작을 가진 작업 화면이다.** 파일 하나로 정본 22,840건을 한 번에
갱신할 수 있고, **적용 후에는 되돌리기가 없다**(아래 ③·⑥). 동시에 이 화면은 그 갱신의
**결과를 계속 되짚어 보는 조회판**을 겸한다 — 업로드 마법사와 이력·오류 조회가 분리된
화면이 아니라 하나의 연속 동작이다.

- 업로드·검증·반영(드라이런→적용)은 **owner 등급만** — 파일 하나가 정본 전체를 덮을 수
  있고 되돌릴 수단이 없어, 운영자 등급에게 열 수 있는 일이 아니다(`api/auth.py`
  `OWNER_WRITE_PREFIXES`에 `/api/admin/catalog-import`가 명시).
- **이력·오류행 조회는 로그인만 되면 등급 무관**(viewer 이상) — `GET /api/admin/
  import-jobs`류는 이 owner 전용 목록에 없다. 즉 "누가 언제 무엇을 올렸는지"는 조회
  등급도 볼 수 있지만, 실제로 새로 올리는 것은 owner만 할 수 있는 **비대칭 권한**이다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **카탈로그(22,840건)를 CSV로 대량 갱신할 방법이 없다.** 이것이 정본 갱신의 유일한
  대량 경로다(단건 수정은 "상품 관리"의 상세 편집 소관).
- **갱신이 실제로 무엇을 바꾸는지 미리 볼 방법이 없다.** 확인 없이 올리면 과거에 실제로
  겪은 사고가 재발한다 — 사양 EAV 없이 마스터만 올렸다가 추천 후보가 -1, 검수 대기가
  +169건 늘어난 전례(슬라이스 50, `CLAUDE.md`). 드라이런이 "몇 건"이 아니라 "무엇이
  바뀌는가"(신규/갱신, 추천 후보 진입/이탈, 검수 새로 회부)를 먼저 말해야 하는 이유다.
- **과거에 무엇을 얼마나 올렸는지, 왜 특정 행이 거부됐는지 되짚을 곳이 없다.** 특정
  상품이 반영되지 않은 이유를 확인할 유일한 창이다.

## ④ 데이터

### 실측 방법

`api.db.engine`으로 `csv_import_jobs`·`csv_import_errors`·`product_imports`·
`products`를 직접 SELECT(읽기 전용). 아래는 2026-08-13 스냅샷.

### 파일 형식(고정 계약 — 사람이 열을 매핑하는 기능 없음)

- **마스터 CSV(필수)**: 헤더에 정확히 이 14개 컬럼명이 있어야 한다 — 자체상품코드·
  상품명·카테고리1·카테고리2·카테고리3·상태값·매입가·일반회원·시중가·공급처·스펙·
  제조사·모델명·다나와No. 하나라도 없으면 즉시 거부(400, 무엇이 없는지 명시).
- **사양 EAV(선택, 2개 파일 세트)**: `db_products`(product_id↔자체상품코드 매핑) ·
  `db_specs`(product_id·spec_key·spec_value) — **둘 중 하나만 올리면 막힌다**(400).
  안 올리면 사양은 마스터의 "스펙" 열 원문에서만 추출되고, 이미 확인된 기존 사양값은
  그대로 유지된다(지우지 않는다).
- **`자체상품코드`는 팝콘PC 쇼핑몰의 상품코드(`pd_no`)와 같은 값이다**(2026-08-11 확정,
  `.claude/CANON.md` §3). 이 코드로 `products.product_code`가 그대로 결정된다 — 잘못된
  코드로 올리면 실제 라이브 몰 상품과 코드가 충돌하거나 엉뚱한 상품을 덮어쓸 수 있다.

### 쓰는 테이블

| 테이블 | 역할 | 비고 |
|---|---|---|
| `products` | upsert 대상(정본) | `product_code` 기준. **삭제는 없다** — 올린다고 기존 상품이 사라지지 않는다. `locked_fields`에 있는 필드(운영자가 손으로 고쳐 잠근 값)는 덮지 않는다 |
| `product_specs` | 사양 upsert | `COALESCE(새 값, 기존 값)` — 채우기만 하고 지우지 않는다 |
| `product_reviews` | 검수 신규 회부 | 이미 같은 (상품,필드) 대기 행이 있으면 중복 생성하지 않는다(재실행 안전) |
| `stock_movements` | 재고 변동 원장 | 절대값이 아니라 델타. `0→N`은 `inbound`, 그 외 조정은 `adjust` — 재고 수량 자체는 원천에 없어 "판매중=1·품절=0"으로 고정 산정(2026-07-26 확정) |
| `csv_import_jobs` | 배치 1건당 1행 | 파일명·전체/신규성공/오류/검수회부 건수·상태·데이터원천·업로더 |
| `csv_import_errors` | 거부 행 원본 | **배치당 최대 200행까지만 저장**(코드 상수, 그 이상은 저장되지 않음) |
| `product_imports` | 성공 행 원본 보관용 테이블 | **실측 0행 — 설계상 항상 비어 있다.** `apply_plan`이 이 테이블에 쓰는 코드가 없다. 성공 행 원문은 원본 CSV를 정본으로 두고 별도 보관하지 않는다(용량 중복 회피, `api/admin_imports.py` 독스트링에 이미 명시) |

### 쓰는 API

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `POST /api/admin/catalog-import/dryrun` (multipart: `master`, `db_products`?, `db_specs`?, `origin=real&#124;demo`) | DB 미변경 계획 수립. `staging_id` 발급, 파일은 서버 임시 폴더에 **최대 1시간** 보관 | owner |
| `POST /api/admin/catalog-import/apply` (`staging_id`, `expect_ok`) | 드라이런에서 본 건수(`expect_ok`)가 지금 재계산과 다르면 거부(409) — 그 사이 DB가 바뀐 것 | owner |
| `GET /api/admin/import-jobs` | 배치 이력 최근 50건 + 합계 + 현재 카탈로그 실측(전체/실데이터/데모) | viewer 이상 |
| `GET /api/admin/import-jobs/{job_id}/rows?limit=` | 그 배치의 거부 행 원본(사유 포함, 최대 500행) + 반영된 상품 목록(SKU만) | viewer 이상 |

## ⑤ 기능 (동사)

**업로드 · 미리보기**
- 마스터 CSV(+선택적으로 사양 EAV 2파일 세트)를 올려 무엇이 바뀔지 미리 본다: 신규·
  갱신 건수, 부품 종류별 분포, 검수 새로 회부되는 수, 추천 후보 진입/이탈 수, 제외
  (skip)·오류 행과 그 사유.
- 데이터 원천(실데이터/데모)을 명시적으로 고른다.
- 미리본 결과를 확인하고 나서만 실제로 반영한다.

**이력 · 오류 조회(같은 화면 안에서 이어지는 동작)**
- 과거 배치 목록(언제·누가·파일명·신규/갱신/오류/검수회부 몇 건)을 본다.
- 방금 적용한(또는 과거) 배치를 눌러 거부된 행의 원본 값과 사유를 확인한다.
- 반영된 행은 SKU로 상품 목록에서 다시 찾아본다(원본 셀 자체는 보관되지 않는다는 사실을
  안다).

## ⑥ 인터랙션 — 입력 · 선택 · 저장 · 이동의 흐름과 결과

- **업로드 → 미리보기(드라이런) → 확인 → 적용의 순서가 강제된다.** 미리보기 없이 바로
  반영하는 경로는 없다.
- 미리보기는 "몇 건"이 아니라 "무엇이 바뀌는가"를 문장으로 먼저 말한다 — 신규 N·갱신
  N·검수 새로 회부 N·제외 N·오류 N, 추천 후보 진입/이탈 건수, EAV를 안 올렸으면 "사양은
  상품명에서만 추출되고 기존 확인값은 유지된다"는 사실.
- 사양 EAV는 두 파일을 함께 올리거나 둘 다 비워야 한다 — 하나만 올리면 그 자리에서
  막힌다.
- 적용을 누르면 미리보기 때 본 건수(`expect_ok`)를 **그대로 함께 보낸다.** 그 사이
  다른 작업으로 DB가 바뀌어 실제 계획이 달라졌으면 반영은 거부되고 "다시 검증하라"는
  안내가 그대로 보인다 — 다른 파일을 실수로 확정하는 사고를 막는 장치다(슬라이스 50
  계약).
- 적용이 끝나면 배치 번호와 함께 반영 결과(반영 N·검수 N·오류 N)와 **지금** 카탈로그·
  추천 후보·검수 대기 총량을 함께 보여준다.
- **적용 후에는 되돌리기 버튼이 없다.** 이 사실이 적용 전(미리보기 단계)부터 분명히
  보여야 한다 — 이 프로젝트의 다른 대부분 쓰기 동작(상품 수정·카테고리 이동·검수 처리
  등)은 되돌리기가 있어서, 이 화면만 다르다는 사실을 특히 명확히 해야 한다.
- 이력 목록에서 배치를 선택하면 그 배치의 오류 행·반영 행 상세로 **같은 화면 안에서**
  이어진다(별도 화면 이동이 아님 — admin-ia-draft의 "3화면을 하나로" 요구와 일치).
- 이력의 배치 합계와 지금 카탈로그 실측이 다를 수 있다는 사실을 화면이 밝힌다 —
  재적재는 upsert이고 삭제가 없어 재실행분이 배치 합에 중복 계상되기 때문이다.

## ⑦ 상태 · 예외

- 빈 파일(0행) → 400. 필수 컬럼 누락 → 400(무엇이 없는지 그대로). UTF-8이 아닌 CSV →
  400("UTF-8 인코딩이 아닙니다 — UTF-8로 저장해야 합니다").
- 파일이 64MB를 넘으면 → 413, 몇 MB인지·한도가 몇 MB인지 함께.
- **미리보기 후 1시간 안에 적용하지 않으면 임시 파일이 청소돼 적용이 404**("업로드가
  만료되었거나 없습니다 — 파일을 다시 올려야 합니다") — 처음(업로드→미리보기)부터
  다시 해야 한다.
- 적용 시점에 계획이 달라졌으면(그 사이 다른 작업으로 DB 변경) 409 — "확인하신 N건과
  지금 계획 M건이 다릅니다 — 다시 검증이 필요합니다."
- 권한 없음(operator·viewer가 업로드·적용 시도) → 403. **이력·오류 조회는 막히지
  않는다**(비대칭 — ①에서 밝힌 그대로).
- **실패한 시도는 이력에 전혀 남지 않는다.** 400/413/404/409로 끝난 업로드는
  `csv_import_jobs` 행을 만들지 않는다 — 이 테이블은 실제로 반영까지 끝난 배치만
  갖는다(실측: 이 테이블에 `'완료'` 외의 상태를 쓰는 코드 경로가 없다). 화면이 "실패한
  시도까지 이력에 나온다"고 오인시키면 안 된다.
- **거부 행(오류) 원본은 배치당 최대 200행까지만 저장된다** — 그 이상은 저장 자체가
  안 된다(코드 상수). 오류가 200건을 넘으면 몇 건이 화면에 안 보이는지 밝혀야 한다.
- **`skip`(제외) 행은 사유별 집계로만 미리보기에 나타나고, 적용 후에는 그 사유 자체가
  사라진다.** `csv_import_jobs`에는 `row_total`·`row_ok`·`row_error`·`row_review`만
  저장되고 `skip` 집계 컬럼이 없다 — "제외 N건"의 이유(예: 원천이 '삭제대기'·
  '내부관리용'으로 분류한 행 — 아래 참고)는 **그 드라이런 화면을 벗어나면 다시 볼 수
  없다.** 적용 전에 사람이 그 사유를 눈으로 확인해야 하는 이유이자, 적용 후 이력에서는
  "왜 24,303행 중 22,808건만 반영됐는지"의 차이(1,495행)를 전부 되짚을 수 없다는 뜻이다.

  > 참고 — 원천 CSV 자체가 이미 "삭제대기"라는 카테고리1 값을 갖는 행을 보낸다
  > (`api/catalog_map.SKIP_L1 = {"삭제대기","내부관리용","고객님 개인결제"}`). 이건
  > **원천(공급/등록 시스템)이 이미 취급 대상이 아니라고 표시한 행**이고,
  > `products.status='삭제대기'`(상품 목록에 이미 들어온 뒤 나중에 운영자가 내리는 상태,
  > "삭제 상품 조회" 정의서 참조)와는 **다른 개념**이다. 혼동하지 않도록 이 화면의
  > 요구사항에 명시해 둔다 — 이 화면에서 스킵된 행은 애초에 `products`에 들어온
  > 적이 없다.

## 비범위 — 이 화면이 하지 않는 일

- **컬럼을 사람이 매핑하는 기능이 없다** — 고정 헤더 계약이다. 헤더가 다르면 재업로드
  해야 한다("단가표 반영"(ADM-PRC 계열, 매입·소싱 그룹) 화면은 다중 레이아웃·프리셋
  매칭이 있지만, **이 화면과는 다른 화면·다른 목적**이다).
- **배치 취소/롤백이 없다.** 적용 후에는 원래대로 되돌릴 수 없다.
- **성공 행 원본 CSV 셀 보존이 없다.** 원본 CSV 파일 자체가 정본이라는 전제다.

## 사장님 결정 필요 지점 (임의로 정하지 않았다)

1. **화면 ID 정리.** ②에서 밝힌 대로 옛 설계 문서(`admin-identity.md`)와 실제 코드
   독스트링이 이 기능들의 ID를 서로 다르게 부르고, 심지어 코드 안에서도 ADM-PRD-040이
   두 번(원본자료 / 상품 상세·수정) 쓰인다. 이 통합 화면을 **ADM-CSV-010** 하나로
   확정하고 나머지(ADM-SYS-030/040, ADM-IMP-010)는 폐기 표기할지 확인 필요.
2. **배치 취소/롤백 기능의 존재 여부.** 옛 설계(`admin-identity.md`, 2026-07-13)엔
   "배치 취소(72h 내, 정본 롤백·원본 보존)"이 있었는데, 실제 구현
   (`api/admin_catalog_import.py`, 슬라이스 50 이후)은 "적용 후 되돌리기는 없다"로
   명시돼 있다 — decision-log에서 이 번복을 기록한 항목을 찾지 못했다. 이 화면
   요구사항에 롤백 기능을 새로 넣을지(신규 구현 필요), 아니면 "없음"을 그대로 확정하고
   문서만 정리할지.
3. **거부 행 200건 초과 시 처리.** 지금은 저장 자체가 안 된다(코드 상수 `errors[:200]`).
   상수를 늘리는 것은 구현 변경이라 이 문서 범위를 벗어나지만, 요구사항으로 "전량 보존"을
   못박을지 확인이 필요하다.
4. **이력·오류 조회를 viewer 등급에게도 그대로 열어 둘지.** 지금 코드상 가능하지만
   업로드는 owner만이라 비대칭이다 — 의도된 설계인지 확인 필요.
