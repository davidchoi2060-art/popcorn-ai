# 재고 입고 — 화면 UI 요구사항 정의서

> **작성 2026-08-17.** 사장님 지시(2026-08-17): 「재고 입고의 경우 단독으로 할 수 있으니까 —
> **업그레이드해서** 만들어야 함」. 구 화면(`mockups/admin/stock-inbound.html`)을 그대로
> 옮기지 않고, 구 화면이 못 하던 것을 고쳐서 `/admin2` 아래 신규로 짓는다.
>
> ⚠ **이 문서는 «요구사항»까지다.** 화면 배치·컴포넌트·색·와이어프레임은 적지 않는다
> (CLAUDE.md §화면 작업의 경계).
>
> ⚠ **§④ 의 수치는 전부 실측이며 잰 시각을 함께 적었다.** 이 저장소는 문서에 수를 박아
> 여러 번 어긋났다 — **인용할 때 시각을 함께 인용한다.** 현재 수가 필요하면 다시 잰다.

## ① 화면 성격

**작업 화면**(쓰기). **원장에 행을 남기는** 자리다.

    매입 견적(ADM-SRC-010)   무엇을 얼마에 살지 «정한다»
    이 화면                   실제로 들어온 수량을 **원장에 «기록한다»**
    추천 가능 재고(ADM-ENG-030)  그 결과가 후보에 반영됐는지 «읽는다»

**이 화면의 쓰기는 `products.stock_qty` 단독 수정이 아니다.** `stock_movements` 행과
`products.stock_qty` 갱신이 한 트랜잭션이며, 되돌림은 삭제가 아니라 역방향 원장 행이다
(CANON.md §2-2·§2-4 · CLAUDE.md §원장·되돌림 규약).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

**(가) 재고가 곧 견적 품질이다**

추천 후보 조회가 재고를 게이트로 쓴다 — 실측 근거:

    api/candidates.py:127     v_recommendation_candidates WHERE stock_qty > 0
    api/recommend.py:503      v_recommendation_candidates WHERE stock_qty > 0
    api/recommend.py:577      v_companion_candidates       WHERE stock_qty > 0

재고가 0이면 검수·가격·사양이 전부 끝난 상품도 견적에 쓰이지 않는다. **재고 입고는
3중 게이트(검수 · 가격 · 재고)의 마지막 관문이다.**

**(나) 원장과 함께 재고를 올리는 «일괄 작업 화면»이 사라진다**

`products.stock_qty` 를 원장과 함께 올리는 코드 경로는 실측 7개다(§⑥-마). 그중 운영자가
**입고 목적으로 직접 부르는** 경로는 `POST /api/admin/stock-inbound/{product_code}`
하나이며, 그것을 부르는 화면은 구 `/admin/stock-inbound.html` 뿐이다. 구 `/admin/*.html`
은 **백업용 동결**(CLAUDE.md §관리자 화면 규약)이므로, admin2 에 이 화면이 없으면 남는
경로는 상품 상세(ADM-PRD-010)의 단건 조정뿐이다 — 대기 15,725건(§④)을 단건 화면으로
처리하는 것은 작업 경로가 아니다.

**(다) 「입고하면 추천에 들어가는가」에 답하는 자리가 없다**

`POST /stock-inbound/{code}` 는 응답에 `pool_entered` 를 실측으로 담는다
(`api/admin_stock.py:60-63` — `v_recommendation_candidates` 조회). 이 값을 보여주는
화면이 없으면 운영자는 입고 후 상품이 후보에 들어갔는지 다른 화면에서 확인해야 한다.

### (나) 쓰는 테이블 — 실측

**`stock_movements`** (컬럼 = `information_schema` 조회)

    movement_id  bigint      PK
    product_code bigint      FK -> products(product_code)
    movement_type varchar    단가 컬럼 없음

    (`pg_constraint` 전수 조회). 값 집합은 코드 관례로만 지켜진다.

### (바) ⚠ 문서가 사실과 어긋난 자리 둘 — **사실을 적고, 어긋남을 밝힌다**

**㉮ `api/admin_nav.py:254` 「재고 입고만 뺐다 — 재고 원장은 쇼핑몰이 갖는다」**

**사실:** 재고 원장은 **우리 DB 에 존재하며 지금도 기록된다.** 2026-08-17 07:08 UTC 실측으로
`stock_movements` **9,326행**이며, `api/admin_stock.py` 가 지금도 그 표에 쓴다
(`INSERT INTO stock_movements` — `:159` `:198`). 추천 후보 게이트도 우리 `stock_qty` 를
읽는다(§③-가). **주석은 사실과 어긋난다.**

다만 **범위 결정(CANON.md §3, 2026-08-11)의 취지 자체는 유효하다** — 결제·배송·환불·
회원관리는 몰 소관이고 가격 원천도 몰이다. 어긋난 것은 「재고 원장」이라는 대상 지정이다.
**주석 정정은 nav 정본 소관**이며 이 화면의 담당 밖이다. 정의서는 사실만 적는다.

**㉯ `api/admin_stock.py:1-13` docstring 「안전재고 미달 유형은 기준 컬럼이 없어 LIVE 제외」**

**사실:** `products.safety_stock` 컬럼은 **실재하고**(마이그레이션 `0004`), 값이 있는
상품이 **30건**이며, **같은 파일의 코드가 실제로 그 컬럼을 쓴다**:

    :41-42   대기 목록 조건    safety_stock IS NOT NULL AND stock_qty < safety_stock
    :53-54   총계 조건         (동일)
    :67-69   행 사유 문구      "안전재고 미달 — 현재 N / 기준 M"

같은 파일 `:26-27` 의 `NOTE` 도 「기준은 상품별 `safety_stock`」이라고 반대로 적는다.
**docstring 만 낡았다.** 구 화면 각주도 이미 「실판정합니다」로 정정돼 있다
(`mockups/admin/stock-inbound.html:234`). 정의서는 **안전재고 미달을 실판정 유형으로
다룬다.**

| 2 | **「보류」가 서버에 닿지 않는다** — `R.splice(i,1)` 로 화면 배열에서만 지우고 「보류 — 재고 미반영」을 표시한다. 목록은 파생이므로 **다음 조회에 그대로 다시 나온다** | `:347-350` |
| 3 | 서버에 닿는 단추는 **「입고 확정」 하나뿐** | `:331-345` |
| 4 | **「직접 입고 등록」도 서버에 닿지 않는다** — `R.unshift(row)` 로 표에 행을 얹고 「표에서 확정하세요」를 표시한다. 즉 등록이 아니라 **입력 준비**다 | `:384-396` |
| 5 | **KPI 4종이 «현재 페이지»만 센다** — `R` 은 한 페이지(기본 50건)다. 서버가 준 `total`(15,725)은 페이지 이동에만 쓰인다. 「입고 대기 50건」이 표시된다 | `:265-270` · `:455-460` |
| 6 | **「오늘 입고」가 서버 값이 아니라 브라우저 세션 카운터다** — `let done=0` 이 페이지 로드마다 0으로 시작한다. 실측 서버 값 `created_at::date = current_date` 인 `inbound` 행은 **0건** | `:245` `:266` |
| 7 | 필터 pill 3종(전체 · 매입 확정분 · 실사 조정)도 **현재 페이지 기준**이며, 라벨이 매입 견적과 무관하다(§④-마) | `:275` |
| 8 | **되돌리기가 브라우저 변수에 의존한다** — `lastAction` 이 JS 변수라 새로고침하면 되돌릴 방법이 화면에서 사라진다. **서버 API 는 과거 회차도 받는데**(§④-가) 화면이 그것을 못 쓴다 | `:352-370` |
| 9 | 「재고 있는 것만」 필터는 **존재하지 않는다** — 표 안 검색·정렬(`list.js`)과 pill 3종이 전부다 | 전문 확인 |

**결함 1·2·4 의 공통점: 운영자는 「저장됐다」고 믿는데 서버는 모른다.** 이것이 이번
업그레이드의 핵심이다.

## ⑤ 기능 — 할 수 있는 일

1. **입고 대상을 조회한다** — 전체 건수와 현재 페이지를 함께 표시한다.
2. **조회 조건을 건다** — 상품명·SKU 검색 · 분류 · 대기 유형(재고 0 / 안전재고 미달).
3. **입고 후 결과를 미리 확인한다** — 입고 후 재고 수량 · 후보 진입 여부 · 미진입 사유.
4. **단건 입고를 확정한다** — 수량과 사유(입고 · 실사 조정)를 지정해 원장에 기록한다.
5. **직접 입고를 등록한다** — 대기 목록에 없는 상품을 검색해 입고한다.
6. **되돌린다** — 역방향 원장 행으로 상쇄한다.
7. **입고 이력을 조회한다** — 언제 · 무엇을 · 몇 개 · 되돌렸는지.
8. **후보 진입 결과를 확인한다** — `pool_entered` 값을 그대로 표시한다.

**이 화면에서 하지 않는 것**

                       — 원장에 단가 컬럼이 없다(§④-나)
    안전재고 기준 설정  현재 어느 화면에도 없다 — §「사장님 결정 대기」
    검수 처리          상품 사양 검수(ADM-PRD-020) 소관
    판매가 산정        판매가 그룹 소관
    상품 등록·분류 변경 상품 관리(ADM-PRD-010) 소관
    일괄 선택·일괄 입고 **규약으로 금지**(CLAUDE.md §목록 화면 규약) — §⑥ 참조

## ⑥ 인터랙션 — 흐름과 결과

### (가) 단건 입고 — **입력과 확정을 한 동작으로 묶는다**

    ① 대상 행에서 수량을 입력한다
    ② 사유를 선택한다 (입고 / 실사 조정)
    ③ 확정한다 → 서버가 원장 행과 재고를 함께 갱신한다
    ④ 결과를 표시한다 — 재고 «이전 → 이후» · 품절 해제 여부 · 후보 진입 여부

**⚠ 「수량 수정」을 별도 동작으로 두지 않는다.** 구 화면의 결함 1(§④-사)의 원인은
「수정」이 저장 동작처럼 보이지만 서버에 닿지 않는 것이었다. 대기 목록은 **파생**이고
수량은 **저장된 값이 아니라 이번 입고에 넣을 입력값**이므로, 수량은 확정과 함께
한 번만 전송한다. **입력만 하고 확정하지 않은 값은 «저장되지 않았다»고 화면이 밝힌다.**

### (나) 결과 문구는 서버 응답만 쓴다

`POST /stock-inbound/{code}` 응답 필드를 그대로 표시한다 —
`stock_before` · `stock_after` · `status_changed` · `pool_entered` · `undo_id` · `sku`.
**화면이 재고를 다시 계산하지 않는다**(CANON.md §2-1).

`pool_entered=false` 인 경우 **사유를 함께 표시한다.** 서버가 목록 응답의 `note` 에
사유를 이미 담는다(`api/admin_stock.py:66-79`) — 검수 미통과 · 판매가 미산정 ·
사양 미등록(`product_specs` 행 없음) · 품절 상태. **화면이 사유를 새로 판정하지 않는다.**

### (다) 되돌리기 — **삭제가 아니라 역방향 원장 행이다**

    · 되돌림은 `POST /stock-inbound/undo/{log_id}` 만 쓴다.
    · 원장 행을 삭제하지 않는다. `adjust` · `-qty` 행이 추가되고 재고가 복원된다.
    · 입고 전 상태가 `품절` 이었으면 `품절` 로 되돌린다.
    · 이중 되돌림은 409 — 화면은 「이미 되돌린 입고입니다」로 안내한다.
    · 현재 재고가 입고분보다 적으면 409 — 「이후 판매·조정이 있어 되돌릴 수 없습니다」.

**⚠ 되돌리기를 브라우저 변수에 의존하지 않는다.** 서버 API 는 **과거 회차도 받는다**
(§④-가). 화면은 **입고 이력을 서버에서 조회해** 그 목록에서 되돌릴 건을 고르게 한다.
구 화면은 `lastAction` JS 변수에 의존해 새로고침하면 되돌릴 방법이 사라졌다(결함 8).

⚠ **입고 이력 조회 API 는 현재 없다.** 원천은 `admin_operator_activity_logs`
(`action='stock_inbound'` · `'stock_inbound_undo'` · `kind='stock'`)이며 `detail` 에
`product_code` · `sku` · `qty` · `why` · `before` 가 들어 있다(실측). **신설이 필요하며,
되돌림 표시는 `detail->>'ref_log_id'` 로 파생한다** — 되돌림 API 가 그 키로 이중 되돌림을
막고 있으므로 같은 키를 쓴다(CANON.md §2-4 · 활동 기록 화면 전례).

### (라) 일괄 선택을 **붙이지 않는다**

**규약이다**(CLAUDE.md §목록 화면 규약 · 2026-08-05): 「재고 입고 — 수량이 상품마다 달라
하나를 일괄 적용하면 거의 항상 틀린다」. 체크박스만 붙이면 아무 일도 못 하는 단추가 되고,
회귀가 `data-bulk-select` 사용 화면에 일괄 동작 코드가 있는지 검사한다.

### (마) 상품 상세(ADM-PRD-010)와의 공존 — **슬라이스 97 이 난 자리다**

`products.stock_qty` 를 원장과 함께 갱신하는 코드 경로는 실측 7개다:

    api/admin_stock.py:159-164      이 화면 — 입고 확정 (inbound|adjust / manual)
    api/admin_stock.py:198-203      이 화면 — 되돌리기 (adjust / manual)
    api/admin_products.py:1347-1360 상품 상세 — 중복 편입 (adjust / manual, 두 행)
    api/admin_products.py:1418-1429 상품 상세 — 편입 되돌리기 (adjust / manual, 두 행)
    api/admin_refunds.py:111-115    환불 복원 (return / refund)
    api/orders.py:182-186           자체 주문 차감 (own_sale / order)
    api/catalog_ingest.py:476-492   카탈로그 적재 — UPSERT 로 재고를 넣고
                                    **직전 값과의 «델타»** 를 원장에 남긴다
                                    (adjust|inbound / catalog. 절대값이 아니다)

**경로가 여럿인 것 자체는 정상이다** — 사고는 **경로 하나가 원장을 남기지 않는 것**에서 났다
(슬라이스 97: 상품 상세 PATCH 가 `stock_qty` 만 바꾸고 원장을 건너뛰었다 ·
슬라이스 98: 카탈로그 적재가 절대값을 넣어 원장 없는 재고 7,547건이 생겼고, 지금은
기초 재고 `adjust`/`opening` **7,594행**으로 기록돼 있다).

**그래서 이 화면의 규칙:**

    · 재고를 바꾸는 모든 동작은 **원장 행을 함께 남긴다** — 예외를 두지 않는다.
    · 이 화면은 **`ref_kind='manual'` · `ref_id`=작업 기록 `log_id`** 로 남긴다
      (이미 그렇게 동작한다 — `api/admin_stock.py:159-161`).
    · **두 화면이 같은 일을 다르게 부르지 않는다**: 상품 상세의 재고 조정은
      「편입」이라는 별개 목적이고, 이 화면은 「입고·실사 조정」이다.
      **화면 문구가 그 구분을 밝힌다.**
    · 상품 상세에서 재고를 조정한 건도 **이 화면의 입고 이력에는 나타나지 않는다**
      (작업 기록 `action` 이 다르다). 이력 화면은 **`action='stock_inbound'` 계열만**
      다룬다고 밝히고, 전체 원장은 상품 상세·작업 기록으로 안내한다.

⚠ **입고 이력 목록에 「이 화면 밖에서 생긴 재고 변동」을 섞을 것인가는 미정이다** —
§「사장님 결정 대기」.

### (바) 직접 입고 등록

대기 목록에 없는 상품(재고 > 0 이고 안전재고 기준이 없는 상품)도 입고할 수 있어야 한다.

    · 후보는 **검색어가 있을 때만** 서버가 조회한다(`catalog_q`, 최대 50건 — 실측).
      전량 전송하지 않는다(슬라이스 54 규약).
    · 등록은 **곧바로 확정 동작**이다 — 표에 행을 얹고 「표에서 확정하세요」로
      미루지 않는다(구 화면 결함 4).
    · 매입가 입력칸을 **두지 않는다** — 원장에 단가 컬럼이 없어 입력해도 저장되지
      않는다(§④-가·나). 구 화면에는 그 칸이 있었다(`:227-228`).

### ⚠ 화면이 반드시 밝힐 것

**(가) 「저장되지 않은 입력」을 저장된 것처럼 보이면 안 된다**

구 화면의 실제 결함 세 가지(§④-사 결함 1·2·4)가 전부 이것이다. **서버에 닿지 않은
동작은 성공 문구를 내지 않는다.** 특히 「보류 — 재고 미반영」처럼 **처리 완료로 해석되는
문구**를 서버 상태 없이 표시하지 않는다.

**(나) 건수는 «전체»를 말하고, 페이지 값과 구분한다**

구 화면은 KPI·필터를 현재 페이지에서 셌다(결함 5·7). 서버가 `total` 을 주므로
**전체 기준 수치를 서버 값으로 표시하고**, 페이지 안 값과 섞지 않는다.

**(다) 「오늘 입고」는 서버가 세야 한다**

구 화면은 브라우저 세션 카운터를 「오늘 입고」로 표시했다(결함 6). 서버 실측
(`created_at::date = current_date` 인 `inbound` 행)은 **2026-08-17 기준 0건**이다.
**이 수치를 표시하려면 서버 집계가 필요하며 현재 API 에 없다** — 없는 동안은
수치를 지어내지 않고 표시하지 않는다(CANON.md §2-1).

**(라) 「매입 확정분」이라는 라벨을 매입 견적과 연결하지 않은 채 쓰지 않는다**

현재 값은 `stock_qty == 0` 에서 파생될 뿐이다(§④-마). 연결 전까지는 **재고 유형을
그대로 부른다**(재고 0 / 안전재고 미달). 매입 견적 확정분과의 연결은 §「사장님 결정 대기」.

**(마) 재고 변동은 견적에 즉시 반영된다**

입고 확정 즉시 `stock_qty > 0` 이 되어 추천 후보 게이트를 통과한다(§③-가).
**되돌릴 수 있지만 그 사이에 나간 견적은 그 재고로 나간다.** 되돌리기가
「없던 일로 만드는 것」이 아님을 화면이 밝힌다.

**(바) 인계는 재고를 차감하지 않는다**

`api/handoff.py` 모듈 docstring 이 「하지 않는 것」으로 명시한다 — 「재고를 차감하지
않는다」(실측). 즉 **인계 건수만큼 재고가 줄지 않는다.** 운영자가 「견적이 나갔는데 왜
재고가 그대로인가」를 오해하지 않도록, 재고를 줄이는 경로가 자체 주문(`own_sale`)과
실사 조정뿐임을 밝힌다.

**(사) 입고해도 후보에 안 들어가는 상품이 많다**

대기 15,725건 중 검수·가격 둘 다 완료는 **13,085건**이고, 사양 행(`product_specs`)
유무는 별개 게이트다. **입고만으로 추천에 진입하지 않는다** — `pool_entered` 를 실측으로
보여주는 이유다.

## 검증이 필요한 것 (확인자에게)

이 문서는 코드·DB 실측만으로 작성했다. **다음은 재지 못했다:**

1. **무세션 요청이 실제로 401 로 막히는지** — `api/auth.py` 코드 판독만 했다. 서버를
   띄우고 쿠키 없이 `GET /api/admin/stock-inbound` 를 호출해 확인해야 한다.
2. **viewer 등급이 POST 에서 실제로 403 인지** — `required_role()` 판독만 했다.
3. **`pool_entered` 가 실제 입고에서 참으로 나오는지** — 후보 게이트를 통과한 재고 0
   상품을 골라 확인해야 한다. ⚠ **검사는 부작용을 남긴다**(원장 행 · 작업 기록) —
   확인 후 되돌리고, 되돌림 행이 남는다는 사실까지 기록한다(슬라이스 78 전례).
4. **`api/admin_nav.py:254` 주석 정정** — nav 정본 소관. 이 문서는 사실만 적었다.
5. **`api/admin_stock.py:1-13` docstring 정정** — 코드 소관. 이 문서는 사실만 적었다.
6. **대기 조건 SQL 3중 복제**(§④-다) — 정본화 여부는 별건이다.
7. **작업 기록 `stock_inbound` 16건과 원장 `inbound`/`manual` 14건의 차이**(§④-나) —
   기록은 남았는데 원장 행이 없는 건이 있는지, 아니면 되돌림 뒤 상쇄 관계인지 재야 한다.
   **어긋난 것이 사실이면 「기록만 남고 원장이 비는 경로」가 있다는 뜻**이므로
   불변식(`stock_qty = SUM(qty_delta)`, 현재 위반 0건)과 별개로 확인이 필요하다.
