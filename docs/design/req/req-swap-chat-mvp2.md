## ① 화면 성격

**독립 화면이 아니라 `CUS-QUO-010`(mvp2 대화형 견적, 단일 SPA) 내부의 대화 계층이다.**
고객이 격자 카드를 하나 선택한 뒤(`state.selected`가 채워진 뒤) 열리는 오른쪽 견적
패널과 왼쪽 대화창 사이에서 동작한다. 새 라우트·새 파일을 만드는 작업이 아니라,
이미 있는 `#chatForm`(대화 입력) → `requestChange(text)` 경로의 내용을 채우는 작업이다.

**작업 화면(제한적 쓰기)** — 고객의 자연어 요청을 LLM이 **swap 파라미터로 변환**하고
(A-128 원문), 실제 부품 교체·되돌리기·고정 적용은 결정론 엔진(swap.py 계열)이
수행한다. **LLM은 파싱·설명만 하고 조합·적용 여부를 스스로 정하지 않는다** — A-02
(결정론 엔진)·A-03(LLM은 입력 파싱·근거 설명만, 견적을 생성하지 않는다)은 절대
규칙이고 이 대화층도 예외가 아니다. 이 정의서에 담긴 어떤 기능도 "LLM이 대안을
고른다"가 아니라 "LLM이 고객 말을 구조화하고, 엔진이 그 구조화된 요청에 대해
판정·실행한다"로 읽어야 한다.

## ③ 정의 — 이 계층이 없으면 무엇이 안 되는가

**A-128 결정문 원문**(2026-09-11 사장님 확정, `decision-log.md:6856-6858`):

> 한 줄 입력 → LLM 이 고객의 말을 판별해 우리 조건(게임·사무·AI 등)으로 →
> 격자(grid_quotes)에서 추출해 추천 목록 → 고객 선택 →
> **LLM 과의 대화로 그때그때 부품 교체(제안·비교·적용)**

같은 결정문이 순서 4단계를 승인했고(①목업 반입 ②파서→격자 ③스왑 대화층
④이미지·영상), **③이 이 문서의 대상이며 아직 미착수**다. ①·②는 완료됐다(2026-09-13/14
배포, HANDOFF.md 확인).

- **이 계층이 없으면 카드 선택이 대화의 끝이다.** 고객이 카드를 고르고 "이 구성
  좋은데 좀 더 조용한 케이스로 바꿀 수 있나요?"라고 물어도 돌아오는 답은 고정
  문구 `NOT_READY` + 「예산·용도를 바꾸려면 「＋ 새 대화」에서 다시 말씀해
  주세요.」(`app.js:173`)뿐이다. 부품을 하나라도 바꾸고 싶으면 **처음부터 다시
  대화해 격자에서 다른 카드가 나오길 바라는 것** 말고는 방법이 없다 — 그런데
  격자 카드는 사전 생성된 대표 구성 3장뿐이라(A-128 ②) 미세 조정을 반영할 수
  없는 구조다.
- **정체성 "신뢰 판매자"의 절반만 서 있다.** "왜 이 부품인지 설명한다"(A-01)는
  카드의 `reasons`로 이미 지켜지고 있다(`recommendationMarkup`·`detailMarkup`,
  app.js). 그런데 "설명을 들은 고객이 그 설명에 동의하지 않을 때 대화로 조정할
  길"이 없다 — 설명은 일방적으로 끝난다.
- **이미 있는 자산(swap.py)이 완전히 묶여 있다.** `api/swap.py`(577줄, 실측)에
  세 엔드포인트(`/candidates` · `/apply` · `/refine`)가 이미 동작하는데, mvp2의
  세션리스 구조 때문에 **호출할 방법 자체가 없다**(④ 참조). 자산은 있는데 그
  자산을 쓸 "내 견적"이라는 개체가 서버에 없다.
- **A-128이 명시한 다섯 동사(제안·비교·적용·되돌리기·고정) 중 코드에 실재하는
  것은 절반도 안 된다** — ④·⑤에서 동사별로 정확히 무엇이 있고 무엇이 없는지를
  다룬다.

**이 계층이 하지 않는 것**(비범위에서 다시 정리): 엔진의 조합 로직 자체를 바꾸는
일 · 새 추천을 만드는 일(그것은 ①②단계·격자 소관) · 결제·장바구니(A-128 범위 밖,
`addToCart()`는 여전히 "준비 중" 토스트만 띄운다, `app.js:181`).

### 4-2. swap.py 기존 계약 — 재사용 가능한 자산 (읽기로만 확인, 원장 미오염)

| 엔드포인트 | 입력 | 하는 일 | 실측 확인 |
|---|---|---|---|
| `POST /api/swap/candidates` | `{session_id, tier, access_key}` | **읽기 전용** — 그 견적의 슬롯별 대안 목록(가격차·연쇄 여부 포함)을 8슬롯 전부에 대해 반환 | 존재하지 않는 `session_id=999999999`로 curl → `404 {"detail":"그 상담을 찾을 수 없습니다"}`(계약대로 동작) |
| `POST /api/swap/apply` | `{session_id, tier, access_key, changes:[{slot,product_code}]}` | 실제 교체 적용 — 새 `quote_snapshots` 행 INSERT + `swap_event_logs` 원장 기록 | 같은 방식으로 존재하지 않는 session_id → `404`(같은 문구). **`require_session_owner`가 모든 INSERT보다 먼저 실행돼 여기서 막히면 원장에 아무 것도 안 남는다** — `api/swap.py:426-428`(apply는 `engine.begin()` 블록 안에서도 게이트 확인이 첫 줄) 확인. 원장 오염 없이 계약만 확인했다 |
| `POST /api/swap/refine` | `{session_id, tier, access_key, text}` | 자유 발화를 `talk.parse_talk`으로 파싱 후 매칭되면 적용. 200 고정(실패도 정상 응답) | 같은 방식으로 404 확인. **`require_session_owner`가 `talk.parse_talk`(LLM 호출) 이전에 실행돼(`api/swap.py:491-494`), 404가 나면 LLM 비용도 안 든다** — 방문자 호출 한도를 축내지 않고 계약만 확인했다 |

**⚠ 실측으로 바로잡을 것 — "제안이 GPU 한정"의 정확한 위치.** 작업 배경 문서는
"제안(GPU 한정)"이라 적었는데, 코드를 읽어보면 더 정확히는 이렇다:

- `candidates()`(구조화 데이터 API)는 **8슬롯 전부**에 대해 대안을 만든다
  (`api/swap.py:254-303`, `for s in SLOTS:` 루프 — GPU만 도는 코드가 아니다).
- **GPU 한정인 것은 `refine()`(자연어 인식) 하나뿐이다** — `_norm_part`의
  정규화 원천(`catalog_map.gpu_chipset_key`)이 GPU 모델명만 읽기 때문이다
  (`api/swap.py:12-17` 모듈 docstring 자인).
- **그런데 mvp2에는 슬롯별 [변경] 버튼이 아예 없다**(`mockups/mvp2/app.js` 전수
  확인 — `data-swap`·구조화 슬롯 선택 마크업 0건, mvp1 `s3-detail.html`에는 있다).
  즉 mvp2가 지금 가진 유일한 입력 통로는 자유 발화(`#chatForm`)뿐이고, 그
  통로로 닿을 수 있는 것은 `refine()`뿐이라 **"자유발화로 닿는 제안은 사실상
  GPU 한정"이라는 결론 자체는 맞다** — 다만 원인은 "데이터 API가 GPU만 지원해서"가
  아니라 "① mvp2에 구조화 버튼이 없고 ② 자유발화 인식이 GPU만 되기 때문"이라는
  **두 개의 별도 간극**이다. ⑤-1에서 이 둘을 각각 다룬다.

### 4-3. ★★ 결정적 구조 간극 — 카드 선택이 "내 견적"을 만들지 않는다

`swap.py`의 세 함수 전부 `_load_snapshot(conn, session_id, tier)`로 시작한다
(`api/swap.py:85-93`). 이 함수는:

```sql
SELECT snapshot_id, items, ... FROM quote_snapshots
 WHERE session_id=:s AND quote_type=:t ORDER BY snapshot_id DESC LIMIT 1
```

`session_id`는 `consult_sessions` 테이블(ERD 12번 섹션, `docs/06_db-erd.md:972-989`)을
가리킨다. 옛 S1~S3 흐름(`api/recommend.py:1521-1538`)에서는 견적을 낼 때
`consult_sessions` 행 하나(**+ `access_gate.new_key()`로 만든 `access_key`**,
`recommend.py:1527`) 아래에 quote_type='value'/'recommend'/'highend' 세 개의
`quote_snapshots`를 함께 만든다. 소유권 확인은 `access_gate.require_session_owner`
(`api/access_gate.py:160-190`)가 `consult_sessions.access_key`(32자 URL-safe
토큰, `?k=` 쿼리 또는 `X-Access-Key` 헤더)를 상수 시간 대조하는 방식이다.

**그런데 §4-1에서 실측했듯 `/api/grid/recommend`는 `consult_sessions`도
`quote_snapshots`도 만들지 않는다.** 격자(`grid_cells`×`grid_quotes`, 사전
생성돼 매일 갱신되는 정적 데이터, 여러 방문자가 공유)에서 SELECT만 해서 카드를
만든다. **즉 지금 mvp2에서 카드를 선택하는 순간, "이 고객의 것"이라고 부를 서버측
개체가 하나도 생기지 않는다.** swap.py의 세 엔드포인트 모두 `session_id`를
필수로 받는데, mvp2에는 넘길 `session_id`가 없다.

**DB 실측**(2026-09-14, 읽기 전용 SELECT): `consult_sessions` 13,533행, 그중
`access_key IS NULL` 5,988행(게이트 도입 이전 행), 최근 10행은 전부
`access_key` 있음(`mode='guided'|'chat'`, 옛 S1 흐름이 계속 쌓고 있는 것 —
mvp2가 아니라 mvp1 S1이 만드는 행). **mvp2가 만든 행은 0건이다**(mvp2는 애초에
이 테이블에 쓰지 않는다).

**해소 방법은 두 갈래이고, 이 정의서는 고르지 않는다**(마지막 절로):

- **방법 A**: 카드 선택 시 `consult_sessions`+`quote_snapshots`를 새로 만들어
  (격자 payload를 그대로 복사) 기존 swap.py 인프라·access_key 게이트를 그대로
  재사용한다. `orders.session_id`가 이미 이 테이블을 참조하도록 설계된 원장
  관례(ERD)와도 맞는다.
- **방법 B**: 격자 `quote_id`를 직접 다루는 새 개인화 계층을 만든다 — access_key
  게이트·`swap_event_logs` 원장을 처음부터 다시 설계해야 하고, CANON §1 "정본을
  복제하지 않는다"에 어긋날 위험이 크다.

### 4-4. ★ 추가로 발견한 간극 — 티어 어휘가 서로 다르다 (이번 조사 신규 발견)

방법 A를 쓰더라도 **한 겹 더 있다.** `swap.SwapQuery.tier: str`은 `_load_snapshot`
안에서 **그대로 `quote_type` 컬럼값으로 바인딩**된다(`api/swap.py:66-93`). DB
실측:

| 테이블.컬럼 | 실제 값 집합(distinct, 2026-09-14 SELECT) |
|---|---|
| `quote_snapshots.quote_type` | `{value, recommend, highend}` — 옛 3단계 티어 |
| `grid_cells.tier` | `{팝콘 3, 팝콘 5, 팝콘 5+, 팝콘 7, 팝콘 7+, 팝콘 9, 팝콘 X}` — A-129 신규 7단 티어 |

**mvp2 카드의 `tier` 필드는 두 번째 집합(`팝콘 5` 등, `grid_public.py:291`
`"tier": r["tier"]`)이다.** 만약 그 값을 그대로 swap.py의 `tier` 파라미터로
넘기면 `WHERE quote_type='팝콘 5'`가 되어 **매치되는 행이 영원히 0건**이다 —
그리고 `_load_snapshot`의 404 메시지는 "그 상담을 찾을 수 없습니다"라서, 세션
자체는 있는데 티어 어휘가 안 맞는 경우에도 **"세션이 없다"고 잘못 말하게 된다**
(원인 오귀속). 방법 A를 택해도 swap.py의 `tier`/`quote_type` 처리를 그대로 둘지,
격자 티어 7종을 받아들이게 고칠지, 아니면 mvp2 쪽에서 격자 티어를 옛 3단계로
매핑할지 — **이 자체가 별도 결정 지점**이다(마지막 절에 등재).

### 4-5. 되돌리기(revert) 관련 스키마 상태 — 있는 것과 없는 것

| 무엇 | 실측(2026-09-14 SELECT) |
|---|---|
| `quote_snapshots` 컬럼 | `snapshot_id, session_id, quote_type, items, companion, total_amount, created_at` — 7컬럼. **INSERT-only**, 이전 스냅샷을 지우거나 표시하는 컬럼 없음 |
| `_load_snapshot`의 조회 방식 | `ORDER BY snapshot_id DESC LIMIT 1` — **항상 최신 한 건만** 읽는다(`api/swap.py:88`) |
| 세션 12127(스왑이 반복된 실사례) 스냅샷 수 | `quote_type='recommend'`에서만 5건 누적(snapshot_id 오름차순) — 매 교체가 새 행을 추가할 뿐 이전 행을 참조·표시하는 장치 없음 |
| `swap_event_logs` 컬럼 | `log_id, from_product, to_product, user_id, created_at, session_id, slot, price_delta` — 8컬럼, 650행(2026-09-14). **`ref_log_id` 컬럼이 없다** |
| CANON 절대 규칙 4번 | *"되돌림은 삭제가 아니라 역방향 전이다. 역참조 키는 `ref_log_id`"*(`.claude/CANON.md:65`, `CLAUDE.md:584`) |

**즉 되돌리기는 스키마 차원에서 전무하다** — 스냅샷 히스토리를 "조회"할 API도,
특정 시점으로 "복원"할 API도, 원장 행에 되돌림을 표시할 `ref_log_id` 컬럼도
없다. ⑤-4에서 이 공백 위에 지을 기능을 다룬다.

### 4-6. 부품 고정(lock) 관련 코드 상태 — 전무, 다만 혼동하기 쉬운 이웃 개념 있음

`lock`·`고정`·`pin` 관련 전수 검색(`api/swap.py`·`api/candidates.py`·
`api/recommend.py`·`mockups/mvp2/app.js`·`mockups/mvp1/s3-detail.html`) 결과
**스왑 대화 중 슬롯을 고정하는 코드는 0건**이다. `_find_chain`
(`api/swap.py:184-206`)은 위반 슬롯을 자동으로 가격 오름차순 교체하며, 고객이
"케이스는 그대로 둬" 같은 의도를 표현할 방법이 없다 — 지금 로직대로면 고정하고
싶은 슬롯도 연쇄에 휩쓸려 바뀐다.

**혼동 주의 — `recommend.py`에 "pinned"가 있지만 다른 개념이다.** `api/recommend.py:1245-1259`
`_attach_pin()`은 **최초 추천 시점에 고객이 지정한 GPU 모델**("이 GPU로 해줘")을
반영했는지 여부를 응답에 표시하는 것이다(A-101 "지정 부품" 선례,
`decision-log.md:5497-5521`). 이것은 **최초 견적 생성 단계의 개념**이고, 이번
문서가 다루는 "스왑 대화 중 슬롯을 고정해 연쇄 해소에서 보호하는" 개념과는
**목적도 시점도 다르다**. 같은 낱말(지정/고정)을 쓰지만 구현·설계 시 섞으면
안 된다.

### 4-7. 접근 게이트·호출 한도 상태

  전혀 없다**. 이번 조사에서 새로 발견한 사실이며 ⑦에서 다룬다.
- **방문자 식별**: `api/visitor.py`의 `pc_vid` 쿠키(1년, `HttpOnly`) — mvp2도

  §4-3의 방법 A/B 선택과 얽혀 있다 — 마지막 절로.

## ⑤ 기능 (동사) — A-128 다섯 동사 + 부대 기능

**표시 규칙**: 각 항목 끝에 코드 현황을 표시한다 — **[됨]** 지금 코드로 된다 ·
**[일부]** 부분적으로 된다 · **[전무]** 코드에 없다, 신규 필요.

### ⑤-1. 제안 — 슬롯별 대안을 보여준다

1. GPU를 자유 발화로 요청하면 대안을 찾는다("RTX 5070으로 바꿀 수 있나요"). **[됨]**
   — `refine()`이 `talk.parse_talk`으로 GPU 모델명을 인식해 재고에서 찾는다.
2. GPU 외 7개 슬롯(CPU·MB·RAM·CASE·COOLER·POWER·SSD)을 자유 발화로 요청하면
   대안을 찾는다("케이스 더 조용한 걸로 바꿀 수 있나요"). **[전무]** — `_norm_part`가
   GPU 정규화만 갖고 있어 구조적으로 100% 무음이다(§4-2). 대안 **데이터** 자체는
   `candidates()`가 이미 8슬롯 전부 만든다 — 자연어 **인식**만 없다.
3. 슬롯을 명시하지 않고 "다른 것도 보여줘" 같은 모호한 요청을 처리한다. **[전무]**
   — 지금 파싱 체계는 슬롯을 특정해야 매칭이 시작된다(GPU 모델명 매칭 방식).
   "무엇을 바꾸고 싶으신가요"로 되묻는 절차가 없다.
4. 구조화 버튼(슬롯별 [변경])으로 대안을 연다. **[전무]** — mvp2에 그런 마크업이
   없다(mvp1 `s3-detail.html`에는 있다, §4-2). candidates() API를 그대로 쓸 수
   있는지는 방법 A/B 선택에 달려 있다.
5. 대안 목록을 정렬·필터하는 기준을 고객이 지정한다("더 조용한 것 위주로").
   **[전무]** — candidates()는 이미 "가격이 가까운 순"으로 정렬하지만
   (`api/swap.py:294-301`), 고객이 그 기준 자체를 바꿀 방법은 없다.

### ⑤-2. 비교 — 적용 전 미리보기를 보여준다

1. 대안 하나를 골랐을 때 가격 변화만 보여준다("이걸로 바꾸면 +52,000원").
   **[일부]** — `candidates()` 응답의 `price_diff` 필드는 이미 있다
   (`api/swap.py:276`). 이것을 **대화 응답으로 문장화**하는 계층은 없다.
2. 대안을 골랐을 때 **전체 구성**이 어떻게 달라지는지(연쇄 포함) 미리 보여준다 —
   적용하기 «전» 단계에서. **[전무]** — `candidates()`가 `chain` 필드로 연쇄
   대상은 알려주지만(`api/swap.py:280-292`), 그것은 "이 대안을 고르면 자동으로
   같이 바뀔 것"의 사전 목록이지, 고객이 "적용" 의사를 밝히기 «전» 대화로
   되물어 확인받는 별도 턴은 없다 — 지금은 대안을 클릭하는 것 자체가 곧 적용
   요청이다(mvp1 s3-detail.html `applySwap()`도 동일 — 버튼 클릭이 즉시
   `/api/swap/apply` 호출).
3. 서로 다른 대안 두 개 이상을 나란히 비교한다("A랑 B 중에 뭐가 나아요").
   **[전무]** — candidates() 응답은 슬롯당 대안 «목록»을 주지만, 그중 두 개를
   골라 비교 표로 만드는 개념·API가 없다.
4. 지금 구성과 "격자에서 처음 추천받은 카드"를 비교한다(누적 변경 후 원본 대비
   무엇이 달라졌는지). **[전무]** — §4-3의 구조 간극과 직결된다. 카드 원본이
   서버에 개인화 저장되지 않으므로 "원본"이라는 비교 기준점 자체가 없다.
5. 비교 결과에 "지금 견적은 예산 대비 몇 %"처럼 격자 티어 범위(`tier_range`)를
   같이 보여준다. **[전무]** — 스왑 후 총액이 원래 티어 범위(`tier_range.min/max`,
   `grid_public.py:261`)를 벗어나는지 알려주는 로직이 없다. 카드 단계에서는
   `over_budget` 배지가 있지만(`app.js` `cardMarkup`), 스왑 «후» 총액에 같은
   판정을 다시 적용하는 코드는 없다.

### ⑤-3. 적용 — 실제로 교체를 실행한다

1. GPU를 자유 발화로 적용한다. **[됨]** — `refine()`이 매칭·연쇄 확인 후
   `_apply_changes()`로 실행한다(§4-2). 단, §4-3·§4-4의 구조 간극(session_id·
   tier 어휘)이 풀려야 mvp2에서 실제로 호출 가능하다.
2. 구조화 [변경] 버튼으로 임의 슬롯을 적용한다. **[전무]** — apply()는 어느
   슬롯이든 받을 수 있지만(`ApplyBody.changes: list[Change]`), mvp2에 그
   버튼이 없다.
3. 연쇄 해소가 필요한 교체를 적용하기 전 "이것도 같이 바뀝니다"를 대화로
   설명하고 **명시적 동의**를 구한다. **[전무]** — 지금 `_chain_reason()`
   (`api/swap.py:174-181`)은 고정 템플릿 문구를 만들 뿐이고, 이 문구는
   **대안 목록에 이미 실려** 나간다(적용 «전» 정보 제공) — 그런데 "예/아니오"로
   갈리는 별도 확인 턴은 없다. mvp1 UI도 "대안 버튼 클릭 = 연쇄 포함 즉시
   적용"이라 실질적으로 **사전 고지 + 클릭이 곧 동의**의 원샷 구조다. 대화형
   확인("케이스도 같이 바뀌는데 진행할까요?" → "네" 요구)을 넣을지는 설계
   선택지다.
4. 적용 실패(품절·호환 불가) 시 대안을 자동으로 다시 제시한다. **[전무]** —
   지금은 409 상태코드 + 사유 메시지만 돌아온다(`api/swap.py:337-344`).
   "그럼 다음으로 저렴한 것은요?" 같은 후속 제안 루프가 없다.
5. 여러 슬롯을 한 대화 턴에서 동시에 적용한다("GPU랑 케이스 둘 다 바꿔줘").
   **[일부]** — `apply()`(구조화)는 `changes: list[Change]`로 이미 다중 슬롯을
   한 번에 받는다(원자적 적용 — 하나라도 위반이면 전체 409). **자연어 경로
   (`refine()`)는 한 번에 GPU 하나만 파싱한다** — 다중 슬롯 자연어 요청을
   나누어 순차 처리할지, 아예 못 받는다고 말할지는 미정이다.
6. 적용 후 "다음엔 무엇을 도와드릴까요"로 대화를 이어간다. **[전무]** —
   refine()의 성공 응답은 결과 문장(`message`)만 주고 대화를 어떻게 이어갈지는
   화면(app.js) 쪽 설계다. mvp2에 아직 이 흐름 자체가 없다.

### ⑤-4. 되돌리기 — 이전 상태로 돌아간다

1. 직전 한 단계만 되돌린다("방금 바꾼 거 취소해줘"). **[전무]** — §4-5.
   `_load_snapshot`이 항상 최신 한 건만 읽어서, "그 전 스냅샷을 다시 최신으로
   만드는" API가 없다. CANON 절대 규칙 4번(되돌림은 역방향 전이, `ref_log_id`)에
   맞춰 설계해야 한다 — 단순히 `snapshot_id`를 하나 낮춰 읽는 것이 아니라, 옛
   스냅샷 내용을 **새 스냅샷으로 다시 INSERT**하면서 `ref_log_id`로 원본을
   가리키는 방식이어야 원장 규약과 맞는다.
2. 여러 단계 히스토리를 탐색한다("2번 전 상태로", "아까 그 GPU로 돌아가서
   다시 볼래"). **[전무]** — 히스토리 «조회» API가 없다. session별 스냅샷
   목록을 시간순으로 보여주는 엔드포인트 자체가 없다(swap_event_logs는 있지만
   슬롯당 단일 교체 이벤트 로그이지, 스냅샷 계보를 재구성하는 조회 API가 아니다).
3. "처음 추천으로 리셋"(격자 카드 원본으로 되돌리기)과 "직전 한 단계 되돌리기"를
   구분한다. **[전무]** — §5-2-4와 같은 이유로 "원본"이라는 기준점 자체가
   저장되지 않는다. 방법 A(§4-3)를 택하면 최초 `quote_snapshots` 행이 그
   기준점 역할을 할 수 있다.
4. 되돌리기 자체도 대화로 요청한다("바꾸기 전으로 돌려줘")와 버튼으로 요청하는
   것을 함께 지원할지. **[전무]** — 자연어 되돌리기 의도 인식 자체가 없다
   (`talk.py`의 라벨 6종에 "되돌리기" 관련 라벨 없음, `api/talk.py:209` `LABELS`
   확인).

### ⑤-5. 부품 고정(lock) — 특정 슬롯을 변경 대상에서 뺀다

1. 고객이 "케이스는 그대로 둬" 같은 발화로 슬롯을 고정한다. **[전무]** — §4-6,
   코드에 전무.
2. 몇 개까지 동시에 고정할 수 있는지 상한을 둔다. **[전무]** — 정책 자체가
   없다. (참고 삼아 — 8슬롯 중 몇 개를 고정 가능하게 할지는 설계 판단이지
   이 문서가 임의로 정하지 않는다.)
3. 고정된 슬롯이 `_find_chain`의 연쇄 해소 대상이 되면 무엇을 하는가 —
   ① 그 슬롯을 건너뛰고 다른 해소 경로를 찾는다 ② 해소 경로가 없으면 적용
   자체를 막는다(409) ③ 사용자에게 "고정을 풀어야 가능하다"고 되묻는다. **[전무]**
   — `_find_chain`(`api/swap.py:184-206`)은 고정 개념을 아예 모른다. 지금
   그대로면 고정 요청과 무관하게 연쇄에 휩쓸려 바뀔 수 있다(작업 배경이
   정확히 지적한 위험). 셋 중 무엇을 택할지는 사장님 결정 지점.
4. 고정 상태가 대화 중 계속 표시된다("케이스(고정됨)"). **[전무]** — 표시
   여부는 UI 설계 소관이지만, 그 상태를 담을 서버측 데이터 자리 자체가
   없다(quote_snapshots에 "고정된 슬롯 목록"을 실을 필드가 없다).

### ⑤-6. 예산 기반 자유발화 — "20만원 줄여줘" 파라미터화

1. 절대 금액 절감 요청을 처리한다("20만원 줄여줘" — A-128 원문 예시). **[전무]**
   — talk.py의 `_BUDGET_NUM`/`_BUDGET_BOUND`(`api/talk.py:190-191`)는 **최초
   견적의 절대 예산 상한**("150만원 이하")을 읽는 정규식이지, "지금 견적에서
   상대적으로 얼마를 줄인다"는 델타 요청을 위한 것이 아니다. 라벨 자체
   (`LABELS = ("예산","용도","선호","부품","플랫폼","제외")`, `api/talk.py:209`)에
   델타 예산을 담을 자리가 없다.
2. 상대적 절감 요청을 처리한다("더 저렴하게"). **[전무]** — 목표 금액이 없는
   모호한 요청이라 "얼마나"를 되물어야 하는지, 임의 비율(예: 10%)을 적용할지
   결정이 필요하다.
3. 극단적 절감 요청을 처리한다("최대한 저렴하게"). **[전무]** — 이 경우
   격자의 하위 티어 카드로 안내하는 것이 나을지, 지금 구성 내에서 슬롯별
   최저가로 전부 바꾸는 것이 나을지도 결정이 필요하다(후자는 8슬롯 동시
   교체이므로 ⑤-3-5와도 얽힌다).
4. 어느 슬롯을 낮출지 결정하는 주체 — ① 엔진이 정책(예: GPU를 가장 먼저 낮춘다,
   호환 규칙과 무관한 슬롯부터)으로 자동 결정 ② 고객에게 "어느 부품을
   낮출까요"로 후보를 제시하고 고객이 선택. **[전무]** — 결정 자체가 안
   내려져 있다. 참고로 엔진의 기존 예산 배분 개념(용도별 배분율,
   `usage_alloc.py`)은 **최초 추천 시점**에만 쓰이고, 스왑 대화 중 "이미
   선택된 구성에서 일부만 낮추는" 시나리오에 그대로 재사용될지는 미검증이다.
5. **반대 방향 요청**("성능 더 올려줘", 예산 증액 없이 — 이번 조사에서 후보
   목록에 없던 것을 추가로 찾음). **[전무]** — A-128 예시는 절감(「20만원
   줄여줘」) 쪽만 들었지만, 대칭적으로 "더 좋은 걸로"도 같은 파라미터화 문제를
   가진다. 절감/증액 요청을 같은 메커니즘으로 다룰지 서로 다른 처리가
   필요한지도 결정 사항이다.

### ⑤-7. 카드 전환 vs 지금 견적 다듬기 — 상태 전환

1. 스왑 대화 중 채팅 이력에 남아 있는 **다른** 카드를 다시 클릭해 전환한다.
   **[됨, 단 무경고]** — `selectQuote(index)`는 클릭 시 조건 없이
   `state.selected = copy(q)`로 덮어쓴다(`app.js:167`). 지금까지 진행 중이던
   스왑 조정 내용을 지운다는 확인 절차가 없다(스왑 자체가 아직 없어 "지울
   것"도 없는 상태지만, 스왑이 생기면 이 무경고 덮어쓰기가 데이터 손실
   지점이 된다).
2. 같은 카드 세트가 아니라 **새로 추천받은** 카드 세트로 넘어갈 때는 이전
   카드가 자동으로 비활성화된다. **[됨]** — `recommend()` 시작 시
   `document.querySelectorAll('[data-select]').forEach(b=>b.disabled=true);`
   (`app.js:134`)가 **그 시점까지 DOM에 있던 모든 카드**의 선택 버튼을
   잠근다. 새 카드는 이후 `innerHTML`로 추가되는 새 버튼이라 잠기지 않는다.
   즉 "낡은 추천 묶음"과 "지금 추천 묶음"은 이미 구분되지만, **묶음 안에서는**
   여전히 무경고 재선택이 가능하다(위 1번).
3. "지금 견적을 계속 다듬기"(스왑 대화 지속)와 "다른 카드로 바꾸기"가 같은
   입력창을 공유할 때, 어느 쪽으로 해석할지 파서가 정한다. **[일부]** —
   지금은 `requestChange()`가 `state.selected` 유무만으로 이분화한다
   (`app.js:170-174`): 선택 전이면 조건 변경(파서)으로, 선택 후면 `NOT_READY`.
   스왑이 생기면 "선택 후"의 그 자리가 스왑 대화가 되는데, 그 안에서 다시
   "조건을 바꾸고 싶다"(새 카드를 원한다)는 요청과 "이 카드를 다듬고 싶다"는
   요청을 구분하는 로직이 새로 필요하다.

### ⑤-8. 새 대화("＋ 새 대화") 시작 — 상태 초기화

1. 새 대화 시작 시 진행 중이던 스왑 상태를 지운다. **[됨, 대상 없음]** —
   `home()`(`app.js:183`)이 `state.selected`·`state.constraints`·
   `state.history`·`state.quotes`·`state.grid`를 전부 `null`/`[]`로 리셋한다.
   지금은 스왑 상태 자체가 없어 "지워지는 것"이 없을 뿐, 스왑 히스토리
   객체가 새로 생기면 이 함수가 그것도 같이 지워야 한다(빠뜨리면 다음 대화에
   이전 세션의 스왑 흔적이 남는 사고가 된다).
2. 새 대화 시작 시 **서버측** 개인화 견적(방법 A를 택했을 경우의
   `consult_sessions` 행)을 어떻게 하는가 — 그대로 두는지(원장 보존), 명시적으로
   "종료" 표시를 남기는지. **[전무, 방법 A 선택 시 필요]** — `consult_sessions`에
   상태 컬럼이 없다(스키마 실측: `session_id, member_id, mode, constraints,
   created_at, data_origin, user_id, access_key` 8컬럼 — 활성/종료 개념 없음).
3. 새 대화 시작 직후 곧바로 이전 access_key로 이전 견적에 접근을 시도하면
   (뒤로가기 등) 무엇이 뜨는가. **[전무]** — 지금은 애초에 access_key가
   화면에 없어 발생하지 않는 시나리오지만, 방법 A를 택하면 "만료됐다" vs
   "여전히 유효하다"를 정해야 한다.

### ⑤-9. AI 워크스테이션(완제품) 카드 — 비대상 처리

1. AI 워크스테이션 카드에는 스왑 대화층이 아예 반응하지 않는다. **[명시
   필요, 코드는 자연히 그렇게 됨]** — A-132(`decision-log.md:7113-7114`)가
   이미 "완제품 — 사장님이 구성해 파는 상품 1개, **교체 대상이 아니다**"로
   확정했고, `req-ai-workstation-shelf.md` 비범위에도 "부품 교체 대화(A-128
   ③)에 완제품을 넣지 않는다"고 명시돼 있다. `GET /api/grid/workstations`
   응답에는 `parts`/슬롯 정보 자체가 없어(§4-8 인접 문서 확인) 스왑 엔진에
   넣을 입력이 구조적으로 없다 — 그래서 "막아야 하는 예외"라기보다 **"애초에
   눈에 들어오지 않는" 자연스러운 비대상**이다.
2. 고객이 완제품을 선택한 뒤(`mall_url`로 새 창 이동, §4-8) 그 창을 닫고
   돌아와 "이거 GPU만 바꿀 수 있나요"라고 물으면 어떻게 답하는가. **[전무]**
   — mvp2 자체가 완제품을 "선택"하는 개념(`state.selected`에 담는 것)이
   없다(완제품은 몰 페이지로 나가는 링크일 뿐, app.js `workstationsMarkup`에
   `data-select` 없음). 즉 이 질문 자체가 지금 구조에서는 발생하지 않지만,
   "완제품도 조립 견적처럼 고를 수 있다"고 고객이 오해할 경우의 안내 문구는
   필요할 수 있다.

### ⑤-10. 접근 게이트 — 누구의 견적인지 확인한다

1. `access_key` 링크 기반(기존 swap.py 방식)을 그대로 쓴다. **[일부, 방법 A
   전제]** — 기존 인프라 재사용이 가장 저항이 적으나, mvp2는 지금 URL에
   `?k=`를 노출하지 않는 세션리스 SPA라(§4-1), 링크 기반 게이트를 화면
   상태(예: 메모리·localStorage)에 어떻게 심을지 별도 설계가 필요하다.
2. 방문자 쿠키(`pc_vid`, `api/visitor.py`) 기반으로 소유권을 판정하는 새
   방식을 쓴다. **[전무]** — 지금 `pc_vid`는 집계·한도 용도로만 쓰이고
   (`access_gate.subject_of`), "이 쿠키를 가진 사람만 이 견적을 스왑할 수
   있다"는 소유권 판정으로 쓰인 전례가 없다.
3. 대화 도중 쿠키가 사라지거나(시크릿 모드 등) 다른 기기로 접속하면 무엇을
   하는가. **[전무]** — 두 방식 다 아직 결정 전이라 이 경계도 함께 미정이다.

### ⑤-11. 멀티턴 순차 스왑 — 여러 부품을 차례로 바꾸는 대화 흐름

1. "GPU 바꿔줘" → 적용 → "이번엔 케이스도" → 적용, 이런 순차 대화를 지원한다.
   **[일부]** — 개별 적용(`refine()`)은 매번 새 `quote_snapshots` 행을
   만드므로(§4-5) **기술적으로는** 순차 호출이 가능하다 — 다만 매 턴이 최신
   스냅샷을 다시 읽는 구조라(`_load_snapshot`이 항상 `DESC LIMIT 1`) 두 번째
   요청은 첫 번째 요청이 만든 새 스냅샷 위에서 계속되는 것이 **맞다**(설계상
   누적이 자연히 된다). 문제는 §4-3·§4-4의 session_id·tier 문제가 안 풀리면
   첫 요청부터 불가능하다는 것.
2. 매 턴 새 스냅샷을 만들 것인지, 여러 변경을 모아 뒀다가 "적용" 확정
   시점에 한 번에 반영할 것인지. **[전무, 결정 필요]** — 지금 `_apply_changes`는
   `ch_by_slot: dict`를 받아 **한 번의 호출에서 여러 슬롯을 원자적으로**
   반영할 수 있는 구조다(`api/swap.py:310-392`). 자연어 대화에서 "GPU도
   바꾸고 케이스도 바꿀래"처럼 한 문장에 여러 요청이 섞였을 때 그것을 한
   번에 모아 반영할지, 턴마다 개별 반영할지는 사용자 경험과 직결된 결정이다.
3. 순차 스왑이 이어질수록 방문자 호출 한도(§4-7, 분당 5·일 40)를 더 빨리
   소진한다. **[위험, 신규 발견]** — `refine()` 자체가 `talk.parse_talk()`을
   호출하므로(§4-2) **자연어 스왑 대화 한 턴 = LLM 호출 1회**다. talk.py
   자신의 주석이 이미 경고한다: *"한 사람이 태우는 호출 수가 대화 길이만큼
   늘었다 — … 「한 사이클 최대 4회」는 더 이상 성립하지 않는다"*(`api/talk.py:45-47`).
   스왑 대화가 추가되면 한 세션의 LLM 호출 수가 더 늘어난다 — 지금 한도값이
   여전히 적절한지는 이 문서 범위 밖이지만(정책 값 변경은 `rate_limit_policies`
   테이블 소관), **구조화 버튼 경로(candidates/apply)는 한도 자체가 없다는
   사실**(§4-7)과 겹쳐 고려해야 한다.

## 사장님 결정이 필요한 지점

아래는 이 문서가 **임의로 정하지 않고** 선택지와 근거만 남기는 지점이다. 제목만
먼저 나열하고, 각각 아래에 선택지를 적는다.

1. **카드 선택 시 개인화 방법 — A(consult_sessions+quote_snapshots 신규 생성) vs
   B(격자 quote_id 직접 개인화 계층 신설)**
2. **티어 어휘 불일치 해소 — swap.py의 quote_type 3종을 격자 티어 7종에 맞게
   확장할지, mvp2가 격자 티어를 옛 3종으로 매핑해 보낼지**
3. **접근 게이트 방식 — access_key 링크 유지 vs 방문자 쿠키(pc_vid) 기반 전환**
4. **비교(compare) UI의 구체적 트리거 조건 — 대안 목록에 가격차만 보여줄지,
   적용 전 별도 "미리보기" 확인 턴을 둘지, 서로 다른 대안 간 비교까지 지원할지**
5. **되돌리기 범위 — 직전 1단계만 vs 히스토리 전체 탐색 vs "처음 추천으로
   리셋", 셋을 모두 지원할지 일부만 지원할지**
6. **부품 고정(lock) 정책 — 동시 고정 가능 개수 상한, 고정된 슬롯이 연쇄
   해소 대상이 됐을 때 적용 자체를 막을지 다른 경로를 찾을지**
7. **예산 기반 자유발화의 슬롯 선택 주체 — 엔진 정책이 자동으로 낮출 슬롯을
   고를지, 고객에게 후보를 제시해 고르게 할지**
8. **구조화 경로(candidates·apply)에 방문자 호출 한도(check_rate)를 새로
   걸지 여부 — 지금 이 경로들은 무방비 상태다**
9. **mvp1 `s3-detail.html`(구 S3)의 UI 패턴·문구를 새 대화층 설계의 출발점으로
   삼을지, 완전히 새로 설계할지**
10. **새 대화("＋ 새 대화") 시작 시 서버측 개인화 견적(방법 A 선택 시)을
    유지할지 종료 표시할지**
11. **이 계층에 별도 화면 내 영역 ID를 부여할지**(②, 고객단에 선례 없음)
