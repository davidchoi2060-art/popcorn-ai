# 요구사항 정의서 — 상품 분류 관리 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/categories.html`(ADM-CAT-010)은
> **백업용 동결** — 참고만 하고 옮기지 않는다(P-09). 다만 이 구화면은 지금도 실제
> API(`/api/admin/categories`)에 붙어 살아 있고, 아래 ④의 실사용 실측치(추가 153건 등)는
> 그 화면이 만든 흔적이다 — **백엔드는 이미 성숙했고, 없는 것은 admin2 프런트뿐이다.**
>
> 작성일 2026-08-13. ④의 수치는 **그 시각의 실측 스냅샷**이다 — 화면은 이 문서에 적힌
> 숫자가 아니라 서버 응답만 써야 한다. 재측정은 `.venv/Scripts/python`으로
> `api.db.engine`을 통해 `categories`·`category_margin_policies`·`products`를 다시
> SELECT(읽기 전용)하면 된다.

---

## ① 화면 성격

**구조 관리 화면이다.** 검수 큐처럼 매일 처리해야 할 대기열이 아니라, 판매 분류 트리를
세우고 다듬는 자리다. 트리 자체를 보는 **조회**와 노드를 추가·이동·삭제하고 마진을 거는
**쓰기**가 한 화면에 같이 있다.

- **엔진(추천·견적)은 이 트리를 읽지 않는다.** `categories`는 부품 종류(`part_type`,
  엔진이 읽는 닫힌 집합 19종)와 다른 축이다 — 운영자가 카테고리를 옮겨도 견적 결과는
  바뀌면 안 된다(A-02 재현성). 이 경계 자체가 화면의 정의에 들어간다: **이 화면이 하는
  일은 "판매 탐색·마진 상속·오분류 경고"이지 "추천을 바꾸는 일"이 아니다.**
- 조회(트리·집계)는 로그인만 되면 등급 무관(viewer 이상).
- 추가·수정(이동·이름·정렬·노출·허용 종류)·삭제·마진 설정은 전부 **owner 등급만**
  (`api/admin_categories.py`의 `_owner()`가 각 쓰기 앞에서 직접 확인 — 일반 쓰기 권한
  기준인 operator보다 한 단계 높다. compat_rules·spec_field_defs·usage_floors와 같은
  취급).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **상품에 판매 분류를 매길 대상 자체가 없다.** "상품 분류 매핑" 화면(별도 정의서)은
  이 트리가 있어야만 상품을 옮길 곳이 생긴다 — 두 화면은 한 쌍이다.
- **마진을 카테고리 단위로 상속시킬 방법이 없다.** `category_margin_policies`는
  `categories.category_id`를 FK로 삼아 존재하는 테이블이다 — 트리가 없으면 이 상속
  체계 자체가 설 자리가 없다. 지금은 노드에 값을 안 걸면 전역 기본 마진율
  (`pricing_settings.margin_rate`)로 떨어지는데, 이 화면이 없으면 "이 분류만 마진을
  다르게 주고 싶다"는 요구에 답할 수 없다.
- **엉뚱한 종류의 부품이 잘못된 분류에 들어간 것을 알아챌 안전장치가 없다.**
  `allowed_part_types`(카테고리별로 허용하는 실제 부품 종류)가 이 화면에서만 설정되고,
  이것이 있어야 "상품 분류 매핑" 화면이 위반 매핑을 경고할 수 있다.
- **참고로 이 화면이 없어도 견적·추천은 그대로 동작한다** — 의도된 경계다. `categories`는
  엔진이 읽지 않는 순수 관리자 축이라, 이 화면의 부재가 고객 견적에 영향을 주지는 않는다.
  (반대로 말하면, 이 화면에서 무엇을 잘못 옮겨도 견적이 깨지지는 않는다 — 안전한 축이다.)

## ④ 데이터

### 실측 방법

`api.db.engine`으로 `categories`·`category_margin_policies`·`products`·
`admin_operator_activity_logs`를 직접 SELECT(읽기 전용, DB 미변경). 아래는 2026-08-13
스냅샷.

### 쓰는 테이블

| 테이블 | 역할 | 컬럼(실측) |
|---|---|---|
| `categories` | 분류 트리 본체 | `category_id` PK · `parent_id`(자기참조, NULL=최상위) · `name` · `sort_order` · `is_visible`(bool) · `allowed_part_types`(jsonb 배열, NULL=제한없음) · `created_at`/`updated_at`. **`depth`(단계) 컬럼은 없다** — 저장하지 않고 매 조회마다 재귀 CTE로 파생한다(고정 깊이를 피하려는 설계, `category-plan.md` §2 "고정 깊이 금지") |
| `category_margin_policies` | 노드별 직접 마진율 | `category_id` FK · `margin_rate`(0 이상 1 미만) · `updated_at`. 값이 없는 노드는 조상 방향으로 찾다가 없으면 전역(`pricing_settings.margin_rate`)으로 떨어진다(`api/pricing.resolve_margins`, 단일 원천) |
| `products.category_id` | 상품 ↔ 분류(N:1) | NULLABLE. 이 화면은 이 컬럼을 직접 쓰지 않는다(트리만 관리) — 상품 쪽 배정은 "상품 분류 매핑" 화면 소관 |

### 실측 현재 상태 (2026-08-13)

- **카테고리 34개**: 최상위(대분류) 6개 — 부품(51)·주변기기(52)·확장·연결(53)·
  쿨링·튜닝용품(54)·완제품(55)·기타(56) — 밑에 소분류 28개(예: 부품 밑에 CPU·메인보드·
  메모리·그래픽카드·케이스·CPU쿨러·파워·SSD·HDD 9개). 전부 2단 구조이고, 소분류는 각각
  `allowed_part_types`로 실제 `part_type` 코드를 한정한다(예: CPU 카테고리 →
  `["CPU"]`, CPU쿨러 카테고리 → `["COOLER_CPU_AIR","COOLER_CPU_AIO"]`).
- 소분류 11개는 `allowed_part_types=["ETC"]`다(쿨링·튜닝·케이블·젠더·USB·허브·네트워크·
  외장저장장치·완제품 PC·미니PC·베어본·프린터·복합기·휴대폰·모바일·소프트웨어·미분류·
  마우스패드·모니터 주변기기) — 원천이 부품 종류를 못 정한(`part_type='ETC'`, 실측
  4,725건) 상품들이 실제로는 이미 이 11개 소분류에 나뉘어 배정돼 있다는 뜻이다. 자세한
  분포는 "상품 분류 매핑" 정의서 ④ 참조.
- `category_margin_policies` **0행** — 지금은 어떤 카테고리도 개별 마진을 걸지 않고
  전부 전역 기본값을 상속한다.
- `products.category_id IS NULL`(미매핑) **2건 / 22,840건** — 사실상 전량 매핑 완료
  상태.
- 선택지(허용 부품 종류를 고르는 자리)는 `api/taxonomy.DISPLAY_LABELS`가 단일 원천 —
  실측 **18종**(CPU쿨러 공랭·수랭을 하나로 접은 값). `admin_categories.py` 코드 주석은
  "표시 종류 16종"이라 적혀 있으나 **실측과 다르다**(완제품 PC·베어본 두 종류가 나중에
  추가되며 주석이 갱신되지 않은 것으로 보임 — 화면은 주석이 아니라
  `GET /api/admin/categories`의 `part_types` 배열을 그대로 써야 한다).

### 쓰는 API (전부 이미 구현·실사용됨, `api/admin_categories.py`)

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/categories` | 트리 전체 + 노드별 직속/자손합계/재고있음 상품수 + 마진 3종(자기값·적용값·출처 문장) + 미매핑 집계(전체·재고>0) + 허용종류 위반 집계 + 선택지(18종) | viewer 이상 |

"상품 분류 매핑" 소관.)

## ⑤ 기능 (동사)

- 트리를 본다 — 각 노드에 직속 상품수·자손 합계 상품수·재고 있는 상품수를 함께 본다.
- 카테고리를 추가한다(이름·상위 분류·정렬순서·허용 부품 종류 — 허용 종류는 비워 "제한
  없음"으로 둘 수 있다).
- 이름을 바꾼다 / 정렬순서를 바꾼다 / 노출 여부(`is_visible`)를 켜고 끈다.
- 상위 분류를 바꿔 트리에서 다른 자리로 옮긴다.
- 허용 부품 종류를 지정하거나(여러 개 선택) 비운다(비우면 제한 없음으로 되돌아감).
- 카테고리를 지운다.
- 이 카테고리(및 하위 전체)에 적용할 마진율을 정한다, 또는 정한 값을 지워 상위 상속으로
  되돌린다.
- (조회) 지금 몇 상품이 미매핑인지, 허용 종류를 어기는 매핑이 몇 건인지 본다.

## ⑥ 인터랙션 — 입력 · 선택 · 저장 · 이동의 흐름과 결과

- 추가·수정·이동·마진 설정은 저장 즉시 반영되고, 서버가 "무엇이 몇 건 바뀌는지"를
  문장으로 돌려준다(예: "'CPU' 카테고리를 추가했습니다", "이 분류와 하위의 N건이 다음
  재산정에서 이 마진을 씁니다").
- **상위 분류 이동이 순환을 만들면(자기 자신 또는 자기 하위로 이동) 저장 전에 막히고
  이유가 그대로 보여야 한다** — "자기 자신이나 하위 카테고리 밑으로는 옮길 수 없습니다"
  (400).
- **마진을 정하거나 지워도 판매가는 그 자리에서 바뀌지 않는다.** 응답이 이 사실과
  영향받는 상품 수(자손 포함)를 함께 말한다 — "판매가 재산정" 화면에서 미리보기 후
  확정해야 실제 판매가가 바뀐다는 안내가 저장 직후 결과에 같이 보여야 한다(화면이
  "이미 반영된 것처럼" 말하면 안 된다).
- 허용 부품 종류를 어기는 상품이 이미 그 카테고리에 있어도 저장은 막히지 않는다 —
  위반 건수만 목록·집계에 계속 보인다(경고이지 금지가 아니다).
- 이름·상위를 바꿔서 "같은 부모 밑에 같은 이름"이 생기면 저장이 막히고 그 사실이 그대로
  보여야 한다.
- 삭제를 시도했는데 자식이나 매핑된 상품이 걸려 있으면 막히고, 몇 건이 걸려 있는지와
  "먼저 옮기라"는 다음 행동이 그대로 보여야 한다.
- 이 화면과 "상품 분류 매핑" 화면은 트리를 공유한다 — 한 카테고리의 매핑 상품을 보러
  넘어가는 이동(그 화면으로) 자연스러운 지점이다.

## ⑦ 상태 · 예외

- **빈 트리**: 지금은 34행이 항상 있어 실사용 중 마주치지 않지만, owner가 전부 지우면
  이론적으로 빈 상태가 될 수 있다 — 이 경우 "상품 분류 매핑"·상품 등록 화면에서 고를
  카테고리가 사라진다는 사실도 함께 고려해야 한다.
- **권한 없음 — 두 단계로 나뉜다(실측된 차이, 그대로 반영해야 한다)**:
  1. 미로그인은 401 "로그인이 필요합니다"(공통 미들웨어).
  2. **로그인은 됐지만 operator(운영자) 등급인 경우**: 일반 쓰기 권한 기준(operator)은
     통과하지만, 이 화면의 쓰기는 그보다 한 단계 위(owner)만 허용한다 — 미들웨어를
     통과한 뒤에도 엔드포인트 자체가 403 "관리자(owner)만 카테고리를 바꿀 수 있습니다"로
     막는다. 조회 등급(viewer)은 미들웨어 단계에서 이미 403
     "권한이 부족합니다(필요: operator, 현재: viewer)"로 막힌다. **즉 조회는
     viewer부터, 쓰기는 owner부터** — operator는 "볼 수는 있는데 못 고치는" 중간
     상태다.
- 같은 위치(같은 부모)에 같은 이름을 추가/이동하면 409.
- 없는 상위 분류를 지정하면 404.
- 자식이 있는 카테고리를 지우려 하면 409("하위 카테고리 N개가 있어 삭제할 수 없습니다 — 먼저 옮기거나 지워야 합니다").
- 상품이 매핑된 카테고리를 지우려 하면 409("상품 N건이 있어 삭제할 수 없습니다 — 먼저
  옮겨야 합니다").
- 마진율이 범위(0 이상 1 미만) 밖이면 400.
- 이미 상속 상태(직접 건 마진 없음)인 노드에 마진 해제(null)를 또 시도하면 400
  ("이 분류에 직접 걸린 마진이 없습니다").
- 이름이 비었거나 80자를 넘으면 400.
- **`is_visible` 토글은 저장은 되지만, 지금 이 값을 읽어 걸러내는 소비처가 코드 어디에도
  없다**(실측: `GET /api/admin/categories`·`GET /api/admin/category-mapping` 둘 다
  `is_visible` 값과 무관하게 전 노드를 돌려준다). 즉 지금은 꺼도 관리자 화면에서
  사라지지 않는다 — 향후 고객 노출 화면이 생기면 그때 쓰일 자리로 보이나 **확인 필요**.

## 비범위 — 이 화면이 하지 않는 일

- **엔진(추천·견적)에 영향을 주지 않는다.** 카테고리를 옮기거나 지워도 견적 결과는
  달라지지 않는다(A-02 재현성 — `category-plan.md`가 이것을 회귀 불변식으로 요구했다).
- **상품을 카테고리에 배정하지 않는다.** 그건 "상품 분류 매핑" 화면 소관이다(별도
  정의서).
- **판매가를 바꾸지 않는다.** 마진율을 정해도 판매가 재계산은 별도 화면("판매가
  재산정")에서 일어난다.
- **고객에게 분류 탐색을 보여주지 않는다.** 지금 이 트리는 관리자 전용이다 — 고객
  화면(S0~S5)에 분류 탐색을 넣을지는 `category-plan.md` §5의 열린 질문으로 아직
  미정이다.

## 사장님 결정 필요 지점 (임의로 정하지 않았다)

1. **`allowed_part_types=["ETC"]`인 소분류 11개는 서로 다른 실제 상품을 담고 있지만
   전부 `part_type='ETC'`라 이 화면의 "허용 종류 위반" 경고로는 서로 구분이 안 된다**
   (쿨링·튜닝에 케이블이 잘못 들어가도 경고가 안 뜬다). 이 사각지대를 이 화면의 요구로
   다룰지(예: ETC 안에서의 2차 판별), 아니면 그대로 둘지.
2. **카테고리 자체(추가·수정·삭제·마진)에는 되돌리기(undo) API가 없다** — 실측:
   `api/admin_categories.py`에 `undo` 엔드포인트가 없다("상품 분류 매핑"의 이동
   되돌리기, 상품 관리의 수정 되돌리기와 다르다). 프로젝트 전반의 "되돌림은 삭제가
   아니라 역방향 전이" 원칙에 맞추려면 신규 구현이 필요한데, 이 문서 범위에서 요구할지
   확인 필요.
3. **`is_visible`을 지금 요구사항에 포함할지** — 위 ⑦에서 밝힌 대로 지금은 저장만 되고
   아무도 읽지 않는 값이다. 화면에 넣어 두되 "지금은 효과 없음"을 밝힐지, 아예 이번
   범위에서 뺄지.
4. **고객 노출(카테고리 브라우징) 도입 여부** — 여전히 미정(`category-plan.md` §5-3).
   이 화면 자체와는 무관하지만, `is_visible`의 존재 이유와 맞물려 있어 함께 확인이
   필요하다.
