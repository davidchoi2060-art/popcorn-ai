# 요구사항 정의서 — 추천 가능 재고 현황 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 결정권자(또는 지정 경로)가 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/candidate-pool.html`(ADM-ENG-030)은
> 백업용 동결 — 참고만 하고 옮기지 않는다(P-09).
>
> 작성일 2026-08-13. ④의 수치는 그 시각의 실측 스냅샷이다. 재측정은
> `GET /api/admin/candidate-pool`을 다시 돌리면 된다(서버가 매 호출마다 다시 센다).

---

## ① 화면 성격

**조회 화면이다(순수 집계·읽기 전용).** "지금 팔 수 있는 부품 중 실제로 견적에 쓰일
수 있는 것이 얼마나 되는지"와 "안 되는 것은 어떤 사유로 못 쓰이는지"를 사유별로
집계해 보여주는 자리다. S1 화면의 후보 풀 카운터가 보여주는 숫자의 **뒷단**이다 —
같은 정의(추천 뷰 ∧ 재고>0)를 쓰되, 여기서는 "안 되는 이유"까지 쪼개서 보여준다.

- 열람은 로그인만 되면 등급 무관(viewer 이상).
- 쓰기 기능 없음(이 화면 자체에는 고칠 것이 없다 — 문제를 발견하면 각 사유가 가리키는
  다른 화면으로 이동해서 고친다).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **"후보 수 > 0"이 "견적 가능"이 아니라는 사실을 운영자가 확인할 자리가 없다.**
  CLAUDE.md의 화면 정직성 원칙이 명시하듯, 슬롯 하나가 0이면 조립 자체가 불가능하다.
  이 화면이 없으면 "카탈로그에 22,840개나 있는데 왜 이 조합이 견적이 안 나오지?"에
  답할 방법이 없다.
- **왜 어떤 상품이 추천에서 빠졌는지 사유별로 셀 자리가 없다.** 사양이 없어서인지,
  검수 대기라서인지, 검수는 끝났는데 후보로 승격이 안 됐는지, 가격이 안 매겨졌는지,
  재고가 없는지 — 이 다섯 사유는 **각각 다른 화면에서 고쳐야 하는 다른 문제**다. 이
  화면 없이는 "검수 큐에 5천 건이 있다"는 사실만 보이고, 그중 몇 건이 실제로 매출에
  영향을 주는지(판매중·재고 있는 것)는 안 보인다.
- **"후보가 적어서 위험한 카테고리"를 미리 알 방법이 없다.** 예: 화이트 케이스나
  750W 이상 파워처럼 특정 제약과 결합했을 때만 후보가 바닥나는 경우는, 전체 카테고리
  건수만 봐서는 안 보인다.

## ④ 데이터

### 실측 방법

`GET /api/admin/candidate-pool` 실행 결과 + `api/admin_pool.py` 코드 대조(읽기 전용,
매 호출 실시간 재계산). 2026-08-13 스냅샷.

### 게이트 정의(4중 게이트, ERD §3.6 기준 — 이 화면이 그대로 반영해야 하는 순서)

배타적 사유 배정(우선순위 순으로 첫 미충족 사유 하나만 배정, 슬라이스 23·24 확정):

1. **사양 행 자체가 없음**(`no_specs`) — `product_specs`에 그 상품의 행이 없음
2. **검수 대기**(`need_review`) — `review_required_yn=true`
3. **후보 미승격**(`not_candidate`) — 검수는 끝났는데(`review_required_yn=false`)
   `ai_candidate_yn=false`인, 정상적으로는 드물어야 할 상태
4. **가격 검토 대기**(`no_price`) — `sale_price IS NULL`
5. **재고 없음·매입 필요**(`oos`) — `stock_qty=0` 또는 `status≠'판매중'`

전부 통과하면 `ok`. **S1 후보 카운터와 정확히 같은 집합**(`v_recommendation_candidates`
∧ `stock_qty>0`)이 `ok` 합계와 일치해야 정합이 맞는 것이다 — 어긋나면 이 화면의 계산
로직과 후보 카운터 로직이 서로 다른 말을 하고 있다는 뜻이다.

**시연용 데이터는 모집단에서 제외한다**(`data_origin≠'demo'`) — 사유 버킷이 아니라
애초에 세지 않는다. 이유: 사유는 "왜 추천에 못 쓰이는지, 그래서 무엇을 고쳐야 하는지"를
보여주는 목록인데, 데모 상품은 고칠 대상이 아니라 애초에 자사 상품이 아니기 때문이다.

### 쓰는 테이블

| 테이블 | 역할 |
|---|---|
| `products` | 게이트 판정 원본(조립 부품 10종만, `category_group='core_part'`) |
| `product_specs` | 사양 행 존재 여부·화이트 태그·정격 출력 판정 |
| `v_recommendation_candidates` | 전체 후보 풀 크기(비교 대조용) |

### 쓰는 API

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/candidate-pool` | 카테고리별 게이트 통과/사유별 집계 + 얇은 카테고리 경고 | viewer 이상(쓰기 없음) |

### 실측 값 (2026-08-13)

- 추천 후보 풀 전체(재고>0): **3,219개**(`v_recommendation_candidates`).
- 조립 부품 10종 판정 대상(시연 제외): **12,985개**의 상품 중 `ai_candidate_yn=true`
  **9,751개**, `review_required_yn=true`(검수 필요) **3,235개**.
- 부품 종류별 추천 후보(재고>0) 분포: 케이스 788 · 파워 499 · 메인보드 482 · 메모리
  409 · 그래픽카드 334 · SSD 266 · CPU 211 · 공랭쿨러 138 · 수랭쿨러 48 · HDD 44.
- **얇은 카테고리 경고 임계값 = 3개 이하**(`THIN_THRESHOLD`, 코드 상수 — "현 dev 재고
  규모 기준, 운영 시 재조정 필요"라고 코드가 스스로 밝히고 있다). 위 분포로 보면 HDD(44)·
  수랭쿨러(48)가 임계값에서 가장 멀리 있지 않은 축이지만, **제약이 결합되면(화이트
  태그·750W 이상 등) 사정이 달라진다** — 그래서 이 화면은 카테고리 총량과 별개로 결합
  조건 2종(화이트 케이스, 750W 이상 파워)을 항상 실측해 함께 보여준다.
- 사유별 처리 화면 연결: 사양 미등록→상품 관리, 검수 대기·후보 미승격→상품 사양 검수,
  가격 검토 대기→가격 검토 대기 화면, 재고 없음→재고 입고 화면(전부 다른 LNB 그룹).

## ⑤ 기능 (동사)

- 카테고리(부품 종류)별로 전체·통과(`ok`)·사유별 건수를 표로 본다.
- 전체 사유(5종) 합계와 통과 합계, 통과율(%)을 본다.
- 얇은 카테고리(통과 후보 3개 이하) 목록을 사유와 함께 본다 — "왜 위험한지"(제약이
  겹치면 견적 실패 가능)를 문장으로 함께 본다.
- 결합 조건 2종(화이트 케이스, 750W 이상 파워)의 실제 통과 수를 별도로 확인한다.
- 사유 하나를 골라 그 사유를 실제로 처리할 수 있는 다른 화면으로 이동한다.
- 전체 추천 후보 풀 크기(`pool_total`)를 S1 카운터와 같은 정의로 확인한다.

## ⑥ 인터랙션

- 화면 진입 시 별도 조작 없이 전체 집계가 온다(단일 GET).
- 사유별 숫자를 클릭하면 그 사유에 해당하는 처리 화면으로 이동한다 — 이동 시 "왜
  왔는지"(어떤 사유로 몇 건인지)가 유지되면 좋지만, 지금 API는 목적지 화면에 필터를
  전달하는 파라미터를 주지 않는다(단순 문자열 링크만, 실측: `link` 필드는 파일명
  하드코딩). 필터를 이어 붙이려면 목적지 화면과 별도 합의가 필요하다(결정 필요 지점).
- 이 화면 자체에서 값을 바꾸는 조작은 없다 — 모든 "고치기"는 다른 화면으로 넘어가서
  이루어진다.

## ⑦ 상태 · 예외

- **서버 실패**: 침묵하지 않는다. 원인이 사람에게 보여야 한다.
- **권한**: 미로그인 401. 열람 자체는 등급 무관.
- **빈 상태**: 이론상 발생하지 않는다(조립 부품 카테고리가 12,985건 존재) — 만약
  0건이면 DB 연결 실패를 의심해야 한다.
- **얇은 카테고리 0건**: 정상 상태다(모든 카테고리가 임계값을 넉넉히 넘는 경우) —
  이때는 "위험 카테고리 없음"을 명시적으로 보여줘야 한다(빈 표를 그냥 안 보여주면
  "집계를 가져오지 못했습니다"와 구분이 안 된다).
- **주변기기(peripheral) 풀 집계 없음**: 이 화면은 조립 부품 10종만 다룬다. 주변기기
  풀은 API 자체가 아직 이 집계를 제공하지 않는다(`note`에 "준비 중"으로 명시) — 화면이
  이걸 있는 것처럼 보여주면 안 된다.

## 비범위 — 이 화면이 하지 않는 일

- **사유를 직접 해소하는 일** — 검수·가격 산정·재고 입고는 전부 다른 화면 소관이다.
  이 화면은 "어디로 가야 하는지"까지만 안내한다.
- **얇은 카테고리 임계값(`THIN_THRESHOLD=3`) 조정** — 코드 상수이며, 조정 UI는 지금
  범위 밖이다.
- **규칙·정책의 버전 관리** — `note`가 "규칙·정책 버전 표기는 미모델링"이라고 이미
  명시한다. 지금은 "현재 적용 중인 규칙 1벌"만 있다.
- **주변기기 풀 집계** — 위 ⑦ 참조. 이관 대상으로 명시돼 있다.

## 사장님 결정이 필요한 지점

1. **사유별 링크가 목적지 화면에 필터(예: "이 부품 종류만")를 넘기게 만들지.** 지금은
   화면 이름만 연결돼 있어, 이동한 뒤 사람이 다시 조건을 찾아 걸어야 한다.
2. **`THIN_THRESHOLD=3`을 이 화면에서 조정 가능하게 열지.** 코드 스스로 "dev 재고
   규모 기준, 운영 시 재조정 필요"라고 밝히고 있어 — 운영 전환 시점에 반드시 다시
   짚어야 하는 값이다.
3. **주변기기 풀 집계를 이 화면의 요구사항에 포함시킬지, 별도 화면으로 분리할지.**
   지금은 코드가 "이관"으로만 표시하고 있어 우선순위 결정이 필요하다.
