# 요구사항 정의서 — AI 작업 설정 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> 이 화면은 **old admin에도 대응 화면이 없다 — 완전 신설**이다
> (`api/admin_nav.py` "AI 관리" 그룹, note: "신설 — 작업↔모델 · 폴백"). 옮겨올 구화면이
> 없으므로 이 문서는 오로지 실제 코드·DB·결정 문서에서 실측한 사실만으로 요구를 세운다.
>
> 작성일 2026-08-13. ④의 수치는 그 시각의 실측 스냅샷이다(DB 직접 조회, 읽기 전용).
> 재측정은 `SELECT count(*) FROM api_cost_logs`(및 `cost_thresholds`·`rate_limit_policies`)와
> `grep -n "^model:" .claude/agents/*.md`를 다시 돌리면 된다.

## ① 화면 성격

**정책 설정 화면.** 조회 화면도 작업 큐도 아니다 — "어느 작업에 어느 AI 모델을 쓰고,
실패하면 무엇으로 대체하는지"를 사람이 정하는 자리다. 성격상 `usage_floors`·
`pricing_settings`·`ops_settings`와 같은 급이다: **값 하나가 실제 동작(향후 LLM 호출
결과)을 직접 바꾼다.**

다만 지금은 특수한 상태에 있다 — **이 화면이 정하는 값이 오늘은 어떤 실행도 제어하지
않는다.** 실제 LLM 연동은 보류 결정(2026-07-21, 별도 승인 필요) 상태이기 때문이다.
그래서 이 화면은 "휴면 정책 화면"이다: 값을 미리 준비해 두되, 연동이 재개되는 순간
그대로 살아나야 한다.

- 열람은 로그인만 되면 등급 무관(viewer 이상)으로 제안한다 — 다른 정책 화면(용도별
  최소 사양 등)과 같은 원칙.
- 값 변경(작업↔모델 배정, 폴백 순서, 프롬프트 버전)은 **owner 전용**으로 제안한다 —
  이유는 ④·⑥에서 다룬다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **실제 LLM 연동이 재개되는 순간(2026-07-21 결정, 별도 승인 필요) "어느 작업에 어느
  모델을 쓸지"를 코드 재배포 없이 정할 방법이 없다.** 이 화면이 없으면 모델 배정이
  코드 상수로 박히고, 바꿀 때마다 배포가 필요하다 — 다른 정책류 화면(운영 전환 설정,
  용도별 최소 사양 등)이 전부 "화면에서 즉시 반영"을 원칙으로 하는 것과 어긋난다.
- **"작업↔모델"이라는 개념 자체는 이미 이 저장소에 존재하지만, 그 실체는 고객 파이프
  라인이 아니라 개발팀의 도구다.** `.claude/agents/*.md` 8개(investigator·maker·checker·
  writer·dba·crosschecker·sweeper·specfiller) 전부가 frontmatter에 `model:` 필드를 갖고
  있고, 실측 결과 **8개 전부 `sonnet` 한 값으로 동일하다**(그레프 실행, 2026-08-13). 이건
  Claude Code로 이 저장소를 짓는 **개발 도구 설정**이지, 고객이 마주치는 S1 입력 파싱·S2
  근거 설명·운영 도우미 질의의 설정이 아니다 — 이름이 같아 섞이기 쉽다(비범위 참조).
  즉 **고객 파이프라인 쪽에는 "작업↔모델" 매핑이 실질적으로 하나도 없다.**
- **A-02·A-03(엔진이 견적을 만들고 AI는 파싱·설명만 한다)이 화면 차원에서 지켜지는
  자리가 없다.** decision-log(2026-08-09): "AI가 하는 일의 경계는 그대로다 — 입력 파싱 +
  근거 설명. 견적을 만들지 않는다... 운영 도우미도 같은 규칙을 받는다." 이 화면이 다루는
  "작업 종류" 목록이 임의로 늘어날 수 있다면(예: "AI가 견적 고르기"를 작업으로 추가) 그
  자체가 A-02/A-03 위반이 된다 — 이 화면은 그 목록을 열어두지 않아야 한다.

### AI 축 — 문서 간 불일치 (이 문서가 발견한 실측)

이 화면을 설계하려면 "착수 시 프로바이더가 몇 개인가"를 알아야 하는데, 결정 문서 두
건이 서로 다르게 말한다.

| 결정 | 날짜 | 프로바이더 수 | 목적 |
|---|---|---|---|
| LLM 실연동 파일럿 보류 | 2026-07-21 | **1개** — Claude Opus 4.8(`claude-opus-4-8`) | 팝콘톡 파일럿 한정, 공개 노출(당시 배포 대상은 Firebase Hosting — 이후 실제로는 GCP+FastAPI로 구축돼 이 전제 자체가 낡았을 가능성이 있다) |
| UX-14 부속 "AI 축 — 결정과 전제" | 2026-08-09 | **3개** — Codex·Claude·Gemini | (a) 역할 분담 + (c) 폴백. **(b) 교차 검증은 주목적 아님** |

둘 중 어느 쪽도 decision-log의 폐기 표(⛔)에 오르지 않았다 — **번복 기록 없이 서로 다른
답을 담은 채 공존**하고 있다. 게다가 랜딩(`mockups/mvp1/main-landing.html`)은 이미 "3개
AI가 같은 문장을 읽고 의도가 하나로 수렴했습니다"라는 문구로 **3개 프로바이더 동시 호출**을
고객에게 사전 홍보 중이다(A-07 결정으로 유지 확정, 화면 정직성 규약의 명시적 예외 항목).
이 화면이 "작업당 프로바이더 1개 + 폴백 사슬"을 가정하고 지어지면 이미 나간 저 랜딩
카피와 맞지 않게 된다. → **사장님 결정 필요(①)**.

세 테이블(`api_cost_logs`·`cost_thresholds`·`rate_limit_policies`)은 `docs/06_db-erd.md`
"3.8 유지 테이블"(Ver 2.0 정의 유지) 소속으로 스키마 자체는 오래전부터 있었다 — **작업↔
모델 배정을 저장하는 테이블은 이 셋 중 어디에도 없다.**

### 연동 후에야 생기는 것 / 신설이 필요한 것

- 작업 종류 ↔ 프로바이더/모델 ↔ 폴백 순서 ↔ 프롬프트 버전을 담는 테이블 — **없음, 신설
  필요**(테이블·컬럼 설계는 이 문서 범위 밖).
- 변경 이력 — `ops_settings_history`와 같은 목적의 이력이 필요하다(버전·변경자·사유·
  변경 전후 값).
- 3개 프로바이더 "동시 호출 후 수렴 판정"(랜딩이 이미 약속한 동작)을 표현할 데이터 구조
  — 단순 "1차 실패 시 2차" 폴백과는 다른 개념이라 별도로 정의해야 한다.

## ⑤ 기능 (동사)

- 작업 종류별(닫힌 목록 — 결정 필요 참조) 지금 배정된 프로바이더/모델을 본다.
- 작업 종류별 폴백 순서(1차 실패·시간초과 시 2차)를 정한다.
- (입력 파싱처럼 다중 동시 호출이 확정되면) 동시에 참여시킬 프로바이더 집합을 정한다.
- 프롬프트 버전 식별자를 보고 바꾼다(본문 편집 여부는 비범위 참조).
- 변경 이력(누가·언제·무엇을·왜)을 본다.
- 지금 이 설정이 어떤 실행도 제어하지 않는다는 사실을 조회 결과 자체로 확인한다(⑦ 참조).

## ⑥ 인터랙션

- 저장은 **owner 전용**이며 성공 시 이력에 남는다 — 근거: `api/auth.py`의
  `OWNER_WRITE_PREFIXES`는 이미 "견적·가격을 직접 바꾸는" 화면(용도별 최소 사양, 판매가
  정책, 카테고리 마진, 사양 항목, 운영자·권한, 운영 전환 설정, 카탈로그 일괄 적재)을
  전부 owner로 묶어 두었다(실측). 이 화면은 지금은 아무것도 바꾸지 않지만 연동 후에는
  "고객 응답을 만드는 모델"을 바꾸는 것과 같은 무게라 같은 급으로 다룬다.
- 저장이 즉시 반영인지, 별도 "발행" 절차(초안 저장 → 확정)가 필요한지는 운영 전환 설정
  (`ops_settings`, 즉시 반영 + 이력 기록 방식)을 선례로 제안하되, 최종 방식은 결정 필요.
- 존재하지 않는 작업 종류·모델 문자열을 저장하려 하면 그 자리에서 거부하고 이유를
  보인다(원장 규약 — 실패를 삼키지 않는다).

## ⑦ 상태 · 예외

- **연동 준비 중임을 화면 전체가 명시해야 한다.** "이 설정은 지금 어떤 실행도 제어하지
  않습니다 — 실 LLM 연동 보류(2026-07-21 결정, 별도 승인 필요)"라는 사실을 화면을 여는
  즉시 알 수 있어야 한다. 값을 바꿔도 실제로는 아무 일도 일어나지 않는다는 것을 사람이
  오인하면 안 된다(화면 정직성 규약).
- **빈 상태**: 설정 테이블에 아직 한 행도 없는 최초 상태에서 무엇을 기본값으로 보일지 —
  결정 필요(빈 목록 vs 작업 종류만 나열하고 "미배정"으로 표시).
- **권한 없음**: 미로그인 401, owner 미만 쓰기 시도 403("권한이 부족합니다(필요: owner,
  현재: …)") — 기존 응답 형식(`api/auth.py`)을 그대로 따른다.
- **서버 실패**: 조회·저장 실패를 원인 없이 침묵하지 않는다.

## 비범위 — 이 화면이 하지 않는 일

- **`.claude/agents/*.md`(Claude Code 개발 도구 팀원 설정)를 읽거나 고치지 않는다.**
  이름이 비슷해 혼동하기 쉽지만 대상이 다르다 — 하나는 이 저장소를 만드는 개발팀의
  도구, 하나는 고객이 마주치는 파이프라인이다.
- **웹 사양 채움(specfiller) 배치의 실행·모니터링** — ADM-AI-020(`/admin2/spec-fill`,
  이미 구축)과 작업 현황판(ADM-AI-010) 소관. 다만 specfiller도 실질적으로 "AI가 작업을
  하는" 사례라 이 화면의 "작업 종류" 목록에 포함해야 하는지는 결정 필요(아래).
- **프롬프트 "본문 텍스트"의 작성·편집 UI** — 이 문서는 버전 식별자 조회까지만 요구한다.
- **실제 모델 호출·비용 발생** — 이 화면은 설정만 하고 실행하지 않는다(실행·비용은 AI
  사용량·비용, AI 응답 기록 소관).

## 사장님 결정이 필요한 지점

1. **착수 시 프로바이더가 1개(Opus 4.8, 2026-07-21)인지, 3개 역할분담+폴백(Codex·
   Claude·Gemini, 2026-08-09)인지** — 두 결정이 서로 다른 채 공존한다("AI 축 — 문서 간
   불일치" 참조). 이 화면의 기본 구조(작업당 모델 1개 vs 작업당 프로바이더 집합)가 이
   결정에 좌우된다.
2. **"작업 종류" 목록을 입력 파싱·근거 설명·운영 도우미 질의 셋으로 닫을지, 웹 사양
   채움(specfiller류)도 포함할지.**
3. **랜딩이 이미 약속한 "3개 AI 동시 교차 해석"을 "폴백"과 구분되는 별도 동작으로 화면에
   표현해야 하는지.**
4. **프롬프트 버전 관리의 범위** — 식별자만 볼지, 본문 편집까지 이 화면이 할지.
5. **저장이 즉시 반영인지 발행 절차(초안→승인)가 필요한지.**
