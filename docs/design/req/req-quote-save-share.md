## ① 화면 성격

조회 화면. 새 화면을 신설하는 것이 아니라 **이미 있는 두 자리의 빈 상태를 채우는
확장**이다 — S2(FR-REC-020, 견적 제안서)에 「저장·공유」 동작을 더하고, MY-010
(마이페이지)의 「상담 내역」 카드가 지금 내보내는 "저장은 아직 준비 중이에요"
문구 대신 실제 목록을 조회하게 한다.

## ② 제목 · 화면 ID

- **확장 대상 ①** S2 견적 제안서 — `FR-REC-020` (`mockups/mvp1/s2-result.html`).
  기존 화면에 저장·공유 동작만 추가한다. 화면 자체를 새로 만들지 않는다.
- **신설 ②** 상담 내역 목록·상세 — 기존 채번(MY-0xx, `docs/design/screen-flow.md`
  §④ MY-010~MY-040) 다음 순번인 **`MY-050`** 을 제안한다. MY-010(마이페이지)의
  「상담 내역」 카드가 이 화면으로 연결된다(주문 내역이 MY-020으로 연결되는 것과
  같은 구조).

## ③ 정의 — 지금 이 자리가 비어 있으면 무엇이 안 되나

- **고객이 지금 만든 견적을 나중에 다시 볼 방법이 없다.** S2의 견적은
  `localStorage['popcorn-quote']`에만 있다(`s2-result.html:584` 실측) — **같은
  브라우저·같은 기기에서만** 남고, 브라우저 데이터를 지우거나 다른 기기로 접속하면
  사라진다. **로그인해도 다르지 않다** — `api/recommend.py`는 `member_id`를
  로그인 여부와 무관하게 항상 `NULL`로 적재하고(실측: `consult_sessions` INSERT문,
  `cols = "member_id, mode, constraints, user_id, data_origin"`, `vals`의
  `member_id` 자리는 항상 `NULL` 리터럴), `/api/my/*` 계열에 상담·견적을 돌려주는
  엔드포인트가 **0개**다(실측: `api/recommend.py`·`api/swap.py`에 `GET`
  라우트는 `/showcase` 하나뿐 — 세션 단위로 견적을 다시 읽는 `GET`이 없다).
  이 사실은 `mockups/shared/auth.js` 자체의 주석(32~35행)에도 이미 적혀 있다.
- **그 결과가 화면에 이미 드러나 있다** — 로그인해 마이페이지를 열면 「상담 내역」
  카드가 "상담 내역 저장은 아직 준비 중이에요"라고 스스로 말한다(2026-08-29 실측,
  로그인 상태로 확인). **비어 있다고 감추지 않고 밝히는 것은 옳다** — 다만 그 옆
  「내 후기」·「관심 부품」 카드와 달리, 이 카드가 가리키는 기능은 **더 필요한
  자리다**: 견적은 부품 8종에 수십만~수백만 원이 걸린 결정이라, 한 번 보고 그
  자리에서 결정하기보다 **저장해 두고 다시 보거나 남에게 보여주고 의논하는 행동이
  자연스럽다**(다나와 PC견적의 "견적 저장 및 공유" — 2026-08-29 확인, 대조 근거일
  뿐 베끼는 근거가 아니다).
- **공유도 안 된다.** S2에 "공유"·"저장하기"·"링크 복사"류 동작이 **0건**이다
  (실측: `grep -n "공유\|저장하기\|링크 복사\|share" mockups/mvp1/s2-result.html`
  — 매치 없음, 라이브러리 로드 줄만 걸림). 가족·지인에게 "이 견적 어때?"라고 물어볼
  방법이 없다.

## ④ 데이터 — 실측 근거

**있는 것**

| 무엇 | 어디 | 비고 |
|---|---|---|
| 견적 스냅샷 | `quote_snapshots`(`snapshot_id`·`session_id`·`quote_type`·`items`·`companion`·`total_amount`·`created_at`) | `POST /api/recommend`가 매 확정마다 이미 적재한다(실측 2026-08-29, 전체 28,937행) |
| 상담 원장 | `consult_sessions`(`session_id`·`member_id`·`mode`·`constraints`·`created_at`·`data_origin`·`user_id`·`access_key`) | `member_id`는 항상 NULL(위 §정의) |
| 조회용 열쇠 | `consult_sessions.access_key` | 이미 있다 — S2가 `POST /api/recommend/pin`류 호출에 그대로 쓴다(`s2-result.html:687` 인근 주석 "열쇠는 견적 응답이 준 값을 그대로 되돌려 보낸다") |

**없는 것 — 새로 지어야 한다**

| 무엇 | 실측 |
|---|---|
| 세션 단위로 견적을 다시 읽는 `GET` | `api/recommend.py`·`api/swap.py`에 `GET` 라우트 1개(`/showcase`)뿐 — 세션별 재조회 라우트 없음 |
| 회원-세션 연결 | `member_id`가 항상 NULL로 적재됨(위) — 로그인 회원의 견적이라는 사실 자체가 지금 어디에도 없다 |
| 목록 조회(마이페이지용) | `/api/my/*`에 상담·견적 목록을 주는 엔드포인트 없음(실측: `api/my_account.py`·`api/my_orders.py`류 파일에 해당 라우트 없음) |
| 공유 링크 검증 | 비로그인 사용자가 남의 견적을 못 보게 막을 장치(로그인 회원 것은 소유자 확인, 비로그인 것은 `access_key` 같은 열쇠 확인) — 지금 이 흐름을 위한 것은 없음 |

**참고 — 비슷한 선례가 이미 있다**: `api/handoff.py:174`의 `get_handoff()`는
"완료 화면과 관리자 「인계 기록」이 함께 쓴다"는 docstring을 달고 있지만 **실제로는
어느 화면도 부르지 않는다**(`docs/decisions/decision-log.md` **U-14**, 2026-08-17
등재, 아직 미정). 세션 열쇠로 과거 결과를 다시 여는 것과 똑같은 모양의 문제가 이미
한 번 있었다 — 이번에 새로 설계하면 그 미결까지 함께 볼 필요가 있다.

## ⑤ 기능 — 할 수 있는 일

- **S2에서 저장한다.** 로그인 상태면 그 견적(스냅샷)을 회원 계정에 연결해 저장한다.
- **S2에서 공유 링크를 만든다.** 로그인 여부와 무관하게, 이 견적만 다시 열 수 있는
  링크(열쇠 포함)를 만든다.
- **마이페이지 「상담 내역」에서 목록을 조회한다.** 로그인 회원이 저장한 견적을
  최신순으로 본다.
- **공유 링크로 견적을 다시 연다.** 링크를 받은 사람(로그인 여부 무관)이 그 시점의
  구성·가격·근거를 S2와 같은 형태로 본다.
- **저장한 견적에서 이어간다.** 목록에서 하나를 골라 S3(부품 변경)·S4(주문 확인)로
  이어갈 수 있다.

## ⑥ 인터랙션 — 입력·선택·저장·이동의 흐름과 결과

- S2 하단(현재 「부품 변경」·「장바구니 담기」가 있는 자리)에 저장·공유 동작을 더한다.
  **위치·모양은 정하지 않는다**(설계 소관) — "이미 있는 두 버튼과 나란히 둘지,
  다른 자리에 둘지"도 설계 판단이다.
- 저장·공유를 눌렀을 때:
  - 로그인 안 한 상태에서 「저장」을 누르면 로그인을 요구한다(기존 로그인 모달
    재사용 — `window.popcornAuth.open('login', ...)`, 새 모달을 만들지 않는다).
  - 「공유 링크」는 로그인 여부와 무관하게 항상 만들 수 있다(비로그인 고객도 지금
    막 만든 견적을 카톡으로 보낼 수 있어야 한다).
- 마이페이지 「상담 내역」 카드를 누르면 목록 화면(MY-050)으로 이동한다. 목록의 각
  행을 누르면 그 견적을 다시 S2와 같은 형태로 연다.
- 공유 링크로 들어온 방문(로그인 안 한 상태 포함)은 **그 즉시 새 상담을 만들지
  않는다** — 저장된 스냅샷을 그대로 읽어서 보여준다. 여기서 「부품 변경」을 누르면
  그 시점부터는 새 세션이 된다(현재 재고·가격으로 다시 검증해야 하므로 — 옛 스냅샷
  그대로 진행시키면 §화면 정직성의 "실시간 재고 검증"과 어긋난다).

## ⑦ 상태 · 예외

- **빈 목록**: 저장한 견적이 없으면 지금 문구("상담 내역 저장은 아직 준비 중이에요")
  대신 "아직 저장한 견적이 없습니다" 류로 바꾼다(§문서·화면 어휘 표준 — 명사형·
  시스템 안내체, 정확한 문구는 문안검사 대상).
- **미로그인으로 목록 접근**: 마이페이지 전체가 이미 로그인 전제다(§실측 참조) —
  같은 규칙을 따른다.
- **공유 링크의 대상이 삭제·만료됐을 때**: 무엇을 "만료"로 볼지(예: 재고·가격이
  크게 달라진 경우 재검증을 요구할지)는 **미정** — 임의로 정하지 않는다. 최소한
  "이 견적은 더 이상 유효하지 않습니다. 지금 조건으로 다시 만들어 보세요"처럼
  **지어낸 값으로 재검증 없이 그대로 보여주지는 않는다**(§화면 정직성).
- **다른 사람 열쇠로 접근**: 로그인 회원이 저장한 견적을 열쇠 없이 회원 소유
  목록으로만 보호할지, 비로그인 저장분처럼 열쇠로도 열리게 할지는 **미정** —
  개인정보(회원 이메일 등은 스냅샷에 없으므로 노출 위험은 낮지만, 소유 개념 자체를
  어떻게 정의할지는 사장님 결정 대기).
- **서버 실패**: 침묵하지 않는다(`if(!res.ok) return;` 금지, 기존 규약 그대로).

## 비범위 — 이 확장이 하지 않는 일

- **관심 부품(찜) 저장** — 마이페이지의 다른 빈 카드("관심 부품 저장은 아직 준비
  중이에요")다. 이 문서는 상담·견적만 다룬다.
- **공유 링크의 SNS 자동 게시·이미지 카드 생성** — "링크를 만든다"까지가 이 문서의
  범위다. 공유 매체별 미리보기 카드 디자인은 설계 소관이다.
- **인계(`handoffs`) 원장과의 통합** — 인계는 이미 별도 원장이고(`CANON.md` §3),
  이 문서가 다루는 "저장한 견적"은 인계 이전 단계의 조회 기능이다. 둘을 합칠지는
  이 문서가 판단하지 않는다.

## 판정 못 한 것 (사장님 결정 대기 — 임의로 메우지 않는다)

1. **소유 판정 방식** — 로그인 회원 견적을 무엇으로 "내 것"이라 판정할지(§⑦).
2. **만료 정책** — 저장된 견적의 재고·가격이 지금과 달라졌을 때 화면이 어떻게
   말할지(§⑦).
3. **위치·모양** — §화면 작업의 경계에 따라 이 문서가 정하지 않는다.
