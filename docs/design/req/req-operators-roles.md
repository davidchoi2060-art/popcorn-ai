# 요구사항 정의서 — 운영자 · 권한 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> **대상은 admin2 신규 구축이다 — 구 `mockups/admin/operators.html`을 옮기는
> 것이 아니라 새로 만드는 것이다.** 구화면은 백업용 동결(수정·링크 금지, P-09).
>
> 작성일 2026-08-13. ④의 수치는 **그 시각의 실측 스냅샷**이다(`api.db.engine`으로
> `admin_operators`·`admin_sessions`를 직접 SELECT, 읽기 전용·DB 미변경 + `api/auth.py`·
> `api/admin_operators.py`·`api/admin_profile.py`·`api/passwords.py` 코드 직접
> 대조로 얻었다). 화면은 이 문서의 숫자를 그대로 박지 않는다 — 서버 응답만 쓴다.

---

## ① 화면 성격

**관리 화면 — 승인 게이트 + 권한 관리(owner 전용).** 조회조차 owner만 허용된다
(`api/auth.py` `required_role()`: `/api/admin/operators`는 GET도 owner — "계정
목록은 민감"이라는 코드 주석 그대로). 남을 승인·강등·정지시키는 화면이며,
본인 정보를 보는 화면("내 정보", `GET/PATCH /api/admin/my-profile`)과는 **분리된
별도 API**다(아래 비범위 참조).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

신청 계정은 **승인되기 전까지 어떤 데이터도 보지 못한다**(`auth.py` 미들웨어가
승인 전 상태를 전부 401/403으로 막는다). 이 화면이 없으면:

- 신청이 들어와도 그것을 승인할 수단이 없다 — 시스템 전체가 아무도 못 쓰는
  상태로 굳는다(사실상 owner 한 명이 API를 직접 호출해야 한다).
- 비밀번호가 없는 계정은 로그인 자체가 불가능한데(아래 ④), 발급할 화면이 없으면
  그 운영자는 영영 못 들어온다.
- 퇴사·사고 대응(정지 + 세션 즉시 무효화)을 할 수단이 없다.
- 오타 이메일(아래 ④ 실측 사례)로 신원이 꼬인 계정을 고칠 수단이 없다.

## ④ 데이터

### 실측 방법

`api.db.engine`으로 `admin_operators`(18행) 전수 SELECT + `api/auth.py`·
`api/admin_operators.py`·`api/admin_profile.py`·`api/passwords.py` 코드 대조.
2026-08-13.

### 권한 3단계 (코드 상수, `api/auth.py` `ROLE_RANK`)

| role 값 | 한글 라벨 | rank |
|---|---|---|
| `viewer` | 조회 | 1 |
| `operator` | 운영자 | 2 |
| `owner` | 관리자 | 3 |

**경로별 최소 등급**(`required_role()`): 관리자 API 대부분은 GET=viewer,
쓰기=operator가 기본값이다. 다음은 **operator로는 못 하고 owner만 되는 쓰기**다
(`OWNER_WRITE_PREFIXES`): 운영자 관리(`/operators`, 조회도 owner) · 운영 전환
설정(`/ops-settings`) · 카탈로그 일괄 적재(`/catalog-import`) · 사양 항목 추가
(`/spec-fields`) · 용도 하한(`/usage-floors`) · 마진 정책(`/pricing-settings`,
`/category-margins`).

### 상태 3단계 (DB 문자열 그대로 — **한글이다, 영문 아님**)

| status 값 | 의미 |
|---|---|
| `대기` | 신청 접수, 미승인 — 로그인 시 "승인 대기 중" 메시지만 받는다 |
| `활성` | 승인됨 — 로그인 가능(단, 비밀번호가 있어야 함, 아래 참조) |
| `정지` | 퇴사·사고 등으로 접근 차단 — 로그인 즉시 403, 기존 세션도 전부 무효 |

`resolve_session()`은 `status != '활성'`이면 세션을 즉시 버린다. **`'active'`
같은 영문 문자열을 넣으면 로그인 자체는 200을 주는데(잘못된 코드 경로) 세션
검증이 조용히 실패해 계속 401이 나는 함정이 실제로 있었다** — 이 화면(과 그
API)이 다루는 값은 반드시 한글 리터럴이어야 한다.

### 신청 · 신원 확인 — 지금은 dev 어댑터다

`POST /api/admin/auth/login`의 신원 검증은 **`"@" in email` 한 줄**이 전부다
(`api/auth.py`). `provider`(예: `"google"`)는 **클라이언트가 보낸 값을 그대로
저장**할 뿐 서버가 검증하지 않는다 — `admin_profile.py`의 `PROVIDER_KO` 라벨이
모든 경우에 `verified: False`를 명시한다("클라이언트가 보낸 제공자 이름을
그대로 기록한 값입니다. id_token 검증은 아직 하지 않습니다"). 실 OAuth 훅
(`_verify_google()`)은 자리만 있고 비어 있다. **이 화면은 이 사실을 감추면
안 된다** — 과거 실제 사고: 승인 화면이 오랫동안 "직원이 회사 계정으로 본인
확인을 마친 신청입니다"라고 적어 왔는데, dev 어댑터에서는 그런 확인이 일어난
적이 없었다(`admin_operators.py`의 `_pending_note()` 자체 docstring이 이 사고를
그대로 기록하고 있다). 그래서 승인 판단 문구는 신청 상태에서 **서버가 파생**한다
(`admin_profile.identity_reasons()`가 유일한 판정 함수 — 운영자·권한 화면과
"내 정보" 화면이 이 함수 하나를 공유한다. 여기서 다시 구현하면 문구를 고칠 때
한쪽만 고치는 사고가 난다).

### `ADMIN_BOOTSTRAP_EMAILS` — 최초 관리자 자동 승인

`.env`의 `ADMIN_BOOTSTRAP_EMAILS`(쉼표 구분)에 있는 이메일은 **첫 로그인 시도
자체가 신청이 아니라 즉시 활성 owner 계정 생성**으로 처리된다(승인자 없음 —
`identity_reasons()`가 이런 계정을 "부트스트랩(자동)"으로 라벨링한다). **실측:
2026-08-13 현재 이 변수는 비어 있다**(`.env`에 `ADMIN_BOOTSTRAP_EMAILS=`만
존재) — 지금 새로 신청하는 이메일은 전부 `대기` 상태로 접수되고 사람이 승인해야
한다.

### 비밀번호 — 저장은 해시만, 미설정이면 로그인 불가

`api/passwords.py`: `hashlib.scrypt` 해시만 저장(원문은 로그·응답·예외 어디에도
없음). 최소 10자 + 대문자·소문자·숫자·기호 중 3종 이상 + 연속반복 금지 +
이메일 로컬파트 포함 금지 + 흔한 단어 금지 규칙이 `GET
/api/admin/auth/password-policy`로 노출된다(화면이 규칙을 베껴 적으면
안 된다 — 규칙이 바뀌면 화면이 거짓말하게 된다).

**활성(`활성`) 계정이라도 `password_hash`가 없으면 로그인 자체가 403
`password_not_set`으로 막힌다.** 발급은 owner가 `POST
/api/admin/auth/operators/{id}/password`로 임시 비밀번호를 내려주는 방식뿐이고
(발급된 비밀번호는 응답에 다시 나타나지 않는다 — 별도 채널로 전달해야 함),
받은 사람은 최초 로그인에서 강제로 비밀번호를 바꿔야 한다
(`must_change_password`).

### 지금 계정 분포 (2026-08-13 실측, 18행)

| role | status | 건수 |
|---|---|---|
| owner(관리자) | 활성 | **13** |
| owner(관리자) | 정지 | 2 |
| operator(운영자) | 정지 | 1 |
| viewer(조회) | 정지 | 2 |
| (대기 상태) | — | **0건** |

**활성 계정 13개가 전부 owner(관리자)다 — 활성 상태인 operator·viewer는
지금 하나도 없다.** 3단계 권한 체계가 코드로는 구현돼 있지만 실사용에서
등급 분리가 거의 이뤄지지 않고 있다는 뜻이다. 13개 중 3개는 부트스트랩
자동승인(`approved_by IS NULL`), 10개는 다른 owner가 명시적으로 owner 등급을
부여해 승인한 것(`approved_by IS NOT NULL`) — 승인 화면은 `role` 파라미터를
자유롭게 받으므로(`ApproveBody.role` 기본값은 `operator`이지만 승인자가 바꿀
수 있다) 최고 등급 부여에 별도 확인 절차가 없다. 활성 13개 중 **1개는 비밀번호가
없어 지금 로그인할 수 없다**(발급 대기), 10개는 `must_change_password=true`
(임시 비밀번호 발급 후 미변경) 상태다.

### 이메일 정정 — 실제로 필요했던 사례가 DB에 있다

`operator_id=11`의 이메일이 `lsa@proteam13@@`로 등록돼 있다(`@`가 두 번 —
신청 화면 오타로 추정). `POST /api/admin/operators/{id}/email`(owner 전용,
슬라이스 73)이 이런 경우를 위해 존재하며, 이메일을 바꾸면 **비밀번호를
함께 초기화하고 기존 세션을 전부 끊는다**(신원이 바뀌었으므로 새 주소의
주인이 맞는지 다시 확인받아야 한다는 설계).

### 세션 — 8시간 절대 만료 · 30분 유휴 만료 · 다른 기기 로그아웃

- `admin_sessions`: 절대 만료 8시간, 유휴 만료 30분. 지금 살아있는 세션
  **6개**, 누적 발급 **1,046개**(실측).
- 로그아웃·정지는 **삭제가 아니라 `revoked_at` 기록**(되돌림/원장 규약과 동일
  원칙 — 언제 어디서 열려 있었는지를 잃지 않는다).
- 본인이 "다른 기기에서 로그아웃"할 수 있다(`GET /my-profile/sessions`로
  목록+현재 기기 표시, `POST /my-profile/sessions/revoke-others`로 현재
  세션만 남기고 나머지 종료) — 이건 **본인 셀프서비스**이고, "내 정보"
  화면(ADM-SYS-022, 별도 화면) 소관이다.
- 이 화면(운영자·권한)이 하는 "정지"는 **대상 계정의 살아있는 세션을 전부**
  즉시 끊는다(퇴사·사고용).

### 안전장치 (서버가 강제 — 화면이 우회하면 안 된다)

- 자기 자신을 강등할 수 없다(rank가 owner 미만으로 내려가는 자기 변경 거부).
- 자기 자신을 정지할 수 없다.
- **마지막 활성 owner는 정지할 수 없다**(`role='owner' AND status='활성'`
  카운트가 1이면 409) — 시스템 전체가 관리자 없이 잠기는 것을 막는다.
- `대기`/`정지` 상태 계정의 권한은 변경할 수 없다(먼저 승인해야 함).

### 쓰는 API

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/operators` | 전 계정 목록 + 신원 판정(`identity_reasons`) + 대기 안내문 + 세션/작업 수 | owner |
| `POST /api/admin/operators/{id}/approve` | `대기`→`활성`, 등급 부여 | owner |
| `POST /api/admin/operators/{id}/role` | 등급 변경(활성 계정만) | owner |
| `POST /api/admin/operators/{id}/suspend` | `활성`→`정지`, 세션 전체 즉시 무효화 | owner |
| `POST /api/admin/operators/{id}/email` | 이메일 정정(비밀번호 초기화 + 세션 종료 동반) | owner |
| `POST /api/admin/auth/operators/{id}/password` | 임시 비밀번호 발급(`api/auth.py`) | owner |
| `GET /api/admin/auth/password-policy` | 비밀번호 강도 규칙(화면이 그대로 노출) | 공개 |

## ⑤ 기능 (동사)

- 전 계정 목록을 본다(대기 우선 정렬 — `ORDER BY (status='대기') DESC`).
- 신청 계정을 등급을 정해 승인한다.
- 각 계정의 "로그인 방식"·"승인" 근거를 서버가 만든 문장으로 본다(신원이
  검증됐는지 여부 포함).
- 활성 계정의 등급을 바꾼다(자기 자신 강등 제외).
- 계정을 정지한다(자기 자신·마지막 활성 owner 제외) — 그 순간 세션이 끊긴다.
- 비밀번호가 없는 계정에 임시 비밀번호를 발급한다.
- 오기입된 이메일을 정정한다(부작용: 비밀번호 초기화 + 세션 종료를 미리 안다).
- 각 계정의 작업 기록 수·현재 로그인 세션 수를 본다.

## ⑥ 인터랙션

- 승인은 등급을 함께 지정해야 한다(기본값 `operator`이지만 승인자가 자유롭게
  바꿀 수 있다 — 위 ④에서 밝힌 대로 owner 등급 부여에 별도 확인 절차가 없다는
  점을 화면이 인지해야 한다).
- 이미 활성인 계정을 다시 승인하면 409("이미 활성 계정입니다 — 권한 변경을
  사용하세요") — 승인과 등급변경은 서로 다른 동작이라는 것을 화면이 구분해야
  한다.
- 정지 확인 시 "몇 개의 세션이 끊기는지"를 먼저 알려야 한다(다른 화면들의
  "누르기 전에 결과를 안다" 관행과 동일 — 세션 목록 API가 이미 이 값을 준다).
- 이메일 정정 확인 시 "비밀번호가 초기화되고 세션이 끊긴다"는 결과를 먼저
  알려야 한다.
- 비밀번호 발급 후에는 **발급된 값이 화면 어디에도 다시 나타나지 않는다** —
  전달 수단은 이 화면의 범위 밖(운영자 간 별도 채널)이라는 사실을 명확히
  해야 한다.

## ⑦ 상태 · 예외

- **대기 신청 0건**(지금 실제 상태): "승인할 것이 없다"를 정상 상태로 표시해야
  한다.
- **신원 미검증 신청**: `identity_reasons().provider_verified`가 `false`인
  대기 건이 있으면, 승인 전 "신청자에게 직접 확인하라"는 서버 안내문을 그대로
  보여줘야 한다(문구를 화면이 다시 쓰지 않는다).
- **승인자 계정이 나중에 삭제된 경우**: "승인자: (계정 삭제됨)"처럼 승인자
  이름을 조회할 수 없는 상태를 서버가 이미 구분해 준다(`identity_reasons`) —
  화면이 `—`로 뭉개면 안 된다(왜 비었는지의 정보 손실).
- **비밀번호 미설정 활성 계정**(실측 1건): 로그인 불가 상태라는 것을 목록에서
  바로 알 수 있어야 한다(`has_password=false`) — owner가 발급해야 할 대상이라는
  뜻이다.
- **마지막 활성 owner 정지 시도**: 409, 사유 그대로 노출.
- **자기 자신 강등·정지 시도**: 409, 사유 그대로 노출.
- **미로그인 / owner 미만 등급의 접근**: 401 / 403(목록 조회조차 owner
  전용이므로 "권한 부족" 화면이 다른 화면보다 자주 나올 수 있다).

## 비범위 — 이 화면이 하지 않는 일

- **본인 정보 조회·수정**("내 정보", `GET/PATCH /api/admin/my-profile`,
  `api/admin_profile.py` 자체 docstring상 ADM-SYS-022) — 이미 별도로 존재하는
  화면이며, 고칠 수 있는 필드(`name`·`phone`·`duty`)와 세션 셀프서비스가
  이 화면과 분리돼 있다. 이 문서가 그 화면의 요구사항까지 겸하지 않는다.
- **실 OAuth 연동**(구글 등) — `_verify_google()` 훅은 백엔드 작업이며, 이
  화면은 "지금은 검증되지 않는다"는 사실을 보여줄 뿐 검증 자체를 구현하지
  않는다.
- **`ops_settings` 등 정책류 API의 등급 게이트를 바꾸는 일** — `OWNER_WRITE_PREFIXES`
  목록 자체를 조정하는 것은 각 해당 화면(운영 전환 설정 등)의 소관이다.

## 사장님 결정이 필요한 지점

1. **활성 계정 13개가 전부 owner(관리자)인 지금 분포를 그대로 둘지, 재배정할지.**
   조회·운영자 등급이 설계는 됐지만 실제로 쓰이지 않고 있다.
