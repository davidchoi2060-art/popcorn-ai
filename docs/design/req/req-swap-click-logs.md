# 요구사항 정의서 — 부품 교체 · 클릭 기록 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 결정권자(또는 지정 경로)가 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/swap-logs.html`(ADM-ORD-030)은
> 백업용 동결 — 참고만 하고 옮기지 않는다(P-09).
>
> 작성일 2026-08-13. ④의 수치는 그 시각의 실측 스냅샷이다. 재측정은
> `SELECT count(*) FROM swap_event_logs`·`promo_click_logs`와
> `GET /api/admin/swap-logs`를 다시 돌리면 된다.

---

## ① 화면 성격

**조회 화면이다(읽기 전용 관측창) — 그러나 단순 로그 뷰가 아니라 "결과를 정책으로
되돌리는" 화면으로 설계돼 있다.** 고객이 추천을 실제로 얼마나 그대로 받아들이는지
(교체율)와, 어떤 부품의 근거를 눌러 확인하려 했는지(클릭)를 보여준다. **교체율은
"최선의 부품"이라는 정체성 주장의 직접 측정값이다** — 설문도 추정도 아니고 고객의 손이
직접 남긴 사실이다(`docs/design/admin-remodel-2026-08-07.md` §1-①).

- 열람은 로그인만 되면 등급 무관(viewer 이상).
- 쓰기 기능 없음 — 이 화면 자체에는 입력할 것이 없다. 데이터는 고객 화면(S2 근거 클릭,
  S3 부품 교체)에서 자동으로 쌓인다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **"추천이 실제로 받아들여지는지"를 알 방법이 없다.** 추천이 맞았다면 고객은
  그대로 결제하고, 틀렸다면 부품을 바꾼다 — 교체 자체가 추천 정확도의 직접 증거다.
  이 화면 없이는 "추천이 잘 되고 있다"는 말이 근거 없는 자기 확신이 된다.
- **교체 기록이 쌓이기만 하고 아무 데도 안 가면, 기록은 기록으로 끝난다.** 이 화면의
  핵심은 "어느 방향으로 교체됐는가"(더 비싼 것으로/더 싼 것으로/같은 값으로)가 **어느
  정책 화면을 고쳐야 하는지**를 직접 가리키는 것이다(아래 "정책 연결" 참조) — 이 연결이
  없으면 숫자만 쌓이고 아무도 조치하지 않는다.
- **근거 클릭이 없으면 "설명이 부족한 부품"을 찾을 방법이 없다.** 정체성이 "모든
  견적에는 이유가 있습니다"인데, 어떤 부품의 이유를 사람들이 자꾸 눌러 확인하려
  하는지를 모르면 그 근거를 개선할 근거가 없다.

### 정책 연결 — 이 화면이 실제로 하는 일(코드에 이미 구현됨)

교체율표의 각 행은 평균 가격 변화 방향에 따라 **가리키는 화면이 다르다**(`_fix()`,
`api/admin_swap_logs.py`):

| 평균 가격 변화 | 해석 | 가리키는 화면 |
|---|---|---|
| 상향(+) | 추천이 보수적이었을 수 있음 | 「용도별 최소 사양」(하한이 낮아 싼 부품이 뽑혔을 수 있음) |
| 하향(−) | 예산 압박 신호 | 「추천 기준 설정」(예산 배분이 그 슬롯에 과했을 수 있음) |
| 변화 없음 | 취향·재고 사유 | 「부품 등급 관리」(값은 같은데 바꿨다면 매긴 서열이 취향과 어긋남) |

이 세 화면은 전부 이번 정의서 세트("상품사양관리" 그룹)에 포함돼 있다 — 이 화면은
그 셋과 이어지는 **결과→정책 피드백 루프의 종점이자 시작점**이다.

## ④ 데이터

### 실측 방법

`SELECT` 직접 실행(`swap_event_logs` 279행·`promo_click_logs` 270행, 읽기 전용) +
`GET /api/admin/swap-logs` 코드 대조. 2026-08-13 스냅샷.

### 쓰는 테이블(둘 다 이 화면 밖에서 쌓인다 — 아래 "데이터 출처" 참조)

| 테이블 | 역할 |
|---|---|
| `swap_event_logs` | 교체 사실 원장. `log_id`·`from_product`·`to_product`·`user_id`·`session_id`·`slot`·`price_delta`·`created_at` — 8컬럼. 슬라이스 46(2026-07-26)부터 쌓인다 |
| `promo_click_logs` | 근거 클릭 원장. `log_id`·`product_code`·`user_id`·`created_at` — 4컬럼. 슬라이스 49(2026-07-27)부터 쌓인다 |
| `quote_snapshots` | 교체율의 **분모**(그 슬롯이 실제로 몇 번 제안됐는지) — `recommendation_items`는 0행·엔진 미사용이라 분모로 쓸 수 없다(실측 확인됨) |

### 데이터 출처 — 이 화면이 만들지 않는다

- 교체 기록은 고객이 S3(부품 변경 화면)에서 실제로 부품을 바꿀 때 서버가 남긴다
  (`api/swap.py`, "교체 사실을 원장에 남긴다").
- 클릭 기록은 고객이 S2에서 부품 행을 눌러 근거를 확인할 때 `POST /api/promo-click`이
  남긴다(`api/clicks.py`). **비로그인 방문자도 기록된다** — 로그인은 조건이 아니다.
- `user_id`는 **회원 ID가 아니라 익명 방문자 키**(FK `users`)다. `member_id`를 쓰면 FK
  위반으로 조용히 롤백되는 사고가 실제로 있었다(슬라이스 49, 첫 두 건 유실) — 지금은
  회원이어도 방문자 키가 없으면 식별 없이 기록된다.

### 쓰는 API

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/swap-logs?limit=` | 교체 쌍 집계·슬롯별 교체율·최근 교체·클릭 집계를 한 번에 반환(`limit` 기본 100, 최대 500) | viewer 이상(쓰기 없음) |

### 실측 값 (2026-08-13)

**교체 279건**(2026-07-26~2026-08-12): GPU 273 · 메인보드 3 · CPU 2 · 메모리 1.
**교체는 압도적으로 GPU에서 일어난다**(97.8%).

**GPU 교체의 실체(중요 — 소수 조합이 대부분을 차지)**: 273건이 **서로 다른 273개
세션, 26명의 방문자, 단 4개의 (원래상품→교체상품) 조합**에서 나왔다. 그중 한 조합
(상품 124630 → 상품 110226)이 **246건(전체 GPU 교체의 90%)**을 차지하며, 발생 기간도
2026-07-26~2026-08-08로 12일에 걸쳐 있다(하루 몰림이 아니라 반복적으로 일관되게
나타나는 패턴). 이 조합의 평균 가격 변화는 GPU 전체 평균(약 −55만원)과 궤를 같이
한다 — **"GPU 추천이 특정 상품(124630) 쪽으로 쏠리는데, 절대다수가 이를
받아들이지 않고 더 싼 상품(110226)으로 직접 바꾼다"는 것이 지금 데이터가 말하는
가장 뚜렷한 신호다.**

**근거 클릭 270건**(2026-07-27~2026-08-12): 식별됨(방문자 키 있음) 35건 · 식별
안 됨 235건. 클릭이 가장 많은 상품은 **`product_code 110226`(231건, 전부 식별
안 됨)** — 공교롭게도 위 GPU 교체 패턴에서 **고객이 바꿔 타는 바로 그 상품**이다.
두 번째는 `product_code 116443`(25건, **전부 식별됨** — 25명 전원이 서로 다른
방문자)이며, 이 상품은 최근(8/10~8/12) 활발해진 두 번째 교체 패턴(125182→116443
17건, 119556→116443 9건)의 목적지이기도 하다. **클릭과 교체가 같은 상품을 가리키는
것은 우연으로 보기 어렵다** — "이 상품이 왜 더 나은지 근거를 눌러 확인한 뒤 실제로
그쪽으로 바꾼다"는 하나의 일관된 고객 행동으로 읽을 수 있다(다만 이는 화면이 내려야
할 해석이 아니라 데이터가 보여주는 상관관계이며, 화면은 사실만 보여주고 해석은
운영자가 하게 한다).

## ⑤ 기능 (동사)

- 전체 교체 건수와 슬롯별 분포를 본다.
- **교체 쌍**(어떤 상품에서 어떤 상품으로, 몇 번, 평균 가격 변화)을 빈도순으로 본다.
- **슬롯별 교체율**(그 슬롯이 제안된 횟수 대비 실제로 교체된 비율)을 본다 — 분모는
  실제 제안 횟수(`quote_snapshots`)다. 교체율이 높은 슬롯이 추천 정확도가 가장 낮은
  부품이라는 해석 문구와 함께 본다.
- 각 슬롯의 평균 가격 변화 방향에 대한 **읽기**(추천이 보수적이었다/예산 배분이 과했다/취향 차이다)와
  **어느 정책 화면을 봐야 하는지**를 함께 본다(위 "정책 연결" 표).
- 최근 교체 20건을 원본(누가·언제·무엇을·얼마나)으로 본다.
- 근거 클릭 총건수·식별/비식별 건수·가장 많이 클릭된 부품 상위 10개를 본다.

## ⑥ 인터랙션

- 화면 진입 시 별도 조작 없이 전체 집계가 온다.
- `limit` 조정으로 교체 쌍 목록의 표시 개수를 바꿀 수 있다(최대 500) — 단, **오프셋이
  없어 다음 페이지로 넘어가는 개념 자체가 없다**(지금 데이터량 279건 기준으로는 500
  이내라 실질적 문제는 아니지만, 데이터가 늘어나면 CLAUDE.md 목록 규약대로 실제
  페이지네이션이 필요해진다).
- "정책 연결" 표의 각 행에서 제시하는 화면 이동(예: "추천 기준 열기")을 누르면 해당
  화면으로 이동한다.
- 근거 클릭 상위 목록에서 상품을 클릭하면 그 상품의 상세(상품 관리 화면)로 이동할 수
  있으면 좋다(연결 대상 화면의 정확한 이동 방식은 이 문서 범위 밖).

## ⑦ 상태 · 예외

- **클릭 0건과 "아직 아무도 안 눌렀다"는 다른 말이 아니다 — 그런데 "수집 자체가
  안 된다"와는 달라야 한다.** 슬라이스 49 이전에는 클릭 수집 경로 자체가 없어
  `promo_click_logs`가 항상 0행이었다. 지금은 경로가 있고 실제로 270건이 쌓였지만,
  **혹시 미래에 다시 0건이 되는 상황이 오면 화면은 `empty:true`+사유("수집 경로는 정상입니다 — 아직 클릭이 없습니다")를 구분해서 보여줘야 한다** — 0을 "측정 실패"와
  "관심 없음"으로 섞어 말하면 안 된다(배지 3종 규약, CLAUDE.md 근거).
- **교체 0건인 슬롯**: "교체가 없습니다 — 제안이 그대로 받아들여졌습니다"로
  긍정적으로 읽되, 애초에 그 슬롯이 제안된 적 자체가 없는 경우(분모 0)와는 구분해야
  한다(분모가 0이면 비율 자체가 뜻이 없다).
- **서버 실패**: 침묵하지 않는다.
- **권한**: 미로그인 401. 열람은 등급 무관.
- **오래된 형식의 스냅샷 혼입**: 교체율 계산은 `items`가 배열이든 `{parts:[...]}`
  객체든 방어적으로 읽어야 한다(견적 상담 기록 화면과 같은 이슈, 실측 12,401건 중
  1건이 구형식).

## 비범위 — 이 화면이 하지 않는 일

- **교체·클릭 이벤트를 직접 만드는 일** — 둘 다 고객 화면(S2·S3)에서만 발생한다. 이
  화면은 결과만 본다.
- **"왜 246건이 몰렸는지"에 대한 원인 분석·조치 실행** — 이 화면은 신호를 드러내고
  어느 화면으로 가야 하는지 안내할 뿐, 실제 조치(하한 조정·배분율 조정·등급 조정)는
  각각의 다른 화면(용도별 최소 사양·추천 기준 설정·부품 등급 관리) 소관이다.
- **주변기기(모니터·키보드 등) 교체·클릭** — 지금 데이터는 8슬롯 조립 부품에 한정된다
  (실측: `slot` 값이 전부 CPU/MB/RAM/GPU 중 하나).
- **회원 단위 식별** — `user_id`는 익명 방문자 키다. 회원으로 연결하는 것은 실 인증이
  붙은 뒤의 일이다.

## 사장님 결정이 필요한 지점

1. **`api/admin_swap_logs.py` docstring의 "ADM-ANL-020" 오기를 admin2에서는 어떻게
   참조할지** — 이 문서는 마크업+카탈로그 일치를 근거로 ADM-ORD-030을 확정했지만,
   코드 자체의 오기 수정은 별도 확인이 필요하다.
2. **GPU 124630→110226(246건) 패턴에 대한 실제 조치를 이 화면이 안내하는 수준을
