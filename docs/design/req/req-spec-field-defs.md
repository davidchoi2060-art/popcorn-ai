# 요구사항 정의서 — 상품 사양 정의 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 결정권자(또는 지정 경로)가 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/spec-fields.html`(ADM-PRD-050)은
> 백업용 동결 — 참고만 하고 옮기지 않는다(P-09).
>
> 작성일 2026-08-13. ④의 수치는 **그 시각의 실측 스냅샷**이다 — 화면은 이 문서의 숫자가
> 아니라 서버 응답만 쓴다. 재측정은 `.venv/Scripts/python`으로 `api.spec_fields.all_fields()`,
> `information_schema.columns`, `db/migrations/versions` 목록을 다시 대조하면 된다.

---

## ① 화면 성격

**설정·구조 관리 화면이다.** 검수 큐도 아니고 매일 드나드는 조회판도 아니다 — "이 부품
종류에 새로운 사양 항목이 필요하다"는 현장 발견이 생겼을 때 찾아오는 화면이고, 동시에
"지금 사양이 부품별로 얼마나 채워졌는지·어떤 규칙이 그 값을 읽는지"를 상시 확인하는
참고판이기도 하다. **이 화면이 하는 일은 단순한 CRUD가 아니라 스키마 변경이다** —
`product_specs` 테이블에 실제 컬럼을 만드는 유일한 비개발자 경로다(아래 "엔진 계약" 참조).

- 열람(충족률·필드 목록)은 로그인만 되면 등급 무관(viewer 이상).
- 새 항목 추가는 **owner 등급만**(스키마를 바꾸는 일이라 슬라이스 56에서부터 그렇게
  막혀 있다).
- 항목을 **삭제하는 기능은 의도적으로 없다** — 컬럼을 지우면 그 안의 값이 함께 사라지고
  되돌릴 수 없기 때문이다(⑦ 참조). "쓰지 않는 항목을 감춘다"는 다른 방법(part_types를
  비움)으로 해결한다.

**주의 — 이름이 비슷한 다른 화면과 반드시 구분한다(CANON.md 경고 사례):**
"조립 사양 표준"(`/admin2/spec-standard`, 이미 구축됨)은 `std.spec_defs`/`std.part_specs`라는
**전혀 다른 저장소**를 관리한다. `std.*`는 아직 견적 엔진이 읽지 않는, 사람이 조립 경험으로
넓혀가는 새 표준 스키마다(EAV라 컬럼 추가가 필요 없다). 이 화면(상품 사양 정의)이 다루는
`spec_field_defs`/`product_specs`는 **지금 실제로 추천 엔진이 읽는 살아있는 스키마**다. 둘을
섞으면 "쿨러 채움률 48%"(std 값)를 엔진 채움률로 오진한 2026-08-11 전례가 반복된다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **개발자 없이는 사양 항목을 하나도 늘릴 수 없다.** 현장 검수·매입 담당이 "이 부품에는
  이런 값도 있어야 한다"를 발견해도, 이 화면(정확히는 이 화면이 부르는 API)이 없으면
  개발 배포를 기다리는 수밖에 없다 — 그 사이 값은 엑셀과 머릿속에만 남는다(슬라이스 56
  배경 그대로).
- **사양 항목 하나가 실제로 몇 곳에 쓰이는지 볼 자리가 없다.** 필드 이름만 봐서는 알 수
  없다 — 예를 들어 `capacity_gb`는 호환 규칙 어디에도 안 쓰이지만 게임용 SSD 500GB
  하한(용도 하한)이 이 값을 읽는다. 이 화면(`used_by`)이 없으면 "이 필드 안 쓰는 것
  같은데 지워도 되나?"를 사람이 추측으로 판단하게 된다.
- **"항목 하나 추가"가 사람이 손으로 하기엔 위험이 크다** — 아래 엔진 계약 ①처럼 넷이
  동시에 맞아야 하는데, 하나라도 빠지면 "값은 있는데 엔진이 못 읽는" 종류의 버그가
  생긴다(가장 찾기 어려운 종류 — 에러가 안 나고 결과만 조용히 줄어든다). 이 화면의 API가
  넷을 한 트랜잭션 + 자동 파일 기록으로 묶어 그 실수를 구조적으로 막는다.

### 엔진 계약 — 이 화면이 실제로 지키는 것(CLAUDE.md 근거)

**사양 항목 추가는 네 가지가 함께 일어나야 완결된다** (`api/admin_spec_fields.py`
`add_spec_field`, CLAUDE.md "사양 항목" 절):

1. **`product_specs` 실제 컬럼** — `ALTER TABLE product_specs ADD COLUMN`.
2. **메타 행** — `spec_field_defs`에 label·data_type·part_types·required_for 등 기록.
3. **엔진 사양이면(`is_engine=true`) 추천 뷰 재생성** — `CREATE OR REPLACE VIEW`로
   **끝에 컬럼 하나만 추가**한다. 뷰는 순서 변경·컬럼 삭제를 거부한다
   ("cannot drop columns from view") — 그래서 기존 정의를 그대로 두고 마지막 컬럼
   뒤에 한 줄만 끼우는 방식으로 구현돼 있다.
4. **마이그레이션 파일 기록 + 버전 스탬프** — 이게 없으면 서버를 새로 세우거나 백업에서
   복구할 때 화면에서 만든 컬럼이 **사라진다.**

**④가 실패해도 요청을 실패로 만들지 않는다(슬라이스 81 실사고 반영).** 배포 서버는
앱 계정이 리포 폴더에 파일을 쓸 수 없다(써서도 안 된다 — working tree drift). 실제로
`cpu_gpu` 항목을 만들 때 ①~③은 성공했는데 ④(파일 쓰기)만 500으로 실패한 적이 있다.
운영자에겐 "실패"로 보였지만 **컬럼은 이미 생겨 있었다** — 되돌릴 수도, 이력을 남길
수도 없는 상태로 하루 남아 있다가 발견됐다. 그래서 지금은 ④가 실패해도 ①~③의 성공을
부정하지 않고, 대신 "이 항목은 코드 이력이 없습니다"는 사실을 화면이 계속 표시하게 만든다
(`unrecorded` 목록, 아래 실측 참조). **이 사고는 이미 해소된 과거 사례다** — `cpu_gpu`는
현재 `db/migrations/versions/0020_spec_field_cpu_gpu.py`로 기록이 채워져 있다(2026-08-13
실측: `unrecorded=[]`). 화면은 이 상태(정상/미기록)를 계속 구분해서 보여줘야 한다 — 다음에
같은 실패가 나면 또 감춰지지 않아야 하기 때문이다.

**⚠ 실측된 결함 — 뷰 재생성이 실제로는 하나뿐이다.** 이 API의 모듈 docstring은
"② 추천 뷰 **두 개** 재생성"이라 적었지만, 실제 `add_spec_field` 함수는
`v_recommendation_candidates` 한 곳만 `_add_col_to_view`로 재생성하고
**`v_companion_candidates`는 손대지 않는다**(2026-08-13 코드 실측). 지금까지 문제가
드러나지 않은 이유는 `is_engine=true`로 지정된 22개 필드가 전부 8슬롯(CORE_TYPES) 부품
필드이고, 주변기기 전용 필드 8종(`size_inch`·`resolution`·`refresh_hz`·`panel`·
`switch_type`·`key_layout`·`connection`·`ports`)은 전부 `is_engine=false`이기 때문이다.
**앞으로 누군가 주변기기(모니터·키보드 등) 관련 필드를 `is_engine=true`로 추가하면,
메타에는 있는데 `v_companion_candidates`에는 없는 컬럼이 생겨 컴패니언 추천이 그 값을
조용히 못 읽는다** — 이 화면의 요구사항에 반영할지는 결정이 필요하다(아래 결정 필요
지점 참조).

## ④ 데이터

### 실측 방법

`api.spec_fields.all_fields()`(=`spec_field_defs` 테이블), `information_schema.columns`
(`product_specs`), `db/migrations/versions/` 파일 목록을 직접 대조(읽기 전용). 2026-08-13 스냅샷.

### 쓰는 테이블

| 테이블 | 역할 |
|---|---|
| `spec_field_defs` | 항목 메타의 단일 원천. `field_key`(PK 역할)·`label`·`data_type`·`unit`·`part_types`(JSONB)·`required_for`(JSONB)·`is_engine`·`is_custom`·`in_ingest`·`sort_order`·`note`·`created_by`·`created_at` — 13컬럼 |
| `product_specs` | 실제 값이 저장되는 EAV 아닌 wide 테이블. 항목 추가 시 여기 컬럼이 생긴다(현재 38컬럼) |
| `v_recommendation_candidates` | `is_engine=true` 항목 추가 시 재생성 대상(현재 50컬럼). 8슬롯 견적 엔진이 읽는다 |
| `admin_operator_activity_logs` | 추가 이력(`spec_field_add`) 기록 — 다만 아래 ⑥에서 밝히듯 **되돌리기 실행 경로는 없다** |

### 쓰는 API

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/spec-fields` | 항목 목록 + 부품별 충족률 + 자료형 설명 + `ghosts`/`unrecorded` | viewer 이상 |
| `POST /api/admin/spec-fields` | 항목 신설(위 엔진 계약 ①~④ 한 번에) | **owner 전용**(`auth.OWNER_WRITE_PREFIXES`) |

삭제(`DELETE`) 엔드포인트는 **존재하지 않는다** — 설계상 의도(⑦ 참조).

### 실측 값 (2026-08-13)

**전체 31개 항목**: 커스텀 아님·엔진 미사용(표시용 프리셋) 8개 · 커스텀 아님·엔진 사용
22개 · **커스텀 1개**(`cpu_gpu`, 내장그래픽, BOOLEAN, 2026-07-28 이 화면의 API로 실제로
만들어진 유일한 사례). `required_for`가 비지 않은(필수 판정에 실제로 쓰이는) 항목은
**17개**. 자료형 5종: INTEGER·NUMERIC·VARCHAR·BOOLEAN·JSONB.

부품 종류(`part_types`)별 필수 사양(`required_map()` 실측, 10개 조립 부품 전부에 존재):

| 부품 | 필수 사양 |
|---|---|
| CPU | socket, tdp_watt |
| MB(메인보드) | socket, chipset, mem_type, form_factor |
| RAM | mem_type, capacity_gb, clock_mhz |
| GPU | required_power_watt, length_mm, pcie_gen |
| SSD / HDD | capacity_gb, form_factor, interface |
| POWER(파워) | rated_watt, form_factor |
| CASE(케이스) | gpu_max_mm, cooler_height_mm, form_factor_list |
| COOLER_CPU_AIR(공랭) | socket_list, cooler_height_mm, cooler_tdp |
| COOLER_CPU_AIO(수랭) | socket_list, cooler_tdp |

**건강 상태 지표(화면이 매번 다시 계산해 보여줘야 하는 값, 지금은 둘 다 정상)**:
`ghosts`(메타는 있는데 실제 컬럼이 없음) = 0건 · `unrecorded`(커스텀인데 마이그레이션
파일 이력이 없음) = 0건.

**부품별 충족률**은 `products.status='판매중' AND stock_qty>0`인 상품만 분모로 삼는다
(전체 카탈로그를 분모로 하면 품절이 대부분이라 영원히 낮게 보인다 — 슬라이스 83 근거).
예: CASE는 필수 3항목(`gpu_max_mm`·`cooler_height_mm`·`form_factor_list`) 각각의
`count(...)`를 판매중·재고>0 케이스 모집단으로 나눈 값이 그 필드의 실제 진척이다.

## ⑤ 기능 (동사)

**공통(누구나 열람)**
- 전체 사양 항목을 목록으로 본다 — 라벨·자료형·단위·적용 부품·필수 여부·엔진 사용
  여부·현재 채움 건수.
- 부품 축으로 갈아 본다 — 부품 하나를 고르면 그 부품에 걸리는 사양만, 필수인지, 어떤
  호환 규칙·용도 하한이 그 값을 실제로 읽는지(`used_by`)를 함께 본다.
- 부품별 판매중·재고 보유 수와 카탈로그 전체 보유 수를 함께 본다(적은 이유가 "품절이
  많아서"인지 "실제로 부족해서"인지 구분하기 위해).
- 이 항목이 코드 이력(마이그레이션 파일)까지 남았는지 확인한다.

**owner만**
- 새 사양 항목을 만든다: 키(영문 소문자·숫자·밑줄, 2~39자)·표시 이름·자료형(정수/소수/
  짧은 글자/예·아니오/목록 중 하나)·단위·적용 부품·그중 필수로 만들 부품·엔진이
  읽을지 여부·적재(카탈로그 업로드)가 채울 값인지 여부를 지정해 만든다.
- 항목을 만들면 그 결과로 ⓐ 실제 컬럼이 생겼는지 ⓑ 추천 뷰가 다시 만들어졌는지(엔진용일
  때만) ⓒ 마이그레이션 파일이 기록됐는지(못 기록했으면 그 사실과 사유)를 확인한다.

## ⑥ 인터랙션

- 항목 추가 폼에서 **필수로 지정한 부품은 적용 대상(부품 종류)에 포함된 것만 고를 수
  있다** — 서버가 이를 어기면 400으로 막는다("필수로 지정한 종류가 적용 대상에
  없습니다"). 적용도 안 하는 부품에 필수를 걸면 그 부품이 영원히 검수 대기가 되기
  때문이다.
- 키가 예약어(`product_code`·`select`·`from` 등)이거나 이미 쓰이는 컬럼명이면 그 자리에서
  거부된다(각각 400·409) — 저장을 시도한 뒤에야 실패를 아는 일이 없어야 한다.
- 저장에 성공하면 응답에 `revision`(마이그레이션 번호)·`recorded`(기록 성공 여부)·
  `view_rebuilt`(뷰 재생성 여부)가 온다. **`recorded=false`면 "코드 이력에 남기지
  못했습니다 — 지금 상태로 서버를 다시 세우면 이 항목이 사라집니다. 개발 PC에서 마이그레이션을
  추가해야 합니다"는 문구를 그대로 보여줘야 한다** — 조용히 "성공"이라고만 말하면 슬라이스
  81의 사고가 반복된다.
- 응답에 `undo_id`가 오지만 **이 값을 소비하는 되돌리기 API가 없다**(⑦ 참조) — 화면은
  이것을 클릭 가능한 "되돌리기" 버튼처럼 보이게 만들면 안 된다. 감사 로그 참조번호로만
  다뤄야 한다.
- 목록에서 `ghosts`·`unrecorded`가 1건이라도 있으면, 그 항목이 무엇이고 왜 위험한지
  (재구축·복구 시 사라진다)를 목록 안에서 바로 알아볼 수 있어야 한다 — 별도 화면을
  뒤져야 알 수 있으면 늦다.

## ⑦ 상태 · 예외

- **삭제 기능은 설계상 없다.** 컬럼을 지우면 그 안의 데이터가 함께 사라지고 되돌릴 수
  없기 때문이다(CLAUDE.md 명문 규칙). 쓰지 않게 하려면 "적용 부품(part_types)을 전부
  비우는" 방법만 요구사항에 넣는다 — 값은 남고 화면·판정에서만 빠진다.
- **컬럼명 중복**: 이미 있는 컬럼명으로 추가를 시도하면 409("'{key}' 컬럼이 이미
  있습니다").
- **잘못된 키 형식**: 영문 소문자로 시작하지 않거나 특수문자가 섞이면 400. 예약어면 400.
- **모르는 자료형·모르는 부품 종류**: 400.
- **표시 이름 미입력**: 400("표시 이름을 입력하세요").
- **owner가 아닌 사용자의 추가 시도**: 401(미로그인) 또는 403(등급 부족, "필요: owner").
  열람은 등급 무관.
- **마이그레이션 파일 쓰기 실패(배포 서버 등 쓰기 권한 없는 환경)**: 요청은 200으로
  성공 처리하되(컬럼·메타·뷰는 이미 반영됐으므로), `recorded=false`와 실패 사유를
  응답에 담아 사람이 알게 한다 — **이걸 감추면 다음 서버 재구축 때 컬럼이 소리 없이
  사라진다.**
- **빈 상태**: 이론상 발생하지 않는다(부트스트랩만으로 31항목이 항상 존재 —
  `alembic upgrade head`가 보장). 만약 0건이면 DB 연결·마이그레이션 실패를 의심해야
  하므로 화면은 "사양 정의가 비어 있습니다"를 침묵하지 말고 드러내야 한다.

## 비범위 — 이 화면이 하지 않는 일

- **사양 값 입력 자체** — 상품 하나하나의 실제 값(예: 이 CPU의 소켓이 무엇인지)을
  넣는 일은 상품 상세(`PATCH /api/admin/products/{code}/specs`, 슬라이스 57) 소관이다.
  이 화면은 "어떤 항목이 존재하는가"만 정의한다.
- **검수 승인** — 값이 없어 검수 대기인 상품을 채우는 일은 「상품 사양 검수」
  (ADM-PRD-020, 다른 팀원이 별도로 정의 중) 소관이다.
- **`std.spec_defs`(조립 사양 표준) 관리** — 위 "주의" 참조. 이름이 비슷해도 다른
  화면·다른 저장소다.
- **호환 규칙·용도 하한의 값 자체를 고치는 일** — 이 화면은 "그 규칙이 어떤 필드를
  읽는지(`used_by`)"만 보여준다. 규칙 값 자체는 「조립 호환 규칙」·「용도별 최소 사양」
  화면 소관(각각 별도 정의서).
- **항목 삭제·이름 변경** — 위 ⑦ 참조. 의도적으로 열지 않은 기능이다.

## 사장님 결정이 필요한 지점

1. **`v_companion_candidates` 미재생성 결함을 이 화면의 요구사항에 포함할지.** 위 "엔진
   계약" 실측 결함 참조 — 지금까지 사고가 없었던 것은 우연(주변기기 필드가 아직 전부
   `is_engine=false`)이다. 앞으로 주변기기용 엔진 필드가 생길 가능성이 있다면 이 화면(의
   API)이 두 뷰를 모두 재생성하도록 요구사항에 못박아야 한다.
2. **`unrecorded`(코드 이력 없음) 상태가 실제로 발생했을 때 화면이 취할 조치의 강도.**
   지금은 "표시만" 한다. 배포를 막을지, owner에게 강한 경고를 띄울지는 설계 판단이라
   이 문서가 정하지 않는다.
3. **되돌리기(항목 자체를 없던 일로) 기능을 새로 열지, 지금처럼 "감추기(part_types 비움)"
   만으로 충분한지.** 컬럼 삭제를 열지 않는다는 원칙은 확정 규칙이지만, "메타만 비활성화"
   같은 중간 단계를 만들지는 결정 필요.
