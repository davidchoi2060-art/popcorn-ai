# 요구사항 정의서 — 인계 기록 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> **구화면 대응 없음 — 완전 신규.** 자체 판매 전제로 짜인 기존 22화면 카탈로그
> (`docs/decisions/admin-identity.md`)에는 이 축 자체가 없었다(2026-08-11 결정 —
> "자체 판매 전제로 짜인 IA라 「매출 집계」가 있고 「인계 성과」가 없었다",
> `docs/decisions/decision-log.md`). LNB 그룹 "인계 · 성과" 신설의 일부
> (`api/admin_nav.py`).
>
> 작성일 2026-08-13. ④의 수치는 `api.db.engine`으로 직접 SELECT(읽기 전용,
> `handoffs` 3행·`handoff_items` 27행 전수) + `api/handoff.py`·
> `db/migrations/versions/0042_handoffs.py`·`mockups/mvp1/s4-cart.html`·
> `mockups/mvp1/s5-complete.html` 코드 대조로 얻은 그 시각의 실측 스냅샷이다.
> 재측정은 `SELECT * FROM handoffs ORDER BY handoff_id`를 다시 돌리면 된다
> (지금 규모에서는 전량 조회가 곧 실측이다).

## ① 화면 성격

**조회 화면이다(읽기 전용 원장 열람 — 마스터-디테일 성격).** LNB 비고 원문
(`api/admin_nav.py`): *"신설 — 무엇을 언제 어떤 견적으로 넘겼나"*. 인접 화면인
견적 상담 기록(ADM-ORD-010, `req-consult-sessions.md`)이 "AI가 무엇을 제안했나"의
원장이라면, 이 화면은 그중 **"어디까지 실제로 쇼핑몰에 넘겼는가"**를 보여주는
원장이다 — 서로 다른 사건을 기록하는 서로 다른 화면이다(아래 ③).

- 열람은 로그인만 되면 등급 무관일 가능성이 높다(같은 그룹의 인접 화면들과 동일
  성격) — 최종 등급 기준은 결정 필요.
- **쓰기 기능 없음.** 인계 레코드는 오직 고객이 S4(`s4-cart.html`)에서 "팝콘PC에서
  구매하기"를 눌러 `POST /api/handoff`가 성공했을 때만 생긴다 — 관리자가 이 화면에서
  인계를 만들거나 취소하는 기능은 지금 코드 어디에도 없다(아래 비범위).

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **"누가 언제 무엇을 얼마에 넘겼는지"를 지금은 DB를 직접 조회해야만 알 수 있다.**
  이 문서를 쓰기 위해 실제로 `SELECT * FROM handoffs`를 돌렸다 — 그 결과를 볼 화면이
  운영자에게 없다. 고객용 단건 조회(`GET /api/handoff/{handoff_no}`)는 있지만
  **목록·집계를 보여주는 admin API가 아예 없다**(`api/` 전수 확인 — `handoff`를
  다루는 파일은 `handoff.py`·`mall.py`·`main.py`(라우터 등록)뿐).
- **이웃 화면의 판정 기준을 이 화면이 정정한다.** `req-consult-sessions.md`가 실측한
  바에 따르면, 지금 "견적 상담 기록" 화면은 "완주 → 주문"을 **`orders` 테이블
  기준**으로 보여주는데, `orders`는 A-10 커머스 시절(2026-07-16~2026-08-10) 데이터로
  **8/10 이후 갱신이 없다.** 반면 실제로 CANON 확정(2026-08-11) 이후 쌓이기
  시작한 원장은 `handoffs`다(3건, 8/11~8/12 — `orders`의 마지막 행보다도 나중).
  **이 화면이 없으면, 8/11 이후 실제로 일어난 인계(3건)가 관리자 눈에 전혀 안
  보이는 상태가 계속된다.**
- **"인계 = 완료"가 아니라는 사실을 드러낼 유일한 자리다.** 아래 ④에서 실측했듯
  지금 시스템은 견적을 쇼핑몰 **장바구니에 실제로 담는 동작을 하지 않는다** —
  고객에게 몰의 "장바구니 목록" 페이지 링크를 열어줄 뿐이다. 이 화면이 "인계 기록"을
  "구매 기록"처럼 보여주면 사실과 다른 확신을 준다.

## ④ 데이터

### 실측 방법

`api.db.engine`으로 직접 SELECT(읽기 전용, `handoffs`·`handoff_items` 전수 —
지금 각 3행·27행이라 전수 조회가 곧 실측이다) + `api/handoff.py`·
`db/migrations/versions/0042_handoffs.py`·고객 화면 두 개(`s4-cart.html`·
`s5-complete.html`) 코드 대조. 2026-08-13 스냅샷.

### 쓰는 테이블

| 테이블 | 컬럼(15개) | 비고 |
|---|---|---|
| `handoffs` | `handoff_id`·`handoff_no`(예 `HO-1001`)·`session_id`·`snapshot_id`·`quote_type`·`member_id`·`user_id`·`total_quoted`·`total_mall`·`price_checked`·`changed_cnt`·`soldout_cnt`·`status`·`note`·`created_at` | `handoff_no`는 `HO-`+연번, `pg_advisory_xact_lock`으로 동시 채번 보호(`api/handoff.py _no()`) |

| 테이블 | 컬럼(10개) | 비고 |
|---|---|---|

### 실측 값 (2026-08-13, 시스템에 존재하는 전부)

- **인계 3건**(`HO-1001`·`HO-1002`·`HO-1003`), **라인 27개**(2026-08-11 2건,
  2026-08-12 1건). `status`는 3건 전부 `'인계'` — **다른 상태값이 관측된 적이
  없고, 코드에도 다른 상태로 전이시키는 로직이 없다**(INSERT 시 상수 `'인계'`
  1회뿐, `api/handoff.py` L138).
- **세션 2개에서 3건이 나왔다** — `session_id=4247`이 `HO-1001`(12:56:58)과
  `HO-1002`(13:00:44)로 **4분 간격 두 번** 인계됐다(같은 세션, `user_id`는
  473→474로 다르다). `session_id=4315`는 `HO-1003` 한 건. **원인은 이 실측만으로는
  알 수 없다**(재시도인지 중복 클릭인지 별개 방문자의 재상담인지) — 화면이
  "세션 1개 = 인계 1건"을 전제로 설계되면 안 된다는 근거다.
- **`item_kind` 분포: `core_part` 24 · `assembly_service` 3 · `peripheral` 0.**
  주변기기(`periph`)를 함께 넘기는 기능은 `api/handoff.py`의 `HandoffBody`에 이미
  있지만, **실제 인계 3건 중 하나도 주변기기를 담지 않았다** — 만들어졌지만
  실사용례가 아직 없는 경로다(`req-consult-sessions.md`의 `expert` 모드 0건과
  같은 종류의 사실).
- **`member_id`는 3건 전부 NULL, `user_id`는 3건 전부 있다**(473·474·563) —
  회원 인증이 아직 없는 지금 상태에서는 정상이다(견적 상담 기록의 실측과 같은 패턴).
- `quote_type` 분포: `highend` 2 · `recommend` 1. `value`(가성비)로 인계된 사례는
  아직 없다.
- **몰과의 가격 차이가 라인 27개 중 13개(48.1%)에서 났다**(`req-mall-sync.md`와
  동일 소스 실측 — 상세는 그 문서 참조). 이 화면은 그 요약값(`changed_cnt`)을
  건별로 보여주는 자리이지, 동기화 상태 자체를 감시하는 자리는 아니다(역할 분담은
  `req-mall-sync.md` 참조).
- `total_quoted` 합계 6,086,700원 vs `total_mall` 합계 5,940,400원 — **단, 이
  합산은 순수 비교가 아니다.** `HO-1002`는 라인 2개(`확인못함`)의 몰값을 못 읽어
  `total_mall` 계산에 **`price_quoted`로 대체**했다(`api/handoff.py` L124,
  `l["mall"] if l["mall"] is not None else (l["quoted"] or 0)`) — 이 화면이 두
  총액을 나란히 보여주려면 이 대체가 있었다는 사실을 함께 밝혀야 왜곡이 없다.

### 실측된 간극 — "인계"는 몰 장바구니에 실제로 담겼다는 뜻이 아니다

`api/handoff.py`가 돌려주는 `cart`는 "담을 목록"이고 `cart_url`은
`mall.BASE + "/shop/order_basket_list.html"`(몰의 **장바구니 목록 페이지** URL)이다.
그런데 **이 서버가 실제로 그 주소에 상품을 담는 요청(`POST
/shop/order_basket_action.php`)을 보내는 코드는 어디에도 없다.** 고객 화면
(`s4-cart.html`)도 확인 결과 인계 성공 후 그냥 자체 완료 화면(`s5-complete.html`)
으로 이동시킬 뿐이고, `s5-complete.html`은 `cart_url`을 **새 탭으로 여는 링크**로만
쓴다(고객이 직접 눌러야 열린다). 이것은 결정 필요 사항으로 이미 문서화돼 있다
(`decision-log.md` "🟡 미정 — 인계를 무엇으로 하나": (가) API 서버 대 서버 연동
vs (나) 폼 자동 제출, **둘 다 아직 구현되지 않았다**). **즉 이 화면이 보여주는
"인계 기록"은 "우리가 쇼핑몰에 넘기려고 시도한 기록"이지 "고객의 몰 장바구니에
실제로 담긴 기록"이 아니다.** 이 구분을 화면이 흐리면 안 된다.

### 실측된 간극 — 데모 상품이 인계 라인에 실제로 등장한다

`HO-1001`의 라인 3·8(RAM `20483003`, SSD `20486102`)은 `products.data_origin='demo'`인
8자리 코드다(`req-mall-sync.md`가 같은 사실을 다른 각도로 다룬다). `price_mall`이
`0`(HO-1001) 또는 `NULL`(HO-1002, 같은 상품인데 결과가 다르다 — 실시간 스크래핑의
비결정성을 보여준다)로 남아 있다. 이 화면이 라인 상세를 보여줄 때 **"0원"과
"확인 안 됨"을 시각적으로도, 문구로도 구분해야 한다** — 이미 `mall_status` 컬럼이
그 둘을 `가격변동`/`확인못함`으로 구분해 저장하고 있으므로 화면은 그 값을 그대로
따르면 된다(새로 판단할 필요 없음).

## ⑤ 기능 (동사)

- 인계 건을 최신순으로 본다(번호·시각·티어·우리 총액/몰 총액·상태).
- 인계 건 하나를 열어 라인 전체(부품/조립비/주변기기 구분, 상품코드·당시 표시명·
  우리값·몰값·확인 상태)를 본다.
- 그 인계가 어느 상담 세션·어느 견적 스냅샷에서 나왔는지 연결해서 본다(다른 화면
  "견적 상담 기록"으로 건너가는 근거가 된다).
- 가격이 달라진 라인만 걸러본다.
- 확인하지 못한 라인만 걸러본다.
- 방문자(익명 `user_id`) 단위로 같은 사람이 여러 번 인계했는지 본다(실측상 이미
  한 세션이 2번 인계된 사례가 있다 — 위 ④).

## ⑥ 인터랙션

- 목록에서 인계 건을 고르면 라인 상세가 펼쳐진다(별도 페이지 이동 없이 같은
  화면에서 보는 방식을 권장하되, 방식 자체는 UI 설계 영역).
- 상세에서 "이 상담 세션 보기"를 누르면 견적 상담 기록 화면으로 이동한다(두 화면이
  같은 `session_id`를 공유하므로 상호 참조가 자연스럽다).
- 필터(기간·티어·가격변동 유무)를 걸면 목록이 다시 요청된다 — 단, 지금은 목록
  API 자체가 없으므로 백엔드 신규 개발이 선행돼야 한다.
- 지금 데이터량(3건)에서는 페이지네이션이 급하지 않지만, CLAUDE.md 목록 규약
  ("목록은 전부 서버 페이지네이션")은 예외를 두지 않는다 — 신규 API를 만들 때부터
  갖추는 것이 맞다.

## ⑦ 상태 · 예외

- **0건 상태**: 이론상 가능하다(기능이 2026-08-11부터 존재하므로 그 이전 기간을
  보면 항상 0건). "아직 아무도 인계하지 않았다"와 "조회 실패"를 구분해야 한다.
- **`price_mall`이 `0`인 라인과 `NULL`인 라인은 다른 뜻이다** — 위 실측된 간극
  참조. `mall_status` 값을 그대로 신뢰하고 노출한다(화면이 새로 판정하지 않는다).
- **`status`가 사실상 상수(`'인계'` 하나뿐)라는 점**을 화면이 마치 여러 상태를
  오가는 것처럼(상태 배지·필터를 과하게) 표현하면 안 된다 — 지금 코드에는 다른
  상태로 넘어가는 경로가 없다.
- **서버 실패**: 침묵하지 않는다.
- **권한**: 미로그인 401. 열람 등급은 결정 필요.
- **주변기기 라인 0건**: "주변기기 열이 항상 비어 있다"를 오류처럼 보이지 않게
  해야 한다 — 기능은 있으나 실사용이 아직 없는 정상 상태다.

## 비범위 — 이 화면이 하지 않는 일

- **인계를 취소하거나 되돌리는 일** — 코드에 그런 기능 자체가 없다(원장·되돌림
  규약상 "역방향 전이"가 있어야 정상인데, 지금 `handoffs`에는 그 경로가 없다는
  사실 자체를 이 문서가 짚어 둔다. 만들지 여부는 결정 필요가 아니라 별도 백엔드
  기획 사안).
- **몰 장바구니에 실제로 상품을 담는 자동화** — 위 실측된 간극 참조. 아직 없고,
  이 화면이 만드는 것도 아니다.
- **인계 이후 실제 결제·구매 여부 확인** — 그건 「유입 성과」
  (`req-funnel-performance.md`) 쪽에서 다루되, 그 문서도 실측하듯 지금은 몰
  데이터가 없어 답할 수 없다.
- **회원 식별·매핑** — `member_id`가 항상 NULL인 지금 구조적으로 불가능하다.
- **가격 재확인 로직 자체(동기화 건강 상태 감시)** — `req-mall-sync.md` 소관.
  이 화면은 그 결과값(`changed_cnt`·`mall_status`)을 건별로 보여줄 뿐이다.

## 사장님 결정이 필요한 지점

1. **`GET /api/handoff/{handoff_no}`(인증 없는 고객용 엔드포인트)를 admin2가
   그대로 쓸지, admin 전용 신규 엔드포인트를 만들지.** 지금 것은 권한 체크가
   없다 — 그대로 쓰면 handoff_no만 알면 누구나 조회 가능한 상태가 admin2에도
   이어진다.
2. **"인계했지만 몰 장바구니 도달 여부는 모른다"는 사실을 화면에 어떻게
   드러낼지.** 위 실측된 간극이 명확한 사실이라, 화면이 이걸 숨기면 "인계 =
   판매"로 오인시킨다.
3. **`status` 컬럼을 화면에서 어떻게 다룰지** — 지금은 사실상 상수 하나뿐이라
   상태 필터·배지를 만드는 게 의미가 있을지, 훗날(취소·재시도 등) 값이 늘어날
   것을 가정해 미리 자리를 만들어 둘지.
4. **화면 ID·경로 확정.** 후보 `ADM-HND-020`은 이 문서의 제안일 뿐이다 — 세 화면
   (쇼핑몰 동기화·인계 기록·유입 성과)의 접두어를 함께 정해야 한다.
