# 요구사항 정의서 — 로그인 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 사장님(또는 지정 경로)이 별도로 한다.
>
> **대상은 admin2 신규 구축이다** — 사장님 지시("admin2 스타일로 새로") 그대로,
> 구 `mockups/admin/login.html`을 옮기는 것이 아니라 새로 만드는 것이다. 구화면은
> 백업용 동결(수정·사용자 안내·화면 간 링크 금지, P-09 — 다른 admin2 재구축 화면과
> 동일 규칙).
>
> 작성일 2026-08-15. ④의 사실은 **그 시각의 코드·설정 실측**이다(`api/auth.py`·
> `api/admin_ui_common.py`·`api/admin_profile.py`·`mockups/admin/login.html`·
> `.env`(`ADMIN_BOOTSTRAP_EMAILS` 존재 여부만 확인, 값 자체는 이 문서에 옮기지
> 않았다) 직접 대조 — 읽기 전용, DB에 쓰지 않았다). 화면은 이 문서의 문구·숫자를
> 그대로 박지 않는다 — 서버 응답만 쓴다.
>
> ⚠ **이 화면은 인증 게이트 그 자체와 얽혀 있다** — §⑦ ㉮를 반드시 먼저 읽는다.

---

## ① 화면 성격

**관문(gate) 화면 — 이 화면을 통과하지 않으면 관리자 쪽 어떤 데이터도 볼 수 없다.**
로그인(인증)과 신규 직원의 **계정 사용 신청 접수**를 겸한다. 승인 자체는 이 화면의
소관이 아니다(③·④ 참조).

## ② 제목 · 화면 ID · 경로

| 항목 | 값 | 근거 |
|---|---|---|
| 화면 라벨 | 로그인 | 사장님 지시 원문("admin2 스타일로 새로") — 현재 화면 타이틀은 "직원 로그인" |
| 화면 ID | **ADM-SYS-021**(기존 식별자 재사용) | `mockups/admin/login.html`의 `data-screen-id`(실측 — 저장소 전체에서 이 ID를 쓰는 파일은 이 하나, 충돌 없음). ⚠ **`docs/decisions/admin-identity.md` 카탈로그에는 이 ID가 없다**(실측: "ADM-SYS-021" 전수 검색 결과 그 문서 안에는 0건 — 형제 화면 ADM-SYS-020(운영자·권한)·ADM-SYS-022(내 정보)는 등재돼 있다). 이 문서는 새 ID를 만들지 않지만, 카탈로그 등재는 이 문서 권한 밖이다(§사장님 결정 4) |
| 경로(신) | **/admin2/login**(제안) | 사장님 지시를 그대로 따른 제안 — 확정은 이 문서 권한 밖. ⚠ 이 경로가 게이트 대상이 되는 순환이 있다 — §⑦ ㉮ |
| 구화면 | `mockups/admin/login.html` | 백업용 동결. 참고만, 수정·안내·링크 금지(P-09) |
| LNB 위치 | **없음** | 인증 전 화면이라 메뉴 대상이 아니다(실측: `api/admin_nav.py` 전수 검색 "로그인" 0건) |

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

이 화면이 없으면 **아무도** 관리자 화면에 들어갈 수 없다 — `/api/admin/*`와
`/admin2/*` 전체가 인증 게이트 뒤에 있고(실측 `api/auth.py` `_is_gated()`), 게이트를
거치지 않고 열린 경로는 `/api/admin/auth/`(인증 자체) 하나뿐이다(`OPEN_PREFIXES`).

동시에 **신규 직원이 계정을 갖는 유일한 입구**다. 저장소 전체에서 `admin_operators`에
행을 넣는 코드는 셋뿐이다 — 개발 시드(`db/seed/seed.sql`, 최초 관리자 1건, 화면과
무관) · 점검 계정 CLI(`tools/ui_check_account.py`, 자동화 도구이지 화면이 아니다) ·
이 화면이 부르는 `api/auth.py`의 `login()`. **화면을 통해 계정을 만드는 경로는 이
하나뿐이다** — 이 화면이 없으면 신규 직원은 신청할 수단 자체가 없다.

## ④ 데이터

### 실측 방법

`api/auth.py`·`api/admin_ui_common.py`·`api/admin_profile.py`·
`mockups/admin/login.html`을 직접 대조. `.env`는 `ADMIN_BOOTSTRAP_EMAILS` 키의
**존재 여부만** grep(값은 옮기지 않음). 전부 읽기 전용, DB 미변경.

### 로그인 방식 — 넷 (지금 있는 것)

| 방식 | 트리거 | 비밀번호 | 비고 |
|---|---|---|---|
| 비밀번호 로그인 | 이메일+비밀번호 제출, 계정이 `활성`이고 `password_hash` 있음 | 필요 | 이 화면의 기본 경로 |
| 부트스트랩 자동승인 | 이메일이 `.env`의 `ADMIN_BOOTSTRAP_EMAILS`에 있고 계정이 아직 없을 때 첫 제출 | 불필요 | 신청 없이 즉시 `활성`·`owner`로 생성 + 세션 발급. **실측(2026-08-15): `.env`에 이 키 자체가 없다** — 코드는 없으면 빈 문자열로 취급해(`bootstrap_emails()`) 빈 집합과 동일하게 동작한다. **지금은 이 경로로 자동 승인되는 이메일이 없다** |
| 기기 기억(device-login) | `popcorn_admin_device` 쿠키(최대 30일, 슬라이딩) | 불필요 | **이 화면은 지금 이 엔드포인트(`POST /api/admin/auth/device-login`)를 한 번도 부르지 않는다**(실측: `mockups/admin/login.html` 전수 검색 "device-login" 0건). 또한 이 기능의 마이그레이션(`db/migrations/versions/0051_admin_operator_devices.py`)이 **파일만 있고 아직 DB에 적용되지 않았다**(실측: git 미커밋 — 같은 물결의 다른 정의서(`spec-spec-fill.md`)도 별도로 같은 사실을 확인함). 지금은 화면을 연결해도 서버가 `_schema_ready()`로 조용히 건너뛴다 |
| dev-login | `GET /api/admin/auth/dev-login` 직접 호출 | 불필요 | **화면의 로그인 수단이 아니다** — 자동화 점검 전용. `.env`의 `UI_CHECK_DEV_LOGIN=1` + localhost 요청만 + 점검 계정 활성, 셋이 함께 있어야 동작. 이 화면에 버튼·링크가 없다 |

### 세션 규칙 (실측 상수, `api/auth.py`)

| 규칙 | 값 | 상수명 |
|---|---|---|
| 절대 만료 | 8시간 | `ABSOLUTE_HOURS` |
| 유휴 만료 | 480분(8시간) | `IDLE_MINUTES`. **2026-08-15 사장님 지시로 30 → 480** — 코드 주석 "하루 일하다 퇴근하면 끝". 절대 만료와 사실상 같아져, 유휴 만료가 먼저 걸리는 경우가 거의 없어졌다 |
| 로그인 실패 제한 | 5회 | `MAX_FAILS`. 계정 단위 잠금(같은 IP의 다른 사람 작업은 막지 않는다) |
| 잠금 시간 | 15분 | `LOCK_MINUTES` |
| 기기 기억 기간 | 30일(슬라이딩 — 쓸 때마다 연장) | `REMEMBER_DEVICE_DAYS`. 위 표대로 지금은 미적용 |

확인법: `grep -n "ABSOLUTE_HOURS\|IDLE_MINUTES\|MAX_FAILS\|LOCK_MINUTES\|REMEMBER_DEVICE_DAYS =" api/auth.py`(상수 선언부가 한 화면에 보인다).

### 기기 기억이 요구하는 화면 요소

체크박스 하나 — `remember_device`(`LoginBody` 필드, 기본값 `false`). 서버는
**비밀번호를 실제로 확인한 로그인에서만** 등록한다(`_remember_device()`는 `login()`의
비밀번호 검증 성공 분기에서만 호출된다 — device-login·부트스트랩·dev-login 경로에서는
호출되지 않는다, 실측 코드). 즉 이 체크박스는 **"비밀번호 로그인" 제출에만** 의미가
있다 — 계정 신청 제출, 부트스트랩 자동승인에는 적용되지 않는다.

⚠ 위 표에서 밝힌 대로 **지금 이 체크박스를 켜도 실제로 아무것도 등록되지 않는다**
(마이그레이션 미적용). 노출 여부·시점은 설계 소관(§사장님 결정 5).

### password_not_set — 비밀번호 미설정 계정이 막히는 경로

활성 계정인데 `password_hash`가 비어 있으면 로그인 자체가 **403**
`{"error":"password_not_set","message":"비밀번호가 아직 설정되지 않았습니다 —
관리자에게 발급을 요청하세요"}`로 막힌다(실측 `login()`). **이 화면은 발급 수단을
갖지 않는다** — 발급은 owner가 「운영자·권한」 화면에서
`POST /api/admin/auth/operators/{id}/password`로 임시 비밀번호를 내려줘야 한다
(`req-operators-roles.md` ④ 대조). 이 화면이 할 수 있는 일은 이유를 그대로 보여주는
것까지다.

### 계정 신청 → owner 승인 흐름이 이 화면에 있는가

**신청 접수는 이 화면에 있다.** 이메일이 `admin_operators`에 없으면 같은
`POST /api/admin/auth/login` 제출이 `status='대기'` 행을 만든다 — 이름·연락처·담당
업무가 승인 판단 자료로 함께 저장된다(실측: 현재 화면의 `name`·`phone`·`duty`
입력칸이 그대로 요청 본문에 실린다). **승인은 이 화면에 없다** — 승인·등급 부여는
「운영자·권한」(ADM-SYS-020, `/admin2/operators`)의
`POST /api/admin/operators/{id}/approve` 소관이다(`req-operators-roles.md` ④ 대조).
이미 대기 중인 이메일로 다시 제출하면 새 신청을 만들지 않고 같은 "승인 대기
중입니다 — 관리자에게 승인을 요청하세요" 문구를 돌려준다(실측 `login()`의
`status=='대기'` 분기).

### 이 화면이 걸쳐 있는 다른 연결점

무세션으로 `/admin2/*`를 열면 게이트가 안내 페이지를 보여주고 1초 뒤 이동시키는데,
그 목적지는 지금 **`_LOGIN_PAGE = "/admin/login.html"`**(구화면)로 고정돼 있다(실측
`api/admin_ui_common.py`). 이 화면이 `/admin2/login`으로 서더라도, **이 상수가 함께
옮겨지지 않으면 게이트에 걸린 사람은 계속 구화면으로 안내된다** — 새 화면은 주소를
직접 아는 사람만 쓰게 된다. 이 문서는 요구사항까지만 다루므로 상수를 바꾸라고
지시하지 않지만, 이 화면이 실제로 쓰이려면 이 연결점이 있다는 사실은 밝혀 둔다
(§사장님 결정 6).

## ⑤ 기능 — 동사

- 회사 이메일과 비밀번호로 로그인한다.
- 계정이 없는 이메일이면 이름 · 연락처 · 담당 업무를 함께 제출해 계정 사용을
  신청한다.
- "이 기기에서 로그인 유지"를 선택해 다음 방문의 비밀번호 입력을 생략한다(§④ 제약
  참조).
- 이미 로그인된 상태로 이 화면에 들어오면 그 사실을 확인하고 이동한다.
- 임시 비밀번호로 로그인했을 때 비밀번호를 아직 바꾸지 않았다는 사실을 안다.
- 로그인이 안 되는 이유(형식 오류 · 자격 불일치 · 잠금 · 승인 대기 · 정지 · 비밀번호
  미설정)를 구분해서 안다.

## ⑥ 인터랙션 — 입력 · 선택 · 저장 · 이동의 흐름과 결과

- 제출 → 성공(`state:"active"`) → 서버가 준 안내문 노출 → 대시보드로 이동. 실측(현재
  화면): 0.9초 뒤 이동. `must_change_password`가 true여도 **화면이 비밀번호 교체를
  강제하지 않고 그대로 이동한다**(1.6초 뒤, 안내 문구만 다르게) — 있는 그대로의 동작
  기록이지 권고가 아니다.
- 제출 → 신청 접수(`state:"pending"`) → 승인 대기 안내(서버 message 그대로) → 화면에
  남는다(이동하지 않는다).
- 제출 → 실패 → 서버가 준 문구를 그대로 보여준다(화면이 다시 쓰지 않는다) — 계정
  존재 여부를 감추는 문구도 서버가 정한다(`bad_credentials`는 이메일·비밀번호 중
  어느 쪽이 틀렸는지 밝히지 않는다, 실측).
- "구글/카카오 계정으로 계속"은 지금 실제 OAuth를 타지 않는다 — 이메일 칸이 채워져
  있으면 같은 `POST /login`을 `provider` 값만 바꿔 보낸다(dev 어댑터, 실측
  `social()`). 이메일이 비어 있으면 그 사실을 안내하고 제출하지 않는다.
- 로드 시 `GET /api/admin/auth/me`로 이미 로그인 상태인지 먼저 확인한다(실측). **기기
  기억 쿠키로 자동 재로그인을 시도하는 절차는 없다**(§④ 참조, `/device-login`
  미호출).

## ⑦ 상태 · 예외

### ㉮ 경로 순환 — 게이트 대상이면서 게이트 뒤 화면 (실측 · 사장님 결정 있음)

`_is_gated(path)`는 `path.startswith("/api/admin/")`이거나 `_is_admin2_path(path)`이면
참이다(`api/auth.py`). `_is_admin2_path`는 `/admin2` 전체를 게이트 대상으로 본다 —
그 안에서 게이트를 **면제**하는 화이트리스트는 지금 **0건**이다(실측:
`ADMIN2_JSON_DATA_PATHS`는 `/admin2/handoff-log/data` 하나뿐이고, 이것도 "거절
형식만 JSON으로 하는" 예외일 뿐 게이트 자체는 그대로 받는다 — 로그인 화면에 필요한
것과는 다른 종류의 예외다).

**그래서 이 화면을 그대로 `/admin2/login`으로 옮기면 그 경로 자체가 게이트 대상이
되어, 무세션 요청은 로그인 화면 대신 401을 받는다** — 로그인하려는 사람이 로그인
화면에 못 들어가는 순환이다.

→ **사장님 결정(2026-08-15): 게이트에 예외를 둔다.** `/admin2/login`으로 옮기되 그
경로만 게이트에서 빼는 예외를 신설한다.

⚠ **이 결정에는 조건이 붙는다 — 인증 게이트 자체를 건드리는 변경이라 검증을 강하게
해야 한다.** 이 문서는 요구사항까지만 다루므로 예외를 "어떻게" 구현할지는 정하지
않지만, 확인해야 할 것은 밝혀 둔다: 이 예외가 **로그인 경로 하나만** 열고 다른
`/admin2/*` 화면까지 함께 여는 실수가 없는지(2026-08-15 이 저장소에서 정확히 반대
방향의 사고가 났다 — 서버 렌더 화면 3종이 자체 게이트 없이 실데이터를 흘렸다,
`api/auth.py` 커밋 `7ccb68d` 참조. 이번은 그 반대 — 예외 범위가 넓으면 다른 화면이
무세션으로 열린다).

### ㉰ 셸 상속과의 긴장 (사실만 — 풀이는 설계 소관)

admin2 화면은 예외 없이 `templates/admin/_admin2_shell.html.j2`를 상속한다(실측:
`templates/admin/*.html.j2`(38개, `_admin2_shell.html.j2` 자신과 폐기된
`_layout.html.j2` 제외) 중 다른 것을 상속하는 화면 0건 — 아래 확인법). 셸은
**로그인한 운영자**를 전제로 사이드바 메뉴·권한 표시·상단바를 그린다.

로그인 화면은 정의상 **무세션 상태에서 열리는 화면**이다(§③) — 그릴 "로그인한
운영자"가 없다. 셸을 그대로 상속하면 없는 정보를 그리려 하고, 상속하지 않으면
"예외 없이 상속한다"는 지금까지의 관행이 깨진다. **이 문서는 이 긴장을 사실로만
남긴다 — 상속할지, 최소 셸을 따로 둘지, 완전히 독립된 화면으로 둘지는 설계(사장님)
소관이다**(§사장님 결정 1).

확인법: `grep -rL '{% extends "admin/_admin2_shell.html.j2"' templates/admin/*.html.j2`
— 결과에서 `_admin2_shell.html.j2` 자신과 `_layout.html.j2`(더 이상 아무도 상속하지
않는 폐기 파일, 파일 상단 주석 참조)를 빼면 나머지는 0건이어야 한다.

## 비범위 — 이 화면이 하지 않는 일

- **계정 승인 · 등급 부여** — 「운영자·권한」(ADM-SYS-020, `/admin2/operators`) 소관.
- **임시 비밀번호 최초 발급** — 같은 화면 소관(owner가 누른다). 이 화면은 발급받은
  비밀번호로 로그인하는 쪽일 뿐이다.
- **본인 비밀번호 변경** — 「내 정보」(ADM-SYS-022, `POST /api/admin/auth/password`)
  소관.
- **기기 기억 목록 조회 · 개별 기기 잊기** — 「내 정보」
  (`GET/POST /api/admin/my-profile/devices...`) 소관. 이 화면은 등록(체크박스)까지만
  한다.
- **실 OAuth 검증 자체** — `_verify_google()`은 백엔드 훅이고 비어 있다. 이 화면은
  "지금은 검증되지 않는다"는 사실을 보여줄 뿐 검증을 구현하지 않는다.

## 사장님 결정이 필요한 지점

1. **㉰ 셸 상속을 어떻게 풀지** — 상속 / 예외 / 최소 셸 신설 중 무엇을 택할지. 이
   화면의 UI 설계 단계에서 가장 먼저 부딪히는 질문이다.
2. **로그인과 계정 신청을 한 화면에서 계속 겸할지** — 지금은 같은 폼(이메일·
   비밀번호 + 이름·연락처·담당업무)이 두 가지를 겸한다(§④). 유지·분리는 설계
   판단이다.
3. **㉯ 세 문구를 무엇으로 고칠지** — "고쳐야 한다"는 확정됐다(사실이 아니므로).
   새 문장은 승인 디자인 단계에서 정해진다.
4. **화면 ID `ADM-SYS-021`을 `admin-identity.md` 카탈로그에 정식 등재할지** — 지금은
   화면 파일에만 있고 카탈로그에는 없다(§② 참조). 이 문서 권한 밖 — 기록자 후속
   확인 대상.
5. **기기 기억 체크박스를 지금 노출할지** — 노출해도 마이그레이션 미적용 상태라
   당장은 조용히 아무 효과가 없다(§④). 마이그레이션 적용 이후로 미룰지, 지금부터
   노출해 둘지.
6. **게이트 예외 신설 후 `_LOGIN_PAGE` 상수를 함께 옮길지** — 옮기지 않으면 무세션
   접근자는 계속 구화면으로 안내된다(§④ "이 화면이 걸쳐 있는 다른 연결점").
