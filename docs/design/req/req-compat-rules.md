# 요구사항 정의서 — 조립 호환 규칙 (admin2 신규 구축)

> 이 문서는 **요구사항만** 담는다. 배치·컴포넌트·와이어프레임·색은 담지 않는다
> (`CLAUDE.md` §화면 작업의 경계, 2026-08-13 사장님 지시). UI 설계는 이 문서를
> 입력으로 결정권자(또는 지정 경로)가 별도로 한다.
>
> 대상은 admin2 신규 구축이다. 기존 `mockups/admin/compat-rules.html`(ADM-ENG-010)은
> 백업용 동결 — 참고만 하고 옮기지 않는다(P-09).
>
> 작성일 2026-08-13. ④의 수치는 그 시각의 실측 스냅샷이다. 재측정은
> `SELECT * FROM compat_rules ORDER BY sort_order`를 다시 돌리면 된다.

---

## ① 화면 성격

**조회 화면이다 — 지금은 쓰기 기능이 없다(아래 ④ "쓰기 경로 실측" 참조).** "조립이
가능한 조합인지"를 매 견적마다 실제로 판정하는 규칙 9종의 근거를 사람이 읽을 수 있게
보여주는 자리다. 값을 바꾸는 화면이 아니라, **지금 엔진이 정확히 무엇을 기준으로
거르고 있는지**를 감사·설명하는 자리다("모든 견적에는 이유가 있습니다"의 근거 문서화).

- 열람은 로그인만 되면 등급 무관(viewer 이상).
- 규칙 값을 고치는 동작은 **현재 어떤 등급에도 열려 있지 않다** — API 자체가 없다.

## ③ 정의 — 이 화면이 없으면 무엇이 안 되는가

- **"왜 이 조합이 견적에 못 들어갔는지"를 사람이 확인할 자리가 없다.** 호환 판정은
  `compat_rules` 테이블 9행이 전부다(엔진의 단일 원천, 슬라이스 34). 이 화면 없이는
  운영자가 이 표를 SQL로 직접 봐야 한다.
- **NULL 값의 취급 원칙이 눈에 보이지 않는다.** 이 엔진의 가장 중요한 계약은 "값을
  모르는 부품은 호환으로 판정하지 않는다"(불통과 우선, 신뢰 판매자 원칙)인데, 이건
  코드에만 있고 화면이 없으면 아무도 확인할 길이 없다.
- **규칙 하나가 실제로 어떤 사양 필드를 잡아먹는지 추적할 수 없다.** 예를 들어
  `cooler_height`(공랭 전용) 규칙은 `part_types=["COOLER_CPU_AIR"]`로 좁혀져 있어
  수랭 쿨러에는 적용되지 않는다 — 이런 "부품 종류 한정" 사실이 눈에 안 보이면, 어떤
  쿨러가 왜 후보에서 빠졌는지 설명할 수 없다.

## 엔진 계약 — 이 화면이 반영해야 하는 사실(CLAUDE.md 근거)

**호환 규칙에 새 필드를 쓰면, 그 필드를 싣는 곳을 전부 늘려야 한다.** 규칙 하나가
참조하는 사양 필드(`field`·`ref_field`)는 최소 **세 곳**에 동시에 존재해야 판정이
성립한다(하나라도 빠지면 500이 아니라 **조용히 결과가 0건**이 된다 — 가장 위험한
실패 양상):

1. `product_specs` 실제 컬럼 (「상품 사양 정의」 화면 소관)
2. `recommend._load_pool()`의 SELECT 목록 — 견적 엔진이 풀을 불러올 때 이 필드가
   빠지면 규칙이 그 값을 아예 못 본다. 실측 예: 슬라이스 39에서 `socket_list`를
   빼먹어 KeyError로 견적이 500이 된 전례가 코드 주석에 그대로 남아 있다.
3. `swap.SPEC_COLS`(부품 교체 대안 탐색이 읽는 컬럼 문자열, 실측 16개 필드:
   `socket, socket_list, mem_type, tdp_watt, rated_watt, required_power_watt,
   length_mm, gpu_max_mm, cooler_height_mm, cooler_tdp, radiator_rows,
   radiator_max_rows, form_factor, form_factor_list, tag_white, tag_silent`) —
   여기 빠지면 스왑 대안 추천이 그 필드를 무시한다.

**규칙 로딩 자체의 안전장치(코드에 이미 있음, 화면이 알아야 하는 사실)**:
① `ref_slot`은 슬롯 탐색 순서(CPU→MB→RAM→GPU→CASE→COOLER→POWER→SSD)에서
`slot`보다 **앞이어야** 하고, 이를 어긴 규칙은 로드 시 건너뛰며 경고만 낸다(엔진을
죽이지 않기 위해) ② `active=false` 규칙은 아예 로드되지 않는다 ③ 규칙이 바뀌면
견적 결과가 바뀌므로 회귀 검증 대상이다.

## ④ 데이터

### 실측 방법

`SELECT * FROM compat_rules`(9행, 읽기 전용) + `GET /api/admin/engine-rules`의
`compat` 응답부 코드(`api/admin_engine_rules.py`) 대조. 2026-08-13 스냅샷.

### 쓰는 테이블

| 테이블 | 역할 |
|---|---|
| `compat_rules` | 규칙 본체. `rule_id`·`rule_key`(UNIQUE)·`slot`·`field`·`op`(eq/gte/lte/contains)·`ref_slot`·`ref_field`·`label`·`detail_fmt`·`blocking`·`active`·`sort_order`·`updated_at`·`part_types`(JSONB, 빈 배열=슬롯 전체 적용) — 14컬럼 |

### 쓰는 API — **읽기만 있다(실측)**

| 엔드포인트 | 역할 | 권한 |
|---|---|---|
| `GET /api/admin/engine-rules` | `compat`(규칙 9종+필수 사양 매트릭스)·`tiers`·`budget`·`pricing`·`weights`를 한 응답에 묶어 반환 | viewer 이상 |

**규칙 값을 쓰는(POST/PUT/DELETE) 엔드포인트가 코드베이스 어디에도 없다**(2026-08-13
전수 검색 확인 — `compat_rules`에 대한 INSERT/UPDATE/DELETE 구문이 API 계층에 0건).
`engine-rules` 라우터에 있는 유일한 쓰기(`POST /pricing-settings`)는 **다른
화면(판매가)의 마진 정책 저장**이며 규칙 9종과는 무관하다. 즉 지금 이 화면이 요구할 수
있는 것은 **정확히 조회뿐**이다 — "규칙을 고친다"는 동사를 이 문서 ⑤에 넣으려면
백엔드 작업이 먼저 필요하다(아래 결정 필요 지점 참조).

### 실측 값 (2026-08-13)

**9행 전부 `active=true`·`blocking=true`**(경고 전용 규칙은 아직 하나도 없다).

| rule_key | 대상(slot.field) | 연산 | 비교 대상(ref_slot.ref_field) | 부품 한정 |
|---|---|---|---|---|
| socket | MB.socket | = | CPU.socket | 전체 |
| mem | RAM.mem_type | = | MB.mem_type | 전체 |
| gpu_len | CASE.gpu_max_mm | ≥ | GPU.length_mm | 전체 |
| case_board | CASE.form_factor_list | 포함 | MB.form_factor | 전체 |
| cooler_socket | COOLER.socket_list | 포함 | CPU.socket | 전체 |
| cooler_tdp | COOLER.cooler_tdp | ≥ | CPU.tdp_watt | 전체 |
| cooler_height | COOLER.cooler_height_mm | ≤ | CASE.cooler_height_mm | **COOLER_CPU_AIR만** |
| radiator | COOLER.radiator_rows | ≤ | CASE.radiator_max_rows | **COOLER_CPU_AIO만** |
| power | POWER.rated_watt | ≥ | GPU.required_power_watt | 전체 |

이 9종이 "호환성 5종"·"8종" 같은 문서상의 옛 숫자와 다를 수 있다 — CLAUDE.md가 명시한
전례대로(문서에 8종이라 적힌 채 실제로 늘어 있었던 사고, 2026-07-30) **이 화면은 항상
`compat_rules`를 직접 세어서 보여줘야 하고, 이 문서의 "9"라는 숫자를 화면에 박으면 안
된다.**

## ⑤ 기능 (동사) — 지금 API가 실제로 지원하는 것 기준

- 활성 규칙 9종을 전부 본다 — 어느 슬롯(부품)이 어느 슬롯을 참조해 무엇을 비교하는지
  (`슬롯.필드 연산 참조슬롯.참조필드` 형태의 사람이 읽을 수 있는 문장으로).
- 규칙이 **어느 부품 종류에만 적용되는지**(빈 값=전체, 값 있으면 한정)를 본다 —
  `cooler_height`·`radiator`처럼 공랭/수랭으로 갈리는 규칙이 실제로 어느 한쪽에만
  걸리는지 확인하기 위함이다.
- 부품 종류별 **필수 사양 매트릭스**를 함께 본다(10개 조립 부품 × 각 필수 필드) —
  이 데이터는 `spec_field_defs`가 원천이며, 이 화면은 "상품 사양 정의" 화면과
  **같은 계산 함수**(`spec_fields.required_map()`, `spec_fields.rule_readers()`)를
  써서 두 화면이 서로 다른 답을 하지 않게 한다.
- "값을 모르면 불통과"라는 NULL 처리 원칙을 근거 문구로 함께 읽는다.
- 활성 규칙 수가 지금 추천 후보 풀(재고>0)에 몇 건이 얹혀 있는지 함께 본다(`pool_size`).

## ⑥ 인터랙션

- 화면을 열면 규칙 9종 + 필수 사양 매트릭스가 한 번에 온다(현재 API가 한 응답에
  묶어 준다) — 별도 조작 없이 진입 즉시 전체를 본다.
- **지금은 편집·토글·저장에 해당하는 상호작용이 없다** — 이 화면에서 "고친다"는
  인터랙션을 요구하면 그 즉시 백엔드에 새 API가 필요하다는 뜻이 되므로, 이 문서가
  임의로 그 인터랙션을 만들어 넣지 않는다(아래 결정 필요 지점 1번).
- 각 규칙이 참조하는 사양 필드를 클릭(또는 이동)하면 「상품 사양 정의」 화면의 해당
  필드로 갈 수 있어야 한다 — 두 화면이 같은 사실(`used_by`)을 다루므로 오가는 길이
  있어야 "이 필드를 지우면 이 규칙이 죽는다"를 실제로 확인할 수 있다.

## ⑦ 상태 · 예외

- **빈 상태**: 이론상 발생하지 않는다 — `alembic upgrade head` 부트스트랩이 8종 이상을
  항상 심는다(`docs/07_운영-시작-순서.md`). 다만 CLAUDE.md는 **"호환 규칙이 비면 엔진은
  실패하지 않고 조용히 전부 통과시킨다"**(규칙 없는 슬롯 = 독립)는 사실을 명시한다 —
  0건이 되는 것은 "화면 오류"가 아니라 "그 순간부터 조립 불가 조합이 정상 견적으로
  나간다"는 뜻의 훨씬 심각한 사고다. 화면은 0건일 때 이 위험성을 그대로 경고해야 한다
  (단순히 "규칙 없음" 빈 리스트로 조용히 넘기면 안 된다).
- **서버 실패**: `GET /api/admin/engine-rules` 실패 시 원인 없이 침묵하지 않는다.
- **권한**: 미로그인 401. 열람 자체는 등급 무관 — 처리 권한을 확인하는 절차는 없다
  (쓰기 기능이 없으므로).
- **규칙 로드 스킵**: `ref_slot`이 탐색 순서상 `slot`보다 뒤인 잘못된 규칙은 엔진이
  조용히 건너뛴다(경고 로그만). 이 화면이 그런 규칙을 감지해 표시할지는 결정 필요
  지점(아래 3번) — 지금 API 응답은 이 구분을 제공하지 않는다(실측: `engine-rules`가
  돌려주는 건 `compat_rules` 원본 그대로이지 "로드 성공 여부"가 아니다).

## 비범위 — 이 화면이 하지 않는 일

- **규칙 값 자체의 수정·활성/비활성 토글·신설·삭제** — 위 ④에서 실측했듯 쓰기 API가
  없다. 옛 카탈로그(`docs/decisions/admin-identity.md`)가 그렸던 "규칙 R-01~06
  토글+파라미터(여유율%)"는 **지금 구현과 다르다** — 실제 규칙은 R-01~06이 아니라
  9종의 (슬롯,필드,연산,참조) 튜플이고 "여유율%" 같은 파라미터 개념 자체가 없다(op은
  eq/gte/lte/contains 넷뿐). 옛 문서 기준으로 요구사항을 쓰면 존재하지 않는 기능을
  요구하게 된다.
- **필수 사양 자체를 고치는 일** — 「상품 사양 정의」(ADM-PRD-050) 화면 소관. 이 화면은
  결과(어느 부품에 뭐가 필수인지)만 보여준다.
- **"조립 호환 지도"(`/admin2/build-map`, `std.compat_pairs`)** — 이미 구축된 다른
  화면이고 다른 저장소(28쌍, 사람이 읽는 관계표)를 쓴다. 엔진이 실제로 판정에 쓰는
  것은 이 화면의 `compat_rules` 9종이지 `std.compat_pairs`가 아니다.
- **가격·재고 관련 정보** — 이 화면은 호환 판정 규칙만 다룬다.

## 사장님 결정이 필요한 지점

1. **이 화면에 "규칙을 실제로 고치는" 기능을 새로 요구할지, 지금처럼 조회 전용으로
   둘지.** 옛 카탈로그(admin-identity.md)는 "규칙 토글+파라미터, 버전 발행 시
   추천 가능 재고 재계산 경고"까지 그렸지만, 지금 백엔드는 조회 API 하나뿐이다.
   편집을 요구하면 이 문서 이후 별도의 백엔드 작업(정책 버전 관리 포함)이 필요하다.
2. **규칙 변경(만약 열린다면)에 "버전 발행" 개념을 넣을지.** `pricing_settings`는 이미
   이력 테이블(effective_from)로 버전 관리가 되는데, `compat_rules`는 현재 단일 행
   갱신 구조(UPDATE면 이전 값이 사라짐)다. 과거 견적을 "그때 규칙 기준으로" 재현하려면
   여기도 이력화가 필요한지 판단이 필요하다.
3. **로드 시 건너뛰어진(순서 위반) 규칙이 있는지를 이 화면이 능동적으로 검사해 보여줄지.**
   지금 API는 이 정보를 주지 않는다(원본 그대로만 반환) — 추가하려면 백엔드가 로드
   로직의 결과(스킵 여부)를 별도로 노출해야 한다.
