## 두 안이 가른 축

**「빨리 훑어 처리한다」 vs 「한 건을 판단하고 처리한다」.** 대기 15,725건이라는 규모와, 입고해도 후보에 못 들어가는 상품이 2,640건(15,725 − 13,085)이라는 사실이 서로 다른 방향을 가리킨다.

| | 1a 표 안 확정 | 1b 목록 + 작업 패널 |
|---|---|---|
| 처리 단위 | 행 안에서 수량·사유·확정 | 왼쪽에서 고르고 오른쪽에서 확정 |
| 판단 근거 | 행 한 줄의 「후보 진입 판정 + 사유」 | **3중 게이트(검수·가격·사양·재고)를 펼쳐 보여준다** |
| 되돌리기 | 하단 「이력 열기」 | **작업 패널 안, 그 상품의 원장 바로 아래** |
| 강한 쪽 | 15,725건을 훑는 속도 · 여러 건 연속 처리 | 「입고하면 추천에 들어가는가」에 정면으로 답한다 · 되돌릴 건을 문맥과 함께 고른다 |
| 약한 쪽 | 후보 미진입 사유가 한 줄에 갇힌다 | 한 건씩 — 대량 처리에 느리다 |

**추천: 1a를 기본, 1b의 작업 패널을 행 확장으로 얹는다.** 두 안은 배타적이지 않다 — 1a의 행을 펼치면 1b의 오른쪽이 그대로 들어간다. 다만 지금 결정할 것은 **어느 쪽이 기본값인가**이고, 모집단이 15,725건이므로 1a가 기본이어야 한다고 본다. 1b만 택하면 「검수·가격이 다 된 13,085건을 골라 연속 입고」하는 작업이 클릭 수에 눌린다.

## 구 화면 결함 9가지를 고친 자리

화면 하단 표에 옛 동작과 새 동작을 나란히 실었다. 핵심은 **결함 1·2·4의 공통점** — 운영자는 「저장됐다」고 믿는데 서버는 모른다. 두 안 모두:

- **서버에 닿지 않은 입력은 「아직 저장되지 않았습니다」로 못 박는다** — 성공 문구를 내지 않는다.
- **「수량 수정」을 별도 동작으로 두지 않는다** — 수량은 저장값이 아니라 이번 입고의 입력값이므로 확정과 함께 한 번만 전송한다.
- **건수는 서버 `total` 기준** — 「전체 15,725건 중 1–50」. 페이지 안에서 세지 않는다.
- **「오늘 입고」는 표시하지 않는다** — 서버 집계가 없다. 구 화면은 이 자리에 브라우저 세션 카운터를 넣었다(지어낸 수). 자리만 남기고 이유를 적었다.
- **되돌리기는 서버 이력에서** 고른다 — 새로고침해도 되고 과거 회차도 된다(서버 API가 이미 받는다). 브라우저 변수에 의존하지 않는다.
- **「매입 확정분」 라벨을 쓰지 않는다** — 지금 값은 `stock_qty==0` 파생일 뿐 `product_sourcing_quotes`를 조회하지 않는다. 재고 유형을 그대로 부른다.
- **일괄 선택 없음** — 규약. 체크박스도 두지 않았다(붙이면 아무 일도 못 하는 단추가 된다).
- **매입가 입력칸 없음** — 원장에 단가 컬럼이 없다. 구 화면에는 그 칸이 있었다.

## 신설이 필요한 서버 것 둘

1. **입고 이력 조회 API** — 지금 없다. 원천은 `admin_operator_activity_logs`(`action='stock_inbound'`·`'stock_inbound_undo'`·`kind='stock'`), 되돌림 표시는 `detail->>'ref_log_id'`로 파생한다(되돌림 API가 그 키로 이중 되돌림을 막으므로 같은 키를 쓴다). **이것 없이는 결함 8을 고칠 수 없다** — 두 안 모두 이 API를 전제한다.
2. **「오늘 입고」 집계** — 🟦 결정 대기. 없는 동안은 표시하지 않는다.

## 결정 대기 — 트윅으로 그 자리에서 갈아 볼 수 있다

- **🟥 보류를 남길 것인가** — `holdPolicy` 트윅. ㉠ 없앤다(추가 개발 0) / ㉡ 서버 상태(**마이그레이션 + ERD 개정이 화면보다 먼저**) / ㉢ 조회 조건으로만(조회줄에 조건 하나 늘어난다). 기본값은 ㉠. **㉡을 택하면 이 화면은 스키마 뒤에 선다.**
- **🟥 안전재고 기준을 누가 정하는가** — `safetyStock` 트윅. 지금 `safety_stock`은 **쓰기 경로가 저장소에 0건**이고 값이 30건뿐이다. ㉠을 택하면 안전재고 열이 편집 가능해지고 **쓰기 경로 신설이 필요하다**. ⚠ **기준을 전 상품에 걸면 대기 목록 규모가 바뀐다**(현재 미달 2건) — 화면이 다룰 모집단이 달라지므로 화면 확정 전에 답이 필요하다.
- **🟧 「매입 확정분」을 매입 견적과 실제로 연결할 것인가** — 지금 두 안 모두 ㉡(라벨을 사실대로)로 그렸다. 연결한다면 `product_sourcing_quotes` 상태 `확정` 5건을 조회하는데, **확정 5건의 `confirmed_at`이 전부 NULL**이라 확정 시각은 아직 못 쓴다.
- **🟧 입고 이력에 다른 경로의 재고 변동을 섞을 것인가** — 두 안 모두 ㉠(이 화면 것만)으로 그렸고, 이력 하단에 「전체 원장은 상품 상세·작업 기록에서」라고 밝혔다. ㉢(기본 이 화면 것 + 전체 원장 조건)으로 가면 이력 헤더에 조건 하나가 붙는다.
- **🟦 입고 수량 상한** — 지금 서버는 `qty <= 0`만 막는다. 두 안 모두 ㉠(상한 없음 + 확정 전 되읽기)로 그렸다.

## 화면이 계속 말해야 하는 것

- **입고 확정 즉시 견적에 반영된다** — `stock_qty > 0`이 되어 추천 후보 게이트를 통과한다. **되돌릴 수 있지만 그 사이 나간 견적은 그 재고로 나갔다.** 되돌리기는 「없던 일로 만드는 것」이 아니다.
- **인계는 재고를 차감하지 않는다** — 견적이 나가도 재고는 그대로다. 재고를 줄이는 경로는 자체 주문과 실사 조정뿐이다.
- **입고만으로 추천에 들어가지 않는다** — 사양 행 유무는 별개 게이트다. `pool_entered`를 실측으로 보여주는 이유다.
- **매입가 「미등록」 3,919건 · 공급처 4건** — 값을 지어내지 않고 빈 칸을 견디는 표시로 뒀다.
- **viewer는 단추를 감추지 않고 비활성 + 사유 병기** — 조회 viewer · 쓰기 operator(owner 전용이 아니다).

## 정의서가 밝힌 문서 오류 둘 — 화면은 사실 쪽을 따랐다

- `api/admin_nav.py:254` 「재고 원장은 쇼핑몰이 갖는다」 — **사실과 다르다**(우리 DB에 9,326행, 지금도 기록된다). 화면은 원장을 우리 것으로 다룬다. 주석 정정은 nav 정본 소관.
- `api/admin_stock.py:1-13` docstring 「안전재고 기준 컬럼이 없어 제외」 — **사실과 다르다**(같은 파일 코드가 그 컬럼을 쓴다). 화면은 **안전재고 미달을 실판정 유형으로** 다룬다.
