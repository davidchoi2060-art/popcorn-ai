# ★ 추천 후보 진입 판정 — 3중 게이트 + 재고

우 패널에 칩 넷이 선다. **서버가 `v_recommendation_candidates` 를 실조회한다 — 화면이 판정하지 않는다.**

    검수      통과 / 미통과
    판매가    산정 완료 / 미산정
    사양 행   `product_specs` 행 있음 / 없음
    재고      확정하면 0 -> N

**왜 필요한가**: 대기 15,725건 중 검수·가격 둘 다 완료는 13,085건이고(**2026-08-17 실측 — 아래 §실측값. 지금 값이 아니다**) 사양 행 유무는 별개 게이트다 — **입고만으로 추천에 들어가지 않는다.** 그래서 `pool_entered` 를 실측으로 보여준다.

목록 행에도 「입고 후 · 후보 진입 판정」을 함께 보여준다(1a 에서 가져온 열) — 판정 + 사유 한 줄.

> ⚠ **「화면이 판정하지 않는다」는 이 계약이 실제로 깨져 있었다** (2026-08-18 제작자 실측 ·
> `decision-log` **A-68 부기**). 목록 행 판정을 화면이 `reviewed && priced && has_specs`
> 셋으로 조합했고, 뷰가 함께 거르는 나머지(`ai_candidate_yn`·`category_group`·`part_type`·
> `data_origin`·`status`)를 못 봐서 **그때 실측 3,876행을 「후보 진입 가능」이라 잘못 말했다.**
> 지금은 서버가 뷰를 실조회한다(`_pool_of()` — 상태 넷 `in`/`enters`/`out`/`unknown`).
> **품절 행은 예측하지 않는다** — 뷰가 거르는 `status='판매중'` 을 입고 확정이 바로 바꾸므로
> 그 false 로는 나머지 게이트를 알 수 없다(`unknown` · 「입고 확정 후 판정」).
> ⚠ **라벨과 사유는 «같은 판정»에서 나온다** — 판정만 뷰로 옮기고 사유를 옛 원천에 두면
> 한 행 안에서 「추천 후보 제외」와 「입고 시 추천 가능 재고 진입」이 **동시에** 뜬다.
> 같은 날 실제로 그렇게 떴다(확인자 재검증 · `rowHtml()` 의 `it.note || it.pool_note` 단락평가로
> **`pool_note` 가 대기 목록에서 한 번도 안 쓰였다**). 수정 방향은 **`pool_state` 와 같은
> 원천으로 사유를 맞춘다**로 확정 — 경과·재상신 조건은 `decision-log` **A-68 부기 §후속 결함**.
> 확인법: `grep -n "verdictOf" templates/admin/stock_inbound.html.j2`(**0건**이어야 한다) ·
> 목록을 브라우저로 열어 **한 행의 라벨과 사유가 반대말을 하지 않는지** 본다.

# 서버 응답 — 사유를 갈라 말한다

> **2026-08-18 개정 — 제목에서 수를 뺐고 「보류 중」 행을 더했다.**
> 이 표는 「서버 응답 12가지」였는데 그 사이 **보류가 ㉡ 서버 상태로 확정**(A-58)되면서
> 확정 경로에 409 가 하나 늘었다. **코드가 맞고 표가 낡았다** — 표에 상태가 늘 때마다
> 제목이 틀리므로 **수를 부르지 않는다**(§회귀 세트 「건수를 문서에 박지 않는다」와 같은 처방).
> 지금 몇 가지인지는 **표를 세면 안다.**
> 확인법: `api/admin_stock.py` 의 `inbound()` 안에서 `stock_inbound_holds` 를 조회해
> 409 를 던지는 자리를 보면 된다(문구는 그 줄이 원천이다).

**화면이 재고를 다시 계산하지 않는다.** `stock_before` · `stock_after` · `status_changed` · `pool_entered` · `undo_id` · `sku` 를 **그대로** 표시한다.

| 상태 | 코드 | 문구 | 되돌리기 |
|---|---|---|---|
| 응답 없음 | — | 확정하면 여기에 서버 응답이 그대로 섭니다 | 없음 |
| 성공 · 후보 진입 | 200 | 입고 완료 — 재고 0 → N · 품절 해제 · 추천 후보 진입 | 있음 |
| 성공 · 후보 미진입 | 200 `pool_entered=false` | 입고 완료 — 다만 추천 후보에는 들어가지 않았습니다 | 있음 |
| 사유 오류 | 400 | 알 수 없는 사유입니다 (허용값 `inbound`·`adjust` 둘뿐) | 없음 |
| 수량 오류 | 400 | 입고 수량은 1 이상이어야 합니다 (**상한은 서버에 없다**) | 없음 |
| 상태 오류 | 400 | 「단종」·「삭제대기」 상품에는 입고할 수 없습니다 | 없음 |
| 보류 중 | 409 | 보류 중인 상품입니다 (보류 #`hold_id` · 사유 `reason`) — 보류를 먼저 해제한 뒤 입고를 확정하십시오 | 없음 |
| 상품 없음 | 404 | 상품을 찾을 수 없습니다 — 조회 이후 삭제됐습니다 | 없음 |
| 기록 없음 | 404 | 되돌릴 입고 기록이 없습니다 | 없음 |
| 이중 되돌림 | 409 | 이미 되돌린 입고입니다 (`detail->>ref_log_id` 로 막는다) | 없음 |
| 재고 부족 | 409 | 입고분보다 재고가 적습니다 — 이후 판매·조정이 있어 되돌릴 수 없습니다 | 없음 |
| 권한 없음 | 403 | viewer 등급은 입고 확정·되돌리기를 할 수 없습니다 | 없음 |
| 서버 오류 | 5xx | 서버 오류로 입고를 기록하지 못했습니다 (사유까지 표시) | 다시 시도 |

⚠ **403 은 단추를 감추지 않고 «비활성 + 사유 병기»** 한다.
⚠ **원장 행과 재고 갱신은 한 트랜잭션이다** — 부분 반영은 없다.
⚠ **보류 409 는 «확정» 경로만 막는다 — 되돌리기는 보류 중에도 된다.** 되돌리기는 새 입고가 아니라 «교정»이고, 보류가 교정을 막으면 잘못 넣은 수량이 보류 때문에 굳는다(근거는 확정 가드 바로 위 주석). 그래서 이 행의 되돌리기 열 「없음」은 **확정 자체가 성립하지 않았다**는 뜻이지 그 상품을 되돌릴 수 없다는 뜻이 아니다.

> **① ② 는 2026-08-17 · ③ ④ 는 2026-08-18 확정이다.** ③ ④ 는 **승인 디자인에 없던 배치를

> 않도록 **무엇이 원안과 다른지**를 함께 적는다. 근거 전문 = `decision-log` **A-68**.

**① 보류 = ㉡ 서버 상태로 남긴다** (2026-08-17)

> 대기 목록은 저장이 아니라 **파생**(재고 0 또는 안전재고 미달)이다 — 화면에서 지워도 다음 조회에 돌아온다. 구 화면은 배열에서만 지우고 「보류 — 재고 미반영」을 띄웠다.
> **㉡ 를 택했으므로 보류 사유·해제 시각을 담을 표 또는 컬럼이 필요하다 — 마이그레이션 + ERD 개정이 화면보다 «먼저»다.**
> 목록 행마다 「보류」 단추가 서고, 보류분은 기본 조회에서 빠지며 별도 조건으로 다시 본다.

**② 안전재고 = ㉡ 상품 상세에서 정한다** (2026-08-17)

> 이 화면에서는 **읽기 전용**이다. 기준 변경은 상품 관리(ADM-PRD-010) — 「상품 작업의 유일한 진입점」 규약과 맞춘다.
> ⚠ `safety_stock` 컬럼은 실재하고 값이 30건 있는데 **쓰기 경로가 저장소에 0건**이다. 상품 상세에 그 경로를 만드는 것은 **이 화면의 범위가 아니다**(별건).

**③ 미선택 시 패널 「입고 이력」 = 전체(이 화면 처리분)** (2026-08-18)

> **원안과 다른 점**: 1b 는 이력 제목을 **「이 상품의 입고 이력」** 하나로만 그렸고

> 않았다 — 1b 의 목록은 언제나 한 건이 선택된 모습이다.
> **확정**: 미선택이면 **전체(이 화면 처리분)** 를 보여준다. 제목이 둘로 갈린다 —
> 「입고 이력 — 전체(이 화면 처리분)」 / 「이 상품의 입고 이력」.
> ⚠ **범위는 여전히 「이 화면으로 처리한 입고」다** — 전체 재고 원장이 아니다

## ✅ 확정(2026-08-18) — 대기 유형 필터는 **서버에 만든다** · 아직 구현 전

**대기 유형(재고 0 / 안전재고 미달) 필터 · 유형별 건수.** 이 계약이 위 둘(이력 API · 보류 표)만
적고 **이 자리를 빠뜨렸다.** 2026-08-17~18 사이 **미정 U-17** 로 올라가 있었고,
**2026-08-18 사장님이 ㉮ 「서버에 유형 파라미터·집계를 신설한다」로 확정**했다
(`decision-log` **A-68 ㉰** · U-17 은 §5 미정 표에서 빠졌다).

    확정      서버에 **조회 파라미터 + 유형별 건수**를 신설한다.
              정의서 §⑤ 2번을 **줄이지 않는다** — 화면이 요구한 것이 옳고 서버가 따라간다
    ⚠ 미구현  **다음 물결 몫이다.** 오늘 바뀐 것은 «만든다»는 결정뿐이고 서버는 그대로다.
              **확정을 구현으로 읽지 마라** — 아래 「서버에 있는 것」은 여전히 사실이다
    그동안    화면은 유형 칩 둘을 **비활성 + 사유 병기**로 둔다(수 없음).
              「비활성 칩이 남아 있다」는 것은 결함이 아니라 **이 확정이 아직 안 지어졌다**는 표시다
    ⚠ 맞물림  안전재고 기준 소유(위 §② — 상품 상세)는 바뀌지 않았고 **쓰기 경로는 0건**이다.
              기준이 실제로 세워지면 「안전재고 미달」 유형의 모집단이 달라진다

아래는 **확정 당시(2026-08-18) 서버 실측**이다 — 신설이 끝나면 이 표가 낡는다.

    정의서가 요구한 것   `docs/design/req/req-stock-inbound.md` §⑤ 2번
                         「조회 조건을 건다 — 상품명·SKU 검색 · 분류 · **대기 유형
                         (재고 0 / 안전재고 미달)**」
    서버에 있는 것       목록 조회 조건은 `q` · `part_type` · `catalog_q` · `hold` 넷뿐
                         (`api/admin_stock.py` `stock_inbound()` 시그니처).
                         **유형을 가르는 파라미터가 없다.**
    집계도 없다          응답이 주는 수는 `total` · `pages` · `held_total` 이다.
                         **유형별 건수를 세는 자리가 없다.**
    유형이 «있기는» 하다  행 단위로는 판정한다 — `safety_stock` 값과 사유 문구
                         (`_note_of()` 「안전재고 미달 — 현재 N / 기준 M」).
                         즉 **행마다 보이지만 그것으로 거르거나 셀 수는 없다.**
    화면이 한 것         **없는 것을 지어내지 않았다** — 유형 칩 둘을 «비활성»으로 두고
                         사유를 `title` 에 적었다. 수는 붙이지 않았다
                         (CANON §2-1 — 화면이 숫자를 지어내지 않는다).

**확인법**: `api/admin_stock.py` 에서 `def stock_inbound(` 한 줄을 보면 받는 조건이 전부 나오고,
`pending_where()` 가 그 조건을 만든다 — 거기에 유형 분기가 없다는 것이 근거다.

# 이 화면이 «하지 않는» 일

| 무엇 | 어디서 |
|---|---|
| 매입가 변경 | 단가표 반영 · 매입 견적 — 원장에 단가 컬럼 없음 |
| 안전재고 기준 설정 | 상품 관리 ADM-PRD-010 (쓰기 경로 신설 필요) |
| 검수 처리 | 상품 사양 검수 ADM-PRD-020 |
| 판매가 산정 | 판매가 그룹 |
| 상품 등록 · 분류 변경 | 상품 관리 ADM-PRD-010 |
| 일괄 선택 · 일괄 입고 | **규약으로 금지** — 수량이 상품마다 다름 |
| 예약 재고(가용재고) 계산 | 계산 코드가 저장소에 없음 |

⚠ **인계는 재고를 차감하지 않는다** — 견적이 나가도 재고는 그대로다. 재고를 줄이는 경로는 자체 주문과 실사 조정뿐이다.
⚠ **되돌려도 그 사이 나간 견적은 그 재고로 나갔다** — 되돌리기는 「없던 일」이 아니다.
