## 3. 이 세션이 실측한 것

### ① 깊이 — 제한이 이미 없다 (7단 가능)

| 층 | 실측 |
|---|---|
| 스키마 | `0027_categories.py` — `parent_id INTEGER REFERENCES categories(category_id)` **자기참조 하나뿐.** 깊이 컬럼 없음 |
| 조회 | `api/admin_categories.py` `_rows()` — `WITH RECURSIVE`로 자손 합계(`n_sub`)를 센다. 단계 수 가정 없음 |
| 상한 | 저장소 전체에서 `MAX_DEPTH` 류 상한 **0건** |
| 화면 | `templates/admin/product_category.html.j2` — 트리에서 분류를 고르면 「+ 하위 분류 추가 — <이름>」이 붙는다(2026-08-14 (가)안). `walk(pid, depth)` 재귀 렌더 |
| 규약 | 9/3 엑셀도 이미 같은 말을 한다 — *"parent_id 트리로 두고 깊이는 파생한다 — 5단이 필요해져도 구조를 바꾸지 않는다"* |

**7단으로 올릴 때 실제로 드는 값은 세 곳뿐이다.**

| # | 무엇 | 위치 | 성격 |
|---|---|---|---|
| ㉠ | **5~7단을 부를 이름이 없다.** 대·중·소·세는 4개까지만 이름이 있다 | 규약·화면 문구 전반 | 결정 필요(깊이 번호로 갈지, 이름을 정할지) |
| ㉡ | 통계 카드가 **2단을 전제**한다 — `'대분류 ' + top + ' · 소분류 ' + (total - top)`. 3단 이상이 전부 「소분류」로 세어진다 | `product_category.html.j2` **:824** | 문구·계산 수정 |
| ㉢ | 서랍의 「상위 분류 — 이동」 드롭다운이 **최상위 노드만** 나열한다 → 3단 이상 노드를 다른 가지로 옮기는 길이 없다 | 같은 파일 독스트링 **③**(:138~) · 서버는 더 깊은 이동을 받아 준다 | **이미 알려진 구멍.** 4단 이상이 되면 실사용을 막는다 |

㉢은 **깊이를 늘리기 전에 먼저 고쳐야 한다** — 안 고치면 잘못 만든 3단 이상 노드를 화면에서 되돌릴 수 없다.

### ② 「폐기하는 축」의 실측 폭발 반경

9/3 규약의 한 줄 — *"폐기하는 축: part_type(19종) · categories(37노드) · category_group(3종) … 하나의 트리로 통합한다"*.

| 실측 | 값 | 명령 |
|---|---|---|
| `part_type` 참조 파일 | **126** | `grep -rl part_type --include=*.py --include=*.j2 --include=*.html --include=*.sql .` |
| `part_type` 참조 건수(.py) | **785** | `grep -rn part_type --include=*.py . \| wc -l` |
| 그중 회귀 | **110** (`tests/regression.py` 단일 파일) | `grep -rc part_type tests/regression.py` |
| 상위 모듈 | `admin_products` 73 · `admin_reviews` 49 · `catalog_map` 38 · `admin_std` 35 · `admin_category_mapping` 34 · `recommend` 33 · `admin_categories` 30 · `taxonomy` 20 · `candidates` 20 · `expert` 19 · `catalog_ingest` 19 | 위와 같음 |

**두 축이 분리돼 있다는 것 자체를 회귀가 계약으로 지키고 있다.**

- `[32] 부품 어휘 단일 원천` (`tests/regression.py`:1481) — `part_type` 정의가 `taxonomy.py` 밖에 있으면 실패.
- `[33] 카테고리 트리 — 판매 축은 엔진과 분리돼 있다` (:1782) — **엔진 모듈**(`recommend`·`candidates`·`swap`·`usage_floors`·`taxonomy`)이 `categories`를 코드에서 읽으면 실패.
- 그 뒤 항목(:2048~)은 **정적 검사로 못 잡는 간접 경로**까지 본다 — 실제로 견적을 낸 뒤 그 부품들을 다른 분류로 옮기고 **같은 견적이 나오는지** 확인한다.

계약의 이유는 `api/taxonomy.py` 머리말에 코드로 적혀 있다:

> `part_type`은 **닫힌 집합이다. 운영자가 늘릴 수 없다** — 엔진이 읽기 때문에 슬라이스로만 바뀐다.
> (판매용 분류는 별도 축인 `categories`가 맡는다 — **그쪽은 운영자가 자유롭게 만든다.**)

**두 축을 한 트리로 합치면 운영자가 폴더를 옮겨 견적을 바꿀 수 있게 된다.**
그것이 임대 관리자(윈윈소프트)에서 미매핑 1,458건(판매중 325건)을 만든 병이고, 회귀 `[33]` 독스트링이 그 사고를 근거로 적혀 있다.

**다만 9/3 규약이 짚은 문제는 실재한다** — CPU 679 대 682 · RAM 1,801 대 1,804 · GPU 2,482 대 2,488.
**세 축이 각자 편집되니 어긋나는 것이지, 축이 둘이라서 어긋나는 것이 아니다.**

## 4. 결정 상태

### 확정된 것 (사장님, 2026-09-03 — 엑셀 「설계 규약」 시트)

§8 부록 B 18항 전체. 핵심 넷:

1. 계층은 **대·중·소·세 최대 4단**, 대분류 8개(부품·주변기기·쿨링튜닝·연결확장·완제품·소프트웨어·기타·중고)
2. **부품 대분류의 중분류 = 견적 엔진 슬롯**
3. **CPU 세대는 분류가 아니라 사양**(`std.spec_defs`의 `cpu_generation`) — *"세대는 계속 늘어나므로 트리에 박지 않는다"*
4. **중고는 판매 형태가 아니라 대분류로 분리**(다나와 방식)

> ⚠ 이 18항은 **엑셀에만 있고 `decision-log.md`에 등재되지 않았다.** 결정 번호(A-126 이후)가 아직 없다.

### 미정 — 사장님 답을 기다리는 것

| # | 무엇 | 상태 | 근거 |
|---|---|---|---|
| **미정-1** | **CPU 세대·i시리즈를 트리에 둘 것인가 사양으로 둘 것인가** | 2026-09-04 **"일단 조금만 더 고민해봅시다"** — 보류. 선택지 4개를 §5-①에 정리 | 이번 세션 |
| **미정-2** | **깊이 상한을 4에서 7로 올릴 것인가** | 미정-1과 함께 보류. **기술적으로는 공짜**임을 확인함(§3-①) | 이번 세션 |
| **미정-3** | 「폐기하는 축」 — ㉮ 파생 / ㉯ 통합 / ㉰ 병존 | **묻지 않았다.** 미정-1이 정해진 뒤 물을 것 | 이번 세션 |
| **미정-4** | 9/3 엑셀을 저장소에 넣을 것인가(파일째 커밋 / 마크다운 정본화 / 둘 다) | 이 문서 §7·§8이 마크다운 사본이다. 엑셀 자체 커밋 여부는 미정 | 이번 세션 |

> **미정-1이 나머지를 막는다.** 그것이 정해져야 트리 최종형이 서고, 트리가 서야 마이그레이션·재매핑 스크립트를 쓸 수 있다.

**되돌리는 값이 비대칭이라는 점만 기록해 둔다** — 사양으로 뒀다가 나중에 트리로 옮기는 것은 언제든 된다(사양값으로 노드를 자동 생성).
반대로 트리에 박았다가 사양으로 빼는 것은 **상품 2만여 건의 매핑을 되돌리는 일**이다.

## 5. 다음 사람이 할 일

### ① 먼저 미정-1을 받는다 — 선택지 4개

| 안 | 트리 모양 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ㉮ **사양으로**(9/3 규약 유지) | `부품 > CPU > 인텔/AMD` 에서 멈춤 | 세대×i시리즈×소켓 **조합** 필터. 상품명 파싱으로 자동 백필. 새 세대가 나와도 운영자 할 일 없음 | 「폴더를 타고 내려가는」 탐색감이 없음 |
| ㉯ 트리 — 세대 먼저 | `… > 인텔 > 14세대 > i7` | 「14세대 전부 보기」 | **「i7만 모아 보기」가 영영 안 됨.** 세대마다 노드 생성·재매핑 |
| ㉰ 트리 — i시리즈 먼저 | `… > 인텔 > i7 > 14세대` | 「i7만 모아 보기」 | 「14세대 전부 보기」가 안 됨 |
| ㉱ 절충 | 트리는 제조사까지 · 세대·i시리즈는 사양이되 **분류 화면이 사양 기반 「가상 하위」를 그린다** | 보기엔 7단, 데이터는 사양이라 순서 자유 | **화면을 새로 지어야 한다** |

**구조적 근거(어느 쪽을 고르시든 사실이다):** 상품은 트리 노드 **하나에만** 들어간다. 그래서 트리는 **파고드는 순서가 하나로 고정된다.**
사양은 그 제약이 없다 — 9/3 규약이 GPU 칩셋을 「상품명에서 94.3% 추출 가능」이라 적은 그 방식이 세대·i시리즈에도 그대로 적용된다.

### ② 미정-1이 정해진 뒤 — 순서

1. **결정 로그 등재** — 9/3 규약 18항 + 이번 결정을 A-126 이후로 등재. (`decision-log.md` · `.claude/CANON.md`)
2. **㉢ 먼저 고친다** — 「상위 분류 — 이동」 드롭다운이 3단 이상을 못 옮기는 구멍(§3-①). **깊이를 늘리기 전에.**
3. **㉡ 통계 문구** — `product_category.html.j2`:824.
4. **트리 세우기 마이그레이션** — `0072_category_tree_4tier`(가칭). 9/3 트리 70행을 노드로. **정리 대상 3건 동시 제거** — 테스트 대분류(479) · 새 대분류(488) · 테스트2(487).
5. **재매핑 스크립트** — ETC 4,751건이 주 대상. 엑셀이 밝힌 대로 **오분류는 191건뿐이고 나머지는 자리가 없어 밀려난 것**이다(케이블 1,141 · 시스템팬 928 · 소프트웨어 378 · 네트워크 340). **원장 역방향 전이로 되돌릴 수 있게** 짓는다(`admin_category_mapping` 규약 그대로).
6. **회귀** — `[32]`·`[33]`과 그 뒤 「옮겨도 견적 불변」 항목을 **반드시** 돌린다. 미정-3에서 ㉯를 고르셨다면 이 셋은 재작성 대상이다.
7. **역방향 검사** — 재매핑 전 `products`의 `category_id` 스냅샷을 뜬다. 몰 카탈로그 재적재 사고(2026-08-15~16) 전례가 있다.

### ③ 미정-3(폐기하는 축)은 트리가 선 뒤에 묻는다

트리를 세우는 것과 축을 합치는 것은 **다른 일**이다. 트리는 미정-3 없이도 세울 수 있다.

## 6. 이 세션이 못 한 것 — 환경 제약

| 못 한 것 | 이유 |
|---|---|
| `alembic upgrade` · 회귀 실행 · 서버 기동 | 이 세션에는 **PC에서 명령을 돌릴 수단이 없다**(`device_bash` 미제공). 파일 읽기/쓰기만 된다 |
| DB 실측(현재 트리·건수 확인) | DB는 **Cloud SQL**이고 이 컨테이너는 승인된 네트워크가 아니다. §2의 건수는 **엑셀이 적은 9/3 스냅샷을 그대로 옮긴 것**이지 이 세션이 잰 값이 아니다 |
| 미커밋 작업 확인 | `git status`를 못 돌린다. 최상위 파일 mtime으로만 봤고 **하위 폴더는 못 봤다** — 다음 세션이 PC에서 `git status`로 재확인할 것 |

**따라서 이 문서의 수 중 이 세션이 직접 잰 것은 §3(코드 실측)뿐이다.** §2·§7의 건수는 엑셀 인용이다.

## 8. 부록 B — 설계 규약 18항 (9/3 엑셀 사본)

| 항목 | 확정 내용 |
|---|---|
| 분류 계층 명칭 | 대분류 · 중분류 · 소분류 · 세분류 (최대 4단) |
| 대분류 8개 | 부품 · 주변기기 · 쿨링·튜닝 · 연결·확장 · 완제품 · 소프트웨어 · 기타 · 중고 |
| 중분류 = 견적 슬롯 | 부품 대분류의 중분류가 견적 엔진 슬롯과 일치한다 (CPU · 메인보드 · 메모리 · 그래픽카드 · SSD · HDD · 케이스 · 파워 · CPU쿨러) |
| 중고 | 판매 형태가 아니라 대분류로 분리한다 (다나와 방식) |
| CPU쿨러 | 부품에 둔다 (견적 필수 슬롯). 시스템팬은 쿨링·튜닝으로 분리한다 |
| **CPU 세대** | **분류가 아니라 사양으로 둔다** (`std.spec_defs`의 `cpu_generation`). 세대는 계속 늘어나므로 트리에 박지 않는다 |
| GPU 칩셋 | 신설한다 — `gpu_chipset_maker` / `gpu_chipset_family` / `gpu_chipset_model`. 상품명에서 **94.3% 추출 가능**하고 나머지는 정돈 엑셀(칩셋모델 258건)로 백필한다 |
| 모니터 | 크기로 나눈다. 패널·주사율은 사양으로 둔다 |
| 분류 노드 속성 | 이름·깊이 / 견적 슬롯 여부·슬롯 키 / 필수 사양 항목 / 허용 부품 종류 |
| DB 구조 | `parent_id` 트리로 두고 깊이는 파생한다 — **5단이 필요해져도 구조를 바꾸지 않는다** |
| **폐기하는 축** | 지금의 `part_type`(19종) · `categories`(37노드) · `category_group`(3종)이 같은 사실을 세 벌로 표현하고 있었다 (CPU 679 대 682 · RAM 1,801 대 1,804 · GPU 2,482 대 2,488). 하나의 트리로 통합한다 |
| 정리 대상 | 정본 트리에 남은 테스트 노드 3개 — 테스트 대분류(479) · 새 대분류(488) · 테스트2(487) |
| 재분류 대상 | 현재 ETC **4,751건 중 오분류는 191건뿐**이고 나머지는 자리가 없어 밀려난 것이다 (케이블 1,141 · 시스템팬 928 · 소프트웨어 378 · 네트워크 340) |
| 상위 골격 (09-03 확정) | 부품 마스터(사양이 한 번만) → 구성(슬롯+대안) → 판매 품목(형태·가격·재고) → 공급처별 매입가. **완제품은 이름을 얻은 견적**이며 견적과 같은 자료 구조를 쓴다 |
| 진열 축 (09-03 확정) | 관리 트리와 별도로 둔다. **용도별 · 예산대별 · 게임 타이틀별 3축**이며, 목록이 아니라 **견적 엔진 입력 조건**으로 정의한다 |

> **「폐기하는 축」 항은 §3-②의 실측(785곳·회귀 110곳·회귀 계약 2건)과 충돌한다.** 미정-3으로 남겨 둔다.
> **「CPU 세대는 사양」 항은 미정-1과 충돌한다** — 사장님이 2026-09-04에 「7단으로 늘려 CPU를 세대별·i시리즈별로」를 물으셨다.
