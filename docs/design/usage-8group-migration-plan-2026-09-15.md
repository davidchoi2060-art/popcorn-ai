## §2. 충돌 발견 — 이 xlsx가 `office-subdivide-plan-2026-09-15.md`를 대체한다

**시간순**: `docs/design/office-subdivide-plan-2026-09-15.md`는 같은 날 11:33에
작성됐고, 그 문서는 사무 용도를 **6갈래**(`office_docs`·`office_lecture`·`office_web`·
`office_meeting`·`office_finance`·`office_design_light`)로 세분화하는 설계를 냈다.
이 xlsx 원본 파일의 수정 시각은 **12:50**로 그보다 **늦다**.

**내용 충돌**: xlsx는 그룹 1의 이름 자체가 "일반 **사무 및 인강용**"이고, 과업 제목도
"사무·인강 **통합**"이라 못박는다. 6갈래 세분화 설계와 정면으로 반대 방향이다 — 세분화가
아니라 **통합 유지**가 사장님의 최신 지시다.

**이 문서의 처리 방침**: 그룹 1(사무·인강)은 §4-1에서 지금의 단일 `office` 키를
**그대로 유지**하는 쪽으로 설계한다. `office-subdivide-plan`의 6갈래안은 이 xlsx
확정으로 **사실상 대체(supersede)됐다고 판단**하지만, 그 판단 자체는 이 문서(조사자
산출물)가 내릴 수 있는 게 아니라 **사장님 확인이 필요한 지점**으로 남긴다(§10-1).
6갈래안 문서 자체는 지우지 않는다 — 결정 이력으로 남긴다.

## §4. 그룹별 `usage_floors` 값 설계 — xlsx 모델명 → 재고 실측 와트값

### 방법론 (모든 그룹 공통)

xlsx는 GPU를 **모델명**으로 적었다(RTX 3050, RTX 5060 Ti …). `usage_floors`가 걸 수
있는 GPU 필드는 `required_power_watt`(W) 하나뿐이므로, 각 모델명을 재고
`product_specs.required_power_watt`로 전수 대조해 실측했다(판매중·재고>0 GPU 300건
기준, `vram_gb` 있음 282건·`required_power_watt` 있음 266건):

| GPU 모델 | 실측 `required_power_watt` | 표본 n |
|---|---|---|
| RTX 3050 | 550W | 16 (6GB 13 · 8GB 3) |
| RTX 5060(비Ti) | 550W | 34 |
| RTX 5060 Ti | 600W | 33 (8GB 27 · 16GB 6) |
| RTX 5070(비Ti) | 650W | 21 |
| RTX 5070 Ti | 750W | 19 |
| RTX 5080 | 850W | 30 |
| RTX 5090 | 1000W | 14 (VRAM 32GB 12건 · NULL 2건) |
| RX 6600(전 라인업) | **재고 0** — 전량 품절 | 0 |

⚠ **RX 6600은 실측 불가다** — 그룹 2(주식·다중작업) 원문이 "RTX 3050 **및** RX6600
이상"이라 적었지만, 재고에 RX 6600 계열이 판매중인 것이 하나도 없다(전량 품절).
GPU 하한값은 확인 가능한 RTX 3050(550W) 쪽만으로 잡고, 이 사실을 그대로 남긴다 —
RX 6600 쪽 수치를 지어내지 않는다.

각 그룹의 GPU 하한은 **xlsx가 그 그룹에 적은 범위의 최솟값**을 채택한다(기존
`usage_tier_rules`·`spec_tiers` 설계가 이미 쓰는 "하한 = 범위 최솟값" 관례,
`docs/design/spec-tier-migration-plan-2026-09-14.md` §1-2와 동일한 철학).

### 4-1. `office`(사무·인강) — 재사용, 값 유지

xlsx: RAM 8~16GB · SSD 256~512GB · GPU 없음(내장그래픽 충분).

| 필드 | 지금 값 | xlsx 범위 | 제안 |
|---|---|---|---|
| RAM | ≥8 | 8~16 | **유지**(≥8, 하한=범위 최솟값과 이미 일치) |
| SSD | ≥250 | 256~512 | **유지**(≥250, 실질 동일 — 256과 250 차이는 무시 가능한 오차) |
| GPU | 없음 | 없음 | **유지**(없음) |

**변경 없음** — 8군 중 유일하게 지금 값이 이미 xlsx와 정합한다.

### 4-2. `trading`(주식·다중작업) — 재사용 + GPU 하한 신설

xlsx: RAM 16~32GB · SSD ≥512GB · GPU RTX3050/RX6600 이상(신규 요구 — 현재 없음).

| 필드 | 지금 값 | xlsx 범위 | 제안 |
|---|---|---|---|
| RAM | ≥16 | 16~32 | **유지**(≥16) |
| SSD | ≥500 | ≥512 | **상향 검토**(500→512, 재고에 512GB급 다수 — §4 서두 SSD 분포 참조) |
| GPU | **없음** | RTX3050 이상 | **신설**: ≥550W(RTX3050 실측, RX6600은 실측 불가로 미반영) |

⚠ **가장 큰 변경**: 지금 `trading`은 GPU 하한이 아예 없는데, xlsx는 "4K 차트 동시
출력"을 위해 GPU를 명시 요구한다. GPU 슬롯을 새로 거는 것은 견적에 GPU 값이 추가됨을
뜻한다 — 가격에 미치는 영향이 있으므로 사장님 확인 필요(§10-2).

### 4-3. `game_casual`(캐주얼 게임용) — 신규

xlsx: RAM 16GB · SSD 512GB · GPU RTX 3050.

| 필드 | 제안 |
|---|---|
| RAM | ≥16 |
| SSD | ≥500(512에 가장 가까운 기존 관례값, 재고 512GB 다수) |
| GPU | ≥550W(RTX3050 실측) |

### 4-4. `game`(게임용·일반) — 재사용, 재정의

⚠ **지금 `game`의 GPU 하한(450W)은 xlsx 캐주얼(550W)보다도 낮다** — 지금 값을 그대로
"일반" 등급에 쓰면 캐주얼보다 낮은 사양이 "일반"으로 잘못 불리는 역전이 생긴다. 값을
전면 교체해야 한다.

xlsx: RAM 16~32GB · SSD 1TB · GPU RTX5060~5060Ti.

| 필드 | 지금 값 | 제안 |
|---|---|---|
| RAM | ≥16 | **유지**(≥16) |
| SSD | ≥500 | **상향**: ≥1000(1TB, 재고 1024GB 다수 확보 — §4 서두 표 참조) |
| GPU | ≥450 | **상향**: ≥550(RTX5060 비Ti 실측 — 범위 최솟값) |

⚠ **`game_casual`과 GPU 하한이 550W로 같아진다.** xlsx 원문 자체가 캐주얼="RTX 3050"
단일 모델, 일반="RTX 5060 ~ RTX 5060 Ti" 범위인데, 그 범위의 **최솟값**(RTX5060 비
Ti)이 우연히 RTX3050과 같은 550W 등급으로 실측됐다(§4 서두 표 — 두 모델 다 550W).
`required_power_watt`를 성능 대리 지표로 쓰는 지금 체계의 구조적 한계다 — VRAM이나
세대가 아니라 전력 등급만 보면 두 모델이 같은 칸에 들어간다. **SSD(500 vs 1000)가
사실상 유일한 하드 구분축**이 된다는 뜻이다. 이건 `spec-tier-migration-plan-2026-09-14.md` §1-2가 이미 짚은 "T3/T4가 VRAM만으로는 안 갈린다"는 것과 같은 종류의 문제이고,
office-subdivide-plan §2-2가 "하한이 같아도 무방하다, 구분은 match_terms와 화면
문구로 한다"고 정리한 선례와도 같은 성격이다 — 지어낸 상향 조정으로 억지로 가르지
않고, 이 사실 자체를 사장님께 그대로 보고한다(§10-3).

### 4-5. `gaming_high`(고사양 게임용) — 재사용, 대폭 상향

⚠ **지금 값(GPU≥550W)이 xlsx 고사양 하한(RTX5070=650W)보다 훨씬 낮다** — 지금
`gaming_high`는 RTX5060/5060Ti급(방금 정의한 `game` 일반과 같은 등급대)도 통과시키고
있었다. 8군 확정으로 명확히 상향해야 한다.

xlsx: RAM ≥32GB · SSD 1~2TB · GPU RTX5070~5090.

| 필드 | 지금 값 | 제안 |
|---|---|---|
| RAM | ≥16 | **상향**: ≥32 |
| SSD | ≥500 | **상향**: ≥1000(1TB, 범위 최솟값) |
| GPU | ≥550 | **상향**: ≥650(RTX5070 비Ti 실측 — 범위 최솟값) |

### 4-6. `design`(디자인·사진편집) — 재사용 + GPU 하한 신설

xlsx: RAM 16~32GB · SSD 512GB~1TB(+백업 HDD, 반영 불가 — 아래 참조) · GPU RTX3050
또는 RTX5060(가속 기능 목적).

| 필드 | 지금 값 | 제안 |
|---|---|---|
| RAM | ≥16 | **유지**(≥16) |
| SSD | ≥500 | **유지**(≥500, xlsx 하한 512와 실질 동일) |
| GPU | **없음** | **신설**: ≥550W(RTX3050/RTX5060 둘 다 550W 실측 — §4 서두 표) |

⚠ **"백업용 HDD"는 반영 불가**: `usage_floors`의 `slot`은 SSD/RAM/GPU처럼 단일
슬롯이고, "SSD 512GB~1TB + 별도 HDD"라는 **두 슬롯 조합** 요건을 한 필드로 표현할
방법이 없다(HDD 슬롯 자체에 거는 것과 SSD와 별개로 "추가로"를 표현하는 것은 다른
설계가 필요 — 이 표 구조 밖의 문제). 지어내지 않고 이 사실만 기록한다.

⚠ **GPU 하한 신설이 `design`에도 적용된다** — §4-2(trading)와 같은 성격의 변경.
지금까지 GPU 하한이 없던 두 용도(trading·design)에 동시에 하한이 생기므로, 가격
영향 확인이 필요하다(§10-2).

### 4-7. `video`(영상편집) — 재사용, 라벨 의미 좁힘 + 값 상향

⚠ **지금 `video`는 "영상편집" 하나로 3D까지 뭉뚱그리고 있었다** — 이번 8군 확정으로
영상편집과 3D가 별도 그룹(4항·8항)이 됐으니, 기존 `video` 키는 **영상편집 전용**으로
의미를 좁히고 값을 그 그룹 기준으로 올린다.

xlsx(영상편집): RAM 32~64GB · SSD ≥2TB(고속 NVMe) · GPU RTX5060Ti~5070.

| 필드 | 지금 값 | 제안 |
|---|---|---|
| RAM | ≥32 | **유지**(≥32, 하한은 범위 최솟값과 일치) |
| SSD | ≥1000 | **상향**: ≥2000(2TB, 재고 2048GB 55건 확보) |
| GPU | ≥450 | **상향**: ≥600(RTX5060 Ti 실측 — 범위 최솟값) |

### 4-8. `video_3d`(3D 그래픽) — 신규

xlsx: RAM ≥64GB · SSD ≥2TB(고속 NVMe) · GPU RTX5080 또는 5090(전문가용 쿼드로/RTX
Ada 계열은 재고에 없다고 판단 — 아래 참조).

| 필드 | 제안 |
|---|---|
| RAM | ≥64 |
| SSD | ≥2000(2TB) |
| GPU | ≥850W(RTX5080 실측 — 범위 최솟값) |

⚠ **쿼드로/RTX Ada 계열은 검증하지 않았다** — xlsx가 "전문 작업용은 고려"라고 괄호로
덧붙인 수준이라, 이 문서는 주 옵션(RTX5080/5090)만 실측하고 워크스테이션 카드 재고
여부는 확인하지 않았다(범위 밖으로 남긴다).

### 4-9. CPU 필드 — `usage_floors`로는 표현 불가 (정직한 한계)

xlsx 8군 전부가 CPU 등급(i3~i9, 라이젠3~9)을 명시하는데, **`usage_floors`의
`FLOOR_FIELDS`에는 CPU 필드가 없다**(§1-1). 재고에서 i-등급·라이젠 등급별 코어 수를
참고로 실측했지만(아래), 이 값을 `usage_floors`에 걸 자리 자체가 없어 **이 표만으로는
반영이 불가능**하다:

| 등급 | 코어 수 실측(판매중+재고>0) |
|---|---|
| i3 | 4코어 고정(n=22) |
| i5 | 6~14코어(n=56, 12세대 이상 하이브리드 코어 포함이라 범위가 넓다) |
| i7 | 4~20코어(n=42, 구형 4코어 제품 혼재 — 세대 구분 없이는 하한을 못 낸다) |
| i9 | 8~24코어(n=25) |
| 라이젠3 | 4코어 고정(n=2) |
| 라이젠5 | 4~6코어(n=29) |
| 라이젠7 | 8코어 고정(n=18) |
| 라이젠9 | 12~16코어(n=10) |

i7 실측이 4~20코어로 폭이 매우 넓은 것은(6세대 구형 4코어 제품이 "i7" 문자열에
그대로 걸리기 때문) **상품명 문자열만으로 세대를 가르지 못한다는 뜻**이다 — 억지로
숫자 하한을 뽑으면 지어내는 것과 같다. CPU 축은 이 문서의 범위에서 뺀다 — 다만
`usage_tier_rules`는 `cpu_cores` 필드를 이미 쓰고 있으므로(§1-2), CPU 반영이 꼭
필요하면 그 표로 옮기는 것이 다음 단계다(§7).

## §5. `match_terms` 설계 — 8군 검색어 그대로, 충돌 1건 발견·처리

각 그룹의 `match_terms`는 xlsx "용도 및 검색어" 열을 그대로 옮긴다. `usage_floors.match()`
가 **부분일치·sort_order 오름차순·첫 hit 하나만**(§1-1 구조 그대로)이므로, 순서(좁은
것 먼저)가 중요하다.

| usage_key | match_terms(제안, xlsx 그대로) | sort_order 제안 |
|---|---|---|
| `game_casual` | 캐주얼 게임용, 리그 오브 레전드, 발로란트, FC 온라인, 저사양 게임용, FHD 해상도 입문형 | 가장 먼저(0번대) |
| `gaming_high` | 고사양 게임용, AAA, 싸이버펑크 2077, 레드 데드 리뎀션 2, 스팀 패키지 게임, 4K 고해상도 풀옵션, 레이 트레이싱, 패스 트레이싱 | 그 다음 |
| `game` | 게임용, 배틀그라운드, 오버워치2, 디아블로4, 스팀 게임, QHD 해상도 방어 | 가장 넓은 "게임" 계열 마지막 |
| `office` | (변경 없음) | 유지 |
| `trading` | (변경 없음, GPU 하한만 추가) | 유지 |
| `design` | (변경 없음, GPU 하한만 추가) | 유지 |
| `video` | 영상 편집, 유튜브 영상, 4K/8K 고화질 영상, 컷 편집, 애프터 이펙트, 프리미어 프로, 다빈치 리졸브, 멀티캠 편집, VFX 가속 | 유지 위치 |
| `video_3d` | 3D 그래픽, 건축 디자인, 3ds Max, Maya, Blender, CAD, 엔지니어링, 수백만 폴리곤 렌더링 | `video` 바로 뒤 |

⚠ **충돌 1건 발견 — "발로란트"가 xlsx 원문에서 캐주얼(3항)과 게임용·일반(4항) 양쪽에
중복**돼 있다(§0 원문 그대로 옮긴 표 확인). `usage_floors.match()`는 첫 hit 하나만
쓰므로 두 그룹에 동시에 넣으면 sort_order가 앞선 쪽이 항상 이기고 뒤쪽은 죽은
낱말이 된다(`0057` 마이그레이션이 이미 같은 종류의 문제를 "죽은 낱말은 표에 올리지
않는다"고 처리한 전례). **이 설계의 제안**: "발로란트"는 `game_casual`에만 남기고
`game`(일반)의 목록에서 뺀다 — 발로란트는 사양 요구가 낮은 이스포츠 타이틀이라
캐주얼 쪽 정의(실측: `spec-tier-migration-plan-2026-09-14.md` §2-3이 이미 "발로란트"를
E등급/이스포츠 경량으로 확정 분류한 전례)와 더 맞는다. **다만 이것은 xlsx 원문을 그대로
옮기지 않고 조사자가 벌인 첫 해석적 판단**이므로 §10-1에서 사장님 확인이 필요한
항목으로 명시한다 — 원문 자체는 §0에 손대지 않고 그대로 남겨 뒀다.

## §6. Orphan — 8군에 없는 기존 5개 usage_key (`ai`·`dev`·`stream`·`media`·`web`)

xlsx 8군은 지금 `usage_floors`의 11개 키 중 6개(`office`·`trading`·`game`·`gaming_high`·
`design`·`video`)만 다시 확인했다. 나머지 5개는 이 xlsx가 언급하지 않는다:

| usage_key | 현재 상태 | 이 문서의 처리 |
|---|---|---|
| `ai` | 활성, 27행 중 3행, `usage_tier_rules`·`usage_alloc`에도 존재 | **손대지 않는다** — A-135가 이미 "AI는 지금 구조(`ai_workloads`) 유지"로 별도 결정함(decision-log A-135, 게임·영상편집 재설계 범위에서도 AI 제외) |
| `dev` | 활성, `usage_tier_rules`에도 존재 | **미정** — xlsx 8군에 "개발" 용도가 아예 없다. 폐기할지 유지할지 사장님 확인 필요 |
| `stream` | 활성 | **미정** — 같은 이유 |
| `media` | 활성(0057 신설) | **미정** — 같은 이유 |
| `web` | 활성(0057 신설) | **미정** — 같은 이유. `office`(사무·인강)와 RAM/SSD 하한이 이미 같아 겹침 위험이 기존에도 있었다(`0057` 마이그레이션 자체 문서화) |

**이 문서는 이 5개를 지우거나 값을 바꾸지 않는다** — xlsx가 이들을 언급하지 않는다고
곧바로 폐기 신호로 해석하면 지어내는 것이다. 사장님이 "8군 외 용도는 유지" 또는
"8군으로 전면 교체"를 확정해야 다음 단계가 정해진다(§10-4).

## §7. `usage_tier_rules`·`usage_alloc` — 이번 범위와 후속 필요성

**이번 설계는 `usage_floors`(레이어 1 하한)만 다룬다.** `usage_tier_rules`(예산 티어별
겨냥값)와 `usage_alloc`(슬롯 배분율)은 각각 다른 트리거 축(예산)을 쓰는 다른 표라서,
`usage_floors` 값이 바뀌면 두 표도 재검토가 필요하지만 **이 문서의 새 usage_key
(`game_casual`·`video_3d`) 둘은 아직 그 표에 행이 없다**:

- `usage_tier_rules`에 `game_casual`·`video_3d` 행 없음 — 신설 시 시장 표본(analysis.md)
  기반 재조사가 필요(이 문서는 xlsx 하한만 다뤘지, 예산 티어별 겨냥값까지는 조사하지
  않았다).
- `usage_alloc`에도 `game_casual`·`video_3d` 행 없음 — 없으면 `usage_alloc.for_usage()`가
  기본(NULL) 행을 상속하므로 **엔진이 죽지는 않는다**(안전한 폴백), 다만 8군 전용
  배분율은 아직 없다는 뜻이다.
- `video`의 라벨 의미가 "영상편집+3D"에서 "영상편집 전용"으로 좁아지면(§4-7), 기존
  `usage_tier_rules`·`usage_alloc`의 `video` 행 근거(analysis.md 표본)가 3D를 포함한
  채 잡힌 값일 수 있다 — 그대로 못 쓴다. **재조사 필요**(이 문서 범위 밖).

이 문서는 이 두 표에 아무것도 쓰지 않는다 — §9 DDL 초안도 `usage_floors`만 다룬다.

## §8. `grid_cells` — 이 문서와의 관계 (순서만 명시, 재편은 범위 밖)

§1-4에서 확인한 대로 `grid_cells.usage` 8라벨은 이 xlsx 8군과 다른 분류축이다.
`spec-tier-migration-plan-2026-09-14.md`(A-135)가 이미 격자 티어 자체를 가격 축에서
스펙 축(T0~T5)으로 재설계하는 상위 작업을 진행 중이다 — **이 문서(레이어 1의
`usage_floors` 8군 이행)가 먼저 확정돼야, 그 위에서 A-135의 격자 재편이 8군 기준으로
용도 라벨을 다시 정할 수 있다.** 순서를 뒤집으면(격자부터 8군으로 바꾸고 `usage_floors`
는 그대로) 화면 라벨과 서버 하한이 서로 다른 용도 이름을 쓰는 불일치가 생긴다. 이
문서는 `grid_cells` 자체를 설계하지 않는다 — 순서 관계만 남긴다.

## §10. 사장님 확인이 필요한 지점 (이 문서가 대신 결정하지 않은 것)

1. **office-subdivide-plan(6갈래) 폐기 여부**(§2) — 이 xlsx의 "사무·인강 통합"이
   그 설계를 대체한다고 이 문서는 판단했지만, 공식 폐기 선언은 사장님 몫이다.
2. **GPU 하한 신설 2건의 가격 영향**(§4-2 trading, §4-6 design) — 지금까지 GPU 없이
   나가던 두 용도에 GPU가 추가되면 최저가 구성 총액이 오른다. 승인 필요.
3. **`game`/`game_casual`의 GPU 하한 동률(550W) 처리**(§4-4) — SSD만으로 구분하는
   현재 설계를 그대로 채택할지, 아니면 RAM 상한(`game_casual`은 16GB **고정**, `game`은
   16~32GB 허용— 지금 `usage_floors`에 상한 필드가 없어 이것도 표현 불가라는 점까지
   함께 확인 필요) 등 다른 축을 추가할지.
4. **orphan 5종(`ai`·`dev`·`stream`·`media`·`web`) 존치 여부**(§6) — 8군 확정이
   "이 8개로 전면 교체"인지 "8개를 추가/갱신하고 나머지는 유지"인지.
5. **"발로란트" 중복 처리**(§5) — 캐주얼 전용으로 좁히는 조사자 제안의 승인 여부.
6. **디자인 "백업용 HDD" 반영 불가**(§4-6) — 이대로 SSD 하한만 걸고 HDD 요건은 포기할지,
   별도 설계(HDD 슬롯에 독립 하한을 거는 방식 등)가 필요한지.
7. **CPU 등급 축 자체가 `usage_floors`에 없다는 구조적 한계**(§4-9) — `usage_tier_rules`
   로 옮길지, `FLOOR_FIELDS`를 확장할지, 이번엔 보류할지.

## §11. 확인법 (구현 착수 시)

- `usage_floors` 갱신 후: `SELECT usage_key, slot, field, op, value FROM usage_floors
  WHERE active ORDER BY sort_order`로 §9 UPDATE/INSERT 값이 실제로 반영됐는지 대조.
- GPU 하한 실측 재검증: `SELECT required_power_watt, count(*) FROM products p JOIN
  product_specs ps ON ps.product_code=p.product_code WHERE part_type='GPU' AND
  product_name ILIKE '%모델명%' AND status='판매중' AND stock_qty>0 GROUP BY 1` —
  §4의 표와 일치하는지 재고가 바뀌었을 때마다 재확인.
- `match_terms` 충돌 검사: `admin_talk_patterns.py`가 쓰는 것과 같은 방식(같은 낱말이
  두 usage_key에 동시에 걸리는지)으로 8군 전체를 한 번 더 스캔.
- 8군 도입 후 `/api/candidates/count`를 그룹별 대표 검색어("롤 하려고요"·"3D 렌더링용"
  ·"주식 차트 여러 개"·"사진 보정용")로 8회 호출 — 서로 다른 후보 수·가격대가 나오는지
  확인(§4-4 동률 경고 지점은 SSD로 갈리는지 특히 확인).
- 회귀 세트(`tests/regression.py`)를 8군 반영 후 전수 재실행 — 기존 `game`·`gaming_high`
  ·`design`·`video` 값이 바뀌므로 그 값에 의존하는 FIXED 기대값이 있다면 갱신 필요.
