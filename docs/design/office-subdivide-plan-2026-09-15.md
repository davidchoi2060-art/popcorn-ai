## §0. 근본 원인 진단 (배경 4개 지적의 공통 뿌리)

## §1. 내장그래픽(iGPU) 판정 함수 설계 — `cpu_has_igpu(product_name, maker)`

### 1-1. 왜 필요한가

사무 세분화의 핵심 축은 "이 CPU만으로 화면이 나오는가"다. 지금 재고엔 이 사실을
직접 담은 컬럼이 없다(`cpu_gpu`는 죽은 필드 — `db/migrations/versions/0020_spec_field_cpu_gpu.py`,
1/678만 채워짐, `docs/design/part-spec-standard-2026-08-10.md` 42행 "죽은 필드").
`cpu_bundled_cooler`(`api/catalog_map.py` 255행)가 이미 같은 문제를 풀었다 —
DB에 없는 사실을 **상품명 표현 패턴**으로 판정하는 단일 원천 함수. 그 패턴을
그대로 벤낀다: 같은 파일에 나란히 둔다, 판정 로직은 정규식 하나, 독스트링에
근거·예외·검증 방법을 남긴다, 호출부는 이 함수 하나만 부른다.

### 1-2. 판정 규칙 (실측 검증)

```python
# api/catalog_map.py — cpu_bundled_cooler(255행) 바로 다음에 신설 제안

# CPU 내장그래픽(iGPU) 유무 — 상품명 패턴 판정(제조사별 명명 규칙, 2026-09-15 실측).
#
# `cpu_gpu`(0020) 컬럼이 죽은 필드라(1/678만 채워짐) DB 값을 못 믿는다. `cpu_bundled_cooler`
# 와 같은 이유로 **상품명에서 판정**한다 — 다만 근거 성격이 다르다: 쿨러는 "상품명이
# 스스로 밝힌 것만" 인정하는 표현 매칭이고, 여기는 **인텔·AMD가 실제로 지키는 모델
# 명명 규칙**(구조적 패턴)이다. 표현이 아니라 규칙이므로 판정 방향이 비대칭이 아니다.
CPU_IGPU_INTEL_NO_IGPU = re.compile(r"(?<![0-9A-Za-z])\d{3,5}K?F(?![0-9A-Za-z])")
CPU_IGPU_AMD_HAS_IGPU  = re.compile(r"(?<![0-9A-Za-z])\d{3,4}G[ET]?(?![0-9A-Za-z])")


def cpu_has_igpu(product_name: str, maker: str) -> bool:
    """CPU가 내장그래픽을 갖는가 — 제조사별 모델 명명 규칙으로 판정한다.

    ⚠ 제조사를 먼저 본다 — 인텔·AMD 규칙이 정반대다(인텔은 '없다'는 표시,
    AMD는 '있다'는 표시). 제조사를 안 가르면 서로의 접미 문자를 오판한다.

      인텔: 모델 번호가 F(또는 KF)로 끝나면 iGPU 없음 — 그 밖(K 포함)은 있음.
            "14700F"·"245KF" → 없음. "13600K"·"14700" → 있음(K는 배수잠금
            해제일 뿐 iGPU 유무와 무관 — `recommend._cpu_unlocked_suffix`와
            같은 접미 판정이지만 **다른 질문**이라 별도 정규식이다, §1-4 참조).
            ⚠ 제온(Xeon) 계열은 F 유무와 무관하게 대부분 iGPU가 없다 — 재고
            표본 4건 전부 F가 없는데도 실제로는 서버용이라 iGPU 미탑재(§1-3).
            상품명에 '제온'·'Xeon'이 있으면 F 판정보다 먼저 False로 확정한다.
      AMD:  모델 번호가 G·GE·GT로 끝나면 iGPU 있음(APU) — 그 밖은 없음.
            "5600G"·"8700G"·"5500GT" → 있음. "7600"·"9700X" → 없음.

    실측 검증(2026-09-15, 재고 CPU 683행 중 판매중+재고>0 276건 전수 대조):
    이 규칙으로 나온 판정에서 오탐(규칙과 실제가 다른 사례) 0건 — 제온 4건만
    F-suffix 규칙 예외로 별도 처리했고, 그 밖은 전수 일치했다.

    값 모르면(maker가 인텔·AMD 둘 다 아니면) False로 둔다 — 지어내지 않는다.
    """
    name = product_name or ""
    mk = (maker or "").strip()
    if mk in ("인텔", "Intel", "INTEL", "intel"):
        if "제온" in name or "xeon" in name.lower():
            return False
        return not bool(CPU_IGPU_INTEL_NO_IGPU.search(name))
    if mk in ("AMD", "amd"):
        return bool(CPU_IGPU_AMD_HAS_IGPU.search(name))
    return False
```

DB 접속(`D:/DEV/popcorn-ai/.env`의 `DATABASE_URL`)으로 `products` 테이블 CPU
683행 전체를 읽고, 위 함수를 그대로 실행해 대조했다.

**전체 분포** (`part_type='CPU'`, maker×status):

| maker | status | 건수 |
|---|---|---|
| 인텔 | 품절 | 284 |
| 인텔 | 판매중 | 182 |
| AMD | 품절 | 120 |
| AMD | 판매중 | 94 |
| 검증제조사 | 삭제대기 | 1 |
| ASUS | 품절 | 1 |

**판매중+재고(`stock_qty`)>0 CPU 276건**(인텔 182+AMD 94, 나머지 3건은 재고 0)에
`cpu_has_igpu()`를 적용한 결과:

- **iGPU=True: 118건 / iGPU=False: 158건** (합계 276 일치)
- 추천 엔진이 실제로 쓰는 `v_recommendation_candidates`(status='판매중' AND
  sale_price 있음 AND `ai_candidate_yn=true` AND `review_required_yn=false`
  등 추가 필터) 기준 CPU 144건으로 좁히면 **True 49 / False 95**.

**검증한 예외 케이스**:
1. **제온(Xeon)** — 판매중+재고>0 4건 전부 F suffix가 없어 규칙만 그대로
   적용하면 오판(True)이 났다. 서버용 CPU는 iGPU를 탑재하지 않는 것이 통례라
   `제온`/`Xeon` 문자열을 F 판정보다 먼저 검사해 False로 확정했다(위 코드
   반영). 표본이 4건뿐이라 **일반화 근거는 약하다** — §3 리스크 참조.
2. **인텔 K(비F) 계열** — "13600K"·"12700K"·"14600K" 등은 실제로 iGPU를
   갖는다(배수잠금 해제만 표시, iGPU 유무와 무관). 규칙이 `K?F`(F 앞의 K는
   선택)로 "K만 있고 F가 없으면 True"를 정확히 재현했다 — 전수 대조에서
   오탐 0건.
3. **AMD G/GE/GT 전 세대** — 2세대 피카소(3200G)부터 5세대 8500G/8600G/8700G,
   4세대 5300G/5600G/5600GT/5500GT까지 재고에 있는 모든 세대에서 규칙이
   일치했다(전수 대조, 오탐 0건).
4. **역검증** — "인텔 판매중+재고>0 중 F로 끝나지 않는데 False로 나온 상품"을
   별도로 찾았다 — **0건**(규칙이 스스로 모순되지 않음을 재확인).

### 1-4. 기존 CPU 접미 정규식과의 관계 — 혼동 주의

`api/recommend.py`(724~761행)에 이미 두 개의 CPU 접미 정규식이 있다 —
`_cpu_unlocked_suffix`(K/KF/X 접미 판정, 쿨러 정책용)와 `_cpu_aio_preferred`
(U7-K/U9/i9/R9-X 판정, 수랭 우선순위용). **이 둘과 `cpu_has_igpu`는 완전히
다른 질문**이다 — 접미 판정은 "고성능/오버클럭 등급인가"를 묻고, iGPU 판정은
"화면이 CPU만으로 나오는가"를 묻는다. "14700K"는 접미 판정으로 True(K 접미)
지만 iGPU 판정으로도 True(F가 없어 iGPU 있음) — 우연히 값이 겹칠 수 있지만
**같은 정규식을 재사용하면 안 된다**(질문이 다르므로 한쪽이 바뀌면 다른 쪽도
깨진다). 이 설계는 처음부터 별도 정규식 두 개(`CPU_IGPU_INTEL_NO_IGPU`·
`CPU_IGPU_AMD_HAS_IGPU`)를 새로 선언한다 — 기존 `CPU_UNLOCKED_SUFFIX_RE` 등을
import해서 재사용하지 않는다.

## §2. 사무 용도 세분화 설계

### 2-1. 확정 갈래 — 사장님 6갈래 (2026-09-15 확정, U-48 3갈래 대체)

U-48(2026-08-22)의 예시 셋(문서·인터넷 위주 / 엑셀 대용량·다중 창 / 자료·사진
보관)은 **2026-09-15 사장님이 아래 6갈래로 직접 확정하며 대체됐다** — 이
문서 초안이 U-48로 되돌아간 것은 조사자 지시서에 확정 목록이 누락된 하네스
실수였고, 그 자리를 사장님 확정안으로 고쳤다. GPU 정책은 **6갈래 전부
내장그래픽(iGPU) 적용**(2026-09-15 사장님 확정 — "사무 전체 적용").

| # | usage_key 제안 | 갈래 | GPU 정책 |
|---|---|---|---|
| 1 | `office_docs` | 문서작성(한글·워드·엑셀·파워포인트) | iGPU |
| 2 | `office_lecture` | 인강·온라인강의 시청 | iGPU |
| 3 | `office_web` | 웹서핑·이메일·유튜브 시청(초경량) | iGPU, 최저사양 |
| 4 | `office_meeting` | 화상회의·웹카메라(Zoom·팀즈) | iGPU, CPU 약간 여유 |
| 5 | `office_finance` | 회계·재무(더존·샘범컬) | iGPU, 다중창 안정성 위주 RAM 약간 높임 |
| 6 | `office_design_light` | 가벼운 웹디자인·포토편집(포토샵·캔바) | iGPU 유지, RAM·CPU 약간 상향 |

### 2-2. 여섯 갈래를 가르는 축 — RAM·SSD 하한 (조사자 제안, 미확정)

U-49가 지적한 병("이름만 다르고 사양이 같아지는 위험")을 피하려면 갈래마다
**다른 하한 값**이 있어야 한다. 지금 office 하한은 RAM·SSD 둘뿐이라(§0②) 이
둘로는 갈래를 가를 수 없다(가른다 해도 차이가 미미해 U-24 재현 위험). §1의
`cpu_has_igpu()`가 새 축 하나를 더한다 — 6갈래 전부 iGPU 적용이 확정이므로
GPU는 갈래 구분축이 아니고, **RAM·SSD·CPU 여유만으로 6갈래를 갈라야 한다.**

| usage_key | RAM 하한(제안) | SSD 하한(제안) | 구분 근거(제안) |
|---|---|---|---|
| `office_web` | 8GB | 250GB | 6갈래 중 최저사양 — "초경량"이 명시적 기준 |
| `office_docs` | 8GB | 250GB | 최저사양과 동급(문서 작업은 웹서핑과 부하 유사) — CPU 코어 하한만 별도 검토 |
| `office_lecture` | 8GB | 250GB | 스트리밍 위주라 저장공간 안 씀, 최저사양과 동급 |
| `office_meeting` | 16GB | 250GB | "CPU 약간 여유" 지시 반영 — 화상회의+화면공유+메모 동시 실행 |
| `office_finance` | 16GB | 250GB | "다중창 안정성 위주 RAM 약간 높임" 지시 그대로 |
| `office_design_light` | 16GB | 500GB(상향) | "RAM·CPU 약간 상향" 지시 반영, 포토샵 캐시로 SSD도 상향 |

⚠ **이 표의 숫자(8/16GB·250/500GB)는 시장 표본 근거는 없고 지시문 의미
("여유"·"약간 상향" 등)로 방향만 잡은 엔지니어링 판단이다(2026-09-15
사장님 채택 — 시장표본 조사보다 착수를 우선함).** 실제 반응(가격 불만·
교환 요청 등)이 쌓이면 재조정한다(§3-1-5).

⚠ **`office_docs`·`office_lecture`·`office_web` 셋이 지금 표에서 완전히
동일한 하한(8GB/250GB)이다 — 이것은 결함이 아니라 의도다(2026-09-15 사장님
확정).** 목적은 "실제로 다른 부품을 사게 만드는 것"이 아니라 **고객이 자기
용도에 맞춘 것처럼 느끼는 선택지를 다양하게 보여주는 것**이다 — 사무용이
하나로 뭉뚱그려진 것 자체가 "성의 없다"는 지적이었지, 하드웨어가 반드시
갈라져야 한다는 뜻이 아니었다. 그래서 이 셋은 **RAM·SSD 하한이 같아도
무방**하고, 구분은 §2-3의 `match_terms`(검색어 인식)와 화면 근거 문구로
충분하다 — U-49의 "이름만 다른 갈래" 경고는 **엔진 판정이 갈래를 혼동하는
경우**(예: 문서작성으로 물었는데 웹서핑 갈래로 잘못 잡히는 것)에 적용되는
것이지, 하한값이 같다는 사실 자체에는 적용되지 않는다.

### 2-3. 지적 ④ 해결 — `match_terms` 복원·확장 (6갈래 배분)

§0④가 확인한 소실(엑셀·웹서핑 등 소실, 오피스 SW 어휘 전무)을 갈래별로
복원·확장한다. 사무 SW 명칭을 **갈래별로 분배**한다(한 갈래에 다 몰아넣으면
다시 ③번 문제 — "이름만 다른 갈래"가 재현된다):

```
office_docs         : 문서, 한글, 워드, 엑셀, 파워포인트, PPT, 오피스, 문서작성
office_lecture       : 인강, 온라인강의, 강의, 이러닝, 줌강의
office_web           : 웹서핑, 이메일, 유튜브, 인터넷, 넷플릭스, 웹서핑용
office_meeting       : 화상회의, 웹캠, 줌, zoom, 팀즈, teams, 미팅
office_finance       : 회계, 재무, 더존, 세무, 경리, 회계프로그램
office_design_light  : 포토샵, 일러스트, 캔바, 웹디자인, 포토편집, 가벼운 디자인
```

`엑셀`을 `office_docs`에 둔 것은 사장님이 갈래 1을 "문서작성(한글·워드·
엑셀·파워포인트)"로 직접 명시했기 때문이다(U-48 시절의 "엑셀=heavy 전용"
매핑은 6갈래 확정으로 대체됐다).

### 2-4. 지적 ①②③ 해결 — 세분화가 만드는 것

- **①(가격 반영 미흡)**: 6갈래 전부 `cpu_has_igpu()`로 iGPU CPU를 우선하면
  (§4에서 엔진 연결 필요, 아래 §2-5 참조), 별도 GPU 값이 총액에서 빠져
  **iGPU를 쓰면 실제로 싸진다는 사실이 가격에 나타난다**(GPU 자체는 6갈래
  구분축이 아니므로 이 효과는 6갈래 공통).
- **②(검색어별 가격 변별력 없음)**: 갈래마다 다른 RAM·SSD 하한(§2-2 표, 숫자
  미확정)을 걸면 "엑셀 자주 써요" vs "화상회의용" 검색어가 **다른 하한 →
  다른 후보 풀 → 다른 가격**으로 갈라진다 — 단 §2-2의 3갈래 동일값 경고 참조.
- **③(용도 변경 기준 모호)**: §2-2 표의 하한 값 자체가 "기준"이다 — 사장님이
  숫자를 확정하는 순간, "이 정도 용량이 필요하면 어느 갈래로 바뀐다"는 기준이
  문서로 남는다(지금처럼 갈래 이름만 있고 조건이 없는 상태를 벗어난다).

### 2-5. 엔진 연결 — 범위와 한계 (설계만, 미구현)

`cpu_has_igpu()`가 있어도 **엔진이 GPU 슬롯을 생략하게 만드는 것은 별도
작업**이다 — `docs/design/spec-tier-migration-plan-2026-09-14.md` §1-3이 T0
(사무·웹) 설계에서 이미 같은 한계를 지적했다: `taxonomy.SLOTS`가 GPU를 8개
필수 자리 중 하나로 고정해 뒀고, `usage_alloc`(0086)도 "GPU 슬롯 필수인 현
엔진에선 최저가로"라고 이미 타협해 둔 상태다. 이 설계가 제안하는 것은:

1. `cpu_has_igpu()`를 `api/catalog_map.py`에 신설(§1) — **이것만으로 즉시
   쓸 수 있는 부분**. GPU 후보 필터링(6갈래 전부에서 GPU를 초저가로 고정)이나
   화면 안내("이 CPU는 내장그래픽 있음" 배지)에 바로 붙는다.
2. `usage_floors`에 6갈래(`office_docs`/`office_lecture`/`office_web`/
   `office_meeting`/`office_finance`/`office_design_light`) 행 신설(§2-2 표
   값은 사장님 확정 후) — 이건 기존 인프라(`usage_floors.py`) 그대로 재사용
   가능, 새 스키마 불필요.
3. `usage_alloc`(0086) office 행을 6갈래로 쪼개 GPU 배분을 갈래별로 다시
   건다 — 전 갈래가 현재 `(0, 0.15)`보다 더 낮춰도 된다(iGPU 확정 후보면
   GPU 후보 자체가 최저가 1종으로 수렴).
4. **"GPU 슬롯 자체를 생략한다"는 `taxonomy.SLOTS` 변경은 이 문서 범위
   밖이다** — spec-tier-migration-plan이 이미 같은 결론을 냈고(§1-3 "범위
   밖, 별도 결정 필요"), 이 설계도 그 결론을 뒤집지 않는다. 세분화만으로는
   ①번 지적(가격 반영)이 "덜 비싼 GPU를 고른다"까지는 가지만 "GPU를 아예
   안 산다"까지는 못 간다 — 그 마지막 단계는 엔진 아키텍처 변경이 필요하다.

## §3. 리스크와 확인법

### 3-1. 리스크

1. **제온 예외의 일반화 근거가 얇다.** 재고 실측 4건 전부 같은 방향(F 없이도
   iGPU 없음)으로 나왔지만 표본이 작다 — 새 제온 모델이 입고되면 개별 확인
   없이 규칙만 믿으면 안 된다. 정기적으로(§3-2 확인법) 재검증이 필요하다.
2. **`cpu_bundled_cooler`와 판정 성격이 다르다는 것을 문서에 명시해 뒀지만,
   향후 개발자가 "같은 파일, 비슷한 이름"만 보고 같은 원칙(표현만 인정)으로
   오해할 위험이 있다** — §1-4에서 경계를 명시했지만 코드 리뷰 시 재확인
   필요.
3. **엔진이 GPU 슬롯을 강제한다는 한계는 이 설계로 안 풀린다**(§2-5-4) —
   ①번 지적("가격 반영 미흡")을 절반만 해결한다는 뜻이다. 사장님께 "완전
   해결이 아니라 개선"이라고 정직하게 보고해야 한다.
4. **`match_terms` 확장이 기존 키와 충돌할 수 있다.** 예: '워드'가 문서
   프로그램(한컴오피스 워드프로세서/MS Word)을 가리키는지 다른 의미로
   쓰이는지 모호할 수 있다 — `admin_talk_patterns.py`의 기존 충돌 검사
   로직(`match_terms` 중복 탐지, 81~104행)을 새 갈래 추가 시 반드시 돌려야
   한다.
5. **6갈래 하한 값(§2-2)이 조사자 제안이지 시장 실측이 아니다.** 다른
   `usage_floors`/`usage_tier_rules` 행들은 전부 "표본 n건" 근거를 달고
   있는데(예: office CPU 31%(n=31)), 새 사무 갈래는 그 표본이 없다 — 다만
   갈래 간 하한 중복(§2-2 경고)이 2026-09-15 사장님 확정으로 의도된 것이라
   시장 표본으로 "갈라야 한다"는 압박은 사라졌다. 엔지니어링 판단으로 둔
   8/16GB·250/500GB 값 자체는 검증 전이므로, 실제 반응(가격 불만·교환 요청
   등)이 쌓이면 재조정 여지를 남긴다.
6. **grid_cells 스키마 확장이 필요하다.** 지금 U1(사무·인터넷) 14칸은 단일
   `usage='사무·인터넷'` 문자열이다. 6갈래로 나누면 `grid_cells.usage`
   값이 늘거나(6배), 별도 서브갈래 컬럼이 필요하다 — 어느 쪽이든 마이그레이션
   과 A-129/0082 경계 재검토가 딸려온다(이 문서 범위 밖, 별도 설계 필요).

### 3-2. 확인법 (구현 착수 시)

- `cpu_has_igpu` 신설 후: `SELECT product_name, maker FROM products WHERE
  part_type='CPU' AND status='판매중' AND stock_qty>0` 전수를 다시 돌려
  이 문서의 실측 수치(True 118/False 158, 제온 4건)와 일치하는지 대조.
- 제온 재검증: `product_name ILIKE '%제온%' OR product_name ILIKE '%xeon%'`
  신규 입고분이 생기면 개별 확인 후 예외 패턴을 갱신.
- `usage_floors`에 6갈래 신설 후: `admin_talk_patterns.py`의 충돌 검사로
  `match_terms` 중복 0건 확인.
- 6갈래 도입 후 `/api/candidates/count`를 각 갈래 대표 검색어("엑셀 자주
  써요"·"화상회의용"·"인강 듣는 용도")로 6회 호출 — 서로 다른 후보 수·가격대가
  나오는지 확인(같으면 ③번 지적이 재현된 것 — 특히 §2-2 동일값 3갈래 주의).

값·§2-5 GPU 슬롯 정책) 이후 별도 작업이다.*
