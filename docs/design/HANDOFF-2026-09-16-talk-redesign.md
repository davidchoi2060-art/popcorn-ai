## 2. ② 팝콘톡 재설계 — 왜 했나

**사장님 지적(2026-09-16)**: *"지금은 너무 키워드, 즉, 게임명, 사무용, 200만원.. 이런 단어만
기다리니까.. 제대로 고객 대응이 안되는 것인데"*

실제 결함(조사 기록 `docs/design/flow-mvp2-talk-to-grid-2026-09-16.md`): 고객이 "오버워치"라고
세 번 말해도 매번 「게임명을 알 수 없습니다」가 반복됐다. 원인은 **라벨 계약이 세 곳에서 서로
다르게, 그리고 불완전하게 정의**돼 있던 것:

- `talk.py` `LABELS` 에 "게임명" 라벨 자체가 없음 → LLM이 뽑아도 버려짐
- `grid_public.py` 가 **존재하지 않는 "요청" 라벨**을 최우선으로 찾고 있었음(제작자의 근거 없는 가정)
- `PREF_VALUES=(저소음,화이트)` 화이트리스트라 게임명이 "선호"에도 못 담김
- 서버 내부 사유 문자열이 고객 말풍선에 그대로 노출

**바꾼 방향**: AI 역할을 「키워드 추출기」 → 「격자 안내자」. DB 어휘(티어 6 · 등급 6 ·
확정 게임 21 · 용도 9)를 매 요청 프롬프트에 실어, AI가 **격자 좌표**를 직접 판단한다.
설계서 = `docs/design/talk-grid-guide-redesign-2026-09-16.md`

## 4. 이번에 얻은 교훈 (규약 후보)

- **존재하지 않는 계약을 가정하고 짜면 코드는 멀쩡히 돌면서 기능만 죽는다.** `grid_public.py` 가
  `talk.py` 의 "요청" 라벨을 있다고 가정했고, 그 라벨은 어디에도 없었다. 콘솔은 조용했고 회귀는
  통과했으며 화면만 매번 같은 안내를 반복했다. **다른 모듈의 상수를 참조할 때는 grep 으로 실재를
  확인한다** — 주석에 적힌 이름은 증거가 아니다.
- **같은 개념을 두 모듈이 각자 정의하면 반드시 갈린다.** 그래서 이번엔 계약 파일
  (`api/talk_schema.py`)을 **먼저 확정하고** 세 제작자를 병렬로 띄웠다. 이 순서가 규약이 될 만하다.
- **서버 내부 사유와 고객 응대 문구는 다른 것이다.** `note` 하나가 둘을 겸하다가 디버그 문장이
  고객 말풍선에 그대로 나갔다. 지금은 `notes[]`(내부 전용)로 이름을 바꿔 옛 화면이 실수로 쓰지
  못하게 했다.
- **`--reload` 가 도는 것과 실제로 새 코드를 태우는 것은 다른 사실이다.** 확인 방법:
  파일을 고친 뒤 응답이 실제로 바뀌는지 본다(프로세스가 살아 있는 것만으로는 증명되지 않는다).
