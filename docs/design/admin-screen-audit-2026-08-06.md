## 왜 다시 했는가

첫 진단은 **정적 마크업 크기**로 화면을 줄 세웠다. 그런데 우리 관리자 화면 다수는
본문을 **JS로 그린다** — 마크업에는 빈 컨테이너 하나(`#liveRules`·`#host`·`#body`)만 두고
fetch 뒤 채운다. 그래서 "875자짜리 초라한 화면"으로 지목한 것들이 실제로는 충실했다.

두 번 틀린 뒤 내린 결론: **화면이 무엇을 보여주는지는 열어 봐야 안다.**
이 프로젝트는 이미 같은 것을 배웠다(CLAUDE.md "브라우저에서 실제로 열어 봐야 보이는 것").

**방법 표기(정직):** 22화면은 화면을 캡처해 눈으로 봤고, 13화면은 렌더된 본문·행수·카드수·
섹션 제목을 뽑아 확인했다. 아래 표의 `본` 열에 어느 쪽인지 적는다 — 텍스트로만 본 화면은
레이아웃 결함(열 접힘 같은 것)을 놓칠 수 있다.

**2026-08-07 갱신분은 전부 `≡` 다.** 그날은 Browser 창이 닫혀 있어 **캡처가 아예 되지
않았고**(페이지가 프레임을 그리지 않는다), 확인은 DOM 실측값으로 했다 —
열 폭 · 줄 수 · 행 높이 · 넘침 여부처럼 **숫자로 잴 수 있는 것**은 이 방법이 오히려 정확하지만,
색·간격·정렬처럼 **눈으로만 보이는 것은 그날 확인하지 못했다.**

**관리자 UI는 내가 처음 말한 것보다 훨씬 나은 상태다.** 36화면 대부분이 KPI 타일 ·

## 고쳤다 — 셋 (2026-08-07 확인)

**셋 다 처리됐다.** 아래 '확인법'은 코드에서 한 줄로 되짚는 방법이다 — 다음 사람이
이 문서를 믿지 말고 그 자리를 직접 보라고 적는다.

### ① 대시보드 주문 상태 차트가 echarts 기본 팔레트를 썼다 → **고침**

`chOrders` 가 `itemStyle.color` 없이 그려져 기본 팔레트(`#91cc75`·`#3ba272` 두 초록 포함)로
떨어졌다. 초록 없음(U-01)과 토큰 단일 원천을 동시에 어겼다.

지금은 토큰 7종 순서 팔레트를 쓴다. **주문 상태는 통과/위험이 아니라 공정 단계**라
의미색이 아닌 순서색이 맞다는 판단이 코드 주석에 남아 있다.

```
확인법: mockups/admin/index.html 에서 ORD_TONES 를 찾는다(2곳).
        원시 HEX 는 '왜 고쳤나'를 적은 주석 1곳에만 남아 있다.
```

### ② 상품 관리 목록의 상품명 열이 3~4줄로 접혔다 → **고침**

고정 열 합이 996px 인데 `min-width` 가 1080px 이라 상품명에 84px 만 남아 있었다.
고정 열을 줄이고 최소 폭을 넓혀 상품명이 나머지 전부를 받게 했다.
**좁은 화면에서는 접히는 대신 가로로 스크롤한다** — 스캔이 목적인 표에서는 그쪽이 낫다는
판단이고, 그 근거가 마크업 주석에 있다.

```
확인법: mockups/admin/products.html 의 <table> 에 table-layout:fixed·min-width 가 있고
        colgroup 의 상품명 <col> 만 width 가 없다(나머지를 받는다는 뜻).
실측(2026-08-07 · 뷰포트 969·1280): 상품명 열 540px · 전 100행 1~2줄 · 행 높이 45~47px.
```

### ③ 추천 기준 설정에 같은 문구가 두 번 나왔다 → **고침**

서버가 준 `weights.note` 를 섹션 설명과 가중치 카드 두 곳에 그렸다.
지금은 카드가 "등록된 가중치가 없습니다."만 말하고, 그 이유가 주석에 있다.

```
확인법: mockups/admin/policy-weights.html 의 weightsBox 분기에 weights.note 가 없다.
```

## 새로 확인된 것 — 판단이 필요하다 (2026-08-07)

### 표가 가로로 넘친다 — 439px 〔확인됨 · 의도된 선택〕

②의 해법이 만든 결과다. 뷰포트 969px 에서 표 폭 1320px, 스크롤 컨테이너 904px →
**439px 이 화면 밖**이다. 재고 · 공급처 · 판매가 · 상태 · [수정] 버튼이 오른쪽으로 밀린다.

| 뷰포트 | 표 폭 | 넘침 |
|---|---|---|
| 969px | 1320px | 439px |
| 1280px | 1320px | 약 105px |

**이건 결함이 아니라 맞바꿈이다.** 세로로 접으면 이름이 3~4줄이 되고, 가로로 두면
오른쪽 열을 스크롤해야 한다. 지금 코드는 후자를 골랐고 근거를 주석에 남겼다.
**바꾸려면 운영자 판단이 필요하다** — 실제로 어느 열을 자주 보는가에 달렸다.
선택지는 셋이다:

1. 그대로 둔다(현행). 1280px 이상에서는 넘침이 105px 뿐이다.
2. 열을 줄인다. `공급처`(수 하나) · `자체 상품번호 · SKU`(둘 중 하나)가 후보다.
3. `table-layout:fixed` + `min-width` 제거. 넘침은 0 이 되지만 좁은 화면에서
   상품명이 124px 까지 줄어 말줄임이 생긴다.

임의로 정하지 않는다.

### 상품명에 두 줄 제한과 전체 이름 툴팁을 달았다 (2026-08-07)

지금 폭에서는 효과가 없다(전 행이 1~2줄). 창을 좁혔을 때 4줄로 늘어나는 대신
2줄에서 멈추고, 전체 이름은 `title` 로 남는다. Phoenix 유틸리티 `line-clamp-2` 를 써서
새 CSS 를 만들지 않았다. `title` 속성에 상품명이 들어가므로 **따옴표를 막는 `esc()`** 를
함께 넣었다 — 안 막으면 이름에 `"` 가 있는 상품 하나가 그 행 마크업을 통째로 깨뜨린다.

## UI 가 아닌 발견 — 운영 결함 하나

**상품 매핑의 `허용 종류 위반` 422건 = 완제품 PC 318 + 베어본 104.**
**2026-08-07 현재 그대로 422건이다** — 아직 아무도 손대지 않았다.

마이그레이션 `0031` 이 이 둘을 `part_type` 축에 새로 넣었는데(A-31), **판매 분류 트리에는
받아 줄 자리가 없다.** 그래서 전부 위반으로 잡힌다. 화면은 정확히 동작하는 중이고,
할 일은 카테고리 트리에 자리를 만들거나 기존 분류의 `allowed_part_types` 를 넓히는 것이다.
**이건 운영자 판단이라 임의로 하지 않는다.**

### 이 문서를 다시 쓸 때의 규칙

- **판정과 수치를 섞지 않는다.** 판정(양호/보완/빈 상태)은 오래가고 수치는 하루면 틀린다.
- **고쳤다고 적을 때는 확인법을 함께 적는다.** "고침"만 적힌 문서는 다음 사람이 못 믿어서
  결국 코드를 다시 읽게 되고, 그럴 바엔 문서가 없는 것과 같다.
- **판단이 필요한 것은 '결함'으로 적지 않는다.** 맞바꿈이면 선택지와 근거를 적고 비워 둔다 —
  결함으로 적으면 다음 사람이 운영자에게 묻지 않고 한쪽으로 정해 버린다.
