# 웹 사양 채움 파이프라인 — 화면 편입 방향 제안 (2026-08-13)

> ## ⚠ 폐기 — `docs/design/req/req-spec-fill.md`로 대체 (2026-08-13)
>
> 사장님 지시로 이 화면은 **처음부터 다시 정의**한다. 이 문서를 근거로 삼지 말 것.
> 남겨 두는 이유는 **결정 이력** 때문이다 — 여기서 추천한 것은 A안(화면 신설 없음)인데
> 실제로는 B안(전용 화면)이 지어졌다. 그 간극이 재정의의 출발점이다.
>
> 재정의 전제가 이 문서와 다른 지점:
> - **재구축** — 스키마 변경까지 포함한다(당시엔 "스키마 무개정"을 미덕으로 봤다)
> - **admin2 전면 신규** — 구 admin 확장이라는 전제 자체가 사라졌다
>
> 바뀌지 않는 것: **A-18 계약**(수집은 제안까지, 정본은 사람 승인으로만).

> 이 문서는 **제안서다. 만든 것이 없다.** 코드 변경은 별도 착수분(마이그레이션 0045 ·
> `tools/spec_fill_apply.py` · 팀원 `specfiller`)에서 이미 됐고, 여기서는 **그것을
> 화면에 어떻게 편입할지**만 다룬다. 사장님이 아침에 읽고 하나만 고르면 된다.

## 결정할 것 (한 줄)

전용 화면을 새로 만들 것인가, **기존 자리(작업 현황판 + 상품 사양 검수)를 확장**할 것인가.

## 배경 — 지금 무엇이 생겼나

- **채움 담당(specfiller)**: 미충족 사양 상품을 읽기 전용 조회 → 웹 검색(제조사 공식
  자료 우선) → `suggestions.jsonl` 작성. DB에 직접 쓰지 않는다.
- **`tools/spec_fill_apply.py`(DBA 전용)**: JSONL을 검증 → `product_reviews.suggested_value`
  + `spec_web_suggestions`(출처 URL 포함)에 반영. 기본 드라이런, `--apply`로만 실제 반영.
  **`product_specs`는 절대 쓰지 않는다.**
- 정본 반영은 여기서 끝나지 않는다 — **사람이 검수 화면(ADM-PRD-020)에서 승인해야**
  `product_specs`에 들어간다. `danawa_fetch.py`(A-18)와 완전히 같은 계약이다.

## ① 화면이 필요한가 — 기능 넷으로 쪼개서 본다

| 필요 기능 | 이미 있는 자리 | 비고 |
|---|---|---|
| 배치 실행(채움 담당을 부른다) | 작업 현황판(`/admin2/dash`, AI 관리 그룹) | 팀원을 불러 진행을 보고 말을 거는 자리가 이미 정본이다(`api/dash.py`). 다만 `TEAM_KO` 딕셔너리에 `specfiller` 항목이 아직 없다 — 전사본에 이 이름이 뜨면 한글 표시가 안 된다(한 줄 추가 필요, §5) |
| 진행 열람 | 위와 동일 | 세션 전사본을 읽는 방식이라 별도 배선이 필요 없다 |
| 결과 열람(제안 몇 건 · 어떤 출처) | 상품 사양 검수(ADM-PRD-020, `suggested=1` 필터) | "외부 제안이 붙은 것만" 보는 필터가 이미 서버에 있다(`api/admin_reviews.list_reviews`) — 다나와 제안 때 만들어 둔 것을 그대로 쓴다 |
| 검수 승인 연계 | 상품 사양 검수 그대로 | 승인 함수(`_approve`)는 값의 출처가 다나와든 웹이든 구분하지 않는다 — 새 분기가 필요 없다 |

**넷 다 이미 자리가 있다.** 실제로 비어 있는 것은 화면 하나가 아니라 **표시 항목 둘**이다:
① "이 제안이 다나와가 아니라 웹 검색에서 왔다"는 표시, ② **출처 URL을 사람이 눌러 볼 수
있는 자리**. 지금 검수 화면은 `suggest_source`를 "danawa"/"ai" 이분법으로만 판정한다
(`detail`에 "다나와 제안" 문자열이 있는지로 구분) — 이대로면 웹 제안이 "AI 지식"으로
잘못 표시된다. 다나와 사고(슬라이스 51 — 남의 자료를 우리 것처럼 보이게 하면 안 된다)와
같은 종류의 문제다.

## ② LNB — 신설한다면 어디

- `api/admin_nav.py`의 항목 상태는 **재구축(`new`)/신설예정(`todo`) 둘뿐이다**(P-09,
  2026-08-12 확정 — 구화면 유무 구분은 폐기됨).
- 상품사양관리 그룹에 "상품 사양 검수"가 이미 `todo`(신설예정)로 있다 — 이 재구축 대상이
  바로 ADM-PRD-020이다.
- 새 메뉴 항목(예: "웹 사양 제안 이력")을 따로 추가하면 검수 화면과 내용이 대부분 겹치는
  화면을 하나 더 만드는 셈이다 — CANON 1항("정본을 복제하지 않는다") 위반 위험이 크다.
- **신설한다면 "상품 사양 검수" 재구축 시 필터/뱃지로 흡수한다.** 별도 메뉴 항목을 만들지
  않는다.

## ③ 기존 검수 화면(ADM-PRD-020)과의 관계

- `suggest_source` 파생 로직에 "웹 제안" 문자열 분기를 추가해야 한다 — 안 그러면 위에서
  말한 오표시가 생긴다.
- `spec_web_suggestions.source_url`은 지금 검수 화면이 읽지 않는 값이다. 상세 패널에
  "출처 보기" 링크 한 줄만 추가하면 채움 담당·crosschecker 공통 규칙("근거 URL을 반드시
  붙인다")이 화면에서도 지켜진다.
- 승인·되돌리기(`_approve`/`undo`)는 출처와 무관하게 이미 동일 경로다 — 손댈 곳이 없다.

## ④ 대안 비교

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 화면 신설 없음**(추천) | 검수 화면에 출처 표시 2곳만 확장 — ①`suggest_source`에 웹 분기 ②`source_url` 링크 | 정본 복제 없음 · 구현 범위 최소 | 없음 |
| B. 전용 실행 화면 | "웹 사양 채움" 버튼 → 진행 바 → 결과 미리보기 → 적용 | 원클릭 흐름이 눈에 보인다 | 작업 현황판·검수 화면과 대부분 겹친다 — 트리거 UI만 다르고 나머지는 복제 |
| C. 전용 열람 화면 | `spec_web_suggestions` 감사 전용 목록(출처 이력 전체) | 출처 이력을 통째로 조회 가능 | 검수 화면이 이미 그 정보의 상위집합을 보여준다. 별도 화면은 "이 상품이 왜 검수 대기인가"를 볼 때 화면 두 개를 오가게 만든다 — P-09가 막으려던 문제와 같은 종류 |

## ⑤ 추천 1안

**화면을 새로 만들지 않는다.** 대신 기존 정본을 세 곳만 넓힌다:

1. `api/dash.py`의 `TEAM_KO`에 `"specfiller": "채움 담당"` 한 줄 추가 — 작업 현황판이
   새 팀원 호출을 인식하고 한글로 표시한다.
2. `api/admin_reviews.list_reviews`의 `suggest_source` 판정에 "웹 제안" 문자열 분기
   추가(다나와 판정과 같은 방식 — `detail`에서 파생, 스키마 무개정).
3. 검수 화면(ADM-PRD-020) 재구축 시 상세 패널에 `source_url` 링크 한 줄 추가.

셋 다 **기존 정본을 한 줄씩 넓히는 것**이지 새 정본을 만드는 것이 아니다. 이 저장소가
가장 자주 걸리는 병(같은 것을 두 벌 두는 것)을 피하는 선택이다.

**조건부 예외**: 웹 제안 건수가 커져(수천 건 규모) "다나와 제안"과 "웹 제안"을 완전히
나눠 따로 작업해야 하는 운영 필요가 실제로 생기면, 그때는 검수 화면에 이미 있는
`field=`(사양 하나만 보기) 파라미터와 같은 방식으로 `source=danawa|web` 필터를 하나 더
추가하는 것으로 충분하다 — 이때도 전용 화면은 필요 없다.
